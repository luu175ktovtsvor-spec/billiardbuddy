# BOSS 招聘

把自然语言招聘目标编排成一次可观察、可暂停的 BOSS 招聘会话。Skill 负责理解目标、形成筛选逻辑、选择执行通道、追问缺失事实和控制副作用，不保存招聘数据库，也不预设门店、工资、班次、人数或候选人条件。

## 先建立本次招聘事实

从用户当前消息、会话和用户指定资料中提取已知事实，用普通话复述本次要招什么人。只追问会改变搜索或沟通结果的缺失信息，已经给过的内容不要再问。

优先补齐岗位名称、门店和城市、招聘人数、核心职责、班次、薪资与福利、必须具备的经验或证书、到岗时间、不可妥协的业务条件，以及用户希望本次查看或联系多少人。可以把仍缺的信息合并成一轮简短问题，让用户自行填写；不要给不可靠的数字默认值，也不要为了凑表单询问与结果无关的数据。

追问时可以用球房行业的常见结构帮用户把需求想清楚，但结论必须由用户给出，不替用户定标准：

- 岗位放进门店结构里问：店长、前厅主管、助教管理、助教、教练、服务员、收银、保洁——新店筹备期通常先搭管理层、再由助教管理招助教、临开业才招服务员；可以按用户门店的球台规模和所处阶段提示“当前最该补哪个缺口”，由用户确认。
- 招助教时引导用户区分两类人：本地做过助教、自带客户基础的成熟助教，和需要从头培养、靠线上渠道拓客的新助教——两类的筛选侧重、话术重点和到岗预期不同，问清楚这次要哪类、比例如何。
- 薪酬引导用户给出可承诺的口径（底薪、提成或分成方式、结算周期）；用户没确认的待遇不能写进草稿。
- 渠道由用户选：本 Skill 只执行 BOSS 直聘通道；用户提到转介绍、校园、同业、抖音等其他渠道时可以给建议，但不要代替用户在其他平台操作。

用户没有提供的待遇、门店情况和职位承诺一律视为未知。未知事实可以留空或继续询问，不能由 Agent 编造后写进筛选条件或招呼语。

行业课程和门店资料里若出现“以非助教岗位名义面试转化”“线上不提及真实工作内容”“看照片或朋友圈长相筛人”“深夜集中群发私信”这类话术，一律不采用，也不据此设计筛选或草稿：招聘沟通必须如实说明岗位与工作内容，筛选只依据用户设定的、与工作直接相关的条件。用户主动要求这样做时，说明不这么做的原因并给出合规替代（如实岗位文案 + 用户确认的硬条件筛选）。

## 选择现有执行通道

先检查当前会话是否已经有 BOSS 专用 CLI 或 Playwright 浏览器工具，不要先安装东西：

- 本机已经存在 `boss` 命令时，只把它当作登录、读取、定位会话和发送的传输适配器。不要采用 CLI 自带的 AI 匹配、自动评分、深搜决策、批量打招呼或自动跟进逻辑。只检查现有命令，不静默安装、升级或运行远程 `latest` 包。
- 没有专用 CLI 时，通过 `tool_search` 查找 Playwright 的导航、页面快照、点击和输入工具。产品内置的“浏览器自动化（Playwright）”MCP 是默认浏览器通道。
- 两种通道都不可用时，明确告诉用户到“插件 → MCP”启用“浏览器自动化（Playwright）”，然后停在可恢复位置；不要退化为 Computer Use 点击浏览器，也不要用屏幕坐标脚本冒充连接器。

无论选哪种通道，都复用同一个可见浏览器会话。不要读取、打印、复制或保存 Cookie、Token、密码和验证码；不要把候选人资料、聊天内容或截图写进普通日志。

## 把登录交还给用户

打开 BOSS 招聘者官方登录页或当前招聘工作台，读取页面状态。如果页面需要扫码、短信、密码、验证码、设备确认或安全验证，告诉用户在可见浏览器中亲自完成，并等待用户明确说已经登录。用户接管期间不轮询、不代填凭据、不尝试破解验证码。

用户说登录完成后重新读取页面，只有看到招聘者工作台、职位选择或候选人入口等已登录证据才继续。仍在登录页时如实说明尚未登录，不把“浏览器已打开”当成成功。

## 在用户给定范围内找人

先确认 BOSS 当前选中的招聘职位与本次目标一致；不一致时先让用户选择或确认正确职位。把用户提供的城市、经验、技能、班次、证书和到岗条件映射到页面现有筛选项，只使用用户已确认的事实。

筛选逻辑必须由当前 Agent 根据本次用户输入生成，不能把 BOSS 页面排序、CLI 匹配分、第三方 LLM 评分或平台推荐理由当作本产品的最终判断。把条件分成三类：

- 用户明确说“必须具备”的事实作为硬条件，只根据可见证据判断符合、不符合或未知。
- 与岗位相关但不是硬门槛的经历和技能作为优势证据，用文字说明，不套固定权重或通用分数。
- 页面没有提供、表述含糊或需要沟通才能确认的内容列为待确认项；未知不等于不符合，不自动淘汰。

先用已确认的页面筛选项缩小范围，再逐个读取完成判断所需的可见资料。每位候选人的结论由 Agent 输出“符合的硬条件、相关优势、待确认项、明显不符合项和建议下一步”，让用户看到筛选依据。CLI 和浏览器只返回事实与执行动作，不替 Agent 选择联系谁。

优先使用候选人的稳定页面引用、列表序号或“姓名 + 当前岗位 + 关键经历”等可区分组合。出现同名候选人时禁止只按姓名操作。只查看完成本次目标所需的候选人范围，不做无界翻页、全站抓取或后台批量导出。

候选人判断只依据与岗位直接相关且页面真实可见的经历、技能、证书、意向、地点和活跃状态。不要按性别、民族、宗教、婚育、残障、外貌等受保护或无关特征筛选，也不要从照片、姓名或聊天措辞推断这些信息。

先给用户一份紧凑候选清单，列出可核验事实、匹配理由和仍需确认的问题，并由用户确认准备联系的对象。没有看过的简历内容不能写成匹配理由，平台或 CLI 的推荐顺序不能替代这次确认。

## 起草真实、个性化的沟通

根据用户确认的岗位事实和候选人页面中真实可见的一两个相关点生成草稿。文案应说明具体岗位与门店、为什么联系对方，以及一个明确的下一步问题；语气自然，不群发套话，不夸大待遇，不承诺未确认的录取、薪资、住宿、社保或工作时间。

用户确认要联系某位候选人后，先用 `recruitment_add_candidates` 把对方登记进招聘记录（带 external_ref 可区分引用），再用 `recruitment_save_draft` 保存草稿；这样草稿、阶段和跟进都沉淀在同一份业务数据里，换会话也不丢。

候选人已经回复时，先读取当前会话的必要上下文，再针对最后一个未解决问题起草回复。不要重复询问对方已经回答的内容，也不要把其他候选人的信息带进当前会话。

## 每次外部动作都在最后一刻确认

搜索、阅读和起草不代表授权发送。打招呼、发送消息、索要简历、交换联系方式、标记不合适、修改备注或切换职位上下架，都是新的外部动作。

在真正点击或调用发送命令前，向用户展示：当前账号可识别信息、目标职位、候选人的可区分信息、完整消息正文、动作类型和本次人数。明确问是否按所示内容执行，并停下来等待回答。用户只批准了草稿、搜索或某一位候选人时，不能扩大到其他候选人；正文、收件人、职位或人数发生变化时必须重新确认。

即使底层工具另有权限卡，也不能省略这次业务确认。Skill 不声明 `allowedTools`，因此不会借调用 Skill 自动放开浏览器、命令或 MCP 权限。

## 执行后必须读回结果

获得确认后按候选人逐个串行执行。动作前重新读取当前页面，核对候选人和职位仍与批准内容一致；页面跳转、列表刷新或会话对象不明确时先停止。

使用 Playwright 时优先依赖页面快照、可访问名称和语义定位器，不保存脆弱坐标。使用专用 CLI 时，同名候选人优先使用列表序号或稳定引用；CLI 返回“已发送”只能当作动作结果，不能单独当作业务回执。

发送后重新读取同一候选人会话，确认最新的发出消息包含批准的完整正文或可唯一匹配的文本、对象仍是同一候选人，并且页面显示正常发送状态。只有这些证据成立才能报告“已发送”。

如果只观察到点击、按下 Enter、命令返回成功或加载超时，而没有读回消息证据，把结果标记为 `uncertain`，立即停止后续发送并请用户人工核对。`uncertain`、断网、页面改版和超时都禁止自动盲目重试，避免重复触达。

出现验证码、账号风险提示、频率限制、付费弹层、平台明确拒绝、候选人投诉或“不要再联系”等信号时立即停止，把页面现状交给用户处理。不要切换私有接口、隐身浏览器、指纹伪装或其他通道继续绕过限制。

## 继续跟进与汇报

每轮结束只汇报有页面证据的结果，按“候选人、动作、结果、证据、下一步”简要列出。区分 `sent`、`failed` 和 `uncertain`，不要用笼统的“全部完成”覆盖部分失败。

结果同步进招聘记录：发送有读回证据时用 `recruitment_update_draft` 标记 `sent` 并附上证据原文（工具会拒绝没有证据的 sent，这不是可以绕过的格式要求）；只观察到点击而没有读回证据时标记 `uncertain` 并停止。候选人阶段变化（已回复、加微信、约到店等）用 `recruitment_update_stage` 留痕，下一步和截止时间用 `recruitment_set_followup` 记录。用户问招聘进展时用 `recruitment_funnel_report` 和 `recruitment_list_candidates`（`due_today=true` 是今日跟进队列）回答，不要凭记忆报数。

漏斗、草稿和跟进都存在产品的招聘记录里，不要把候选人隐私信息另存为散落的工作区文件；用户明确要导出表格时，只导出必要字段。

一次成功试跑至少满足：用户自己完成登录；Agent 使用用户提供的岗位事实找到可区分候选人；发送前展示完整对象和正文并获得确认；发送后从同一会话读回消息证据；任何不确定结果没有被自动重试。
