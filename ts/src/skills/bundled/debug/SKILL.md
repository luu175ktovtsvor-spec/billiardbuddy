# 调试问题

用户描述的问题:$ARGUMENTS

(若上面为空,先请用户用一两句话说清:期望是什么、实际发生了什么、怎么触发。)

按「收证据 → 找规律 → 提假设并验证 → 最小修复」的顺序来,别一上来就乱改。

## 第 1 步:收集证据

- 让用户复现一次,拿到确切的报错信息、堆栈、日志、异常输出——原文,别转述。
- 定位相关代码:这块是谁在调、连着什么、最近改过什么。用 grep / 读文件把牵连读全。
- 读取适用的项目指令和模块地图；明确主责模块、边界契约和不应修改的相邻模块。
- 若项目有日志 / 诊断输出,去读最近的 `[ERROR]` / `[WARN]` 与堆栈。

## 第 2 步:找规律

- 什么情况下出、什么情况下不出?边界在哪(某类输入 / 某个时机 / 某个环境)?
- 是稳定复现还是偶发?偶发往往指向时序 / 并发 / 状态残留。

## 第 3 步:提假设并验证

- 基于证据提出**一个**最可能的根因假设,别一次猜一堆。
- 想办法验证它:读相关代码、加一处临时日志、小范围试跑、写个最小复现。假设不成立就换下一个,别硬凑。
- **不复现就不声称已定位**;定位不了就如实写清:试了什么、看到什么、还缺什么。

## 第 4 步:最小修复

- 一次只改一处,优先能真正解决根因的**最小改动**,别顺手重构。
- 修完真跑一遍验证问题消失,并确认没连累别处(跑相关测试,不只改的那块)。
- 若根因要求改变 API、事件或 IPC 契约，同一次修完所有生产者和消费者，不留半截兼容代码。

## 顺带看一眼配置

如果问题可能和配置 / 指令有关,记得这些地方:
- 项目指令:工作区根目录的 `BILLIARDBUDDY.md`、`.billiardbuddy/` 下的规则
- 用户全局指令:`~/.billiardbuddy/BILLIARDBUDDY.md`

## 收尾

用大白话讲清:你找到的根因是什么、怎么修的、怎么验证已解决;还有什么风险或待确认的,一并说明。
