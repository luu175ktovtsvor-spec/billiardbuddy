# Verify:把改动真跑起来验一遍

要验证的改动 / 预期(如有):$ARGUMENTS

「改完」不等于「验过」。你的任务是**真正驱动这处改动、观察它的行为**,确认它按预期工作——不是只跑测试、只过 typecheck 就宣布完成。

## 第 1 步:搞清「验什么」

- 这次改的是哪块?它对外可观察的行为应该是什么(某个命令的输出、某个接口的返回、界面上的某个变化、某个副作用)?
- 找到能触发这条路径的**最直接入口**:一条命令、一个脚本、一次接口调用、一个页面操作。

## 第 2 步:真驱动一次

- 用最贴近真实用法的方式把它跑起来(跑那条命令 / 打那个接口 / 走那个流程),用真实或接近真实的输入。
- 光看代码「应该没问题」不算验证;光有单测绿也不够——单测可能没盖到这条真实路径。
- 若这块有对应的项目验证方式(专门的 e2e / 冒烟脚本 / 启动方式),优先用项目那套。

## 第 3 步:对着预期看结果

- 把**实际观察到的行为**和**预期**逐条对照:一致 = 通过;不一致 = 说清哪里对不上、贴出实际输出 / 报错。
- 记下你跑了什么命令、看到什么(关键输出 / 报错 / 截图线索),让结论有据可查。

## 第 4 步:如实汇报

- 通过:一句话说清「怎么验的 + 看到了什么 + 因此确认生效」。
- 没过:按「[发生了什么] + [下一步怎么办]」讲清楚——别把「跑通了」和「验过了」混为一谈,出错当场认,绝不粉饰。
