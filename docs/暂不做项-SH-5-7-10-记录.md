# 暂不做项记录 · SH-5 / SH-7 / SH-10

> 给将来接手的人（AI + 人）看：这三项是 `docs/完整优化清单.md` 里「支柱 C 增补·Agent 壳机制强化」中**当前判定「鸡肋·暂不做」**的项。
> 不是「做不了」或「不该做」，而是**当前没有业务驱动、做了收益低**。本文记录每项=【是什么】/【为什么暂不做】/【什么信号出现时该做】/【大致怎么做】。

## SH-5 · 工具渐进式披露 + tool_search 元工具（工具层省 token）

**清单原标记**：`P2 · 批次6` ⏭️ 暂不做(鸡肋)：工具不多、无膨胀压力；等工具数量真上来再做。

### 是什么
现在 `registry.to_openai_tools()` 把**全部**工具的完整 schema 一次性塞给模型，`loop.py` 每轮请求都背着全量工具描述。SH-5 想做的是「渐进式披露」：长尾工具初始只露「名字 + 一句话摘要」，模型需要时调一个元工具 `tool_search` 才拿到完整 schema、才可调用。高频工具（写文案/海报/诊断/约客/提问）保持常驻，长尾工具（平台内容/团购/批量/RPA 发布）延迟披露。

### 为什么暂不做（鸡肋·无业务驱动）
当前只有十几个工具，全量 schema 占的 system token 还很可控，**没有膨胀压力**。渐进披露的代价是「多一轮交互（模型先 search 再调）」，工具不多时这笔交互成本 > 省下的 token 收益。清单自己也写了「自适应开关 `should_defer()`：延迟工具 schema 占窗低于阈值就全当常驻发」——即工具不多时这套机制自己也会退化成全量发，做了等于白做。

### 什么信号出现时该做
- 工具数量明显上来（清单点名的增量来源：发布/对账/周报/各平台工具一批批加进来，量级到几十个）；
- 真机/日志观测到**每轮请求的 system token 里工具描述占比偏高**，且很多工具一整轮都用不上；
- BYOK 老板反馈「每条消息都贵」，且拆下来工具描述是大头。

### 大致怎么做（原清单草图）
- `registry.py` 的 `Tool` 加 `defer: bool=False` + `summary: str=""`；
- `to_openai_tools(unlocked)` 常驻工具原样、`defer=True` 的不进数组，改由 `deferred_catalog_lines()` 产「名字 — summary」清单文本；
- 新增元工具 `tool_search`（`read_only=True`，入参 `{query, max_results}`，handler 纯本地匹配：`select:A,B` 精确取名 + 关键词对 name/summary/description 打分），命中后返回完整 schema 文本并把名字写进 `AgentContext.unlocked_tools: set[str]`；
- 每轮 `tools = 常驻 + 已解锁`，**解锁工具追加在末尾不插中间**（保 prompt-cache 前缀，与 SH-9 协同）；
- 自适应开关 `should_defer()`：占窗低于阈值就全当常驻发；
- 先给长尾工具打 `defer=True`，高频工具常驻。
- 牵连风险：解锁追加必须不破前缀缓存（与 SH-9 协同）。

## SH-7 · 子 Agent = 工具，递归复用主循环（独立工具池/maxTurns/abort）

**清单原标记**：`P2 · 批次7` ⏭️ 暂不做(鸡肋)：当前短循环无多步子任务委派需求；等真有复杂编排再做。

### 是什么
现在 `tools.py` 全是扁平单层工具，没有「把子任务派给一个独立工具池 + 独立 maxTurns 的子循环」的能力。SH-7 想把「子 Agent」也做成一个工具 `run_subagent({agent, task})`：它内部递归复用主循环 `run_agent_loop`，但跑在**自己干净的对话上下文**里（context isolation）、用**收窄的只读工具集**、有**独立的防打转计数和 maxTurns**，只把最终消息回灌给父 Agent，中间的工具调用噪音不污染主线。典型用途：读全部报表做季度对账、生成整月内容计划这类重任务。

### 为什么暂不做（鸡肋·无业务驱动）
当前 Agent 是**短循环**（主对话 max_turns 不大、单任务为主），**没有「多步子任务委派」的真实需求**——老板的活基本是「写一条文案/出一张海报/诊断一次报表」这种单层任务，扁平工具就够了。子 Agent 是为「复杂多步编排」准备的，现在没有这类任务，做了就是空架子。且清单自评「架构改动较大（故排后）」，投入产出比当前最低。

### 什么信号出现时该做
- 出现**真·多步重任务**：如「读这一摞月报做季度对账并出周报」「按诊断结论自动排一整月内容计划再逐条改 Excel」——单层循环里中间噪音明显污染主上下文、或主对话被一堆中间工具结果撑爆；
- 观测到某类任务**主对话上下文膨胀失控**，靠 SH-6 压缩也压不住，根因是「一个大任务的中间过程全堆在主线」；
- 产品上要做「派一个专职小助手去干某类活」的能力。
- 前置：依赖 SH-6（子上下文压缩，已完成）就位。

### 大致怎么做（原清单草图）
- 新增 `server/services/agent/subagent.py`，`AGENT_DEFS: dict[str, AgentDef(system_prompt, allowed_tools, max_turns)]` 先硬编码 2-3 个（reconcile 对账周报、research 查历史汇总），后续升级成读 `prompts/agents/*.yaml`（复用 PromptEngine 宽松加载）；
- 工具 `run_subagent({agent, task})`（**不标 deliverable**）handler 内：
  - ① `sub_registry = build_subregistry(default_registry, allowed_tools)` 且**显式排除 run_subagent 自身**（防无限递归）；
  - ② `sub_ctx = replace(ctx, call_counts={}, token_budget=None)`（独立防打转计数、不吃主预算）；
  - ③ 递归 `await run_agent_loop(task, sub_registry, sub_ctx, def.system_prompt, def.max_turns)`；
  - ④ 只回 `result.final_text` 不回 steps；
- `AgentContext` 加 `abort: asyncio.Event|None`，子循环每轮检查（主被中断连带停子）；
- **审批继承（比参考实现更收紧·守铁律）**：子 Agent 工具池白名单**只放只读 + 本地文件类，不给花钱/对外工具**——花钱/对外动作留主 Agent 走审批闸（纯 BYOK + 不自动触达铁律）。
- 牵连风险：架构改动较大；依赖 SH-6；审批冒泡必须回主会话的人。

## SH-10 · 配置驱动 hook 事件点扩展（SessionStart/UserPromptSubmit/PreCompact/SubagentStop）

**清单原标记**：`P3 · 批次7` ⏭️ 暂不做(鸡肋)：无外部配置化 Hook 需求，现有 Hook 三件够用。

### 是什么
现在 `hooks.py` 只有三个事件点：PreToolUse（工具执行前拦截）/PostToolUse（执行后观察）/Stop（阻断停止），全是进程内 Python 回调。SH-10 想再加几个事件点：SessionStart（开会话时注入今日提醒）、UserPromptSubmit（用户输入时合规预检/补门店上下文）、PreCompact（压缩前保关键信息）、SubagentStop（校验子任务产出）。并可选支持从本地 JSON 配置文件读「{事件:[{match:工具名glob, type:deny/builtin}]}」转成进程内回调。

### 为什么暂不做（鸡肋·无业务驱动）
**现有 Hook 三件够用**，且当前生产里这三件 Hook **一个都没注册**（仅测试在用，是故意留的扩展骨架，详见全链路排查报告「Agent 大脑」块）——连现有三件都还没接生产用例，再加四个事件点更是无的放矢。**没有「外部配置化 Hook」的需求**：老板不会去写 hook 配置 JSON。其中 SubagentStop 还依赖 SH-7（子 Agent），SH-7 本身就暂不做。优先级 P3，是整个增补里最低的。

### 什么信号出现时该做
- 真有事件点的具体用例落地：如「开会话自动推今日运营提醒」（SessionStart 联动 proactive）、「用户输入先过一道合规预检」（UserPromptSubmit）、「压缩前必须保住某些关键交代」（PreCompact）；
- SH-7 子 Agent 做了，需要 SubagentStop 校验子任务产出；
- 出现「想让某类工具按规则自动 deny/放行，且规则需要可配置」的需求。

### 大致怎么做（原清单草图 · 克制版）
- **不照搬 shell-out/command 协议**（对桌面过重、有安全面，⛔ 不收）；保留现进程内回调机制；
- `hooks.py` 加 `run_session_start_hooks`/`run_user_prompt_submit_hooks`/`run_pre_compact_hooks`/`run_subagent_stop_hooks`，签名与现三件一致（故障安全、默认空零影响）；
- 接入点：SessionStart 接 `api/v1/agent.py` 起会话处（联动 proactive）、UserPromptSubmit 接进 `run_agent_loop` 前、PreCompact 接 SH-6 autocompact 前、SubagentStop 接 SH-7 子 Agent 收尾；
- 可选新增 `hook_config.py` 从本地 JSON 读 `{事件:[{match:工具名glob, type:deny/builtin}]}` 转成进程内回调注册；
- **`prompt` 型 hook 会花 BYOK 钱 → 默认禁用，要老板显式开**。

## 一句话给接手人

这三项都是**「壳机制层」为未来更复杂场景预留的能力**，地基（SH-6 三级压缩）已就位，但**当前业务（单层短任务 + 十几个工具 + 无配置化 Hook 需求）撑不起它们的收益**。判定逻辑统一：**等真实信号出现（工具变多 / 出现多步重任务 / 有具体 Hook 用例）再做，不提前造空架子。** 做的时候照本文「大致怎么做」的草图走，注意三条铁律：纯 BYOK、不自动触达（子 Agent 不给花钱/对外工具）、prompt-cache 前缀稳定（追加不插中间）。
