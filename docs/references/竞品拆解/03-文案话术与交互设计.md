## A. 文案话术

逐家看四类场景：空状态 / 报错 / 按钮 / 加载与确认，最后提炼各家的整体语气。

### A1. Codex（OpenAI）—— 工程师对工程师，两套语域分裂

- **空状态**：短促陈述句 + 补一句可执行的下一步。实测 `codex.recentTasksMenu.empty` = `"No chats yet"`；引导页 `electron.onboarding.workspace.empty` = `"Add a project to continue."`——不说"暂无内容"这种被动陈述，而是"要往前走，去做这件事"。
- **报错**：公式化到近乎模板——`"Couldn't " + 动词 + 对象`，8 个词以内、零道歉词。实测样本：`"Couldn't copy share link"`、`"Couldn't check worktree status"`、`"Couldn't generate a commit message"`、`"Couldn't finish the import. Try again, or skip for now."`——注意最后一条才罕见地补了"怎么办"，多数报错只说事实不给建议，把决定权留给用户自己判断。
- **按钮**：1-3 词祈使句，`Copy command`、`Archive all`、`Create project` 这类。全库 8858 条文案里 `"Are you sure?"` 作为独立确认标题只出现在一处高风险场景（`composer.mode.agentMode.fullAccessConfirm.warningTitle`，切到"完全自主执行权限"模式时）——说明这家把"确定吗"这句"废话感"很重的话，克制到只留给真正高风险的一次操作，其余确认都换成具体问句。
- **AI 第一人称口吻**（区别于系统文案的第二语域）：引导流程里 AI 说话像口语聊天，用缩写和短句——`"Mind connecting it?"`、`"Got it. I won't make changes to your calendar right now. Want to try another quick example?"`、完成任务用`"Done. I turned the CSV into a chart and saved it to your computer."`——这套语域只在"AI 角色说话"时启用，和上面系统提示的冷峻公式并存，两套文风刻意分裂、不混用。
- **加载态**：每个工具态各自现在分词，不是统一"加载中"。

**语气总结**：系统层文案工程师化、克制、不煽情；AI 角色说话层是随性口语。两层分得很开。

### A2. WorkBuddy —— 外热内专业，"发生什么+怎么办"公式

- **空状态**：`"暂无X"` + 一句具体下一步。实测样本极多（grep 命中近 30 条），比如 `"暂无会话，先新建一条吧"`、`"暂无外部数据源，点击添加开始同步"`、`"当前企业下暂无已发布的企业智能体。"`——比 Codex 更愿意在空状态里多说一句怎么做。
- **报错**：`[发生了什么] + [怎么办]`，几乎不出现道歉词。实测：`"访问令牌校验失败，请检查后重试"`、`"安装失败：下载出错，请检查网络后重试"`、`"访问令牌无效或权限不足。请检查令牌，并确保已授予仓库与用户信息的必要读写权限后重试。"`——后一条把"怎么办"讲到很具体（哪个权限），不是空泛的"请稍后重试"。
- **两段式加载状态**（值得学）：同一动作分阶段换文案，不是一路"加载中"到底。实测确认工具调用类的准备/执行两段：`"正在准备读取文件"` → 执行完回灌 `"用户已批准读取文件：{paths}"`；沙箱环境类：`"正在准备数字员工运行环境…"` → `"正在获取沙箱连接信息…"` → `"正在连接沙箱…"`——每一步都换动词，让用户感觉"真的在推进"而不是卡住转圈。
- **toast 用"已+动词"过去式**：`"已完成绑定"`、`"已重置到所选版本"`、`"已成功召唤专家「{name}」"`——统一过去式，短。
- **长任务陪伴文案**（值得学）：`"你可以先去和 WorkBuddy 聊天或处理其他事情，完成后我会通知你。"`——把"你不用干等"讲清楚，同时暗示"完成会主动通知"，减少用户守着转圈的焦虑。
- **删除确认**：`"确定删除「{name}」吗？删除后将无法恢复。"` / `"确定删除已选的 {count} 个事项？删除后不可恢复。"`——固定公式"确定删除「名字」吗？删除后……"，把不可逆性讲清楚但不吓人。
- **审批/等待类文案**成体系：`"等待审批"`、`"等待 {name} 审批"`、`"排队中，等待空闲后执行"`、`"敏感操作需用户确认。如果你离开屏幕，任务会停在等待状态。仅推荐在本地调试/手动监管时使用。"`——最后这条是在给"自动批准"类高风险模式做劝退式说明，和 Trae 的 YOLO 模式说明是同一套套路（见 A3）。
- **官方词汇表**：对话 / 任务 / 助理 / 专家 / 连接器 / 技能——这几个词在文案里反复出现且从不混用近义词，说明有统一的产品词典约束文案。

**语气总结**：外部热情("先去忙别的""完成后通知你")，内部术语专业且统一，报错讲清楚具体原因而非泛泛"请重试"。

### A3. Trae（字节）—— 设置说明书式的严谨，AI 感弱

- **空状态分场景**：老 IDE 区仍是 VS Code 传统的"暂无X"（如 `"暂无最近任务"`、`"暂无历史记录"`），但新加的 AI 生成类面板换了更"产品化"的鼓励语气：实测确认 `"暂无网页预览，让 AI 生成一些内容看看吧！"`——同一产品新旧模块文风不统一，是技术债的直接证据。
- **报错按根因分支给话**（不是笼统"出错了"）：实测确认导出功能按三种根因给三条不同文案——`"导出数据异常: 网络连接异常，请确认网络正常可用"` / `"导出数据异常: 无权限保存至当前文件，请先获得权限或更换保存位置"` / `"导出数据异常: 磁盘已满，请确认磁盘是否有剩余空间"`。
- **卡顿/慢响应分诊文案**（重点，见 B3 交互态详述）：实测确认至少三种根因对应三条不同 headline——通用："响应时间比预期稍长，你可以新建会话、重试或继续等待。"；网络问题："响应可能受到网络状况影响，你可以检查网络连接、重试或继续等待。"；服务端排队："当前服务正在处理大量请求，你可以切换到其他模型或继续等待。"——每条都是"[诊断] + 你可以[针对性动作]"公式，且随文案联动出不同按钮（检查网络/切换模型/新建会话/重试/继续等待，字符串各自独立存在于文案表）。
- **高风险操作重劝退文案**（YOLO 模式，实测原文较长，摘录关键句）：`"全局自动批准也称为"YOLO 模式"……此操作极为危险，并且"从不"建议使用……此功能会禁用关键安全保护，并导致攻击者能够更容易地入侵计算机。"`——用加粗、多重否定副词("极为""从不""关键")堆叠出强烈警告感，这是全库里语气最重的一条文案，其余场景都很克制。
- **按钮"任务"化但和"会话"混用**：实测同时存在 `"新建任务"`、`"历史任务"`、`"新建会话"` 三种叫法指代相近概念——同一产品里"任务"和"会话"两套名词并存，是命名不统一的技术债（可作为反面案例警示我们自己别犯）。

**语气总结**：说明书式严谨（尤其错误分支和高风险警告），不刻意拟人，AI 感弱于 WorkBuddy/Codex；但"分诊式"报错文案是本文里技术含量最高的一条，值得单独学。

### A4. Qoder（阿里灵码）—— 技术命令式，付费话术露骨

- **空状态**：`"请先打开一个项目"`——命令式祈使句，不铺垫、不安慰。
- **报错**：偏爱把技术细节直接甩给用户，编号步骤排错。实测样本 `terminal.cant.get.output.tips`：`"无法获取终端运行的输出，您可依次尝试以下几种排错方法：1. 可以尝试关闭……2. 检查默认终端配置……3. 手动安装 Shell 集成……"`——三步编号、每步给操作路径（含快捷键），面向"愿意读长文排错"的开发者用户，和小白产品的"一句话说清"完全是两种设计哲学。
- **按钮**：动词+产品名前缀构成品牌记忆点——实测确认 `"Qoder一键修复"`、`"Qoder一键解释"`，把产品名嵌进操作按钮里强化品牌感。
- **Credits/订阅话术**（实测确认、与我们方针相反不学）：`"您的 Credits 已低于 200，用尽后仍可继续使用基础模型。立即查看升级或增购方案"`、`"您已达到配额上限，将在下个订阅周期自动重置……"`——大量文案在"善意告知+引导升级"之间反复横跳，商业化痕迹很重。我们产品是全内置 key、不向用户提配额/花钱，这一整类文案不适用、明确标记不学。
- **确认类**：`"是否继续等待 `{0}`?"` 这种直接把变量名裸露在提示里的写法也出现（说明 Qoder 这类偏 IDE 工具型产品，文案打磨优先级低于 Trae/WorkBuddy 这类 C 端感更重的产品）。

**语气总结**：技术命令式、面向开发者的注册体，报错给深度技术细节而非安抚，商业化话术直白。

## B. 交互设计

逐家给出可验证的动效数值和交互模式名称，重点标出两处"设计含金量最高"的机制（Trae 卡顿分诊、Qoder 澄清面板）。

### B1. WorkBuddy —— "流光扫字"loading + 卡片原地态变

- **动效 token 实测**：`cb-bridge-DjmtYFuW.css` 里贯穿全局的两条缓动曲线是 `cubic-bezier(0.2, 0, 0, 1)`（更"干脆"的收尾）和 `cubic-bezier(0.4, 0, 0.2, 1)`（标准 Material 式加减速）；细粒度过渡集中在 `0.15s~0.2s`（如 `transition: transform 0.2s ease, color 0.15s ease, opacity 0.16s ease;`），没有超过 0.2s 的过渡——整体调性是"快、不拖泥带水"。
- **loading 态命名"流光扫字"**：CSS 动画名直接是 `cb-shining-text-sweep`，周期 `2.2s linear infinite`——一道高亮带从文字上扫过（比常见的"骨架屏灰块闪烁"更有质感，视觉重量比转圈图标轻，适合放在句子级的加载文案上）。
- **工具卡片状态**：运行中整卡 `opacity: 0.88`（实测确认该数值），比默认稍微"退一步"但不完全变灰，视觉上传达"正在进行、还没到你需要看结果的时候"；配合独立的 loading 动画（`cb-loading-rotate 1s linear infinite`）表示子进程活着。
- **审批卡片"原地态变"**：不是"审批中"弹一个模态框然后消失，而是同一张卡片原地从"待审批"态切到"已批准/已拒绝"态（文案上也对应 `"用户已批准读取文件：{paths}"` 这种回填式文案）——好处是用户视线不需要跳转，操作历史留在原地可回溯。
- **hover 反馈**：`translateY` 类位移集中在很小的幅度（-2px 级别），配合阴影变化；"更多操作"类次级菜单默认 `opacity:0`、hover 才淡入（避免界面默认铺满次级按钮造成视觉噪音）。

### B2. Codex —— 分层动效强度 + 悬浮通知塔 + 像素宠物

- **Framer Motion 弹簧强度分层实测**（`stiffness` 常量，数值越大回弹越快越"活泼"）：
  - `avatar-mascot-button-DFHhFEBO.js`：`stiffness: 420`（像素宠物按钮，全库最活泼的交互之一）
  - `avatar-overlay-page-DhVhq3Bh.js`：`stiffness: 360`（悬浮通知塔展开/收起）
  - `onboarding-page-N-jENXWy.js`：`stiffness: 110`（引导页，明显更"沉稳正式"）
  - 其余场景分布在 100~550 之间（`profile` 页 200、部分弹层 500~550）——说明这家不是全局统一一套弹簧参数，而是按"这个元素该有多俏皮"分层调参，娱乐性越强的元素（宠物、悬浮头像）弹性越大，越正式的页面（引导、设置）越克制。
  - 非弹簧类过渡用大量自定义 `cubic-bezier`（实测十余种并存，如 `cubic-bezier(.16,1,.3,1)`、`cubic-bezier(.77,0,.175,1)`），说明动效不是随手一个 ease 打天下，而是每类交互配了专属曲线。
- **悬浮通知塔（avatarOverlay，重点机制）**：从命名（`avatar-overlay-page`、`avatar-overlay-native-frame`、`avatar-overlay-pill-dismiss-button`）可反推是一套独立于主窗口之外的桌面级悬浮通知——后台任务完成时以类似 macOS 通知中心/信息泡的形式弹出，可堆叠多条、可内联操作（从 `pill-dismiss-button` 这类命名看还支持单条快速关闭）。这类"任务在后台跑、完成主动弹通知，不需要你盯着主窗口"的模式，是我们海报/发布/剪辑异步任务最值得抄的交互方向。
- **像素宠物 mascot**：独立的 `avatar-mascot-button` 组件，配合上面 420 的高弹性数值，是纯情感化装饰，不承载功能——说明这类严肃工具产品也会留一个"可爱、没什么用但讨喜"的角落。
- **"Are you sure?" 全库仅此一处**：印证 A1 的报错分析——高风险确认极度克制，用在刀刃上。

### B3. Trae —— 复用 VS Code 原生组件 + 卡顿状态机（重点）

- **组件复用**：Trae 的 AI Chat 面板直接复用 VS Code 原生的虚拟列表/流式 markdown 渲染/工具确认卡片这套底座（毕竟是 VS Code fork），减少自造轮子，但也带来 A3 提到的"任务/会话"命名不统一问题——继承了底座就继承了它的历史包袱。
- **卡顿状态机（本文里设计含金量最高的一处，值得我们单独抄这个模式）**：从 nls 文案表可反推，Trae 对"响应慢"这件事做了**根因分类**而非笼统转圈：
  1. 通用/未知原因 → `"响应时间比预期稍长，你可以新建会话、重试或继续等待。"`（三个按钮都给）
  2. 判断是网络问题 → `"响应可能受到网络状况影响，你可以检查网络连接、重试或继续等待。"`（多一个"检查网络"按钮）
  3. 判断是服务端排队/限流 → `"当前服务正在处理大量请求，你可以切换到其他模型或继续等待。"`（换成"切换模型"按钮，因为重试没用）
  4. 更简单的场景 → `"响应时间比预期稍长，你可以重试或继续等待。"`（少一个按钮）
  - **机制价值**：用户看到的永远是"有点慢"这个大白话 headline，但界面在背后已经区分了"到底是哪里慢"，并只给"这种情况下真正有用"的按钮——不是所有情况都给"重试"（服务端排队时重试没用，给的是切换模型）。这正是我们台球助手在"生图排队/网关限流/模型无响应/工具超时"这几种慢场景上可以直接照搬的思路：不用做到 Trae 那么细，但至少分 3-4 类、每类给对应的按钮，而不是所有慢都用同一句"网络不好，请稍后再试"糊弄过去。
- **高风险模式劝退（YOLO）**：见 A3，是全库语气最重的一条警告文案，交互上大概率配合二次确认弹窗（未直接验证弹窗组件，但从文案的"极为危险""从不建议"措辞看，UI 层级至少是模态阻断级别，不会是轻量 toast）。
- **三档审批范围**（本会话/本工作区/始终）：从产品定位（企业级 IDE）推断出的分层授权粒度，比"一刀切自动批准"更细，但对我们这种小白单机产品而言可能"档位过多反而增加决策负担"（见 C 部分）。

### B4. Qoder —— 澄清面板 askQuestionTool（重点）+ 变形块 loading

- **askQuestionTool 确认存在**：在 `agents-window.desktop.main.js` 里实测检索到 `askQuestionTool` 这个工具名——说明 Qoder 的 Agent 具备"卡壳时主动弹选择题问用户，而不是自己瞎猜"的能力，这是一个**工具**（模型可主动调用），不是写死的 UI 流程，意味着由模型自己判断"这里信息不够、该问一下"，比固定表单更灵活。
- **交互形态（推断自命名+行业常见实现，未逐像素验证 CSS）**：结合 askQuestionTool 这类工具在同类 Agent 产品里的通行做法——弹出一个轻量选择题面板，列出若干候选答案供用户点选，同时留一个"自己打字"的兜底输入框，选完后这轮"提问-作答"会折叠成一条摘要留在对话记录里（不占永久空间）。这个模式解决的核心问题是：**模型对当前任务有微小但关键的不确定性时，别自己瞎猜也别連续追问，而是给个选择题让用户一秒选完**——比"我猜一个方案做错了再来回滚"效率高得多。
- **"关闭确认按卡在哪步给不同文案"**：从 Qoder 报错体系里"按具体故障给具体排错步骤"的整体风格（见 A4 的终端排错三步法）可推断，它在关闭确认这类场景上大概率延续同一套"具体问题具体话术"的产品哲学，而非用一句通用"未保存的更改将丢失"应付所有关闭场景。
- **Credits/订阅商业化 UI**：见 A4，明确标记"与我们方针相反，不学"——我们产品是全内置 key、不向终端用户暴露"配额/升级/购买"这类概念。

## C. 对我们小白台球产品的启发

### 可学（按优先级排序，附对应来源）

1. **卡顿分诊状态机**（Trae，B3）——目前我们对"慢"大概率只有一句"生成中…"糊弄到底。可以照 Trae 的思路，把海报生成/视频渲染/网关排队这几类慢场景分开识别（比如：网关 429 限流 vs 模型真的在算 vs 工具执行超时 vs 网络断连），headline 都说人话"这次有点慢"，但按病因给不同的下一步按钮（换个模型 / 检查网络 / 继续等 / 取消重来）。这是本次调研里唯一一处"直接抄机制、能显著提升体感"的发现。
2. **askQuestionTool 式澄清面板**（Qoder，B4）——用户描述模糊时（比如"帮我做张海报"没说清风格/尺寸/文字），与其让模型瞎猜一版让用户失望重来，不如模型主动弹一个"选一下"的小面板（2-3 个选项+"我自己说"兜底），比连续追问三句话更省用户力气。这和我们"审批闸"的机制是同一个家族（模型主动请求用户输入），可以复用审批闸的 UI 骨架来实现。
3. **两段式状态文案**（WorkBuddy，A2/B1）——"正在准备读取文件"→"正在读取文件"这种阶段递进文案，比一路"处理中…"更让人觉得"真的在推进"。我们的生图/生视频/文件操作都可以在关键节点多插一句阶段文案，成本很低。
4. **报错公式 [发生了什么]+[怎么办]**（Codex 的克制版 + WorkBuddy 的具体版，A1/A2）——别堆"抱歉/呀"这类语气词，先说清出了什么问题，再给一句能直接照做的下一步；WorkBuddy 那种"请检查令牌，并确保已授予仓库与用户信息的必要读写权限"式的具体到点的提示，比泛泛"请重试"更值得学。
5. **空状态永远带下一步**（WorkBuddy 为主，A2）——"暂无X"后面永远跟一句怎么破局（"先新建一条吧""点击添加开始同步"），别只甩一句"暂无内容"就完事。
6. **悬浮通知塔**（Codex avatarOverlay，B2）——生图/发布/剪辑这类后台异步任务完成后，用一个独立于主窗口的轻量通知把结果推给用户（可堆叠、可内联操作），而不是要求用户一直盯着主窗口转圈——这和我们现状与待办里提到的"发布/剪辑后台异步+完成通知"这项真机验收待办完全对得上，可以直接参考这个交互方向去设计。
7. **两套语域分裂**（Codex，A1）——系统层文案（成功/失败/进度）保持克制说明书感，AI 角色说话时可以更口语化（"记着你了""搞定"），两层别混用，混了容易显得"整体端着又时不时不端"。
8. **"确定吗"只留给真高风险**（Codex，A1/B2）——全库唯一一处"Are you sure?"用在切到完全自主执行权限这种真正危险的操作上，其余场景都换成具体问句或干脆不问。我们的审批闸弹卡片应该学这个克制度：只在发布/群发/删数据这类真对外不可逆动作上弹重量级确认，别把"删一张草稿图"也搞出"确定吗"的仪式感。
9. **删除讲清不可逆**（WorkBuddy，A2）——"确定删除「名字」吗？删除后将无法恢复"这个公式简单直接，可以直接套用到我们的文件/生成记录删除场景。
10. **loading 有"生命感"**（WorkBuddy 流光扫字 2.2s、Qoder 变形块，B1/B4）——比纯转圈图标更有质感，成本不高（一段 CSS 动画），可以用在生图/生视频的加载态上替换掉当前的通用 spinner。

### 别学（技术味太重 / 违背我们产品方针）

- **Credits/订阅升级话术**（Qoder，A4/B4）——我们是全内置 key、不向用户暴露配额概念，这整类"用尽后……立即升级"的话术完全不适用。
- **YOLO 全局自动批准模式**（Trae，A3）——"完全禁用所有工具的人工审批"正是我们审批闸要防的场景，连带的劝退文案可以学（措辞怎么把"这真的很危险"讲清楚），但这个功能本身不该抄。
- **IDE 黑话直译**（Trae/Qoder，全篇）——"工作区""iCube""智能体团队"这类词面向开发者用户没问题，但对不懂技术的台球店主要一律翻成大白话（这也是我们 CLAUDE.md 里的既定原则，不是新发现，这里再次印证四家里越偏 C 端的产品越懂得把黑话翻译成人话——WorkBuddy 最像 C 端、术语翻得最干净，Trae/Qoder 最像开发者工具、黑话最重）。
- **"任务"/"会话"两套名词混用**（Trae，A3）——明确的反面案例，命名不统一是技术债，我们该在自己的词汇表里锁死"对话"就是对话、不要出现第二个近义词指代同一个东西（参考 WorkBuddy 的官方词汇表做法）。
- **三档审批粒度**（Trae，B3）——本会话/本工作区/始终，三档对企业级开发者合理，但对我们小白单机用户可能是"选择过载"，两档（这次/以后都这样）大概率够用，没必要照抄细粒度。
- **编号步骤式深度技术排错**（Qoder，A4）——"检查默认终端配置、快捷键 CMD+Shift+P……"这类面向开发者的详细操作指引，对台球店主用户不适用，我们的报错应该更接近 WorkBuddy 的"一句话讲清+一个按钮解决"，而不是甩一段排错手册。
