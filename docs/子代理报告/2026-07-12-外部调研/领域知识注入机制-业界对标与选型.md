## 一、"精炼核心文本注入系统提示"是不是业界主流?

**先说结论:是主流做法之一,而且是"第一梯队默认选项"，不是退而求其次的土办法。** 但业界的共识也很清楚:A/B/C/D 四条路线不是互相取代关系,是"分工"——用错场景才是问题,单独选哪条本身没有对错。

### 四条路线对比表

| 路线 | 干的事 | 什么时候用 | 优点 | 缺点/成本 | 防编造表现 |
|---|---|---|---|---|---|
| **A. 系统提示注入** | 把领域知识整理成一段文本,直接塞进 system prompt,每轮请求都带上 | 知识规模小到中等(官方给出的量化线是 **20万 token / 约500页以内**,见下文)、知识相对稳定、不需要频繁增删 | 实现成本最低(小时级)、无需向量库/embedding pipeline、延迟低、模型能"通读"整段材料做整体推理 | 规模一旦变大,每轮都要重新过一遍全文,费 token;知识增删要改prompt本身 | 中等:内容是策展过的、人工把关,但没有"检索时过滤"这道筛子,防编造全靠模型的指令遵循 |
| **B. RAG 检索增强** | 把知识库切块、做向量嵌入,用户提问时先检索最相关的几段,再喂给模型 | 知识规模大(超过上面那条线)、知识频繁更新、需要按需精确定位(如法规条款、产品手册) | 加一条新文档立刻生效不用重训;能过滤噪音,只把相关片段给模型,看的信息更聚焦 | 要建索引/切块策略/向量库,工程量陡增;检索本身会失败(检索不到=答不上或瞎编);多一层基础设施要运维 | 强(检索质量够好时):答案能明确追溯到具体文档片段,可以做"没查到就说没查到" |
| **C. 微调 Fine-tune** | 用领域数据继续训练模型权重 | 需要改变模型的**说话风格/输出格式/行为模式**,或某类任务出现频率极高值得投入 | 不用运行时额外基础设施,响应快;能让模型"学会"某种任务模式而不只是"知道"某个事实 | 最贵、最慢(要标注数据、要训练、要迭代验证);知识更新=重新训练;所有第三方文章都强调"最容易被过度使用" | 弱(单独用微调最容易产生编造):模型把知识"记"进权重,没有实时可核对的来源,官方/多篇文章都指出微调不解决"答案有据可查"问题 |
| **D. 其他(工具调用式知识库/GraphRAG/混合)** | 让模型自己调用一个"查知识库"的工具函数;或先建知识图谱做多跳推理;或把 A+B+C 组合用 | 工具调用式:知识要按场景动态展开、不想一次性塞满 prompt 时；GraphRAG:问题需要"实体之间怎么关联"的多跳推理,而不是"哪段文本最像";混合:生产级系统的主流做法 | 工具调用式=渐进披露,省 token 又保留精确度;混合(词面检索+语义检索+重排)效果最好 | GraphRAG 建图成本高(建索引阶段能烧到大几万美元级别,小语料库完全不值)；混合方案工程复杂度最高 | 工具调用式类似 A+B 混合,视具体实现;GraphRAG/混合在设计得当时防编造表现最强 |

### 几条最关键、来源最硬的数字/判断

- **Anthropic 官方给出的量化分界线**:"如果你的知识库小于 **20万 token(约500页材料)**,直接把整个知识库塞进 prompt 就行,不需要检索/RAG。"这是目前我查到的、**唯一一条有具体数字的官方分界线**。【官方:Anthropic Engineering Blog《Contextual Retrieval》https://www.anthropic.com/engineering/contextual-retrieval】
- 同一篇官方文章给出的检索失败率改善数据(top-20 检索失败率,基线 5.7%):纯做"上下文感知的 embedding"降到 3.7%(降 35%);加上 BM25 词面检索融合降到 2.9%(降 49%);再加重排(rerank)降到 1.9%(降 67%)。**关键结论是"混合检索(语义+词面)+ 重排" 优于"纯向量检索"**,纯向量库不再是 2025-2026 年公认的 RAG 最佳实践。【官方:同上】
- **长上下文不能完全取代 RAG,反之亦然**——这是查到的所有文章(Databricks/LlamaIndex/MindStudio/SitePoint)高度一致的结论。长上下文赢在"整篇文档级推理、静态且有界的知识库、低频但价值高的分析";RAG 赢在"语料超过上下文窗口、请求量大到 token 成本要精打细算、需要按元数据精确过滤"。Claude 在 100万 token 上下文下检索准确率约 90%(意味着 10 次里有 1 次答错),这也是长上下文本身并非万能的一个实测数字。【二手:MindStudio 博客 https://www.mindstudio.ai/blog/1m-token-context-window-vs-rag-claude ,交叉印证于 Databricks 官方博客 https://www.databricks.com/blog/long-context-rag-performance-llms】
- **RAG vs Fine-tune 的判断口诀**(多篇 2025-2026 文章高度一致):模型"不知道"某个事实 → 上 RAG;模型"知道但格式不对" → 用提示工程;模型"知道但语气/风格不对" → 用微调。三者常组合使用,不是二选一。【二手:综合 Medium/IBM/Nova AI Ops 等多篇同类文章交叉验证,原文摘录见文末来源清单】
- **系统提示注入不是"土办法",是当前 coding agent 类产品的官方标配**:Claude Code 的 `CLAUDE.md` 会被自动注入进每条用户消息(作为 system-reminder,官方文档证实);GitHub Copilot 的 custom instructions 官方文档明确说"每一次请求都会自动注入" 且明确建议"不要在指令文件里直接堆大段上下文,应该做成外部文档引用"(即"骨架注入 + 细节按需展开"这个模式本身就是官方推荐做法);`AGENTS.md` 现在是 Linux Foundation 下的跨工具开放标准。**这条路线是本项目对标的 cc-haha/Claude Code 自己在用的路线**,不是我们独创也不是凑合。【官方:Claude Code Docs `code.claude.com/docs/en/skills`、GitHub Copilot 官方文档;二手:多篇逆向分析文章交叉验证】
- **GraphRAG 对小语料库是过度设计**:多篇文章一致认为——语料小、问题是简单事实查找时,传统 RAG 比 GraphRAG 便宜且够用;GraphRAG 只有在查询明显需要"实体间怎么关联"的多跳推理时才值得投入,建图成本可以烧到 8.5万至50万美元量级(大语料场景)。【二手:多篇 GraphRAG 实践文章交叉验证,如 unalarming.com、falkordb.com、towardsdatascience.com】

## 二、我们这个具体情况,现在的机制到底对不对?

### 本地实况(读代码 + 读原始 PPT 文件实测,不采信转述)

读完 `ts/src/packs/billiards/` 全部相关源码,发现实际机制比任务描述里说的更精细,有必要先把真实情况说准:

1. **不是"一整段裸文本"注入,是结构化策展 + 分层展开**:
   - `knowledge.ts`(378 行)= 结构化的知识条目数组,每条都有 `title`(标题)+ `points`(要点原文)+ `src.line/src.page`(**PPT 原文行号+页码,可回溯审计**)+ `domain`(5 域分类)+ 可选 `hardSpecRefs`(关联硬数字编号)。
   - `hardSpecs.ts`(206 行)= 16 条硬数字单一数据源,其它地方只引用 id、不重复抄写,避免"改一处漏三处"。
   - **会话挂载时真正注入 system prompt 的**(`renderSessionStartContext()`)**只有标题+出处+两条真底线+表达纪律**,不含每条的详细 `points` 正文——这是一份"骨架/目录",体量比源码文件本身小得多。
   - 详细内容通过 `billiards_ops_checklist` 工具按场景动态调出(`findKnowledge`/`findHardSpecs`),用的是**关键词索引 + 子串匹配**做打分排序,不是向量语义检索,但已经是"骨架常驻 + 细节按需检索"的雏形,形状上已经接近 Claude Skills 的"渐进披露"设计,不是一次性铺开。【源码:`ts/src/packs/billiards/index.ts` L20-L76、`knowledge.ts` L357-L378】
2. **项目里已经有一套更成熟的检索机制,只是没用在 PPT 知识上**:`search_store_docs` 工具(`ts/src/server/services/storeDocsService.ts`)对用户自己上传的门店文件(合同/价目表/排班表)做的是**真正的混合词面检索**——BM25 打分(k1=1.35, b=0.72)+ 同义词/语义别名组扩展(比如搜"台费"自动带出"包台/小时费/收费"等)+ 双路召回用 **RRF(Reciprocal Rank Fusion)** 融合排序,并且**明确要求模型按"据 S1《文件名》"格式向用户显式引用来源**,查不到就必须说"资料库里没看到"。这说明团队已经具备构建混合检索的工程能力,**目前的差距精确定位是:这套能力还没有接到 PPT 领域知识本身**,不是完全没有检索能力。【源码:`ts/src/server/services/storeDocsService.ts` 全文,尤其 L412-L521 的 RRF 融合逻辑,L250-L290 的引用格式要求】
3. **原始 PPT 语料的真实体量,比任务描述的"几百页"给人的直觉印象小得多**:实测开发者本机 `~/Desktop/球房-PPT底本-本地存档/PPT原件全文-台球房运营7.23.txt`(项目记忆记录的是"278页8大板块"这份 PPT 的全文抽取版):**文件只有 23,647 个字符、2,155 行、其中汉字 13,408 个**。按常见分词器经验换算(中文字符与 token 的比例视具体分词器在 0.5~1.5 之间浮动,domestic 分词器一般比 GPT 系分词器对中文更省 token),粗估约 **1万~2万 token 量级**——这是【本地实测+推断估算】,不是拿真实分词器跑出来的精确值,但数量级足够支撑判断。【源码:本地文件 `wc -c/-m` 实测 + 项目记忆《资料索引与PPT框架》"PPT《找台球赋能》278页8大板块"】

### 拿业界基准一对照,结论很直白

**Anthropic 官方的分界线是 20万 token(约500页)以内可以直接塞 prompt。我们实测出来,连"没策展过的原始 PPT 全文"都只有 1万~2万 token 量级,是这条官方分界线的 1/10 到 1/20;而真正注入 system prompt 的策展骨架(标题+出处,不含细节正文)体量还要更小。**

也就是说:**不是"我们的注入马马虎虎凑合能用",而是按官方给的量化标准衡量,我们的语料规模离"必须上 RAG"的门槛还差一个数量级以上。** 现在这个"策展精炼核心 + 预留 RAG"的机制,在当前体量下是对的,而且不是退而求其次——它跟 Claude Code 自己给 CLAUDE.md/skills 用的机制(骨架常驻注入 + 完整内容按需展开)是同一形状,我们对标的标杆项目自己也是这么干的。

再加两条支撑:
- **国产模型基本都支持上下文/提示缓存**(DeepSeek/通义千问/Kimi/智谱GLM 等,缓存命中价格可降 80% 以上),意味着"每轮都要重新发一遍这段策展文本"的 token 成本顾虑,在当前几千 token 的体量下几乎可以忽略——多篇中文行业文章交叉确认这已是国产大模型 2026 年的标配能力。【二手:多篇中文行业文章交叉验证,含知乎/腾讯云等,具体见来源清单;⚠️此为"国产模型普遍支持"的行业层面结论，本项目内置 key 对接的具体模型是否已启用该特性、能省多少钱，本报告未做实测,建议单独验证】
- **Claude Code 系统提示的研究提到,指令遵循度会在 8万+ token 时明显衰减**——我们现在注入的骨架体量(几千 token 级)离这个阈值也很远,不存在"塞太多反而模型读不过来"的风险。【二手:`dbreunig.com` 逆向分析文章,交叉印证于本地测得的骨架体量数字】

### "防编造/答案有据可查"够不够?——分两层说,不是一个笼统的"够"或"不够"

**内部可追溯性:够,而且做得比很多"裸 RAG"实现更严谨。** 每条知识都带 PPT 行号+页码(源码级可审计),硬数字用单一数据源避免多处不一致,并且已经写死"PPT 没有的别编"、"资料库里没看到就明说"的红线指令——这本质上就是 RAG 想解决的"防瞎编"问题的另一种实现方式(策展时人工把关 + 显式拒绝指令),只是没有"检索时的强制过滤"这层结构性保证。

**但发现一个具体、和 RAG 决策无关、现在就能改的漏洞**:同一个项目里,`search_store_docs`(门店文件检索)明确要求模型用"据 S1《文件名》"这种结构化格式向**用户可见的回答里**显式引用来源;但 PPT 领域知识这边,`pack.ts` 里的指令只写了一句笼统的"带来源提醒",没有要求模型把"PPT 第几页"这类出处**显式带进给用户看的最终答案**。也就是说——出处数据本身是全的,只是没被同等严格地"逼"进最终答案里。这是一个成本几乎为零的修复(改几行 prompt 措辞,让 PPT 知识引用格式对齐 store_docs 那套"据 XX"的写法),跟接不接 RAG 完全无关,可以现在就做。【源码:`ts/src/packs/billiards/pack.ts` L43/L77(笼统的"带来源提醒") vs `storeDocsService.ts` L275(明确的"引用格式建议写成「据 S1《文件名》」")】

### 什么规模/什么信号出现时应该真的接上 RAG(可执行判断,不是空话)

按重要性排序,给的是可以直接拿去当监控指标用的信号,不是"以后知识库变大了就接"这种空泛判断:

1. **信号一(最重要、最该做的埋点):"资料库里没看到"命中率 + 人工抽查是否为真空白。** 现在的策展骨架只有约 45~60 条(数的是 `KNOWLEDGE` 数组条目),而原始 PPT 全文只有 2,155 行——策展必然有取舍,人工浓缩 278 页/2155行到 60 条,漏掉细节是必然的。做法:统计台球领域问答里模型说"资料库里没看到"/未命中策展知识的比例,挑一批人工回查原始 PPT 全文,如果里面**相当一部分（比如超过一到两成，或者哪怕只有几条但是老板反复问同一个点）确实原文有答案、只是没被策展进 60 条摘要里**,这就是最直接的"该上检索了"的信号——因为这时候问题不是"要不要检索",而是"人工策展的压缩比已经开始丢真实信息"。
2. **信号二:原始语料本身持续变大,人工策展跟不上。** 现在一份 PPT(23,647 字符)人工浓缩成 60 条还扛得住;如果以后台球包之外陆续挂载别的领域包,或者台球这条线自己继续往里加更多源材料(更多 PPT、更多访谈转录、更多门店案例),原始语料量级往几万字符、几十万字符走(哪怕还没到 Anthropic 说的 20万 token 那条线),人工重新策展一遍的维护成本会先扛不住——这时候"加一份新文档、不用人工重新提炼、检索立刻生效"的 RAG 优势才真正开始值回工程成本。
3. **信号三:用户开始要"原文怎么写的"而不是"大概怎么做"。** 现在的 `points` 是策展后的浓缩表达(虽然带出处,但已经不是 PPT 原句);如果出现"老板要核对合同条款措辞/要拿 PPT 原文去对质"这类需要**逐字精确溯源**的场景,策展摘要不如直接检索原始 2155 行文本里的那一段来得可靠。
4. **信号四:多领域包同时挂载导致骨架体量叠加。** 现在只有台球一个领域包;如果以后一个会话可能同时挂载多个领域包,每个包都在会话开始注入自己的骨架,叠加起来的 token 量会往上走——这时候值得给"体量较大的领域包"单独评估要不要把骨架也压缩、把细节转成检索,而不是所有包一刀切都上 RAG。

**只要以上四个信号都没出现,现在"策展精炼骨架常驻注入 + 关键词索引按需展开"这个机制就是对的,不需要因为"业界都在做 RAG"这种从众心理提前上马。**

### 真到了该接 RAG 的那天,接哪种技术路线(具体到选型,不是空泛建议)

如果上述信号触发,建议的技术路线(全部结论都标了来源,选型逻辑也说明白):

- **别学 GraphRAG、别学 RAGFlow/FastGPT/Dify 这类重型平台。** 这些框架解决的是"多租户知识库 SaaS 产品"的问题(建索引 UI、多知识库管理、多路由),我们是单一台球领域包、单一份不算大的语料,上这些框架属于杀鸡用牛刀,维护成本远超语料本身的价值(参考"GraphRAG 建图成本能烧到 8.5万到50万美元"这类量级警示,虽然那是大语料场景,但也说明这类重型方案的固定成本门槛本身就不适合我们这种体量)。
- **直接复用项目里已经写好、已验证的 `search_store_docs` 那套混合检索逻辑(BM25 + 同义词扩展 + RRF 融合)**,新开一个平行工具(比如叫 `search_billiards_ppt`)指向原始 PPT 全文(2155 行)做检索,而不是重新引入一个新框架——这条路线本身也是当前公认最佳实践(官方数据显示"纯向量检索"效果不如"词面+语义混合+重排",我们已有的词面检索部分正好是这个组合里技术含量最高、最容易出错的那一半,已经蹚过了)。
- **语义检索这半,嵌入模型选 BGE-M3(BAAI),不是 m3e**:BGE-M3 是 MIT 许可证、C-MTEB(中文向量榜单)第一梯队、支持 dense+sparse+multi-vector 一个模型三种检索模式、单次最长支持 8192 token 分块,多篇 2025-2026 年综述文章认为它已经取代 m3e 成为生产环境的默认选择(m3e 更老、专精中英双语,但已经不是当前的推荐首选)。【二手:多篇 2025-2026 嵌入模型综述交叉验证,原始项目 GitHub:`FlagOpen/FlagEmbedding`,11,923 star,MIT】
- **本地跑,不调外部 embedding API,延续"全内置/全本地/成本能免费就免费"的产品哲学**:`transformers.js`(Hugging Face 官方项目,16,172 star,Apache-2.0)已经支持在 Bun/Node/Electron 桌面环境里跑 ONNX 格式的 BGE 系列模型(Hugging Face 上有 `Xenova/bge-m3` 镜像,支持 q4/q8 量化压缩体积),而且项目记忆里已经确认 `transformers.js` 在本项目的 Bun 运行时下能跑通(和 sharp/whisper 一起验证过)。这条路线不需要新增外部依赖类别,是最小增量。
- **向量存储别用 sqlite-vec,优先看 LanceDB**:项目铁律是"存储走文件式(JSONL/JSON),别引 SQL 数据库";`sqlite-vec`(7,849 star,Apache-2.0)技术上是个轻量 SQLite 扩展,字面意义上仍是"引入 SQL"；`LanceDB`(10,866 star,Apache-2.0)是文件格式化的嵌入式向量库(类似 DuckDB/Parquet 那种"本地文件即数据库"哲学,没有独立 SQL 服务进程),跟项目现有的文件式存储哲学更贴。这一条是**工程选型层面的建议,不是本报告的核心结论**,真到实施阶段建议单独针对"LanceDB 是否完全满足项目'别引 SQL'的字面/精神双重要求"做一次小范围验证。
- **索引原始 PPT 全文时套用 Anthropic 的"上下文感知分块"技巧**:给每个切片前面拼一句"这段属于哪个域/哪个标题下"的说明再去做 embedding(现成的 `domain`/`title` 元数据可以直接当这句说明用,不用额外调小模型生成),官方数据显示这个技巧本身就能把检索失败率降 35%,配合已有的 BM25 词面检索能降到 49%。

---

## 三、结论汇总(可执行清单)

1. **现在"策展骨架注入 + 预留 RAG"的机制是对的**,不是凑合方案——按 Anthropic 官方"20万 token/500页以下可以直接塞 prompt"的量化标准,我们实测的原始语料只有其 1/10~1/20,注入的骨架体量更小,现在切 RAG 纯属过度工程。
2. **这条路线也不是我们独创的土办法**,是 Claude Code(CLAUDE.md/skills)、GitHub Copilot(custom instructions)这些我们对标的标杆项目自己在用的官方标配路线。
3. **防编造这块,内部可追溯性已经做得不错**(PPT 行号出处 + 单一硬数字源 + "不编造"红线指令),但发现一个和 RAG 无关、现在就该顺手改的漏洞:PPT 知识的引用没有像 `search_store_docs` 那样强制显式带进用户可见的最终回答,建议照抄后者"据 S1《文件名》"的写法,把 PPT 出处也变成必须显式引用的格式。
4. **该上 RAG 的信号是**:①"资料库里没看到"命中率高且人工抽查发现原文其实有答案(最重要);②源材料持续增长到人工策展扛不住;③用户开始要逐字溯源而非大意;④多领域包同时挂载导致骨架叠加过大。四个信号都没出现前不需要动。
5. **真触发时的技术路线**:不用 GraphRAG/RAGFlow/FastGPT 这类重型平台;直接把项目里已经写好且验证过的 `search_store_docs` 混合检索逻辑(BM25+同义词扩展+RRF)复用到 PPT 全文上,加一路 BGE-M3 语义检索(本地用 transformers.js 跑 ONNX 版,不调外部 API),向量存储优先看 LanceDB(比 sqlite-vec 更贴合"别引 SQL"的项目哲学,但这条需要单独小范围验证)。
