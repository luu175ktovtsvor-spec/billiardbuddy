## 已知待办核对结果

1. **边流边执行是否对齐 cc** → **仍缺,确认为结构性 gap**(见表 #8)。根因不在 `loop.ts` 本身,而在 `types/model.ts:29-38` 的 `Model` 接口:`step()` 只返回单个 `Promise<AssistantStep>`,`onDelta` 只搬正文/推理两路 token 级增量,没有"某个 tool_use 块已流完"的信号通道。要对齐 cc 的 `StreamingToolExecutor` 模式,需要扩展 `Model` 接口(新增 tool_use 块完成回调)+ 改造 `streamModelStep`/主循环把工具执行挪进流式消费循环内部——这是架构级改动,不是局部补丁。

2. **max_turns 事件可辨识(前端能区分"到上限"和"正常完")** → **已做**。`types/events.ts:62` `max_turns_reached` 是独立 discriminated union 成员,与 `final`(:45)结构不同、前端可用 `type` 字段直接分支;`loop.ts:762-765` 命中后只 yield 该事件 + return,不再调模型,行为对齐 cc `query.ts:1713-1719`。唯一遗留缺口是硬停 abort 路径没做同样检查(表 #4,P2/S)。

3. **并行只读并发上限数值与 cc 一致否** → **一致**。同一 env var 名 `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`,同默认值 10(cc: `toolOrchestration.ts:8-12`;我们:`loop.ts:927-930`)。但触发并行的**前置条件**不完全对齐:cc 按 `isConcurrencySafe`(工具自报,默认 false)连续分批,hooks 存在与否不影响分批;我们额外加了"只要有任何 hook 规则注册就整体退化全串行"的闸(表 #7,P1/M),这个闸不存在于 cc。

4. **sameCallGuard:cc 到底有没有这东西,形状什么样** → **cc 完全没有代码级机制**,不论硬闸还是软提醒——唯一相关的是 system prompt 里一句劝诫文案(`constants/prompts.ts:233`),不改变任何执行/回灌决策;真正起"防重复调用"作用的是模型自己看到重复的 tool_result 后自行调整,加上人类可打断。`QueryGuard.ts` 是无关的"同一时刻只能有一条 query 在跑"重入闸,不要误认成 sameCallGuard。我们当前状态(`ad90b69` 之后)在 `stuckDetector.ts` 仍保留一套完整的运行时"卡壳检测"状态机(同调用重复计数阈值 4/40、连续报错检测、纯对话不动手检测、总工具数熔断 40),命中即在回灌里插入 `<system-reminder>` 软提醒——**这套机制本身就是 cc 没有的东西**,`ad90b69` 只是把"硬拒执行"降级成了"软提醒",并没有把机制本身去掉。是否保留这套软提醒是产品可以自主拍板的加强项(不算"抄错"cc),但严格按"cc 有没有"的问法回答:cc 没有,我们仍有。

5. **max_output_tokens 续写与 cc 逐行为核对** → **基本对齐,分层不同**。触发条件对齐(finish_reason=length/max_tokens 且当轮无 tool_calls,cc `query.ts:1196` vs 我们 `ProxyModel.ts:41-90` 的 `isTruncatedFinishReason`);两段式结构对齐(先原地升 max_tokens 到 64_000 重试一次,再多轮"从断点续写"元提示最多 3 次);拼接方式对齐(截断的 assistant 部分文本原样留在历史里,靠新一轮 user 元提示让模型自然接续,不做字符串裁剪拼接);上限次数完全对齐(`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT=3`,常量名照搬,`loop.ts:187` vs `query.ts:167`);升级目标值完全对齐(`ESCALATED_MAX_TOKENS=64_000`,`ProxyModel.ts:54` vs `utils/context.ts:32`)。唯一差异:cc 的"原地升 max_tokens"这一步在其默认配置下是**关闭**的(`tengu_otk_slot_v1` growthbook 开关默认 false),而我们把它做成**恒定生效**(无开关)——即我们比 cc 的默认路径更激进一点,但完全符合 cc 代码本身写的逻辑,不算偏离。

## 摘要(供上层引用)

- **aligned:12 项**(循环骨架/退出判据、max_turns 主路径与事件可辨识、tool_use-tool_result 严格配对与异常兜底、并行并发上限数值、入参 schema 三类校验+is_error 包壳形状、max_output_tokens 两段式恢复、代理级模型 fallback 孤儿丢弃、主动+被动压缩双路、并发安全分类机制)
- **gap(cc 有我们没有/不全):2 项** — #8 边流边执行(P1/L,结构性,需扩 Model 接口)、#4 max_turns 检查未覆盖硬停 abort 路径(P2/S)
- **deviation(行为分叉,非产品边界豁免):3 项** — #7 任意 hook 存在即整体禁用并行只读(P1/M,cc 里 hooks 与并发正交)、#12 sameCallGuard cc 零机制我们仍有运行时软提醒状态机(P2/S)、#14 模型重试退避参数弱于 cc(次数 3 vs 10、无 jitter、无 env 覆盖,P2/S)
- **intentional-delta:2 项** — content_delta 事件扁平化(产品前端简化)、streaming 中断/steering 双通道设计(比 cc 更细)

**P1 top: ** ①边流边执行完全不支持(Model 接口结构性缺口,多工具单轮内必须等整轮流完才开始执行第一个工具,拉长多工具回合的端到端延迟);②只要会话里注册了任意一条 hook 规则(哪怕与当前工具无关),并行只读工具执行就整体退化成全串行,cc 里 hooks 和并发分批是正交的两件事。
**P2 top: ** ③max_turns 检查没有覆盖"硬停被 abort"这条路径,cc 在这条路径也会补发 max_turns_reached;④sameCallGuard 在 cc 里完全不存在(纯 prompt 文案),我们仍保留一套运行时软提醒状态机(`stuckDetector.ts`),是刻意加强而非对齐产物;⑤模型调用重试退避的数值参数(重试次数 3 vs cc 10、退避上限 8s vs 32s、无 jitter、不支持 env 覆盖)明显弱于 cc,在国内代理链路抖动场景下韧性偏低。
