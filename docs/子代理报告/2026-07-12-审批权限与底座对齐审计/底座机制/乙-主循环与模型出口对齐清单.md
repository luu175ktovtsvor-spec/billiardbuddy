### 1.1 〔验证通过 · 无问题〕maxTurns 语义与截断次数上限对齐

- 我方 `loop.ts:203`:`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`;`loop.ts:236-237,819-825`:`turn` 从 0 起、每个工具批次结束后 `turn++` 再判 `turn >= maxTurns`。

### 1.2 〔真分叉 · 低,可执行〕硬中断恰好命中 maxTurns 边界时,我方不再上报 max_turns_reached,cc 会

- 我方 `loop.ts:809-825`:
  ```

    if (reason === 'interrupt') { 换新 controller; }
    else { yield context_note; return }   // ← 硬停在这里直接 return,turn++ 和 maxTurns 判断永远走不到
  ```

- cc `query.ts:1492-1523`:硬中断(`abortController.signal.aborted`)分支里**仍然**算 `nextTurnCountOnAbort = turnCount + 1`,若 `maxTurns && nextTurnCountOnAbort > maxTurns` 则**额外** `yield createAttachmentMessage({type:'max_turns_reached', ...})`,即便最终 `return { reason: 'aborted_tools' }`。

- 掰回改法:在 `loop.ts:813`(`else` 分支、`yield context_note` 之后、`return` 之前)补一次 `if (maxTurns !== undefined && turn + 1 >= maxTurns) yield { type:'max_turns_reached', turnCount: turn + 1, maxTurns }` 再 return。工作量:小(加 3 行 + 补一个 loop.test.ts 用例锁边界)。

## 三、模型出口 / 翻译层(`ts/src/proxy/*` + `model/{AnthropicMessagesModel,FallbackModel,fetchRetry,modelContextWindows}.ts` vs cc)

> 口径重申:proxy 层是我方必有而 cc 没有的(cc 直连 Anthropic API),下面的"cc 侧证据"对应的是 cc **原始 Anthropic 协议语义/常量**,对标点是"翻译后模型看到/回出的东西是否等价于 cc 直连时的样子",不是逐行比对一个不存在的 cc-proxy 文件。

### 3.1 〔疑似 · 需验证〕max_tokens "撞顶后静默升到 escalated 值重试一次" 我方恒开,cc 该功能默认关闭(灰度实验,3P 默认 false)

- 我方 `AnthropicMessagesModel.ts:110-113` / `ProxyModel.ts:78-81`:**无条件**——只要 `isTruncatedStopReason && toolCalls.length===0`,立即把 `max_tokens` 升到 `ESCALATED_MAX_TOKENS=64_000` 重试一次,不受任何开关控制。
- cc `services/api/claude.ts:3632-3648`:该逻辑的前提是 `isMaxTokensCapEnabled()`(即 `getFeatureValue_CACHED_MAY_BE_STALE('tengu_otk_slot_v1', false)`——**3P 默认 false**,注释原文"3P default: false (not validated on Bedrock/Vertex)"),且只有在这个 slot-reservation 实验**开启**时,cc 才会先把默认 `max_tokens` **主动降到** `CAPPED_DEFAULT_MAX_TOKENS=8_000`,命中上限后再"升到 64k 重试一次"(`query.ts:1203-1229` `capEnabled && maxOutputTokensOverride===undefined`)。也就是说:cc 的"真实生产默认行为"根本不存在"先降后升"这套流程,直接用模型原生 `max_tokens` 默认值(通常远高于 8k),命中上限就直接进入"断点续写"多轮消息恢复(`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT=3`)。
- 判级:我方把 cc 一个**默认关闭的内部实验**当成了恒定行为来实现,虽然数值(`ESCALATED_MAX_TOKENS=64_000`)抄对了,但触发的前提条件("先用 8k 小预算省容量槽位")完全没有对应、也没必要对应(那是 Anthropic 自家算力槽位优化,我方走网关代理无此顾虑)。这一条本身**结果上更宽松/更省心**(不会先故意压低预算),更像是**产品层合理简化**而非分叉——但由于 cc 源码就是规格、且我方代码注释自称"对齐 cc query.ts:1196-1229 escalate",这个"对齐"表述不准确(cc 该路径默认关闭),建议改注释为"cc 该 escalate 机制默认关闭(3P灰度实验),我方主动常开、跳过其'先降后升'的省槽位前置步骤"以免误导后续对齐审计。
- 验证步骤:若后续要跟 cc 生产行为 1:1,只需确认 owner 是否需要"先用低预算省 token 成本"这层——目前不需要,建议保持现状,仅需**改注释措辞**(工作量:小,纯文档)。

### 3.2 〔真分叉 · 中,可执行〕Anthropic 直连出口默认 max_tokens=4096,明显低于 cc 实际使用的模型原生默认值

- 我方 `AnthropicMessagesModel.ts:69,79`:`DEFAULT_MAX_TOKENS = 4096`,仅当 `RuntimeProviderConfig.maxTokens` 显式配置(`providerConfig.ts:97` 读 `ANTHROPIC_MAX_TOKENS`/`MAX_TOKENS` 环境变量,或 `providerService.ts:230` 读用户在网关侧配置的 `provider.maxTokens`)时才覆盖,否则回退到 4096。
- cc `services/api/claude.ts:3637-3657` `getMaxOutputTokensForModel`:未开灰度时直接用 `getModelMaxOutputTokens(model).default`(模型自身原生默认值,对 Sonnet/Opus 系列通常在 8k-64k 区间,远高于 4096),仅被 `CLAUDE_CODE_MAX_OUTPUT_TOKENS` 环境变量覆盖。
- 毒例 I:网关侧新接一个 Anthropic 协议兼容的国产模型 provider,运维忘记显式填 `maxTokens` 字段(`providerService.ts` 该字段是 `optional`,不填不会报错、不会拦截)。cc 语义预期:模型按自己原生上限(数万 token)输出。我方实际:每次输出在 4096 token 处被硬切,`loop.ts` 的 `MAX_OUTPUT_TOKENS_RECOVERY_LIMIT` 续写机制会被频繁触发(每篇长代码生成天然多切几刀),即便 `AnthropicMessagesModel.ts:110-113` 的 escalate 会救一次(升到 64k),但只在"截断且无 tool_calls"时救一次——如果模型在同一步里既写了长正文又带了 tool_calls,`toAssistantStep`(AnthropicMessagesModel.ts:448-451)判定优先返回 `tool_calls` 分支不触发 escalate,截断的正文只能靠主循环的"断点续写"多轮拼接,徒增往返次数与 token 消耗。
- 测试覆盖:`AnthropicMessagesModel.test.ts` 未见针对"未配置 maxTokens 时的默认值是否合理"的断言(只测协议翻译正确性,不测数值选型)。
- 掰回改法:`AnthropicMessagesModel.ts:69` 的 `DEFAULT_MAX_TOKENS` 从 4096 提到至少 8192(对齐大多数国产 Anthropic 兼容端点/Claude 系列的常见原生默认),或者更彻底地——像 `ProxyModel.ts` 一样**默认不带 `max_tokens` 字段**、交上游自己的默认值(`toOpenAiChatRequest.ts:32` 注释"max_tokens 故意不带:大值容易超过多数国产上游上限,交由上游默认"——`AnthropicMessagesModel.ts` 没有采用同样的策略,两个出口对同一个问题给出了不一致的默认策略,这本身也是内部不一致)。工作量:小(改一个常量或改成条件性省略字段 + 补一条回归测试)。

### 3.3 〔真分叉 · 中,可执行〕瞬时错误重试预算明显低于 cc:重试次数 3 vs 10、退避上限 8s vs 32s、无抖动 vs ±25% 抖动

- 我方 `fetchRetry.ts:26-28`:`DEFAULT_MAX_RETRIES=3`、`DEFAULT_BASE_DELAY_MS=500`、`DEFAULT_MAX_DELAY_MS=8000`;退避公式 `backoffMs = min(max, base * 2**attempt)`,**无随机抖动**。
- cc `services/api/withRetry.ts:51,54,580-598`:`DEFAULT_MAX_RETRIES=10`(可用 `CLAUDE_CODE_MAX_RETRIES` 覆盖);`BASE_DELAY_MS=500`(与我方一致);`getRetryDelay(attempt, retryAfterHeader, maxDelayMs=32000)`:`baseDelay = min(BASE_DELAY_MS * 2**(attempt-1), 32000)`,并额外加 `jitter = Math.random() * 0.25 * baseDelay`(±25% 随机抖动)。
- 我方文件自己的注释(`fetchRetry.ts:5-8`)明确写了这个模块存在的理由:"本项目走国内网关/代理链路,429/5xx/连接闪断这类瞬时抖动概率不低"——但实际给的重试预算(3 次、最高 8 秒)比 cc 默认给的(10 次、最高 32 秒)要**保守得多**,与自己声明的"网关更不稳定所以需要更强重试"的动机方向相反。
- 毒例 I:上游网关连续返回 5 次 429(如高峰期限流)。cc 判:10 次重试预算内可以扛住(delay 序列约 500,1000,2000,4000,8000,16000,32000,32000,32000,32000ms,叠加抖动),第 5 次早就重试成功。我方判:3 次重试预算(约 500,1000,2000ms,总计 3.5 秒)耗尽后直接向上抛错,交给 `FallbackModel` 切到备用出口(若配置了备用出口)或整体失败(若只有单一出口)。
- 毒例 II(无抖动的具体后果):若本机同时起多个并发请求(例如子代理并行调用同一网关),我方所有请求会在**完全相同**的时间点(500ms、1000ms、2000ms 之后)同时重试,无抖动分散,更容易造成"重试风暴"压垮同一网关;cc 的 ±25% 抖动能把并发重试请求错开。
- 判级:这不是"我方产品层故意做小重试预算给多供应商更快切换"的合理解释站不住脚——因为 `FallbackModel` 本身也是我方独有的产品能力(cc 没有多供应商轮询),3 次重试 + 快速切换到 fallback 与 cc 的"单一模型努力重试 10 次"是两种可以共存的策略,但**目前重试预算数值本身没有独立证据支撑"3 次比 10 次更合适"**,应视为真分叉(数值抄少了),而非产品层故意。
- 掰回改法:`fetchRetry.ts:26-28` 把 `DEFAULT_MAX_RETRIES` 提到 10(或至少给一个介于两者之间、有论证的值)、`DEFAULT_MAX_DELAY_MS` 提到 32000,并在 `backoffMs` 里加 `Math.random() * 0.25 * base` 抖动项对齐 cc。工作量:小(改 3 个常量 + 加一行抖动 + 更新 `fetchRetry.test.ts` 里断言具体延迟值的用例)。

### 3.4 〔疑似 · 需验证,产品层判故意的边界情形〕thinking/推理块从不回灌进历史,即便在同一条"思考→工具调用"轨迹内

- 我方 `AnthropicMessagesModel.ts` 的 `toAnthropicBlock` 函数(`AnthropicMessagesModel.ts:216-231`)没有 `block.type === 'thinking'` 分支,落到 `return []` 静默丢弃;`ProxyModel.ts` 的 `convertAssistantMessage`(`toOpenAiChatRequest.ts:119-136`)同样"thinking:默认不回灌(display-only,无 signature)"(见该函数第 131 行注释)。根源在 `loop.ts:666`:"assistant 历史块:正文 text(若有)+ tool_use 块(thinking 不进历史、不回灌模型)"——`messages` 数组从源头就不含任何 `thinking` 块。
- cc `query.ts:154-165` 的"the rules of thinking"注释明确指出 Anthropic 协议的硬约束:"Thinking blocks must be preserved for the duration of an assistant trajectory (a single turn, or if that turn includes a tool_use block then also its subsequent tool_result and the following assistant message)"——即在**同一条推理轨迹**内(模型先 thinking 再 tool_use,随后紧跟 tool_result 和下一条 assistant 消息),真实 Anthropic API 要求把原始 thinking 块(带签名)原样回灌,否则 extended thinking + 工具交织场景可能被 API 拒绝或丢失推理连续性。

- 验证步骤:确认本项目是否存在/计划存在"AnthropicMessagesModel 直连真实 api.anthropic.com 且开启 extended thinking"的部署路径。若从不直连真 Claude(仅用于国产 Anthropic 协议兼容端点),此项按〔降级适配〕结案,建议在 `AnthropicMessagesModel.ts` 补一条注释说明"本类不用于连接真 Claude 官方端点,故不实现 thinking 签名回灌";若确实可能直连,则需按 cc 规则实现"同轨迹内保留 thinking 块 + 签名"，工作量:中-大(需要在 `Message`/`ContentBlock` 类型里保留 thinking 的 signature 字段、loop.ts 里区分"轨迹内"与"轨迹外"两种回灌策略)。

### 3.5 〔产品层故意 · 不算问题〕FallbackModel 多供应商轮询 vs cc 单一 --fallback-model

- 判级:这是本项目"网关藏 key + 白标 + 多国产供应商"产品架构决定的能力(cc 没有多供应商网关的概念),CLAUDE.md 明确允许"生图/剪视频/领域包/白标"这类产品层分叉不算违规,多供应商 fallback 属同类——但触发条件更宽泛(我方任何 `candidate.model.step()` 抛错都会尝试下一个候选,cc 只在 `FallbackTriggeredError` 这个特定信号上切换)这一点值得**记录而非报警**:我方"任何失败都切换出口"的策略配合 §3.3 里"重试预算过小"的问题会放大——一次瞬时网络抖动很容易越过 3 次重试直接触发"切到另一个供应商"而不是"稍等重试成功",这是 §3.3 与 §3.5 两条组合起来的真实风险点,建议一并修。

- 毒例 I:一段 60 条消息的会话,第 50 条消息是一次 100KB 的 `read_file` 大文件读取结果,恰好落在"最近 12 条"窗口内(`60-12=48 < 50`)。cc 判:整个 60 条历史(含第 50 条那 100KB 内容)全部进摘要模型压成一段文字摘要,压缩后文原文完全不含那 100KB 数据,只保留文件路径重建 attachment(重新读一次该文件**当前**内容,受 `POST_COMPACT_MAX_TOKENS_PER_FILE=5000` token 限制)。我方判:第 50 条连同其 100KB 原始文本**原样留在压缩后历史里**(因为它在最近 12 条窗口内),摘要只吃掉了第 1~48 条,压缩省下的 token 空间明显小于 cc,极端情况下下一轮 `maybeCompact` 可能因为这条巨量残留内容而立刻(或很快)再次触发压缩。
- 影响面:①压缩后实际释放的上下文空间系统性小于 cc(压缩效果打折);②`compaction.ts` 头部注释大量引用"对齐 cc autoCompact.ts:30/62/72-91"等具体行号来证明阈值常量对齐,但唯独"保留最近 N 条"这个**决定压缩后消息数组长成什么样**的核心结构性决策,从未在注释里声明"这是我们主动偏离 cc 的地方"——按 CLAUDE.md 自己的铁律"内核直接照 cc 移植,发现分叉就掰回去...对标点是唯一验收硬闸",这是需要掰回或至少显式登记的真分叉,不是可以默认保留的产品层选择。
- 测试覆盖:`compaction.test.ts` 现有测试断言"压缩后 recent 消息保留"是**当前实现的自洽测试**,不代表这与 cc 对齐——它测的是"我们自己设计的行为符合我们自己的实现",没有测试断言过"压缩后是否应该像 cc 一样不保留任何原始消息"。
- 掰回改法:`compactPipeline`(`compaction.ts:269-330`)改为始终 `toSummarize = messages`(全量摘要,去掉 `splitForAutocompact` 的"old/recent"切分),压缩后消息数组变为 `[summary_message, ...postSummaryMessages]`(即去掉 `...split.recent`),依赖已经存在的 `buildRecentFileContextMessage`(`loop.ts:498-501`)承担"近况重建"职责(该机制已对齐 cc 的 `createPostCompactFileAttachments` 数量上限)。工作量:中-大——需要:①改 `compactPipeline`/`splitForAutocompact` 的签名和内部逻辑;②重写 `compaction.test.ts` 里所有断言"recent 消息被保留"的用例(预计影响 5-10 个测试);③确认 `postSummaryMessages`(当前只塞 `invokedSkills`)是否需要补齐 cc 的"计划文件重新附加"逻辑(目前计划的持续性靠 §2.2 提到的"每批必发的 plan reminder" 意外兜底,若那条被节流化修复,压缩后计划模式的连续性会失去这个意外的安全网,需要一并核实);④跑一遍 `loop.test.ts` 确认没有测试假设"压缩后能从 recent 里读到原始工具结果"这类隐性依赖。

### 4.2 〔真分叉 · 中,可执行〕token 级自动压缩触发判断只看"上一轮真实用量",没有像 cc 一样为"上一轮之后新增的内容"补估算增量

- 我方 `compaction.ts:245-247`(`shouldAutocompact`):
  ```
  if (input.lastInputTokens && input.lastInputTokens > 0 && hasWindow) {
    return input.lastInputTokens >= getAutoCompactTokenThreshold(...)
  }
  ```
  `lastInputTokens` 只在 `loop.ts:582` 里"上一次 `model.step()` 返回后"更新一次,而 `maybeCompact()` 在 `loop.ts:547`(循环顶部,**下一次** `model.step()` 之前)被调用——中间夹着一整批工具执行 + `messages.push({role:'user', content: followup})`(`loop.ts:803`),如果这批工具结果本身很大(比如一次读了个大文件),`lastInputTokens` 完全反映不出这次新增的体积。
- cc `utils/tokens.ts:244-275` `tokenCountWithEstimation`:从数组末尾往前找**最近一条带真实 usage 的 assistant 消息**,以它的真实 usage 为基准,再用 `roughTokenCountEstimationForMessages(messages.slice(i + 1))`(字符估算)**补上该消息之后新增的所有内容**(新的 tool_result、新的 user 消息等)。cc `shouldAutoCompact`(`autoCompact.ts:225`)直接用这个"真实用量+新增估算"的复合值去比阈值,不是纯用上一轮的旧用量。
- 毒例 I:上一轮 `model.step()` 回报 `input_tokens=150_000`(阈值 167k,未触发压缩),随后模型调用一次 `read_file` 读入一个 80_000 token 的大文件。cc 判:`tokenCountWithEstimation` = 150k(真实)+ ~80k(新增估算)= 230k,下一次 `maybeCompact` 前即可判定超过 167k 阈值,主动压缩。我方判:`lastInputTokens` 仍是旧的 150k(压根不知道新增了 80k),`shouldAutocompact` 判定"未超阈值",直到**下一次** `model.step()` 真的把这 230k 发出去、要么侥幸没炸、要么触发 `looksLikeContextOverflow` 走 `loop.ts:566-579` 的被动补救路径(靠捕获 API 报错再强制压缩,而不是主动提前压缩)。
- 影响面:大文件读取/大命令输出恰好发生在"压缩阈值附近"时,我方比 cc 晚一整轮才会压缩,期间多发一次可能直接撞上下文上限的真实请求,依赖被动的"报错重试"兜底而非主动预判。
- 测试覆盖:`compaction.test.ts` 有测"lastInputTokens 触发压缩"的用例,但没有"lastInputTokens 陈旧、期间新增大内容"的用例。
- 掰回改法:在 `shouldAutocompact` 里,把 `input.lastInputTokens` 换成 `input.lastInputTokens + estimateMessagesChars(未被上一次真实 usage 覆盖的新增消息) / 估算比例`,或者更简单地——直接对**当前完整 `input.messages`** 调用已有的 `estimateMessagesChars` 并取 `max(基于 lastInputTokens 的真实值, 基于新增消息的估算值)` 做判断(不需要 cc 那种"回溯到最近一条真实 usage 消息"的复杂实现,只要把"最近一次已知真实值之后新增的字符"也纳入估算即可)。工作量:小-中(需要知道"最近一次真实 usage 对应到 messages 数组的第几条"这个锚点,目前 `lastInputTokens` 是纯数字、没有锚点索引,需要额外传参或改造)。

### 4.3 〔真分叉 · 低-中,CJK 相关,可执行〕近期文件/工具结果预算全部按"字符数"而非 cc 的"token 数"计量,CJK 内容下实际保留量与 cc 不成比例

- 我方 `recentFileContext.ts:6-8`:`DEFAULT_RECENT_FILE_CONTEXT_MAX_BYTES_PER_FILE=12_000`(字节)、`DEFAULT_RECENT_FILE_CONTEXT_MAX_TOTAL_BYTES=40_000`(字节)。`toolResultStorage.ts:6-8`:`DEFAULT_TOOL_RESULT_STORAGE_THRESHOLD_CHARS=24_000`(字符)、`DEFAULT_TOOL_RESULT_STORAGE_PREVIEW_CHARS=2_000`(字符)。
- cc `compact.ts:123-124`:`POST_COMPACT_TOKEN_BUDGET=50_000`(**token**)、`POST_COMPACT_MAX_TOKENS_PER_FILE=5_000`(**token**);`utils/toolResultStorage.ts:109`:`PREVIEW_SIZE_BYTES=2000`(**字节**,非字符);`constants/toolLimits.ts:13`:`DEFAULT_MAX_RESULT_SIZE_CHARS=50_000`(字符,这一项单位与我方一致但数值差 1 倍多)。
- 毒例 I(CJK 字符 vs 字节/token 换算错位):中文文本"你好世界"(4 字)UTF-8 占 12 字节,常见分词器(如 cl100k)编码约 4-6 个 token——即中文场景下"字节数"与"token 数"的比例远不同于纯英文场景(英文约 4 字节/token,中文常见约 2-3 字节/token,也就是说**同样字节预算下,中文能装的 token 更少**;但反过来同样"字符数"预算下,中文一个字符往往就是 1-2 个 token,比英文单字符省 token)。这意味着我方用"字符数=24000"卡 `toolResultStorage` 落盘阈值,对中文内容而言实际保留的 token 量与 cc 用"50000 字符"卡的阈值**不是同一把尺子在量同一件事**,且我方阈值只有 cc 的不到一半(24000 vs 50000 字符),对纯中文工具输出会**提前一倍多触发"落盘替换为预览"**,迫使模型多一次 `read_stored_tool_result` 往返才能看到完整内容。
- 毒例 II:`recentFileContext.ts` 单文件预算"12000 字节" ≈ 4000-6000 个中文字符(按 UTF-8 每字 2-4 字节估算)对应中文分词器下约 4000-9000 token;cc 的"5000 token/文件"若按同一分词器折算成中文字符数,量级相近但**不保证一致**——由于两边计量单位从字节/字符换算到 token 天然有波动区间,精确对齐需要引入真实分词器而非用估算比例,当前两套实现各自内部自洽但互相之间没有可验证的等价关系,只能定性判断"量级接近、精确值未经验证对齐"。
- 判级:低-中,原因是只影响"压缩后能看到多少历史文件内容/工具结果预览"的精细预算,不影响功能正确性(不会崩溃或丢失关键信息,只是保留量可能比 cc 少或多),但既然要"对标 cc"就该用同一种计量单位比较。
- 掰回改法:①`toolResultStorage.ts` 的 `PREVIEW_SIZE_BYTES` 类常量,把"字符"改成"字节"计量(与 cc 用同一把尺子);②`DEFAULT_TOOL_RESULT_STORAGE_THRESHOLD_CHARS` 从 24000 提到 50000(对齐 cc `DEFAULT_MAX_RESULT_SIZE_CHARS`);③`recentFileContext.ts` 的 "MAX_BYTES" 系列常量,若要精确对齐 cc 的"5000/50000 token"预算,需要引入近似 token 估算函数(项目里 `estimateMessagesChars` 一类的字符估算已有先例,可复用同一套换算比例)而不是裸用字节数。工作量:小(改常量 + 统一换算函数,补 1-2 条 CJK 内容的回归测试)。

### 4.4 〔我方多出 · 判该留〕30 秒压缩冷却 + "消息数未增长不再压" 门槛,cc 没有对应的时间冷却机制
