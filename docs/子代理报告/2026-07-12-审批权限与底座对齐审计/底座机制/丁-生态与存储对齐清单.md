### 1.2 〔真分叉·高〕workspace trust 门:cc 对"全部来源"一视同仁,我方只挡 `local`

**我方现状** `ts/src/hooks/hooks.ts:232-244`(`shouldRunHookRule`):
```
if (policy.disableAllHooks) return false
if (rule.source === undefined || rule.source === 'managed') return true   // managed 完全不受信任门约束
if (policy.allowManagedHooksOnly) return false
if (rule.source === 'user' || rule.source === 'plugin') return true       // user/plugin 同样不过 workspace trust
if (policy.interactive && !policy.isWorkspaceTrusted(workspaceRoot)) return false   // 只有 local 走到这一行
return true
```
本文件 `hooks.ts:221-231` 自己的注释承认这是"与 cc 的一处有意分叉"。

**cc 侧证据** `src/utils/hooks.ts:289-299`(`shouldSkipHookDueToTrust`):
```
export function shouldSkipHookDueToTrust(): boolean {
  const isInteractive = !getIsNonInteractiveSession()
  if (!isInteractive) return false
  const hasTrust = checkHasTrustDialogAccepted()
  return !hasTrust
}
```
函数头部注释原文:"ALL hooks require workspace trust because they execute arbitrary commands...enforcing trust for ALL hooks prevents: Future bugs...Any codepath that might trigger hooks before trust...Historical vulnerabilities: SessionEnd hooks executing when user declines trust dialog / SubagentStop hooks executing when subagent completes before trust"。调用点 `src/utils/hooks.ts:2012`(`executeHooks` 内,在按 `matchQuery` 过滤具体 hook **之前**就整体短路),同一文件 `:3050`、`:4616`、`:4706` 是其余入口(Notification/Elicitation 等)的同款检查。**全程没有任何按 source 的分支**——即便是 cc 自己的 `managedSettings`(企业策略级 hook,`src/utils/hooks/hooksConfigSnapshot.ts:12-26` 定义的"托管专属"概念)也一样过这道闸,只是另有 `shouldAllowManagedHooksOnly()` 管"仅放行托管源、其余都不放行"这另一件事,两件事互不替代。

**毒例(可直接抄成测试)**:
输入 I:工作区未信任(`mcpTrust.isTrusted(root)` 为 false,产品默认状态——见下方说明),交互模式,`domainPacks.ts` 注入了一条 `SessionStart` 的 managed hook。
- cc 判:`shouldSkipHookDueToTrust()` 为 true → `executeHooks` 整体 `return`,**该 hook 不执行**(不管它的 source 是不是"托管")。
- 我方判:`shouldRunHookRule` 对 `source===undefined`(managed)直接 `return true`,**hook 照常执行**——`ts/src/packs/domainPacks.ts:113-121` 的 `createDomainPackHookRegistry` 就是这类 managed hook,workspace 从未被信任也会正常注入领域包上下文。

**这道闸目前是"活的",不是理论问题**:`configureHookTrust({ interactive: true, isWorkspaceTrusted: root => mcpTrust.isTrusted(root) })` 在 `ts/src/server/index.ts:959` 真实调用;而 `McpTrustStore`(`ts/src/mcp/mcpTrust.ts:13-57`)默认"零信任"(`roots` 只从磁盘 `approvedWorkspaceRoots` 读,首次为空),且全仓库搜索 `trustedWorkspaceRoots`(`server/index.ts:158`)只有定义处和内部使用两处引用,桌面壳启动代码里**从未**传过这个参数——换句话说,**当前生产环境下每一个工作区永远处于"未信任"状态**(前端也还没有信任授予 UI,见项目记忆),`local` 源 hook 因此被闸死是符合预期的,但 `managed`/`user`/`plugin` 三类源全部绕过这道闸,равно于闸门只在字面上存在。

**是否有现实攻击面**:
- `managed` 源当前的两个真实生产者——`createDomainPackHookRegistry`(`packs/domainPacks.ts:113`)、`createGoalHookRegistry`(`goals/goalState.ts:66`)——都是编译进 App 的闭包,不接收工作区任意内容,**今天**不构成可利用的 RCE 面。
- `user` 源(`ts/src/hooks/hookConfig.ts:831-833` `loadUserHookRegistry`,读 `~/.billiardbuddy/settings.json`)**是真实的、用户可写的 command/http hook 配置**(`hookConfig.ts:736-757` 的 `normalizeHookCommand` 支持 `type:'command'` 直接 `spawn(command,{shell:true})`)——这是货真价实的"用户在自己机器上配了一条全局 hook,然后打开一个未信任工作区"场景,cc 的设计意图明确是"这种情况也不该自动触发",我方目前会触发。
- `agentLoader.ts:94-103` 与 `skillLoader.ts:131-137` 都各自写了" 当前生产只从 app 目录加载,若日后接入工作区 `.claude/agents` 必须传 `hookSource:'local'`"的警告注释——这说明**代码作者自己也知道这是个雷**,只是靠"目前没人调用工作区路径"这一实况撑住,不是结构性保证(见 §2.2,commands 层已经出现了一个"作者以为的白名单目录没被正确使用"的真实案例,证明"靠人记得传对参数"这类约定确实会被漏掉)。

**判级**:真分叉(高)。cc 的设计是"入口处按 source 无差别拦";我方把"是否过信任门"下放到每个 hook 注册点自己打标,任何一个新写的注册点忘记打 `source:'local'` 就会静默变成可绕过信任门的攻击面——这是**架构层面比 cc 弱的纵深防御**,不是"当前恰好没利用"能完全化解的问题。

**掰回改法**:在 `runHookEvent`(`hooks.ts:351`)顶部,`disableAllHooks` 检查之后、`allowManagedHooksOnly`/source 分支之前,插入一次"交互模式 + 工作区未信任 → 全部跳过"的硬闸(即把当前"只挡 local"的第 3 个分支挪到最前面、对所有 source 都生效),再把"托管源不受 workspace trust 约束"这条改成显式的第二级判断(类似 cc 的 `shouldAllowManagedHooksOnly` 是叠加关系而非替代关系)。工作量:小(改一个函数 + 补 4-5 条判级测试),但要回归 `hooks.test.ts`/`hookConfig.test.ts` 里所有断言了"managed 不受 trust 约束"这一行为的用例(如果存在的话,需要一并改断言)。

### 1.3 〔真分叉·高〕`SessionStart` 在我方**每个用户回合**都重新触发,cc 只在真正的会话边界触发

**我方现状**:`ts/src/harness/loop.ts:307`——
```
const sessionStart = await applySessionStartHooks(hooksForCurrentSession(), ctx)
```
这一行在 `runAgentLoop`(`loop.ts:233` 起)顶部**无条件**执行,没有任何"是否是新会话"的判断。`RunAgentLoopOptions`(`loop.ts:154-165`)里没有 `skipSessionStart` 这样的选项(只有一个语义完全不同的 `skipUserMessage`,用于 stop-hook 续跑)。而 `runAgentLoop` 本身是**每个用户消息回合都重新调用一次**的生成器——证据:`ts/src/server/index.ts:1979` 是处理单次用户发消息请求的核心分支里对 `runAgentLoop` 的调用点,`opts.userMessage` 是单条(不是数组),即"一次 HTTP 请求 = 一次调用"。

**cc 侧证据**:cc 的 `SessionStart` 载荷带 `source: 'startup' | 'resume' | 'clear' | 'compact'`(`src/entrypoints/sdk/coreSchemas.ts:497`),`getMatchingHooks`(`src/utils/hooks.ts:1642-1643`)按这个 `source` 做 matcher 目标,说明这是一个**只在四种明确的会话边界事件**触发的东西,不是"每次用户说话"都会重发的东西——cc 里对应"每次用户说话"的是 `UserPromptSubmit`(独立事件,我方也有、且用法正确,见 `loop.ts:317-319`)。

**毒例**:输入 I:用户在同一个会话里连续发送 10 条消息(不清空、不刷新、不重启)。
- cc 判:`SessionStart` hook 只在这个会话第一次建立(`source:'startup'`)时触发一次;后续 9 条消息只触发 `UserPromptSubmit`。
- 我方判:`applySessionStartHooks` 被调用 **10 次**——即 `ts/src/packs/domainPacks.ts:118` 的 `pack.sessionStartContext`(领域包/门店画像等大段文本)在 10 条消息里被重复注入 10 次,且每次都会:①往 system prompt 追加相同文本(`loop.ts:311-313`)②往事件流 `yield { type:'context_note', text: extra }`(`loop.ts:308-309`)——即每条用户消息都会在回放 transcript 里多出一条重复的 `context_note`。

**影响面**:①性能/成本——领域包上下文是"常驻大文本",按 cc 的语义应该只算一次 token,我方按当前实现每条消息都要重新计入 prompt(还会打断 prompt-cache 断点,因为 system prompt 内容在两次调用间理论上应该稳定、这里却每次都在结尾追加新内容);② transcript 膨胀——`context_note` 逐条落盘,长会话会堆积大量重复内容;③如果未来给 `SessionStart` 挂了会**改变状态**的 hook(比如"记一次会话数"、"刷新一次外部系统的会话票据"),现在会被每条消息触发一次,产生成倍的副作用。

**判级**:真分叉(高)。这不是"降级适配"能解释的差异——`applySessionStartHooks` 函数本身设计对了(`hooks.ts:457-471`),问题纯粹是调用点选错了位置(挂在"每回合都执行的函数顶部",而不是"仅新会话/resume/clear/compact 时执行一次"的位置)。

**掰回改法**:给 `RunAgentLoopOptions` 加一个显式的 `sessionStartTrigger?: 'startup'|'resume'|'clear'|'compact'` 或者更简单的 `isNewSession?: boolean`,由调用方(`server/index.ts`)在真正的会话边界(新建 session / `/clear` / resume / 压缩后)传入,`loop.ts:307` 改成"传了才调用"。工作量:中(调用点判断"这次请求是不是新会话的第一轮"需要跟 `SessionService` 打通——`sessionService.create()` 时是 startup,`sessionService.get()` 命中已有 meta 时不是——再补 loop.test.ts 里覆盖"连续两轮不重复触发 SessionStart"的用例)。

### 1.4 〔真分叉·中〕`command`/`http` hook 的默认超时比 cc 短 5 倍(120s vs 600s)

**我方现状** `ts/src/hooks/hookConfig.ts:237-241`(`commandTimeoutMs`,无 `raw.timeout` 时的默认值):
```
if (!Number.isFinite(seconds) || seconds <= 0) return 120_000
```
`hookConfig.ts:703`(`runHttpHook`):`hookTimeoutMs(raw.timeout, 120_000)`。

**cc 侧证据**:`src/utils/hooks.ts:169`——`const TOOL_HOOK_EXECUTION_TIMEOUT_MS = 10 * 60 * 1000`(command hook 默认超时,`execCommandHook` 用它,见 `hooks.ts:891-892`);`src/utils/hooks/execHttpHook.ts:12`——`const DEFAULT_HTTP_HOOK_TIMEOUT_MS = 10 * 60 * 1000 // matches TOOL_HOOK_EXECUTION_TIMEOUT_MS`。两者均为 600,000ms,我方均为 120,000ms。

对照:`prompt` hook(cc `execPromptHook.ts:75`:`hook.timeout ? hook.timeout*1000 : 30000` vs 我方 `hookConfig.ts:414`:`hookTimeoutMs(raw.timeout, 60_000)` for agent hook、`hookConfig.ts:477`:`30_000` for prompt hook)——**prompt hook 的 30000 完全匹配**;agent hook 我方 `60_000` 对齐 cc `execAgentHook.ts:75` 的 `60000`。即 4 种 hook 类型里 2 种(prompt/agent)默认超时精确对齐,2 种(command/http)默认值缩水到 cc 的 1/5。

**毒例**:输入 I:一条 `PreToolUse` 的 `command` hook,没写 `timeout` 字段,实际跑 3 分钟(比如内部触发了一次 `npm install`)。
- cc 判:600s 预算内,hook 跑完,正常返回决策。
- 我方判:120s 时命中 `hookConfig.ts:552-555` 的 `setTimeout`,`child.kill()` + `settle({action:'deny', message:'hook command timed out after 120s: ...'})`——同一条 hook 配置在我方环境下会被判定为"超时拒绝",在 cc 环境下会成功。

**判级**:真分叉(中)。找不到任何注释解释这个数字为什么改成 120_000(不像 §1.7 那条上限 clamp 至少有隐含的"防失控"动机),看起来是实现时随手抄了别处的 120s 惯用值,不是有意的产品决策。

**掰回改法**:把 `commandTimeoutMs`/`runHttpHook` 的默认值从 `120_000` 改成 `600_000`,与 cc 一致。工作量:小(改两个字面量 + 补/改 `hookConfig.test.ts` 里断言默认超时的用例)。

  default: return payload.toolName ?? payload.agentType   // SessionStart、FileChanged 都落进这里
}

`HookPayload` 接口(`hooks.ts:56-122`)里没有为 `SessionStart` 定义任何"启动原因"字段,`applySessionStartHooks`(`hooks.ts:457-471`)只传 `{event:'SessionStart', sessionId}`;`FileChanged` 同理只有 `filePath`/`fileEvent`,没有进 `matchTarget` 的 switch。两类事件的 payload 里 `toolName`/`agentType` 永远是 `undefined`,于是 `matchesToolMatcher(matcher, undefined)`(`hooks.ts:305-314`)对任何非空 matcher 恒返回 `false`。

**cc 侧证据**:`src/utils/hooks.ts:1642-1643`——`case 'SessionStart': matchQuery = hookInput.source`(取值 `startup/resume/clear/compact`);`:1683-1684`——`case 'FileChanged': matchQuery = basename(hookInput.file_path)`。两者都是 cc `getMatchingHooks` 明确定义的匹配键。

**毒例**:输入 I:用户配置 `{"SessionStart":[{"matcher":"startup","hooks":[...]}]}`(cc 文档里的标准写法,意图"只在真正冷启动时触发,resume/clear 不触发")。
- cc 判:`matchQuery='startup'` 时命中,`matchQuery='resume'`/`'clear'` 时不命中——按用户意图工作。
- 我方判:不管真实触发原因是什么,`matchTarget` 返回 `undefined`,`matchesToolMatcher('startup', undefined)` 恒 `false`——**这条规则永远不会被触发**,配置形同虚设,且不会有任何报错/警告告诉用户配错了。

`FileChanged` 因为对应的 watcher 基建本来就未接线(`hooks.ts` 头部注释自认"派发器就绪、call site 待宿主运行时出现对应场景时接"),这半条目前还只是死代码,暂不算活跃 bug,但如果日后真的接上文件监听、又没顺手把这个 matcher 目标补上,同样的"配了 matcher 却永远不命中"会立刻复现。

**判级**:真分叉(中高)。定性上跟 §1.2 的 hooks 信任门是同一类问题(cc 有防线、我方对应位置的防线力度不够),但这里更具体、更容易复现,而且 cc 明确是"专门为这类场景加了库依赖",不是顺带具备的能力——即 cc 的作者显式判断了"任务元数据需要跨进程锁",我方对应模块目前没有等价物。

**掰回改法**:引入 `proper-lockfile`(或等价的、Bun 下可用的文件锁库)包一层,在 `readIndex`+`writeIndex` 之间持锁;或者更轻量地把 `tasks.json` 索引这种"共享可变状态"迁到 SQLite/单文件数据库式的原子操作(但 CLAUDE.md 铁律"文件式存储,无 SQL",所以更合理的路线是引入锁库)。工作量:中(加依赖 + 包装 mutateIndex + 补一个真正跑两个进程的并发测试,比单进程模拟更能证明修复有效)。

### 3.4 〔真分叉·高,与 §3.3 同类〕`SessionService` 完全没有 `mutateIndex` 这类保护,比 TaskService 更弱

### 5.2 〔真分叉·高〕`SessionService.appendEvent`/`touch` 完全没有写序列化,比 `TaskService` 更弱、并发写同一 session 可产生重复 `seq`

**我方现状**:`ts/src/server/services/sessionService.ts:276-290`(`appendEvent`):
```
async appendEvent(id: string, event: SessionStreamEvent): Promise<SessionEventRecord> {
  const meta = await this.get(id)
  const lastSeq = ... ?? await this.readLastEventSeq(id)
  const seq = lastSeq + 1
  ...
  await appendFile(path, `${JSON.stringify(record)}\n`, 'utf8')
  await this.touch(id, { lastEventSeq: seq })
  return record
}
```
`touch`(`:219-238`)自己也是直接 `readIndex()` → 改 → `writeIndex()`,**全类里没有任何类似 `TaskService.mutateIndex` 的 `indexQueue` 排队机制**——同一个 `SessionService` 实例内,两次并发 `appendEvent(sameId, ...)` 调用都可能在对方写完之前各自读到旧的 `lastSeq`,各自算出**同一个** `seq` 值并各自 `appendFile` 一行——`events/<id>.jsonl` 文件里出现两条不同内容但 `seq` 相同的记录。

**触发路径(不是纯理论)**:`TurnRegistry.interrupt()`(`sessionService.ts:433-438`)只是 `controller.abort()` + 从 Map 里删除,**不等待**旧一轮循环里正在飞的 `await appendEvent(...)` 真正落盘完成;`TurnRegistry.start()`(`:409-415`)在新一轮开始前调用 `interrupt()`。如果用户在旧一轮某次工具调用的 `appendEvent` 尚未完成 `touch()` 落盘时就发出下一条消息(典型场景:用户看到卡住、手快点了"停止"又立刻发新消息;或网络重试造成的短暂并发请求),旧一轮"迟到"的 `appendEvent` 与新一轮"抢跑"的第一次 `appendEvent` 就构成了同一 `sessionId` 下的并发写。

**cc 侧证据**:cc 是单进程单会话为主的 CLI 架构,`sessionStorage.ts` 里我没有找到 `proper-lockfile` 的使用(`grep lockfile sessionStorage.ts` 零命中)——这印证了 cc 自己的 session/transcript 文件本来就**不需要**跨写者保护,因为 cc 的进程模型保证同一时刻只有一个写者。而 cc 明确**在真正存在多写者风险的地方**(`utils/tasks.ts`,后台任务、可能被多处代码路径或重启后的恢复流程触碰)加了锁——这说明 cc 的作者是按"这个文件到底会不会有多写者"来决定要不要加锁的,不是无差别加锁。

**我方的情况是**:我方把 cc 的"单会话 CLI 进程"改造成了"一个长驻 HTTP 服务器同时管理多个会话、每个会话可有多次相继的 turn"这个新架构(这是产品层的合理选择,不是问题本身),但**在采用这个新架构的同时,没有为它补上 cc 原本因为架构原因不需要、但我们现在确实需要的保护**——即 `SessionService` 对应的正是 cc 里"本来不需要锁"的那个文件,但我们已经不满足"本来"的前提了。

**毒例**:输入 I:同一 `sessionId`,两次 `appendEvent(id, eventA)` 与 `appendEvent(id, eventB)` 在对方完成 `touch()` 落盘前先后调用 `this.get(id)` 读到相同的 `lastEventSeq`。
- 预期(不管 cc 还是常识上"正确"的行为):`events/<id>.jsonl` 里出现两条 `seq` 递增、互不冲突的记录,`loadEvents({after: N})` 能完整、无重复地重放。
- 我方实际行为:两条记录都写 `seq = lastEventSeq+1`(同一个数),`loadEvents`/`iterEventRecords` 按 `seq` 做游标分页(`sessionService.ts:292-303`)时,下游消费方如果用"我已经处理到 seq=N,请求 after=N"的增量拉取模式,会在 `seq` 冲突时出现"两条记录都满足 `record.seq > after`"从而都被下发、或者消费方自己的去重/覆盖逻辑随机丢掉一条——这是一个真实的、可复现的数据完整性问题,不是猜测。

**判级**:真分叉(高,与 §3.3/§3.4 同源、但这里保护力度是全项目里最弱的一个——TaskService 至少有进程内排队,SessionService 连这个都没有)。

**掰回改法**:给 `SessionService` 补一个与 `TaskService.mutateIndex` 同款的按 `sessionId` 分桶的 `Promise` 队列(`appendEvent`/`touch`/`create`/`remove` 涉及同一 `id` 的操作都要走这个队列),这是"至少先做到进程内不丢"的最小修复;如果要做到跨进程也安全(§3.3 同款诉求),再叠加文件锁。工作量:中(补队列 + 补一个"模拟两次几乎同时调用 appendEvent"的并发测试,这个测试应该能在当前代码上稳定复现 bug、修复后稳定通过)。

### 5.3 `Transcript.append()` 的并发分叉风险——同源问题,严重度较低

`ts/src/memory/transcript.ts:322-372` 的 `append()` 用 `knownByteLen` 做"文件字节数没变就用内存缓存"的优化(`:498-513` `syncFromDisk`),但这只是**缓存失效检测**,不是写锁——两个并发 `append()` 调用(同一个 `Transcript` 实例或两个不同实例指向同一文件)各自算出的"新增分叉段"、各自 `appendFile` 写入后,文件里最终的"最后一行"(`reconstructChain` 用来确定活跃链尾的锚点,`:188`)取决于操作系统真实的写入完成顺序,可能导致其中一个分支的消息被静默"晾在一边"(不在 `reconstructChain` 回溯到的活跃链上,但内容仍在文件里、不会真的丢字节)。相比 §5.2 的"seq 冲突"(明确的数据完整性问题),这里因为 append-only 设计本身兜底(内容不丢,只是暂时不在活跃视图里,append-only 特性决定了下次有干净的写入时链会自然接续),严重度更低,标〔疑似,低〕,验证步骤:两个 `Transcript` 实例指向同一文件同时 `append()` 不同内容,断言最终 `load()` 结果是否符合预期(某一分支的消息是否从活跃视图消失)。

### 5.4 fork/rewind 语义核对

- cc 判:`15,000 > 25,000` 为假 → **不截断**,把约 45,000 字节的内容整段塞进系统提示(超出其自身设计意图的 25,000 字节预算近一倍)。
- 我方判:`Buffer.byteLength ≈ 45,000 > 25,000` 为真 → **截断**,正确把注入量控制在设计预算内。

**判级**:这项差异**不建议按"对齐 cc"的思路去改**——对照的是 cc 自身实现里一处针对 CJK 内容的真实计数错误(cc 面向的主要是英文技术社区,这个 bug 在其场景下几乎不会显现),而我方产品明确以中文内容为主(CLAUDE.md 台球运营场景 + 中文用户),现在的 `Buffer.byteLength` 实现是**更正确**的。记录这条的目的是防止以后有人拿着"字节数差 3 倍,和 cc 不一致"当 bug 报上来、按"完全对齐 cc"的字面口径把这里"修"回 `.length`——那样反而是从对变错。**若要动**,唯一值得做的方向是给 cc 的 `truncateEntrypointContent`(如果未来因为其它原因需要抄它的某个新特性)也顺手把 `.length` 换成 `Buffer.byteLength`,而不是反过来。

### 6.4 〔疑似·中〕记忆抽取兜底的"水位"用消息数组长度,而不是消息 uuid——某些非单调场景可能错位抽取窗口

**我方现状**:`ts/src/memory/extractMemories.ts:151-153`:
```
if (input.messages.length < state.lastCount) state.lastCount = 0   // 唯一的自愈信号:数组变短
const sinceIndex = state.lastCount
if (input.messages.length <= sinceIndex) return
```
watermark(`state.lastCount`)是一个纯数字,代表"上次处理到的数组长度",没有绑定到任何具体消息的身份。

**cc 侧证据**:`~/Desktop/cc-haha-ref/src/services/extractMemories/extractMemories.ts:90-109`——watermark 是 `sinceUuid`(具体消息的 uuid),每次都在当前 `messages` 数组里**按内容身份**重新定位这个 uuid 出现的位置,且显式处理了"uuid 找不到了"(被压缩清掉)的情况:"fall back to counting all model-visible messages rather than returning 0 which would permanently disable extraction"(`:103-105`)。

**判级为疑似而非确认真分叉的原因**:我方"数组变短就把水位清零"这条兜底,对"压缩导致消息数变少"这个最常见场景是有效的(压缩几乎总是让 `messages.length` 减少),所以在**最常见的路径**上两边行为大概率一致。真正会分歧的输入需要"数组长度不减反增或持平,但数组中段内容的身份已经变化"——比如 `rewindTo` 之后又发了新消息导致净长度和原来相同或更长(§5 已确认 `rewindTo` 是真实存在的机制)。我没能在预算内构造出一个 100% 确定触发的具体调用序列去实测(需要打通 `Transcript.rewindTo` 与 `extractMemories.ts` 的 `states` Map 之间目前并不存在的耦合关系),所以标〔疑似〕而非〔真分叉〕。

**验证步骤(可直接照做写成测试)**:①正常对话若干轮,让 `state.lastCount` 推进到某个值 N;②对该会话调用 `Transcript.rewindTo` 回退到更早的消息(不经过 `extractMemories.ts` 感知);③在 `messages`(重新 `load()` 得到,已经是回退后的新链)基础上续接新消息,使新数组长度 ≥ N(不触发"变短清零");④调用 `maybeExtractMemories`,断言 `sinceIndex=N` 对应的位置在新数组里是否真的是"上次抽取到的那条消息之后"、还是已经指向了 rewind 之后完全不同分支的内容。如果实测确实错位,应升级为〔真分叉〕并按 cc 的 uuid 定位法重做这个 watermark。

**掰回改法(不管当前是疑似还是确认后的真分叉,修法都一样,可以直接做)**:把 `state.lastCount: number` 换成 `state.lastUuid: string | undefined`,`maybeExtractMemories` 里按 uuid 在当前消息数组里查找位置(找不到就退化成"处理全部 model-visible 消息",与 cc `:106-107` 同款兜底),而不是依赖数组长度这个脆弱代理。工作量:小到中(改 state 结构 + 查找逻辑,消息类型需要确认 `Message` 是否总能拿到 `uuid` 字段——从 `transcript.ts` 的 `StampedMessage` 类型看,落盘层是有 uuid 的,但 `extractMemories.ts` 目前收到的 `input.messages: Message[]` 是否是剥过 provenance 的干净版本需要留意,`transcript.ts:151-153` 的 `stripProvenance` 会把 uuid 剥掉——如果是,这个掰回改法需要先解决"喂给 extractMemories 的消息要保留 uuid"这个前置问题,工作量相应上调)。
