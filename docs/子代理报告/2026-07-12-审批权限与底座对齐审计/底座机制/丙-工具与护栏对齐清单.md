## 一、文件工具(#6 read/write/edit/patch 族)

### 1.1 〔真分叉·高〕Read 工具从不注入行号前缀,cc 永远注入

- **我方**:`ts/src/tools/fileReadTool.ts:99-113`(整读)、`:345-380`(`formatFocusedRead`/`buildFocusedRead`)—— 全文没有任何 `addLineNumbers` 等价调用,返回给模型的永远是原始 UTF-8 内容(聚焦读只在外层 `<file_chunk start_line="" end_line="">` 标签报一次范围,内容本体不带每行编号)。
- **cc**:`FileReadTool.ts:730-732`(`formatFileLines` 调用 `addLineNumbers`)+ `utils/file.ts:290-319`(`addLineNumbers`:默认格式 `${行号.padStart(6,' ')}→内容`,压缩模式 `${行号}\t内容`)——**整读和聚焦读都会**逐行加前缀。`FileEditTool/prompt.ts:20-23` 明确指导模型"行号前缀格式是 spaces+行号+arrow / 行号+tab,匹配 old_string 时绝不能包含这段前缀"——即 cc 依赖模型自己剥离,工具代码里(`FileEditTool/utils.ts`)并不做剥离,`stripLineNumberPrefix`(`utils/file.ts:325-328`)实际只用于 `utils/queryHelpers.ts:440`(压缩/重放后从 transcript 里重建 `readFileState` 缓存时剥前缀还原纯内容),不是 Edit 工具自身逻辑。
- **同输入 I**:`read_file({path:"a.ts"})` 读一个 50 行文件。cc 返回内容形如 `     1→import x\n     2→...`;我方返回原始 `import x\n...`,不带任何行号。
- **次生不一致**:我方自己的编辑后回显反而**有**行号(`fileEditTool.ts:628-641 formatEditSnippet`,格式 `行号| 内容`,用 `|` 不用 `→`)——同一产品里"读的时候没行号、改完看结果有行号"是自相矛盾的体验。
- **部分缓解**:`ts/src/tools/searchTools.ts:268`(`grep_files` 结果自带 `path:行号:内容`)+ `ranges:true` 可直接产出 `start_line/end_line` 喂给 `read_many_files`,所以模型不是完全没有行号来源,只是 `read_file` 本身没有。
- **掰回改法**:在 `fileReadTool.ts` 的整读/聚焦读输出前加一个与 `formatEditSnippet` 复用同一套的行号前缀格式化(建议直接抄 `addLineNumbers` 的两种模式,固定用非压缩的 `→` 格式,不需要 GrowthBook 开关),同步在工具 description 里加"old_string/new_string 不要带行号前缀"的提示。**预估工作量:半天**(核心是格式化函数 + 更新两个工具的 description 文案 + 补 1-2 条快照测试)。

### 1.2 〔真分叉·中〕"读取后文件是否被改过"的陈旧检测缺少内容兜底

- **我方**:`fileEditTool.ts:438`(`assertFreshRead`):`if (info.mtimeMs !== snapshot.mtimeMs || info.size !== snapshot.size) throw`——**严格不等**判定,没有任何内容级兜底。`fileWriteTool.ts:57`(`assertFreshOverwrite`)同款逻辑。
- **cc**:`FileEditTool.ts:290-311`(`call()` 内)与 `FileWriteTool.ts:279-295`——判定是 `lastWriteTime > lastRead.timestamp`(严格**大于**,不是不等),并且明确写了兜底:"Timestamp indicates modification, but on Windows timestamps can change without content changes (cloud sync, antivirus, etc.). For full reads, compare content as a fallback to avoid false positives"——当是整读(`offset===undefined && limit===undefined`)且 `fileContent === lastRead.content` 字节相同时,**放行**,不报"文件已变化"。
- **同输入 I**:read_file 整读一个文件→云盘同步/杀软/某些编辑器"安全保存"触发 mtime 变化但字节内容不变→随后 edit_file。cc:内容比对相同,直接放行编辑。我方:`mtimeMs`/`size` 只要有一丁点变化(即使内容字节相同)就 throw "文件在读取后已变化,请重新 read_file 后再改",模型必须重读一次才能重试。
- **风险场景**:本产品是桌面软件,用户很可能把工作区放在 iCloud Drive / OneDrive 这类云同步目录下(mac 上 `~/Desktop`、`~/Documents` 默认参与 iCloud 云同步是常见配置),这类目录的 mtime 抖动比开发机常见得多。
- **掰回改法**:在 `ctx.fileReads` 记录的快照里增加一个"整读时的内容 hash"字段(仅整读/无 start_line-end_line-max_bytes 时记),`assertFreshRead`/`assertFreshOverwrite` 命中 mtime/size 不一致时,先做一次内容 hash 比对,一致则放行。**预估工作量:半天**(改 3 个文件的快照结构 + 4 处调用点)。

### 1.3 〔真分叉·中〕edit_file 不支持"空 old_string 建新文件"

- **我方**:`fileEditTool.ts:384`:`if (typeof record.old_string !== 'string' || record.old_string.length === 0) throw new Error('edit_file 需要非空 old_string')`——**硬性**要求非空,连文件不存在时都拒绝。
- **cc**:`FileEditTool.ts:224-264`:文件不存在 + `old_string===''` → `{result:true}`(允许,视为新建文件);文件存在但内容为空(`fileContent.trim()===''`)+ `old_string===''` → 同样允许;只有"文件存在且非空"时 `old_string===''` 才拒绝("Cannot create new file - file already exists")。
- **同输入 I**:`edit_file({path:"new.ts", old_string:"", new_string:"export {}"})` 且 `new.ts` 不存在。cc:成功创建文件。我方:在 `validateInput` 阶段(实为函数首行同步校验)直接抛错,连路径解析都不做。

- **掰回改法**:`validateInput`/`execute` 里放宽:`old_string===''` 时,若目标文件不存在或为空,走"整写 new_string"路径(等价于 write_file 的效果,同样走备份/快照)。**预估工作量:半天**。

### 1.4 〔真分叉·低〕引号/标点归一化范围与"归一化后回填原风格"均与 cc 不同

### 1.6 〔我方缺失〕Read 工具没有基于 token 数的二次上限,只有字节上限

### 2.1 〔真分叉·高〕跨调用不保留当前目录(cd 语义丢失)

- **我方**:`ts/src/tools/runCommandTool.ts:173-189`(`runInWorkspace`)——每次 `run_command` 都 `spawn('sh',['-c',command])` 或 `spawn('cmd',['/c',command])` 起一个全新子进程,`cwd` 由 `resolveCommandCwd(input.cwd, ctx)` 当次现算(默认 `ctx.workspace.root`),**没有任何跨调用状态**。
- **cc**:`src/tools/BashTool/prompt.ts:357`(系统提示原文,逐字):**"The working directory persists between commands, but shell state does not. The shell environment is initialized from the user's profile (bash or zsh)."**——这是 cc 对模型的**显式承诺**,背后是真·持久 shell 架构:`src/utils/Shell.ts`(持久 bash/zsh 进程 + `setCwdState`/`getOriginalCwd`)+ `src/tools/BashTool/utils.ts:170-192`(`resetCwdIfOutsideProject`——每次调用后检查 shell 实际 cwd 是否跑出允许目录,越界才强制重置并在 stderr 里追加提示)。
- **同输入 I**(两轮对话):
  - 轮 1:`run_command({command:"cd subdir"})`
  - 轮 2:`run_command({command:"pwd"})`
  - **cc**:轮 2 输出 `.../subdir`(真持久 shell,cd 生效)。
  - **我方**:轮 2 输出工作区根目录(每次全新子进程,轮 1 的 cd 对轮 2 零影响)。
- **确认不是"提示词说谎"**:搜索确认我方系统提示/工具 description 里**没有**照抄 cc 那句"working directory persists"的承诺(`grep "working directory persists\|persist.*between"` 全仓库零命中),所以这不是"答应了却不认账",是一个**架构性差异**——我方设计成每次显式传 `cwd` 参数(工具 description 里写清楚了),但这与 cc 的隐式持久化模型是两套不同的使用习惯,任何按"标准 coding agent 都认 cd 持久化"这一广泛先验训练/使用习惯来操作的模型(不只 Claude,几乎所有见过 cc/Cursor/Aider 之类工具训练数据的模型)大概率会依赖跨轮 cd,遇到我方系统会反复踩坑(表现为"明明 cd 过去了,下一条命令又报路径不对"),尤其是能力较弱的国产模型更不容易靠读 description 自我纠正。
- **判级**:真分叉,高。**掰回改法**:两条路都可选——(a) 结构对齐 cc:每个会话起一个真持久 shell 子进程(bash/zsh -i 或不带 -i),命令通过标记法(如打印一个唯一哨兵到 stdout 判断结束 + 单独查询 `pwd`)取执行后的实际 cwd 并存进会话状态,下次调用作为默认 cwd——**预估 1-2 天**(可直接参考 cc `utils/Shell.ts`/`ShellCommand.ts`/`shell/bashProvider.ts` 移植,许可证已允许直接抄);(b) 更轻量:会话级维护一个"上次解析出的 cwd"字段,命令执行前用一个轻量启发式(检测命令是否以 `cd <dir>`(可选跟 `&&`)开头/结尾)推断新 cwd 存回会话——**预估半天**,但鲁棒性明显弱于 (a)(处理不了 `cd a && cd b`、`cd $(some_cmd)`、失败的 cd 等)。建议按 (a) 走并对齐 cc 源码。

### 2.2 〔真分叉·高〕Shell 命令文本里的 `~root`/`~<user>` 变体未被识别为危险目标

- **我方实测**(`isDangerousCommand`/`classifyCommandRisk`/`shellDangerousRemovalNeedsApproval`,输入均为字符串命令):

  | 输入 | isDangerousCommand | classifyCommandRisk | shellDangerousRemovalNeedsApproval |
  |---|---|---|---|
  | `rm -rf ~` | **true**(硬拒) | destructive | true |
  | `rm -rf ~root` | **false** | destructive | **false** |
  | `rm -rf ~root/.ssh` | **false** | destructive | **false** |
  | `rm -rf -- ~root` | **false** | destructive | **false** |
  | `cat ~root/.ssh/id_rsa` | false | **outreach**(不是 destructive) | — |

- **我方文件级证据**:`ts/src/workspace/pathValidation.ts:85-87`(`normalizeRequestedPathForValidation`)**已经**正确拒绝 `~user` 变体(`if (cleaned.startsWith('~')) throw PathValidationError('~user/~+/~- 波浪号变体需人工确认')`)——**但这条防线只服务结构化文件工具**(`read_file`/`edit_file`/`write_file` 的 `path` 参数走 `resolveToolPath`→这条校验),**没有被 `dangerousCommand.ts` 的 shell 命令文本分类器复用**——`rm -rf ~root/.ssh` 是作为一整条 shell 命令字符串交给 `isDangerousCommand`/`classifyCommandRisk` 分类,这两个函数走的是纯正则/字符串启发式,不会调用 `normalizeRequestedPathForValidation`。
- **cc 证据**:`src/utils/permissions/pathValidation.ts:398-415`(`validatePath` 内,原文注释逐字):"SECURITY: Reject tilde variants (~user, ~+, ~-, ~N) that expandTilde doesn't handle... The shell expands these differently (~root → /var/root...), creating a TOCTOU gap: we validate /cwd/~root/... but bash reads /var/root/..."——cc **专门为这个场景写了安全注释和防御**。更关键的是 cc 把这条校验**接到了 Bash 工具的命令参数解析上**:`src/tools/BashTool/pathValidation.ts:190-260`(`PATH_EXTRACTORS`,含 `rm`/`cat`/`mv`/`cp`/`find`/`ls` 等 24 个命令的专门参数提取器)+ `:603-701`(`validateCommandPaths`——对每个提取出的路径参数调用 `validatePath`,命中 `~user` 拒绝规则时返回 `behavior:'ask'`)。也就是说 `rm -rf ~root/.ssh` 在 cc 里会被**解析出 `~root/.ssh` 这个路径参数**,送进跟文件工具**同一套** `validatePath`,命中"波浪号变体需人工确认"而要求强制人工批准。
- **判级**:真分叉,高。这不是"从零发明"的活——我方 `workspace/pathValidation.ts` 里**已经有**正确逻辑,只是没被 Bash 工具复用。
- **掰回改法**:参考 cc 的 `PATH_EXTRACTORS` 思路,在 `dangerousCommand.ts` 里为 `rm`/`rmdir`/`mv`/`cp`/`cat` 等高风险命令加一个"提取位置参数(正确处理 `--` 结束符,见下条)→ 逐个跑 `normalizeRequestedPathForValidation`"的钩子,命中 `PathValidationError` 时把该命令强制标 `destructive` 且**不可被会话允许规则自动放行**(对齐 cc `suggestions:[]`"不鼓励为危险命令存放行规则"的意图)。**预估工作量:1 天**(不需要整套 AST 级命令解析,先覆盖 `rm`/`rmdir`/`mv`/`cp` 4 个高频命令即可覆盖大部分风险面)。

### 2.3 〔真分叉·高〕`$HOME` 与 `${HOME}` 处理不一致

- **我方实测**:`rm -rf $HOME` → `isDangerousCommand=true`(硬拒,已捕获);`rm -rf ${HOME}`(花括号形式)→ `isDangerousCommand=false`(**漏判**,仅落到 destructive 审批档,与普通 `rm -rf 子目录` 同级)。
- **cc 对照**:`utils/permissions/pathValidation.ts:417-440`(`validatePath` 内)对 `$`/`%`/`=` 开头的 shell 展开语法**统一**拒绝("SECURITY: Reject paths containing ANY shell expansion syntax ($ or % characters)... Nested combinations like $(echo $HOME)"),不区分 `$HOME` 还是 `${HOME}`,一律要求人工确认。
- **判级**:真分叉,高(同类问题,和 2.2 根因相同——我方文件工具侧的 `cleaned.includes('$')` 判断【workspace/pathValidation.ts:88-90】其实已经能同时覆盖 `$HOME`/`${HOME}`,只是这条判断跟 2.2 一样没接进 Bash 命令分类器,`isDangerousCommand` 内部对 `$HOME` 命中是**另一条独立的字符串规则**,凑巧没覆盖花括号形式)。

### 2.4 〔真分叉·高〕flag 注入绕过路径校验(cc 明确记录过的攻击手法)

- **我方实测**:`rm -- -/../.claude/settings.local.json`(cc 源码注释里明确举的攻击例子,替换成我方等价路径 `-/../.billiardbuddy/settings.local.json` 结论相同)→ `classifyCommandRisk = "file"`(**最低档**,与写一个普通文件同级,不是 destructive),`isDangerousCommand=false`。
- **根因**:`--` 后面的参数即使以 `-` 开头也应被当作**位置参数**(路径),我方分类器大概率仍在用"以 `-` 开头就当 flag 过滤掉"的朴素启发式,导致这个"看起来像 flag、实际是路径"的参数被过滤掉,分类器看不到任何路径参数,退化成通用低风险判定。
- **cc 对照**:`src/tools/BashTool/pathValidation.ts:110-139`(`filterOutFlags`,原文注释逐字):"Naive `!arg.startsWith('-')` filtering drops these, causing path validation to be silently skipped for attack payloads like: `rm -- -/../.claude/settings.local.json`... With `--` handling, the path IS extracted and validated"——cc **专门写了 `--` 结束符处理**来堵这个洞,并且在源码注释里承认这是曾经真实发生过的漏洞模式。
- **部分缓解(不等于没问题)**:我方 OS 沙箱的 `denyWrite` 清单(`ts/src/sandbox/osSandbox.ts:43-53`,`sandboxDenyWritePaths`)**已经**显式包含 `<root>/.billiardbuddy/settings.json`/`settings.local.json`/`skills`——如果 OS 沙箱处于激活状态(默认开,见 §三),即使审批分类器判轻了,实际写入这个具体文件时仍会被 OS 层 `EPERM` 挡下。**但**:(a) "全盘 full-disk-access" 会话下 OS 沙箱按设计关闭(`sandbox/sandbox.ts:29-36`),这时分类器是唯一防线;(b) 这个 OS 级清单只覆盖了权限配置文件这一个具体目标,`rm -- -/../其他任意敏感文件` 一样会被这套 flag 注入绕过分类,只是不一定有对应的 OS `denyWrite` 项兜底。
- **判级**:真分叉,高(cc 明确记录过的漏洞类别,我方目前看起来还没补)。
- **掰回改法**:在 `dangerousCommand.ts` 的参数解析里加 `--` 结束符处理(遇到裸 `--` 后,后续全部参数无论是否以 `-` 开头都当位置参数收集),这是 2.2 的前置依赖,建议一并做。**预估工作量:半天**(在 2.2 的"1 天"里)。

### 2.5 〔真分叉·中〕`--no-preserve-root` 反而让分类降级

- **我方实测**:`rm -rf /` → `isDangerousCommand=true`(硬拒);`rm -rf --no-preserve-root /`(GNU coreutils 真实存在、专门用来**关闭** rm 自带根目录保护的旗标)→ `isDangerousCommand=**false**`,仅剩 `classifyCommandRisk=destructive` + `shellDangerousRemovalNeedsApproval=true`(还需要审批,不是裸放行,但从"硬拒绝、无法覆盖"降级成"可审批通过")。

- **判级**:真分叉,中(不是静默执行,用户/审批流程仍会看到确认卡,但把"这是灾难级、不可协商"的信号降级成了"这是需要看一眼的普通危险操作")。

### 2.6 〔真分叉·中〕原始设备重定向/`shred` 未入红线

### 3.1 已用实测验证的边界判定(毒例表)

### 3.2 〔疑似,需 Windows 真机验证〕`isVulnerableUncPath` 非 win32 恒 false

- **我方**:`workspace/pathValidation.ts:43-46`:`if (platform !== 'win32') return false`。
- **cc**:文件工具侧(`FileEditTool.ts:179`/`FileReadTool.ts:468-472`)的 UNC 判定(`startsWith('\\\\')||startsWith('//')`)**不分平台**,任何平台命中都跳过 I/O 走审批;但 cc 的这个判定本身是"防 Windows NTLM 凭据泄漏"这个具体风险模型的产物,在非 Windows 平台上语义上是"过度保守但无害"。
