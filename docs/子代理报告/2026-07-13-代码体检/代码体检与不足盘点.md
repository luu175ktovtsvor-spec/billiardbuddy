# 代码体检与不足盘点 · 2026-07-13

> 证据类报告。结论来自当前分支源码、行数与测试文件扫描、typecheck、质量门和关键调用链复核。

## 一、结论

**项目不是“屎山”，但存在三个高度集中的债务热点。** 后端领域服务、共享契约、renderer 功能域、测试和质量门都真实存在；问题主要集中在少数巨型编排文件，而不是“模块太多”。

当前处理状态：

- `ImageWorkbenchPage.tsx` 已从 2331 行降到 1584 行，画布、资产、类型、样式与纯模型逻辑已有独立模块和测试；页面状态编排仍未完成。
- `server/index.ts` 已从 5088 行降到 3348 行。顶层 helper、媒体路由、Agent WebSocket 生命周期、Provider 管理、插件管理、工作区管理、定时任务、后台任务、门店资料、会话元数据、活动、回退和归档责任已下沉，当前体积基线同步为 3348 行。
- media v1/v2 双轨涉及持久化兼容和迁移，仍保持独立待办，没有混入结构重构批次。
- 媒体测试的本机环境泄漏已修复；显式 `QF_BINARIES_DIR` 现在是排他的二进制查找边界。

## 三、三个债务热点

### 热点 1：`ImageWorkbenchPage.tsx` 状态编排过重

- 当前 1584 行，`CreationPage()` 内有 49 个 `useState` 和 13 个 `useEffect`，没有 feature store。
- 状态横跨创作输入、品牌素材、参考图、异步 job、项目、候选图、画布、蒙版、文字和导出，单个页面仍同时承担工作流编排与视图交互。
- 已拆出的 `imageWorkbenchAssets.ts`、`imageWorkbenchCanvas.ts`、`imageWorkbenchModel.ts`、`imageWorkbenchTypes.ts`、`imageWorkbenchStyles.ts` 和 `CandidatePreview.tsx` 降低了纯逻辑密度，但没有解决状态所有权。
- 下一步应按功能状态切片：先把可测试的 reducer/store 与异步 commands 移出页面，再拆创作、候选、画布和调整面板；同时补 renderer 单元/组件测试。

### 热点 2：`server/index.ts` 仍是后端上帝编排文件

- 当前 3348 行、112 个 import，`startServer()` 从第 214 行延伸到文件末尾，仍汇聚大部分内核装配和 HTTP 分发。
- 主路由仍是长条件链，当前重复出现 68 次 `Method not allowed`、36 次 `req.json().catch` 和 39 次 `as Record<string, unknown>`。
- 正面变化是独立责任正在形成：`websocketHandler.ts` 负责 Agent WS 生命周期，`routes/legacyMediaRoutes.ts`、`canvasRoutes.ts`、`pluginRoutes.ts`、`providerRoutes.ts`、`workspaceRoutes.ts`、`scheduledTaskRoutes.ts`、`taskRoutes.ts`、`storeDocsRoutes.ts`、`sessionMetadataRoutes.ts`、`sessionActivityRoutes.ts`、`sessionRewindRoutes.ts`、`sessionArchiveRoutes.ts` 负责各自 REST 边界，`SessionArchiveService` 负责归档压缩与备份，`index.ts` 保留装配与委托。
- `index.test.ts` 仍有 6210 行，单文件实际运行 114 个 test、815 个 expect，并有 319 处真 `fetch`。它提供了强回归证据，但本身也已成为维护热点。
- 下一步应按领域继续提取 route handler，并让对应特征测试跟随新路由模块；不要先引入全局路由框架或一次性重写整个分发链。`index.test.ts` 同步按领域拆分，保留少量装配级集成测试。

### 热点 3：media v1/v2 双轨与 `MediaJobService` 职责集中

- `mediaJobs.ts` 仍有 2309 行，图像模型路由、provider 回退、QC、肖像预检、品牌素材、brief、上传和任务编排集中在一个服务中；视频入口主要是委托。
- `video-edit/legacyTimeline.ts` 仍有 1652 行且不是死代码：`server/index.ts` 和 `mediaJobs.ts` 仍实例化旧 store，`routes/legacyMediaRoutes.ts` 仍提供活跃兼容路由，`projectStore.ts` 仍读取 v1 schema。
- 这不是普通拆文件问题。收敛前必须先定义旧项目读取、写入格式、双轨期限、迁移失败回滚和客户端发布顺序，单独按 `MIGRATION + CONTRACT` 处理。

## 四、其他不足

1. **renderer 自动化测试薄。** 当前只有 8 个测试文件，复杂工作台页面主要依赖少量模型测试和 Electron E2E，低层状态回归定位成本高。
2. **架构护栏覆盖有限。** 当前检查偏向几个关键禁令和体积基线，尚不能发现任意跨域深层导入、循环依赖或 route 绕过 service。
3. **前端长尾体验仍有缺口。** 消息排队、工具活动摘要、通知收件箱、线程内浏览器、附件体系、语音和子代理面板等以现行差距清单为准。
4. **内核对齐仍有残余开口。** OAuth、headless 拒绝和异步 hooks 等以现行内核差异清单为准。
5. **发布链路未闭环。** 自动更新渠道尚未开放，macOS 仍是本地受控测试包。

## 五、模块多怎么处理

模块数量本身不应压缩。正确方向是保持稳定模块边界，把仍混在巨型文件里的责任迁入其主责模块，并通过公共入口连接。后续批次按风险排序：

1. 继续提取 `server/index.ts` 中边界清晰的领域路由，同时拆分 `index.test.ts`。
2. 重构 `ImageWorkbenchPage` 的状态、commands 和视图组件，并补 renderer 测试。
3. 另立 media v1/v2 迁移规格，完成兼容与回滚设计后再动数据模型。
