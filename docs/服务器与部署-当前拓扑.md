## 2. 模型网关 `qfgw`

代码入口：`gateway/app.ts`

主要职责：

- 校验客户端 Bearer token。
- 双模型路由:请求 `model` 命中 MiMo 白名单且 MiMo 已配置 → 走 MiMo;否则一律走默认 Qwen(白名单外 model 被强制改写为 `GW_QWEN_MODEL`)。**两家各持独立凭据/base/白名单/并发/RPM/重试,绝不静默跨模型回退**;命中的上游未配置返回明确 `503`。
- 在服务器注入模型与供应商密钥,客户端只持可撤销 app token。
- 代理文本、图片生成、图片编辑和图片异步任务;独立的 `POST /v1/web_search`(兼容 Brave provider)承载 Agent 联网搜索,**不做任何模型原生 web_search 注入**。
- 通过统一端点执行语音输入与视频口播转录,provider 为 **Fun-ASR-Flash**。
- 记录不包含密钥的用量信息。

主要端点：

```text
POST /v1/chat/completions
POST /v1/web_search
POST /v1/images/generations
POST /v1/images/edits
POST /v1/images/tasks
GET  /v1/images/tasks/:id
POST /v1/audio/transcriptions
GET  /healthz
```

稳定边界详见 `docs/网关双模型与CC-Haha接轨.md`。健康检查(带有效 app token)的 `features` 只含 `transcription` / `web_search` / `chat_qwen` / `chat_mimo`,`capacity` 含 `qwen` / `mimo` 两个容量池。上游真密钥只在服务器 `gw.env`;迁移服务器只迁受保护环境配置并重新部署 gateway,桌面协议和客户端包不变。搜索词只发给所配置的搜索 provider,用量日志只记录次数、状态和耗时,不记录查询正文。

应用令牌配置在 `GW_APP_TOKENS`。修改环境文件后重启并检查健康状态：

未认证 `GET /healthz` 只返回最小存活状态；桌面端带有效 app token 探测时才返回 `features` 和容量信息，避免公网泄露供应商与运营参数。

```bash
ssh root@<大陆机> 'systemctl restart qfgw && systemctl is-active qfgw'
ssh root@<大陆机> 'curl -s --max-time 8 http://127.0.0.1:8799/healthz'
```

## 3. 语音与口播转录

桌面端固定调用 `POST /v1/audio/transcriptions`，上传音频文件、语言和 `json|verbose_json` 输出格式。网关先执行 app token 鉴权、96MiB 文件上限、类型检查、速率限制和单并发，再调用服务器 provider；音频只写入权限为 `700` 的临时目录，任务结束或取消后删除，不记录音频内容和转写文本。

现行且唯一的 provider 是阿里云百炼 **Fun-ASR-Flash**(DashScope 多模态端点),`verbose_json` 返回词级时间戳供视频字幕使用。转录为云调用,网关主机无需本地 ASR 二进制/模型/GPU。**Whisper 已退役,不运行/下载/部署/回退**;`GW_TRANSCRIBE_PROVIDER` 为 `whisper` 或 `upstream` 等非 Fun-ASR 值时 fail closed(返回 null)。

配置入口：

```text
GW_FUNASR_KEY          # DashScope 密钥,只在服务器 gw.env(600)
GW_FUNASR_MODEL        # 默认 fun-asr-flash 对应模型
GW_TRANSCRIBE_PROVIDER # 留空或 funasr / fun-asr;其它值 fail closed
GW_TRANSCRIBE_RPM
GW_TRANSCRIBE_CONC
GW_TRANSCRIBE_MAX_BYTES
```

客户端不感知 provider。部署随 gateway 一起进行(`gateway/deploy.sh` 含 `transcription.ts`),无单独转录安装脚本;上线前用真实中文音频跑 smoke 验证 text + 词级时间戳。

## 4. 图片 relay `qfrelay`

代码入口：`relay/app.ts`

relay 在美国服务器完成图片生成或编辑调用，桌面端经 gateway 使用 submit/poll：

```text
POST /images/tasks
  { mode, model, prompt, n, size, response_format?, images?, mask?, input_fidelity? }

GET /images/tasks/:id
  { status, data?, error?, created }
```

`status` 为 `queued`、`running`、`succeeded` 或 `failed`。gateway 将 `/v1/images/tasks` 转发到 relay，客户端只访问 gateway。

运维命令：

```bash
ssh root@<美国机> 'systemctl restart qfrelay && systemctl is-active qfrelay'
```

## 5. dataeye

代码入口：`dataeye/receiver/app.ts`、`dataeye/board/app.ts`

桌面 sidecar 在同时配置以下变量时，于应用启动后上传心跳和脱敏崩溃日志：

```text
QF_DATAEYE_URL
QF_DATAEYE_TOKEN
QF_APP_VERSION
```

上传请求使用 gzip JSON、Bearer token 和 `(machine_id, kind, ref_id)` 幂等键。客户端只发送字段白名单，不发送对话内容或门店资料；失败时不影响应用启动。

receiver 写入数据分层，board 读取聚合结果。部署步骤以 `dataeye/deploy/runbook.md` 和服务健康检查为准。

## 7. 组件资产托管

资产管理器代码：`ts/src/assets/assetManager.ts`

默认清单地址：

```text
https://zzyppz.cn/assets/manifest.json
```

客户端可通过 `QF_ASSET_MANIFEST_URL` 指定清单，通过 `QF_ASSETS_AUTOSTART=0` 关闭资产清单初始化。nginx 资产目录建议使用 `/var/www/qf-assets/`：

```nginx
location /assets/ {
    alias /var/www/qf-assets/;
    autoindex off;
}
```

清单结构：

```json
{
  "version": "<version>",
  "assets": [
    {
      "id": "ffmpeg",
      "platform": "darwin-arm64",
      "tier": 1,
      "size": 41234567,
      "sha256": "<64位hex>",
      "url": "https://zzyppz.cn/assets/ffmpeg-darwin-arm64",
      "unpack": "none",
      "dest": "ffmpeg"
    }
  ]
}
```

当前 manifest 发布 macOS/Windows 的 `ffmpeg` 与 `ffprobe`，并保留 Tier 1 优先级标记；客户端不会因应用启动就下载它们，而是在视频分析、渲染、图片本地调整或高清放大首次需要时准备。`Noto Sans SC` 字体是 Tier 2，只在导出含字幕的视频时下载，资产同时包含 OFL 许可。转录走云端 Fun-ASR,清单不含 whisper 资产,也不因远程转录失败自动下载本地 ASR。下载入口只接受 HTTPS，本地开发 loopback 除外；下载链路支持 Range、断点续传、大小与 SHA-256 校验、失败重试和原子落位。

生图工作台、剪视频工作台、Agent 做图和 Agent 剪视频都调用客户端统一资产管理器。Agent 只请求能力，不能拼资产 URL 或执行 `curl`；任务在组件缺失时进入 preparing，资产就绪后由原任务继续，避免用户重复提交和重复计费。

更新顺序：

1. 计算文件大小和 SHA-256。
2. 上传文件到平台目录。
3. 更新并上传 `manifest.json`。
4. 先发布大陆镜像，再发布主入口，最后验证两端 HTTPS 200、Range 206 和文件摘要。

```bash
shasum -a 256 ffmpeg
stat -f%z ffmpeg
scp ffmpeg root@<大陆机>:/var/www/qf-assets/ffmpeg-darwin-arm64
scp manifest.json root@<大陆机>:/var/www/qf-assets/
scp ffmpeg root@<美国机>:/var/www/qf-assets/ffmpeg-darwin-arm64
scp manifest.json root@<美国机>:/var/www/qf-assets/
curl -s https://zzyppz.cn/assets/manifest.json | head
curl -sI -H 'Range: bytes=100-' https://zzyppz.cn/assets/ffmpeg-darwin-arm64 | head -3
```

客户端资产状态通过 `GET /api/v1/assets/status` 和 WS 进度事件提供。

## 9. 新服务器规格与迁移

### 9.1 规格选择

转录已切云调用(Fun-ASR-Flash),网关主机不再需要 ASR GPU 或本地权重,`2 vCPU / 3.4GiB RAM` 级现网机器即可承载网关本身;容量按聊天/图片代理与转录 RPM 评估,而非按 ASR 模型显存。若未来自托管 ASR 再单列规格,当前不做自托管 Whisper/ForcedAligner 规格假设。

### 9.2 迁移顺序

1. 确保 `QF_GATEWAY_URL` 使用稳定 HTTPS 域名，不把服务器 IP 固化进客户端。资产默认入口已经使用 `https://zzyppz.cn/assets/manifest.json`，迁移时只切换域名解析和后端反向代理。
2. 在新机执行 qfgw、转录 provider、nginx、dataeye 和静态资产的可重复部署脚本；模型按固定哈希重新下载，不把模型文件当业务状态搬运。
3. 迁移 `/opt/qfgw/gw.env` 时使用受保护通道并保持 `600`；迁移 `usage.db` 使用 SQLite 在线 backup 或短暂停写后的快照，不直接复制活动 WAL 三件套。
4. `rsync` `/var/www/qf-assets/` 和 dataeye 持久数据，校验文件哈希；在新机用旧 app token 完成健康、鉴权、聊天、图片、语音、时间戳和清理 smoke。
5. 提前降低 DNS TTL，切换域名到新机并观察错误率、延迟、CPU/GPU、内存、磁盘和转录队列。旧机至少保留48小时，不同时写两套用量数据库。
6. 回滚只切回 DNS/反向代理；确认新机稳定后再吊销旧机凭据、停止服务并清理磁盘。密码不写入迁移脚本，服务器长期只允许 SSH key。
