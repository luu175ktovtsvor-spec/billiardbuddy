## 2. 模型网关 `qfgw`

代码入口：`gateway/app.ts`

主要职责：

- 校验客户端 Bearer token。
- **装机公平调度**:客户端头 `X-QF-Client-ID`(桌面持久化的 installationId)+ token 组成公平身份 `token#client`,同一 token 的不同装机各占一份单用户额度(50~100 装机不再被当成同一用户)。装机身份只细分单用户公平与用量归属,受各上游全局并发上限约束,伪造/畸形 id 退回按 token 调度,不提权、不绕全局额度。
- 三模型路由(按 `model` 显式分流,**绝不静默跨供应商回退**):命中 DeepSeek 白名单→DeepSeek;命中 MiMo 白名单→MiMo;否则默认 Qwen(白名单外 model 归一为 `GW_QWEN_MODEL`)。三家各持独立凭据/base/白名单/并发/RPM/重试/单 token 二级并发闸;命中的上游未配置返回明确 `503`。DeepSeek 注入受信 opaque `user_id`(官方字段,`bb_<hash>`,不含隐私、不提权)。**产品默认模型 = `deepseek-v4-flash`**;显式请求 qwen/mimo 固定路由,会话内模型不中途换。MiMo v2.5 是唯一多模态上游:普通图片先由 MiMo 转成结构化文本再交给目标文本模型;带原始截图且启用真实 Computer Use 工具集的回合则整轮直接路由到 MiMo,保留像素、坐标和工具语义。厂商能力矩阵见 `docs/网关多模型与Agent内核接轨.md`。
- **重试收紧**:429 一律不重试直接回传;连接错误/可重试 5xx 最多额外一次(与 CC CLI 重试不相乘)。
- 在服务器注入模型与供应商密钥,客户端只持可撤销 app token。
- 代理文本和图片异步任务；图片提交时把受信 owner=`token#client` 与透传 `Idempotency-Key` 传给 relay，轮询携带同一 owner。同步图片生成/编辑端点不对客户端开放。
- 通过统一端点执行语音输入与视频口播转录,provider 为 **Fun-ASR-Flash**。
- 记录不包含密钥的用量信息(用量 note 含装机 client 做归属)。

主要端点：

```text
GET  /v1/models                 # 鉴权后返回内部模型目录；普通桌面不展示模型名
POST /v1/chat/completions
POST /v1/images/tasks           # 提交转发 relay,带 X-Relay-Owner + 透传 Idempotency-Key
GET  /v1/images/tasks/:id        # 轮询带 X-Relay-Owner,relay 强制同 owner
POST /v1/audio/transcriptions
GET  /healthz
```

DeepSeek V4 Flash 配置(真 key 只在服务器 `gw.env`,`600`):

```text

GW_DEEPSEEK_BASE       # 默认 https://api.deepseek.com(chat 路径 /chat/completions,不带 /v1)
GW_DEEPSEEK_MODEL      # 默认 deepseek-v4-flash;deepseek-chat/reasoner 将于 2026-07-24 退役,勿用 legacy 模型
GW_DEEPSEEK_MODELS     # 逗号分隔追加(如需 deepseek-v4-pro)

GW_DEEPSEEK_USER_CONC  # 单装机并发,线上未设置(私测放开,默认=全局 96)
GW_DEEPSEEK_RPM        # 线上未设置(私测放开,代码默认 100000,不因官方并发 2500 就再收紧)
```

健康检查(带有效 app token)的 `features` 含 `transcription` / `chat_qwen` / `chat_mimo` / `chat_deepseek`,`capacity` 含 `qwen` / `mimo` / `deepseek` 容量池。上游真密钥只在服务器 `gw.env`;迁移服务器只迁受保护环境配置并重新部署 gateway,桌面协议和客户端包不变。用量日志只记录次数、状态和耗时，不记录请求正文。

## 3. 语音与口播转录

桌面端固定调用 `POST /v1/audio/transcriptions`，上传音频文件、语言和 `json|verbose_json` 输出格式。网关先执行 app token 鉴权、96MiB 文件上限、类型检查、速率限制和单并发，再调用服务器 provider；音频只写入权限为 `700` 的临时目录，任务结束或取消后删除，不记录音频内容和转写文本。

现行且唯一的 provider 是阿里云百炼 **Fun-ASR-Flash**(DashScope 多模态端点),`verbose_json` 返回词级时间戳供视频字幕使用。转录为云调用,网关主机无需本地 ASR 二进制/模型/GPU。**Whisper 已退役,不运行/下载/部署/回退**;`GW_TRANSCRIBE_PROVIDER` 为 `whisper` 或 `upstream` 等非 Fun-ASR 值时 fail closed(返回 null)。

配置入口：

```text
GW_FUNASR_KEY          # DashScope 密钥,只在服务器 gw.env(600)
GW_FUNASR_MODEL        # 默认 fun-asr-flash 对应模型
GW_TRANSCRIBE_PROVIDER # 留空或 funasr / fun-asr;其它值 fail closed
GW_TRANSCRIBE_RPM
GW_TRANSCRIBE_CONC
GW_TRANSCRIBE_MAX_BYTES
```

客户端不感知 provider。部署随 gateway 一起进行(`gateway/deploy.sh` 含 `transcription.ts`),无单独转录安装脚本;上线前用真实中文音频跑 smoke 验证 text + 词级时间戳。

## 4. 图片 relay `qfrelay`

代码入口：`relay/app.ts`

relay 在美国服务器完成图片生成或编辑调用，桌面端经 gateway 使用 submit/poll：

```text
POST /images/tasks
  headers: Authorization: Bearer <RELAY_TOKEN>; X-Relay-Owner?: <owner>; Idempotency-Key?: <key>
  { mode, model, prompt, n, size, response_format?, images?, mask?, input_fidelity? }
  → 202 { task_id, status, reused? } / 413 请求体过大 / 429 队列或单用户已满

GET /images/tasks/:id
  headers: Authorization + X-Relay-Owner?
  → 200 { status, data?, error?, created } / 403 owner 不匹配 / 404 未知或过期
```

`status` 为 `queued`、`running`、`succeeded`、`failed` 或 `failed_unknown`。gateway 将 `/v1/images/tasks` 转发到 relay,客户端只访问 gateway、**不得直连 relay**。

私测版加固(向后兼容,旧网关无 owner/无幂等键仍可工作):

- **幂等**:同 `(owner, Idempotency-Key)` 重复提交返回原 `task_id`,只跑一次真实上游、只扣一次费。
- **归属绑定**:任务绑定网关注入的受信 `X-Relay-Owner`;带 owner 的任务只有同 owner 能轮询,越权/无身份→`403`;旧任务(owner 为空)兼容期不设防。旧版无 `Idempotency-Key` 的请求仍可工作,但重复提交有重复计费风险。
- **持久化**:`RELAY_DB`(如 `/opt/qfrelay/relay.db`)存任务元数据+幂等映射;大体积输入/结果放 `RELAY_BLOB_DIR`(`700` 目录)的 blob 文件,不长期堆内存/SQLite。
- **队列上限**:`RELAY_QUEUE_MAX`(全局在途)、`RELAY_USER_MAX`(单 owner 在途)、`RELAY_IMG_CONC`(对 OpenAI 并发)、`RELAY_MAX_BODY_BYTES`(请求体)、`RELAY_TASK_TTL_MS`,全部有界。
- **上游超时与未知结果**:`RELAY_UPSTREAM_TIMEOUT_MS` 默认 5 分钟。连接中断、超时、成功响应读取失败、成功响应损坏或空结果都记为 `failed_unknown`,禁止盲目重提,避免已经扣费却重复生成；明确的上游失败记为 `failed`。
- **终态输入清理**:任务进入 `succeeded`、`failed` 或 `failed_unknown` 后立即删除含提示词、参考图和蒙版的输入 blob,只保留轮询需要的结果与元数据；终态整体记录仍按 `RELAY_TASK_TTL_MS` 清理。
- **重启恢复**:`queued` 读 blob 原始输入续跑;`running` 无法确认结果→`failed_unknown`,同时清理输入 blob 且禁止自动重提。GPT Image 只走异步 relay,relay 故障显式失败,不回退跨境同步长连接。

relay 只监听 `127.0.0.1`,由 nginx 暴露受保护路径 `/relay/imgtasks/`;nginx **仅允许大陆 qfgw 出口 IP 访问并保留 Bearer 鉴权**,客户端不得直连。真 OpenAI key 只在 `relay.env`(`600`)。

运维命令：

```bash
ssh root@<美国机> 'systemctl restart qfrelay && systemctl is-active qfrelay'
ssh root@<美国机> 'curl -s --max-time 8 http://127.0.0.1:8790/healthz'
```

## 7. 新服务器规格与迁移

### 7.1 规格选择

转录已切云调用(Fun-ASR-Flash),网关主机不再需要 ASR GPU 或本地权重,`2 vCPU / 3.4GiB RAM` 级现网机器即可承载网关本身;容量按聊天/图片代理与转录 RPM 评估,而非按 ASR 模型显存。若未来自托管 ASR 再单列规格,当前不做自托管 Whisper/ForcedAligner 规格假设。

### 7.2 迁移顺序

1. 确保 `QF_GATEWAY_URL` 使用稳定 HTTPS 域名，不把服务器 IP 固化进客户端。资产默认入口已经使用 `https://zzyppz.cn/assets/manifest.json`，迁移时只切换域名解析和后端反向代理。
2. 在新机执行 qfgw、转录 provider、nginx 和静态资产的可重复部署脚本；模型按固定哈希重新下载，不把模型文件当业务状态搬运。
3. 迁移 `/opt/qfgw/gw.env` 时使用受保护通道并保持 `600`；迁移 `usage.db` 使用 SQLite 在线 backup 或短暂停写后的快照，不直接复制活动 WAL 三件套。
4. `rsync` `/var/www/qf-assets/`，校验文件哈希；在新机用旧 app token 完成健康、鉴权、聊天、图片、语音、时间戳和清理 smoke。
5. 提前降低 DNS TTL，切换域名到新机并观察错误率、延迟、CPU/GPU、内存、磁盘和转录队列。旧机至少保留48小时，不同时写两套用量数据库。
6. 回滚只切回 DNS/反向代理；确认新机稳定后再吊销旧机凭据、停止服务并清理磁盘。密码不写入迁移脚本，服务器长期只允许 SSH key。
