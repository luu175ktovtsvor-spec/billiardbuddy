# Coding Agent 地基与对标规则

> 📌 状态:✅现行 · 最后核对 2026-07-14

本文是项目、会话、模型、Agent 内核、提示词、扩展披露和上游对标方法的唯一真相源。系统总模块与部署边界见 `当前架构与状态-总览.md`，逐字逆向证据见 `references/` 和仍在执行的 `plans/`。源码、运行行为和测试优先于本文。

## 1. 产品对象模型

```text
桌面应用
  -> 项目(workspaceRoot 标识的工作文件夹)
       -> 会话(session / conversation)
            -> 回合(turn)
                 -> 模型步骤(step)
                      -> 工具调用 / 工具结果
```

### 1.1 项目就是工作文件夹

- 用户选择一个文件夹，等同于添加或激活一个项目。`workspaceRoot` 是项目身份，也是 Agent 文件、命令、Git 和终端操作的默认边界。
- 当前没有独立的项目表。项目列表由会话元数据按 `workspaceRoot` 聚合，侧栏中的项目名取文件夹名。
- 同一项目可以创建任意多个会话。产品模型不设置固定数量上限，实际并发受内存、模型额度、进程和文件冲突约束。
- 同一项目内的会话共享真实文件和 Git 工作树，但不共享 transcript。两个会话同时修改同一文件仍可能冲突；需要代码级并行隔离时使用 Worktree，不能把“会话隔离”误写成“文件隔离”。
- 默认工作目录中的会话归入普通任务组；只有明确选择的非默认目录作为项目分组显示。

### 1.2 每个会话都是独立 session

每个会话至少独立持有：

- `conversationId`、标题、状态和事件序号；
- JSONL transcript、事件回放、压缩与 rewind 历史；
- `workspaceRoot`；
- 会话级领域包状态；
- 会话级临时权限更新、运行中回合、排队消息和 WS 消费者状态。

会话记录按 `projects/<workspace-slug>/<session-id>.jsonl` 分区。选择同一项目只表示这些会话在同一工作文件夹工作，不表示它们共享上下文窗口、聊天历史或审批结果。

### 1.3 模型的实际作用域

- 当前 provider 列表、活跃 provider 和降级顺序是应用级配置，保存在 `providers.json`。
- 每个会话都能发起模型回合；每个回合根据当前 provider 候选创建模型运行实例并执行 Agent loop。
- `SessionMeta` 当前没有 `providerId` 或 `model` 字段，因此不存在“每个项目永久绑定一个模型”或“每个会话持久化独立模型”的实现。
- 准确表述是“每个会话都可以使用模型”，不是“每个会话拥有一套独立模型配置”。
- 如果以后需要会话级模型选择，必须同时定义会话元数据、共享契约、失败降级、恢复行为、前端选择器和旧会话兼容；不能只在组件里存一个下拉值。

### 1.4 运行时拓扑

本项目使用一个 Electron 应用和一个共享 Bun sidecar 承载多会话。各会话有独立状态，但共享 sidecar 进程、provider 服务和大部分注册表；FFmpeg、MCP、shell、转写等按需启动外部进程。

WorkBuddy 的每会话 CLI 进程可以作为故障隔离参考，但不是必须照搬的目标。只有共享 sidecar 的崩溃隔离、资源争用或升级边界被真实测试证明无法接受时，才评估拆成每会话进程。

## 2. 两条产品执行线

| 执行线 | 适用任务 | 核心责任 |
|---|---|---|
| A 线：Agent 对话 | 问答、分析、文件、命令、搜索、浏览器、电脑操作和开放式交办 | 模型决定下一步，内核提供循环、上下文、权限、工具、恢复和验证 |
| B 线：确定性功能 | 生图、剪视频、定时任务、设置和其他有明确状态机的工作台 | 产品代码直接编排 REST job、IPC、本地服务、进度、取消和持久化 |

Coding Agent 不只会写代码。只要注册了受控工具，它也能操作文件、运行终端命令、查询资料和调用电脑能力。生图与剪视频仍保留专用工作台；Agent 通过工具或服务入口调用它们，不复制第二套媒体引擎，也不把所有产品功能塞进聊天 store。

## 3. 提示词与语言分层

提示词按责任组装，不维护一份混合了内核、品牌、台球知识和页面文案的巨型字符串。

| 层 | 默认语言 | 规则 |
|---|---|---|
| Kernel 行为契约 | 英文优先 | 从许可可用的 `cc-haha-ref` 对齐工具、权限、任务纪律和边界限定；保留语义与顺序，用行为测试证明，不按句子相似度验收 |
| 产品身份与安全增量 | 独立短块 | 白标、宿主安全和本项目不可放宽的规则单独叠加，不改写整份母提示词 |
| 输出语言 | 独立 Language 块 | 用户界面和默认回复使用中文；任务标题、问题和自然语言工具参数遵循用户语言 |
| 台球领域知识与门店记忆 | 中文 | 保留真实行业术语、原始来源和门店语境，不为统一语言重复翻译 |
| MCP/插件自带说明 | 保留来源语言 | 先净化和截断，再以明确来源块注入；不能获得高于宿主规则的优先级 |

英文不是天然更高质量。保留英文内核的理由是减少自由翻译造成的限定条件丢失，并方便跟踪上游；最终是否采用某一提示词变体，由当前接入模型的 A/B 行为评测决定。

WorkBuddy 安装包中的专有提示词只用于行为与结构对照，不复制其品牌、政策、服务地址或产品特有段落。可移植实现的工程来源记录为许可可用的参考库。

## 4. 扩展能力的分类与展示

| 类型 | 含义 | 当前作用域 | 用户入口 |
|---|---|---|---|
| 内置能力 | 随应用交付的文件、命令、搜索、媒体等工具 | 应用级可用，执行仍受会话权限和工作区约束 | 自然语言、工具状态页 |
| 领域包 | 成组注入领域上下文、推荐技能、命令和工具 | 会话级启停 | 设置/扩展页开关、领域激活斜杠命令 |
| Skill | 可复用工作流和专项指令，可带工具权限、hooks 或 fork | 系统、个人、项目或插件来源 | 自然语言自动路由、`/`、`@`、扩展页 |
| Command | 用户或模型可展开的快捷任务入口 | 内置、项目、领域包或插件来源 | `/` 命令面板 |
| Plugin | 可安装、启停并贡献 Skills、Commands、hooks、output styles 或 MCP 的扩展包 | 应用级安装与启停 | 扩展页插件区 |
| MCP | 连接本地或远程服务后提供 tools/resources/prompts | 应用配置；工作区 `.mcp.json` 另受项目信任控制 | 扩展页 MCP 服务区，运行时由 Agent 调用 |
| 产品工作台 | 生图、剪视频、定时任务等完整产品能力 | 应用功能域 | 左侧导航或明确命令 |

### 4.1 渐进披露

- 普通用户先看到中文能力名、用途、启用状态和失败原因；内部 tool name、transport、provider 和原始 Schema 只在详情或诊断中出现。
- `/` 面板只列用户可调用的 Command 和 Skill，并显示“系统 / 个人 / 项目 / 插件 / 专家”等来源。自然语言仍可由模型根据发现清单主动选择能力。
- 领域包的激活入口应始终可发现；只有启用后才展示领域子命令并向模型装配领域上下文和工具。
- Plugin 与 MCP 不能混为同一个概念。插件卡展示名称、启停和贡献数量；MCP 卡展示连接、停用、授权、错误和工具数量。
- MCP 首页不平铺所有原始工具。用户展开详情时再看服务说明、来源、工具清单、资源、授权和重连操作。
- 前端继续使用现有 Codex 风格、中性中文和现有布局，不因底层来自英文 CLI 就把工程术语直接暴露给用户。

### 4.2 当前未闭环

- 插件包当前使用根目录 `plugin.json` 并把启停状态写回 manifest；尚未兼容 Claude Code 的 `.claude-plugin/plugin.json`、独立启用策略存储、安装来源证明、版本锁定和内容完整性校验。
- 插件贡献的 Skills、Commands、hooks 和 MCP 已统一接入主 Agent、审批恢复、预热与发现接口；插件 Agents 和 output styles 仍未进入运行时，前端只显示其数量。
- React 插件页可以查看和启停已安装插件，但还没有插件市场、安装来源详情、更新、卸载和策略管理入口。安装 API 仍只接受 Git 仓库地址，新安装项默认停用。
- MCP 首页可以添加、删除、启停并显示连接状态，但 resources、prompts、授权、重连和逐服务工作区信任仍缺少完整的可视化管理入口。

现行安全不变量是：缺少显式 `enabled:true` 的插件不装配；启用前显示信任确认；插件声明的 hook 路径不得越出插件目录；工作区 `.mcp.json` 继续经过独立信任门；所有 MCP 工具继续走权限审批。

## 5. 领域包状态不变量

台球开关位于设置页、扩展页和斜杠命令，但三处必须汇入同一个会话级 `enabledPacks` 状态，不建立三个互不相干的开关。

```text
用户开关 / 斜杠命令
  -> enabledPacksByConv[conversationId]
  -> WS run / approve 的 enabled_packs
  -> SessionMeta.enabledPacks
  -> 每回合 system prompt + commands + skill recommendations + tools
```

- 字段缺失：非前端或旧调用方没有表达新选择，沿用会话持久化状态。
- `enabled_packs: []`：用户明确关闭，不得从旧元数据恢复。
- 开启：每个后续回合都必须有台球领域上下文、领域子命令、推荐技能和 `billiards_ops_checklist` 工具。
- 关闭：下一回合和审批续跑都必须撤销上述贡献，并把空数组写回会话元数据。
- 不同会话互不串状态；项目相同不改变这个规则。

## 6. 正确的上游对标方法

### 6.1 证据角色

| 来源 | 角色 | 不能证明什么 |
|---|---|---|
| Claude Code 官方二进制/CLI 黑盒 | 官方当前外部行为和契约 oracle | 不能直接给出完整模块源码或证明内部实现方式 |
| `cc-haha-ref` | 可读、可运行、许可可用的候选实现和行为映射 | 不能无条件代表官方最新版本，也不能证明没有自定义 Bug |
| WorkBuddy 安装包与产品行为 | 桌面宿主、多进程、交互和安全的参考/反例 | 不能因为长句或结构相同就证明它直接复制自 `cc-haha` |
| 本项目源码、契约与测试 | 最终交付事实 | 不能因为已有实现就证明设计正确或已与上游对齐 |

当前证据能证明 `cc-haha-ref` 与 Claude Code 有大规模强映射，也能证明 WorkBuddy 是 Claude Code-derived 的深度衍生产品。WorkBuddy 是否直接以当前 `cc-haha-ref` 为代码来源仍是 `UNKNOWN`；共同特征也可能来自共同的 Claude Code 母体。

### 6.2 对标单位

不按仓库行数或页面像不像对标，按可观察行为不变量对标。每个工作包只处理一个子系统，例如：

- 消息与 tool use/result 配对；
- 权限规则和危险动作；
- workspace/path/sandbox；
- context、compact、memory；
- Skills、Commands、hooks、plugins、MCP；
- tasks、agents、resume；
- provider 转换和降级；
- 桌面会话、项目、IPC 与进程生命周期。

媒体工作台、台球业务规则和前端视觉不是 Claude Code kernel 对标项。它们只复用稳定的宿主契约和工具入口。

### 6.3 差异分类

每个差异必须落入一个结论，不能只写“看起来不一样”：

| 结论 | 含义 |
|---|---|
| `ALIGNED` | 关键行为与选定上游一致，已有测试证据 |
| `INTENTIONAL_DELTA` | 为本项目产品、白标、运行时或兼容边界有意不同 |
| `UPSTREAM_BUG_FIXED` | 上游行为有可复现缺陷，本项目保留修复并记录反例测试 |
| `NOT_APPLICABLE` | Anthropic/WorkBuddy 专属云能力或不属于本项目边界 |
| `UNKNOWN` | 证据不足，不能猜测实现或继承关系 |

### 6.4 执行流程

1. 写清用户可观察行为和安全不变量。
2. 追生产者、传输、消费者、状态和持久化，不从最大文件开头逐行读。
3. 用同一输入对官方黑盒、`cc-haha-ref` 和适用的 WorkBuddy 行为做结构化快照。
4. 先写最接近边界的特征/差分测试，再决定移植、修正、拒绝或延后。
5. 只修改唯一主责模块和必要消费者；前端、媒体、远程服务不因“可能相关”被一起拖入。
6. 至少保留一个低层行为测试和一个真实装配测试。安全边界再加失败关闭和对抗样例。
7. 用上述差异分类记录结论；上游升级时重新跑同一批行为测试，不靠人工回忆。

## 7. 地基调整优先级

1. 保持项目 -> 会话 -> 回合边界稳定，补齐所有会话级状态的持久化和恢复测试。
2. 把插件 manifest、启用策略、来源、版本和完整性校验拆成稳定契约，再接插件 Agents、output styles、更新和卸载。
3. 补齐 MCP 多模态结果、断线恢复、OAuth、resources/prompts 展示和更细的逐服务信任控制。
4. 建立提示词 section 级快照与模型级 A/B eval，保持英文 kernel、中文产品/领域/输出分层。
5. 继续按子系统拆 `server/index.ts`，但功能修复与结构重构分开提交。
6. 对每个官方新版本只处理有用户价值或安全价值的差异，不追求 CLI 参数和页面数量全量复制。
