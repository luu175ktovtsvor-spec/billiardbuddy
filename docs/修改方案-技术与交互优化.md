## 1. DeepSeek 多轮对话改造

### 1.1 问题描述

当前工作台的"基于此优化"功能是"假多轮"：对话历史被拼接成纯文本追加到 prompt 末尾，而不是作为结构化的 messages 数组传给 DeepSeek API。模型无法区分哪些是历史对话、哪些是当前指令。

**验证来源**：DeepSeek 官方文档 https://api-docs.deepseek.com/zh-cn/guides/multi_turn_chat

### 1.2 DeepSeek V4 Flash 多轮对话格式

DeepSeek API 是无状态的，多轮对话通过 messages 数组实现：

```python
messages = [
    {"role": "system", "content": "你是台球房运营专家..."},
    {"role": "user", "content": "帮我写一条朋友圈文案"},
    {"role": "assistant", "content": "AI 生成的内容..."},
    {"role": "user", "content": "再短一点，活泼一点"},
]
```

支持 4 种角色：`system`、`user`、`assistant`、`tool`

### 1.3 需要修改的文件

#### 文件 1：`server/services/ai/base.py`（第 7-11 行）

**当前代码**：
```python
@dataclass
class TextRequest:
    prompt: str
    system_prompt: str | None = None
    max_tokens: int = 2000
    temperature: float = 0.7
```

**修改为**：
```python
@dataclass
class TextRequest:
    prompt: str
    system_prompt: str | None = None
    messages: list[dict] | None = None  # 新增：多轮对话消息数组
    max_tokens: int = 2000
    temperature: float = 0.7
```

**说明**：`messages` 字段用于传入结构化的多轮对话历史。当 `messages` 不为 None 时，provider 应优先使用它而非 `prompt`。

#### 文件 2：`server/services/ai/providers/deepseek.py`（第 34-38 行，第 83-87 行）

**当前代码**（generate 和 generate_stream 相同逻辑）：
```python
messages = []
if request.system_prompt:
    messages.append({"role": "system", "content": request.system_prompt})
messages.append({"role": "user", "content": request.prompt})
```

**修改为**：
```python
if request.messages:
    # 多轮对话模式：直接使用传入的 messages 数组
    messages = request.messages
else:
    # 单轮模式：保持原有逻辑
    messages = []
    if request.system_prompt:
        messages.append({"role": "system", "content": request.system_prompt})
    messages.append({"role": "user", "content": request.prompt})
```

**说明**：保持向后兼容。现有的单轮调用不需要改动，新的多轮调用通过 `messages` 字段传入。

#### 文件 3：`server/services/ai/providers/deepseek.py`（第 91-97 行）

**当前代码**（流式请求参数）：
```python
response = await self._get_client().chat.completions.create(
    model=self.model_name,
    messages=messages,
    stream=True,
    max_tokens=request.max_tokens,
    temperature=request.temperature,

```

**修改为**：
```python
response = await self._get_client().chat.completions.create(
    model=self.model_name,
    messages=messages,
    stream=True,
    max_tokens=request.max_tokens,
    temperature=request.temperature,
    stream_options={"include_usage": True},  # 新增：获取 token 统计
)
```

**说明**：`stream_options.include_usage=True` 让 DeepSeek 在流式最后一个 chunk 返回 usage 统计（包括 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`）。

**验证来源**：DeepSeek 官方文档确认 stream_options 格式与 OpenAI 兼容。

#### 文件 4：`server/services/ai/providers/deepseek.py`（第 119-122 行）

**当前代码**（流式迭代）：
```python
async for chunk in response:
    if chunk.choices and chunk.choices[0].delta.content:
        yield chunk.choices[0].delta.content
```

**修改为**：
```python
async for chunk in response:
    # 收集 usage 统计（在倒数第二个 chunk 中返回，choices 为空数组）
    if chunk.usage:
        self._last_usage = {
            "prompt_tokens": chunk.usage.prompt_tokens,
            "completion_tokens": chunk.usage.completion_tokens,
            "total_tokens": chunk.usage.total_tokens,
            "cache_hit_tokens": getattr(chunk.usage, 'prompt_cache_hit_tokens', 0),
            "cache_miss_tokens": getattr(chunk.usage, 'prompt_cache_miss_tokens', 0),
        }
    # 正常内容 chunk（choices 非空）
    if chunk.choices and chunk.choices[0].delta.content:
        yield chunk.choices[0].delta.content
```

**说明**：
- usage 在**倒数第二个 chunk** 返回（`data: [DONE]` 之前），该 chunk 的 `choices` 为空数组
- 所有中间 chunk 的 `usage` 字段为 `null`，只有最后一个有值
- 当前代码 `if chunk.choices` 会自动跳过 usage chunk（因为 choices 为空），不需要额外处理
- `_last_usage` 属性需要在类中定义

#### 文件 5：`server/api/v1/stream.py`（第 103-135 行）

**当前代码**（对话历史拼接）：
```python
for i, hg in enumerate(history_gens[-5:], 1):
    hist_params = hg.input_params or {}
    hist_intent = hist_params.get("user_intent", "")
    hist_result_text = hg.result or ""
    if hist_intent:
        history_lines.append(f"用户（第{i}轮）：{hist_intent}")
    if hist_result_text:
        history_lines.append(f"助手（第{i}轮）：{hist_result_text[:800]}")
# ...
rendered_prompt = f"{rendered_prompt}\n\n---\n【对话历史（供参考，不要重复生成相同内容）】\n{history_text}\n---\n"
```

**修改为**：
```python
# 构建 messages 数组
messages = []

# 1. System prompt（从 rendered_prompt 中提取，或单独构建）
if system_prompt:
    messages.append({"role": "system", "content": system_prompt})

# 2. 历史对话（最近 5 轮）
for hg in history_gens[-5:]:
    hist_params = hg.input_params or {}
    hist_intent = hist_params.get("user_intent", "")
    hist_result_text = hg.result or ""
    if hist_intent:
        messages.append({"role": "user", "content": hist_intent})
    if hist_result_text:
        messages.append({"role": "assistant", "content": hist_result_text[:2000]})

# 3. 当前用户输入
messages.append({"role": "user", "content": current_user_intent})

# 传入 TextRequest
request = TextRequest(
    prompt=current_user_intent,
    system_prompt=system_prompt,
    messages=messages,  # 新增
    max_tokens=3000,
)
```

**说明**：
- 不再拼接文本，改为构建结构化 messages 数组
- 历史 assistant 回复截断从 800 字符放宽到 2000 字符（DeepSeek 1M 上下文足够）
- system prompt 保持不变，利用 DeepSeek 的 context caching 降低成本

### 1.4 DeepSeek Context Caching 优势

**验证来源**：DeepSeek 官方文档 https://api-docs.deepseek.com/zh-cn/guides/kv_cache

多轮对话天然受益于 context caching：
- 第 2 轮请求的 messages 前缀（system + 第 1 轮对话）会命中缓存
- 缓存命中价格：$0.0028/1M tokens（vs 未命中 $0.14/1M tokens，便宜 50 倍）
- 无需改代码，DeepSeek 默认启用

### 1.5 注意事项

1. **模型名**：确认 `config.py` 中 `text_model_name = "deepseek-v4-flash"`（已正确）
2. **temperature**：DeepSeek V4 Flash 默认 temperature=1，当前代码显式传 0.7，更稳定（保持不变）
3. **thinking 模式**：V4 Flash 默认启用，`reasoning_content` 字段不需要回传（无 tool call 时）
4. **废弃参数**：`frequency_penalty` 和 `presence_penalty` 已废弃（当前代码没有传，不需要改）

## 2. OpenAI gpt-image-2 quality 参数修复

### 2.1 问题描述

当前代码有两个问题：
1. `quality` 参数没有传给 OpenAI API（默认 `auto`）
2. `quality` 同时用于选择分辨率和控制质量，两个概念混为一谈

**验证来源**：OpenAI Python SDK 源码 `src/openai/resources/images.py`（从 GitHub `openai/openai-python` 仓库获取）

### 2.2 OpenAI quality 参数规范

**SDK 类型定义**（从源码提取）：
```python
quality: Optional[Literal["standard", "low", "medium", "high", "auto"]] | Omit = omit
```

| 值 | 说明 | 价格（1024x1024） |
|---|---|---|
| `standard` | dall-e-2 遗留值，gpt-image-2 可用但不推荐 | 不确定 |
| `low` | 快速草稿，速度最快 | $0.006/张 |
| `medium` | 中等质量，一般用途 | $0.053/张 |
| `high` | 最终生产级品质 | $0.211/张 |
| `auto`（默认） | 模型自动选择 | 不确定 |

**关键发现**：
- `"standard"` 是合法值（dall-e-2 遗留），但对 gpt-image-2 推荐用 `low/medium/high/auto`
- quality 参数对 `images.generate()` 和 `images.edit()` **都支持**（SDK 源码确认）
- 当前代码用 `"standard"` 作为 SIZE_MAP 的 key 来选择分辨率，这不是 quality 参数的正确用法

`images.edit()` 调用：

#### 文件 2：`server/services/poster_service.py`

**当前代码**（SIZE_MAP，约第 22-27 行）：
```python
SIZE_MAP = {
    "3:4": {"standard": "1024x1536", "high": "1536x2048"},
    "1:1": {"standard": "1024x1024", "high": "2048x2048"},
    "9:16": {"standard": "864x1536", "high": "1152x2048"},
    "16:9": {"standard": "1536x864", "high": "2048x1152"},
}
```

**注意**：gpt-image-2 支持任意分辨率（SDK 源码确认），只要满足：
- 宽和高都能被 16 整除
- 宽高比在 1:3 到 3:1 之间
- 最大分辨率 3840x2160
- 超过 2560x1440 的为实验性

所以当前 SIZE_MAP 中的值（如 `1536x2048`、`2048x2048`、`864x1536`）**都是合法的**。

**修改为**（拆分 size 和 quality 为两个独立维度）：
```python
# 尺寸映射：根据比例选择尺寸（固定，不随 quality 变化）
SIZE_MAP = {
    "3:4": "1024x1536",
    "1:1": "1024x1024",
    "9:16": "1024x1536",
    "16:9": "1536x1024",
}
```

**说明**：
- 尺寸和质量解耦：size 只由 ratio 决定，quality 独立传给 OpenAI API
- 去掉 SIZE_MAP 中的 `standard/high` 嵌套，每个 ratio 只对应一个推荐尺寸
- quality 直接透传给 OpenAI API 的 `quality` 参数（`low/medium/high/auto`）
- 用户选 `low` 时速度快成本低，选 `high` 时质量最好

**调用 generate_image 的地方**（约第 164 行）：
```python
# 当前

# 修改为
result_bytes = await provider.generate_image(
    prompt=prompt,
    size=size_str,
    quality=quality,  # 新增：透传 quality
    images=ref_images,
)
```

## 3. 历史记录页面 Markdown 显示修复

### 3.1 问题描述

有两个 bug：
1. 列表页的 `stripMarkdown()` 函数对复杂 Markdown（表格、嵌套列表等）处理不干净，残留语法符号
2. 海报类型的详情弹窗判断逻辑失效，海报图片显示为文本 URL

### 3.2 Bug 1：stripMarkdown 不完善

**文件**：`web/src/app/dashboard/history/page.tsx`（第 20-33 行）

**当前代码**：
```typescript
function stripMarkdown(text: string): string {
  return text
    .replace(/^#{1,6}\s+/gm, "")
    .replace(/\*\*(.+?)\*\*/g, "$1")
    .replace(/\*(.+?)\*/g, "$1")
    .replace(/~~(.+?)~~/g, "$1")
    .replace(/`{1,3}[^`]*`{1,3}/g, "")
    .replace(/\[([^\]]+)\]\([^)]+\)/g, "$1")
    .replace(/^[-*+]\s+/gm, "")
    .replace(/^\d+\.\s+/gm, "")
    .replace(/^>\s+/gm, "")
    .replace(/^---+$/gm, "")
    .trim();
}
```

**修改为**（增加表格处理）：
```typescript
function stripMarkdown(text: string): string {
  return text
    .replace(/^#{1,6}\s+/gm, "")           // 标题
    .replace(/\*\*(.+?)\*\*/g, "$1")       // 加粗
    .replace(/\*(.+?)\*/g, "$1")           // 斜体
    .replace(/~~(.+?)~~/g, "$1")           // 删除线
    .replace(/`{1,3}[^`]*`{1,3}/g, "")     // 代码块
    .replace(/\[([^\]]+)\]\([^)]+\)/g, "$1") // 链接
    .replace(/^[-*+]\s+/gm, "")            // 无序列表
    .replace(/^\d+\.\s+/gm, "")            // 有序列表
    .replace(/^>\s+/gm, "")                // 引用
    .replace(/^---+$/gm, "")               // 分割线
    .replace(/^\|(.+)\|$/gm, "")           // 表格行
    .replace(/^\|[-:\s|]+\|$/gm, "")       // 表格分隔行
    .replace(/\n{3,}/g, "\n\n")            // 多空行压缩
    .trim();
}
```

### 3.3 Bug 2：海报详情判断逻辑失效

**根因**：后端路由层只把数据库的 `result` 映射到了 schema 的 `content` 字段，没有同时映射到 `result` 字段。前端依赖 `detailItem.result` 判断是否显示图片，但该字段永远为 `null`。

**文件**：`server/api/v1/generations.py`

**列表接口**（第 51-61 行）：
```python
# 当前
GenerationListItem(
    ...
    content=item.result,
    # result 字段没有赋值，默认 None
    ...
)

# 修改为
GenerationListItem(
    ...
    content=item.result,
    result=item.result if item.type == "poster" else None,  # 海报类型返回 result
    ...
)
```

**详情接口**（第 85-95 行）：
```python
# 同样修改
GenerationDetailResponse(
    ...
    content=generation.result,
    result=generation.result if generation.type == "poster" else None,
    ...
)
```

**说明**：海报类型需要 `result` 字段来存储图片 URL，文案类型用 `content` 存储文本内容。两者都来自数据库的同一个 `result` 字段，但前端需要区分。

## 4. 海报迭代编辑交互优化

### 4.1 问题描述

当前海报迭代只有一个"基于此调整"按钮，总是传入上一轮生成的图作为参考图。但用户有时想要"重新生成一张全新的"，此时不应传参考图。

### 4.2 设计方案：双按钮

在每张生成的图片下方，提供两个操作按钮：

| 按钮 | 行为 | 传参考图 |
|------|------|---------|
| "基于此调整" | 保留原图构图，局部修改 | ✅ 设置 `refineFrom` |
| "重新生成" | 生成全新图片 | ❌ 清空 `refineFrom` |

### 4.3 需要修改的文件

**文件**：`web/src/app/dashboard/posters/page.tsx`

**当前代码**（图片操作区域）：
```tsx
<button onClick={() => {
  setRefineFrom(generation_id)
  inputRef.current?.focus()
}}>
  基于此调整
</button>
```

**修改为**：
```tsx
<div className="flex gap-2">
  <button onClick={() => {
    setRefineFrom(generation_id)  // 传入参考图
    inputRef.current?.focus()
  }}>
    基于此调整
  </button>
  <button onClick={() => {
    setRefineFrom(null)  // 清空参考图
    inputRef.current?.focus()
  }}>
    重新生成
  </button>
</div>
```

### 4.4 Prompt 保护指令

当用户选择"基于此调整"时，自动在 prompt 末尾追加保护指令：

**文件**：`server/services/poster_service.py`（prompt 构建逻辑，约第 82-118 行）

**当前代码**：
```python

    parts.append(f"门店名称：{store.name}")
    if store.city:
        parts.append(f"城市：{store.city}")

    parts.append("no text, no words, no letters, no typography")
```

**修改为**：
```python
parts = [prompt]
if add_store_info and store:
    parts.append(f"门店名称：{store.name}")
    if store.city:
        parts.append(f"城市：{store.city}")
if no_text:
    parts.append("no text, no words, no letters, no typography")

```

**说明**：这句保护指令告诉模型"保持整体构图和风格不变，只修改用户要求的部分"，减少迭代漂移。

### 4.5 智能默认（可选增强）

在前端检测用户输入，自动建议默认行为：

```typescript
function shouldUseRefineFrom(userInput: string): boolean {
  const resetKeywords = ["重新", "换个", "不要", "全新", "另一个", "换一张", "重来"];
  if (resetKeywords.some(kw => userInput.includes(kw))) {
    return false;
  }
  return true; // 默认传参考图（迭代更常见）
```

### 7.2 需要新增的表

#### 表 1：`conversations`（对话会话表）

**必要性**：支持多轮对话式交互。当前 `conversation_id` 只是 `generations` 表的一个字段，没有独立管理会话生命周期。

```python
class Conversation(Base):
    __tablename__ = "conversations"

    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    store_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("stores.id"), nullable=False, index=True)
    user_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("users.id"), nullable=True, index=True)
    type: Mapped[str] = mapped_column(String(50), nullable=False)  # "workbench" / "poster"
    title: Mapped[str | None] = mapped_column(String(200), nullable=True)  # 对话标题（首条消息摘要）
    status: Mapped[str] = mapped_column(String(20), default="active")  # active / archived
    message_count: Mapped[int] = mapped_column(Integer, default=0)
    last_message_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())
```

**索引**：
- `(store_id, type, last_message_at)` — 查询某门店的对话列表
- `(store_id, user_id)` — 查询某用户的对话

#### 表 2：`conversation_messages`（对话消息表）

**必要性**：将当前 `generations` 表的"一次生成一条记录"改为"每条消息独立存储"，支持真正的多轮对话上下文。

```python
class ConversationMessage(Base):
    __tablename__ = "conversation_messages"

    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    conversation_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("conversations.id", ondelete="CASCADE"), nullable=False, index=True)
    role: Mapped[str] = mapped_column(String(20), nullable=False)  # "user" / "assistant" / "system"
    content: Mapped[str | None] = mapped_column(Text, nullable=True)  # 消息内容
    generation_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("generations.id"), nullable=True)  # 关联的生成记录
    token_count: Mapped[int | None] = mapped_column(Integer, nullable=True)  # 本条消息的 token 数
    model_used: Mapped[str | None] = mapped_column(String(100), nullable=True)  # 使用的模型
    metadata_: Mapped[dict | None] = mapped_column("metadata", JSONB, nullable=True)  # 扩展字段
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
```

**索引**：
- `(conversation_id, created_at)` — 按时间顺序获取对话消息

### 8.4 推荐系统改造：混合方案

**当前状态**：纯规则引擎（7 条 if-else），没有 AI 参与。推荐内容是代码里写死的字符串，根据门店完整度、今日生成数、星期几决定展示哪几条。

**问题**：
- 推荐内容固定，不根据用户历史偏好调整
- 不考虑用户行为（上次效果好不好）
- 不考虑门店特点（竞技球房 vs 商业球房）
- 不考虑时间上下文（节假日、赛事）

**目标方案：规则引擎 + AI 混合推荐**

```
规则引擎处理"确定性推荐"（必须做的、有明确规则的）
  +
AI 处理"创意性推荐"（内容角度、热点关联、个性化）
  →
合并去重排序 → 推荐给用户
```

**为什么用混合方案**：
- 纯规则引擎：零成本，但推荐内容千篇一律
- 纯 AI 推荐：每次打开 Dashboard 调一次 AI，成本 ~$0.001/次，但有延迟
- 混合方案：规则引擎处理确定性推荐（零成本、即时响应），AI 处理创意性推荐（低成本、个性化）

**实现分两步**：

**Step 1：增强规则引擎（先做）**

在现有 4 个输入变量基础上，增加更多数据源：

| 新增输入 | 数据来源 | 推荐规则示例 |
|---------|---------|-------------|
| 上次生成类型 | generations 表 | 上次写了朋友圈 → 推荐"试试活动策划" |
| 上次效果标记 | generations.effect_rating | 上次标记"效果好" → 推荐"基于此再写一条" |
| 距上次活动天数 | generations 表（type=activity） | >7天 → 推荐"策划新活动" |
| 节假日/热点 | hot_topics 表 | 端午节 → 推荐"节日祝福+充值活动" |
| 团队任务状态 | tasks 表 | 助教任务未完成 → 推荐"提醒助教" |
| 剩余配额 | usage_quotas 表 | 剩余 <10 → 提醒"优先用在高价值场景" |

**Step 2：接入 AI 推荐（后做）**

```python
# 规则引擎生成"必做"推荐
rule_recs = build_rules(store, today_count, total_count, weekday)

# AI 生成"创意"推荐
ai_prompt = f"""
门店：{store.name}，{store.city}，{store.table_count}张球台
今日：{weekday}，{is_holiday}，热点：{hot_topic}
历史：共生成{total_count}条，{good_count}条标记"效果好"
上次活动：{days_since_last_activity}天前
团队：{team_status}

请推荐今天应该做的 3 件事，每件附带具体的 prompt。
"""
ai_recs = await ai_provider.generate(ai_prompt)

# 合并去重排序
final_recs = merge_and_deduplicate(rule_recs, ai_recs)
```

**AI 推荐的成本**：每次打开 Dashboard 调一次 DeepSeek V4 Flash，约 500 tokens，成本约 $0.0001（缓存命中时更低）。用户每天打开 3 次，月成本约 $0.009/用户，几乎可以忽略。
