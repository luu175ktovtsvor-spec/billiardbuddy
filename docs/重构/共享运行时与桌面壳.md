# 共享运行时与桌面壳

> 施工状态：仅定义三个领域实际共用的窄边界；完整裁决见 [目标架构与施工顺序](./00-目标架构与施工顺序.md)。本模块不另造通用项目或任务系统。

## 这个模块解决什么

这是三条工作面共用的最小地基，不是另起一套万能工作流框架。用户打开桌面应用时，应当只看到 BilliardBuddy：明确的项目、任务或作品位置，正在运行的事情，以及可验证的成果。Renderer 不保存业务最终事实，也不持有 provider 凭据。

## 领域边界

共享运行时只拥有以下能力：

1. Electron Main、preload、受控 IPC 与本地 Product Server 的启动、关闭和错误呈现；
2. 安装身份、安全存储、能力状态、用户权限和远程能力访问；
3. 操作身份、幂等回执、结果检查点、取消、超时、资源释放、诊断和重启恢复；
4. `ProcessBroker`：受控进程的启动、输入/输出、退出与完全关闭生命周期；
5. 可追溯的附件、资产与导出成果引用；
6. 桌面导航、标签页、窗口恢复、通知、主题和无障碍的视图状态。

它不拥有 Agent 的会话/回合，也不拥有图片的画布/候选或视频的时间线/渲染。这些事实分别留在三个工作面。

模型额度、Gateway/Relay、个人 Key 与协议适配的边界见[模型与远程能力平台](./模型与远程能力平台.md)。该平台只提供受控远程能力，不成为泛化业务引擎。

## 单一事实来源

| 事实 | 最终拥有者 | Renderer 的职责 |
| --- | --- | --- |
| 本机服务和受控能力 | Electron Main 与本地 Product Server | 请求状态、展示修复入口 |
| 有副作用的操作 | 对应领域服务的持久记录与回执 | 发命令、订阅快照和事件 |
| Agent 运行 | Agent 工作台自己的 Thread / Turn / Run 账本 | 渲染活动、审批和结果 |
| 图片作品 | 生图工作台的图片项目 | 渲染画布和版本 |
| 视频作品 | 视频工作台的视频项目 | 渲染时间线和预览 |

任何跨 IPC、HTTP 或 Worker 的变更命令必须有操作身份；任何可恢复异步任务必须能给出已接受、运行、等待用户、成功、失败、已取消、结果未知或需要恢复中的准确终态。不能用前端临时变量、模型文本或进程是否还活着代替该终态。

共同运行时只提供统一机制：`intent -> in_flight -> result_obtained -> domain_checkpointed -> completed`。业务服务必须在把自己的 Item、候选、资产或渲染结果持久化之后才确认操作完成；检查点之前的中断一律保留为 `outcome_unknown` 或可证明未执行的终态，绝不由运行时替领域静默重试。

## 正式边界

```text
Renderer
  -> 受控 IPC / 本地 HTTP 命令
Electron Main
  -> 受限宿主能力、秘密存储、sidecar 生命周期
Local Product Server
  -> 领域状态、操作回执、事件投影、恢复与诊断
Private Worker / FFmpeg / 浏览器等执行者
  -> 受能力与权限约束的实际执行
Gateway / Relay
  -> 托管远程能力、容量、用量和异步结果，不保存本地项目真相
```

官方 Codex 的 App Server 与 exec-server 也采用“会话/回合”和“进程执行”分层：进程句柄是逻辑身份，进程启动、输出、退出和完全关闭是不同事件。BilliardBuddy 只吸收这个边界，不移植其 Rust/CLI 运行时。

私有凭据不得进入 renderer、浏览器可见 WebSocket、任务提示词、日志或模型启动的子进程环境。平台托管能力必须经过 BilliardBuddy 服务；用户主动选定的个人 Key 只在本机服务中直连上游。

## 完成条件

- 桌面壳可恢复窗口和工作面，且只展示服务真实状态；
- 本地服务只监听受控本机地址，崩溃、启动失败和能力不可用都能给出可执行说明；
- 三条工作面都通过自己的领域 API 写入事实，Renderer 没有第二份持久 Store；
- 跨进程动作可取消、可追踪，且启动、输出、退出和关闭的状态不会互相冒充；
- 外部效果只有在领域检查点落盘后才被确认，重启后可恢复或明确标为结果未知；
- 任一模块替换内部实现时，不需要把其业务状态强塞进另一个模块。

## 实施次序

这个模块只在某个工作面确实需要共享边界时改动。不得为了“先搭地基”而暂停用户可见的 Agent、生图或视频旅程，也不得引入没有正式消费者的通用抽象。
