# 模型资源治理分层

## 结论与适用范围

本文件冻结 BilliardBuddy 的**托管模型资源治理**。它解决的不是「把多少人塞进一台服务器」，而是让每一次受管调用在正确的信任边界内被识别、准入、计费、调度和审计：

```text
Agent / 图片建议
  -> Gateway：鉴权、可信 owner、额度账本、准入和路由
      -> 文本 Provider

图片 Sidecar
  -> Image Relay：图片生成 / 编辑任务
      -> Gateway 内网 introspection：只鉴权并解析可信主体
      -> 图片 Provider

视频 Sidecar
  -> Video Media Relay：视频任务 API、媒体/OSS/长 ASR
      -> Gateway 内网 introspection：只鉴权并解析可信主体
```

以下事实在任何实现中都不得混淆：

| 概念 | 它回答的问题 | 不能替代什么 |
| --- | --- | --- |
| 共享模型目录 | 产品提供什么非敏感能力 | 账号、密钥、额度或实时可用性 |
| 物理账号 | 哪一组真实 Provider 凭据和限制承担上游调用 | 用户的额度归属 |
| 调度 owner | 谁在竞争同一物理账号的有限执行能力 | 可伪造的请求字段 |
| 额度 owner | 哪个可信产品主体消耗、退款或查询额度 | Provider 账号或调度队列 |
| API Key | 哪个最小进程可代表主体向上游认证 | 配置、日志、Renderer 或跨服务传递 |

Gateway、Image Relay 和 Video Media Relay 都不是 Agent、Thread、图片 Project 或视频 Timeline 的状态所有者；这些领域事实仍由本地 Rust Core 或各自的本地领域服务保存。本文件只定义远程能力的治理层。

## 1. 共享模型目录：公开能力，不是密钥注册表

共享模型目录是版本化、可审计的非密钥产品契约。每个条目至少包含稳定 `model_id`、展示信息、协议/能力、支持的工作负载、输出限制、弃用状态，以及路由所需的逻辑 `capacity_pool` 与 `quota_bucket`。它可被桌面 UI、Gateway、任务提交器和运维校验共同读取；不同消费者只能投影自己需要的字段。

目录**不得**包含 Provider API Key、Bearer token、Relay 地址、私有账号标识、区域、余额、实时限流值、可用于推断秘密的错误详情，或任何用户个人 Key。真实 endpoint、凭据引用、账号健康和临时熔断属于受限的部署配置与账号绑定，不属于目录。

目录条目只声明「可选择且语义兼容」，不承诺调用当下必然成功。Gateway 在鉴权后结合账号执行准入；目录可见不等于账号有余量、用户有额度或服务可用。个人 Key 的模型发现仅是本机临时能力发现，绝不反向写入共享目录。

目录中的 `capacity_pool` 和 `quota_bucket` 是不同的稳定产品逻辑名。一个 `capacity_pool` 在**同一配置版本**只能绑定一个执行账户及其唯一凭据引用；多个语义兼容的子模型可共享该池，由同一物理账户调度。池的改绑是显式、版本化的迁移：新旧绑定不得在同一版本内并存，必须记录生效版本、账户引用与原因。`quota_bucket` 只定义产品侧的结算分类与额度政策，不等于、也不得拿来充当并发池；一个额度桶可以覆盖多个容量池，一个容量池也可按不同产品规则写入不同额度桶。

## 2. 两条不能合并的治理轴

### 2.1 执行准入按物理账号

Provider 的并发、RPM、TPM、日限额、重试预算和异常熔断都由**物理账号**承担，因此执行准入必须以物理账号为原子单位，而不是以模型名、产品页、用户自报身份或 Gateway 实例为单位。一个请求先从目录得到逻辑池，再由受限账号绑定解析到可执行账号；没有健康且合规的账号时，返回明确的可重试/不可重试拒绝，绝不暗中换到语义不同、价格不同或权限更高的模型。

每个物理账号的调度器必须同时执行：

- 上游速率与并发上限、每类工作负载的保留/上限和重试预算；
- 有界等待时间与有界队列，取消、超时和客户端断开立即释放未执行占位；
- 以验证后的 `scheduler_owner` 做轮转公平队列，并限制一个 owner 的在途加排队总量；
- 已入队项目不被新请求无条件插队；暂时不具备条件的队首不应永久阻塞其他可执行 owner；
- 请求获得许可、真正开始、失败、取消和完成均有一次且仅一次的释放路径。

`scheduler_owner` 从安装凭据的验证结果派生：Gateway 自己执行的短模型请求直接验证安装 bearer；图片和视频任务分别由对应 Relay 将同一短生命周期安装 bearer 送到 Gateway 私网 introspection 后取得。不得信任客户端 body、`X-*` owner 头、模型输入中的 user 字段或 Relay 自己声明的 owner。两个 Relay 调用 introspection 使用各自独立的 service audience 与 service token；该 service token 不得下发给 Sidecar，安装 bearer 也不得缓存为 Relay 任务事实。

公平的目标是防止一个受信安装或服务压垮共享账号，并不保证相同响应时延，也不以一个人连续开多个窗口获得更多份额。Provider 已接收的请求是否可取消取决于其协议；本地释放许可不应谎称撤销了不可撤销的上游费用。

并发采用“**配置外置、算法共享、执行点守门**”，而不是再增加一个中央并发服务器：

- 所有并发、RPM、队列、等待时间和单 owner 上限只在各服务的 capacity policy 中解析，可通过受控部署配置调整，业务 handler 不写第二套数字；
- 公平排队、取消、超时和许可释放由共享 admission kernel 实现；Gateway、Image Relay、Video Media Relay 只在自己真正调用 Provider 的最后边界获取许可；
- Nginx 只限制连接、请求体和基础入口速率，不能替代按账号、模型 workload、owner 和付费状态的应用层准入；
- 当前单实例不增加网络跳转或中央单点。只有进入多实例阶段，才在不改业务 API 的前提下把同一 admission 接口换成带租约和 fencing 的全局协调实现；每个执行进程仍保留本地硬上限作为最后保护。

### 2.2 额度账本按可信边界

额度回答的是「谁应被扣减/退还和谁可看到余额」，不是「哪个 API Key 被调用」。账本 owner 必须从 Gateway 完成的安装认证、订阅/租户授权或受限服务身份中派生，形成不可由请求改写的 `quota_owner`；跨 owner 不得共享余额、历史或幂等结果。

账本是唯一的额度事实来源，至少记录：授权来源与版本、`quota_owner`、逻辑 `quota_bucket`、请求幂等键、保留/实际结算/释放金额、可审计时间戳、失败原因类别和关联的匿名化调用回执。它以原子操作保证同一幂等键不会重复扣费；长 SSE 或异步任务先做可覆盖最坏成本的保留，完成后按已知用量结算，取消、拒绝和未开始调用释放未消费保留。上游用量未知或结算不确定时，账本保留为待核对状态，而不是静默免费或重复扣减。

物理账号的费用、Provider 余额和账本 owner 的产品额度可以有关联，但它们不是同一张表、同一个主键或同一个回滚动作。账号切换不会搬走用户余额；一个用户的余额耗尽也不等于物理账号失效。账本不可用时必须拒绝新的受管付费调用并保留可重试语义，不能以仅记录日志的方式绕过额度。

## 3. API Key 的最小进程归属

密钥只交给发起相应上游认证所必需的最小受信进程，并且按来源分开：

| 密钥类别 | 唯一可读取明文的进程/位置 | 明确禁止出现的位置 |
| --- | --- | --- |
| 用户个人 Provider Key | Electron Main 的系统安全存储；仅本机短生命周期凭据代理在转发时使用 | Rust Core 持久配置、Renderer、Sidecar、Gateway、Relay、日志、崩溃报告 |
| 托管文本 Provider Key | Gateway 的受限部署密钥存储 | 桌面安装包、Renderer、Rust Core、Sidecar、Image/Video Relay、公开配置 |
| 图片 Provider Key | Image Relay 的受限部署密钥存储 | Gateway、桌面端、Video Media Relay、共享目录、日志 |
| 视频媒体/分析 Provider Key | Video Media Relay 的受限部署密钥存储 | Gateway、桌面端、Image Relay、共享目录、日志 |
| Image Relay 到 Gateway introspection 凭据 | Image Relay 与 Gateway 各自受限存储；只验证图片 audience | Renderer、Sidecar、Video Media Relay、长久化任务结果 |
| Video Media Relay 到 Gateway introspection 凭据 | Video Media Relay 与 Gateway 各自受限存储；只验证 introspection audience | 视频 Sidecar、Image Relay、Renderer、长久化任务结果 |

这里的「最小」指密钥的读取权和明文生命周期，而不要求把每次请求拆成更多进程。Gateway 可代替客户端向托管文本上游认证，Image Relay 与 Video Media Relay 只向各自 Provider 认证。任何进程若只需要请求能力，应拿短期限、最小 audience、可撤销的 capability，而不是原始 Key。所有日志、错误、追踪、任务持久化、转储和指标必须脱敏，并在测试中覆盖拒绝泄漏。

## 4. 服务职责与禁止复用的路由

### Gateway

Gateway 是 Agent、通用视觉/媒体推理与图片建议的短模型入口：验证安装身份，派生可信 owner，查询目录投影，检查账本，并在实际 Provider 调用前获取所属物理账号许可。它还为 Image Relay 与 Video Media Relay 提供仅限内网调用、按 audience 隔离的 introspection。Gateway **不代理**图片/视频任务 API、图片或视频字节、结果轮询、取消、ACK、OSS、长 ASR 或 Relay 的 Provider 调用；也不保存 Agent 会话、媒体项目事实、大型媒体字节或 Relay Provider Key。

托管文本的正式入口是 `/v1/responses`。个人 Responses/Chat 仍经本机代理，绕开平台账本与托管账号，不得借由 Gateway 伪装成托管请求。

### Image Relay

Image Relay 由图片 Sidecar 直接调用，只接收图片 **generate/edit** 异步任务。每次受保护请求都把安装 bearer 送到 Gateway 私网 introspection，并只使用返回的可信 owner；它不接受客户端自报 owner。Image Relay 拥有图片上游账号的执行准入、Provider 调用、任务状态和短时签名结果交接。图片候选、CAS、项目、Candidate Group、Canvas 与 ACK 后的领域事实仍属本地图片 Sidecar。公开正式契约为：

```text
POST /v1/images/tasks
GET  /v1/images/tasks/by-idempotency/:key
GET  /v1/images/tasks/:id
POST /v1/images/tasks/:id/cancel
POST /v1/images/tasks/:id/ack
```

`by-idempotency` 只查询同一内省 owner 已持久化的远端任务，用于提交响应丢失后的恢复；404 不构成再次 POST 的许可。只有本地能够证明从未进入提交边界的 operation 才可执行首次 POST。

### Video Media Relay

Video Media Relay 由 Video Sidecar 直接调用其独立的**视频任务 API**，承接受控远程分析、转写或渲染协作；素材、编辑方案、时间线版本、预览、导出和恢复记录仍属于本地视频领域。请求到达后，Relay 仅调用 Gateway 内网 introspection，验证 Video Sidecar 身份并解析不可伪造的 `scheduler_owner`、`quota_owner` 与授权事实；Gateway 不在该路径中转发媒体、OSS、长 ASR 或 Provider 响应。Relay 随后使用自己的 Provider 账号绑定、容量池、任务类型白名单、结果验证和结果交接协议完成工作。视频任务 API 的具体路径以 `docs/operations/production-servers.md` 的实测部署记录为准，在未部署前不得在本文件臆造新路径。

路径文字相似不代表语义可复用。图片与视频**不得**共享 `/v1/images/tasks`、同一个「泛媒体 task」schema、同一 Provider credential、同一结果对象或无类型的 `/media` 路由；也不得把一个 Relay 的服务凭据当作另一个 Relay 的凭据。迁移期可以由明确的领域适配器服务旧客户端，但视频 Sidecar 的正式新写入直接调用 Video Media Relay；适配器必须显式映射领域类型和目标 Relay，禁止让客户端用可选字段决定去图片还是视频。

## 5. small 档位的容量承诺

small 是一档产品运营规模，不是任意固定在线人数的承诺。用户数不能推出并发、token、图片数量、视频长度、区域延迟或 Provider 限制；以静态人数作为架构目标会掩盖真实瓶颈。

small 档位按以下可观测、可调的契约运营：

- 每个物理账号配置且校验自己的并发、速率、队列、最长等待、单 owner 占用和预算阈值；
- 每个逻辑配额桶配置用户可见的产品额度与拒绝/恢复文案；
- 以真实混合负载逐步设定上线值，观察队列等待、拒绝率、上游错误、账本差异、成本和恢复时间；
- 队列或额度触顶时快速、诚实地拒绝或要求稍后重试，而不是无限等待、偷偷降级或把负载转移给其他领域；
- 扩容以实际容量、成本和服务目标为依据；任何对外数字只在对应账号、区域、工作负载和测量窗口中给出。

因此，small 的验收是「治理能在一组明确的有限账号和预算内稳定地保护公平、费用与失败边界」，而不是通过制造空请求获得营销数字。

## 6. 从单实例到多实例

第一版可以由单个 Gateway 实例维护每个物理账号的内存调度器，但必须从第一天就把目录、账号绑定、账本、幂等键、owner 和回执设计成可持久化、可审计的边界。单实例的内存队列不是恢复事实：进程重启后客户端通过相同幂等键查询或重投，账本和 Relay 任务状态决定结果，绝不把「内存中可能执行过」误报为成功。

在以下任一事实出现前，不提前为了「理论扩展性」拆分：单实例经过垂直扩容仍无法满足已测负载；需要跨故障域可用；或单实例维护窗口已不能接受。达到门槛后按此顺序演进：

1. 将目录与账号绑定发布为版本化受限配置，将额度账本和幂等记录迁入具备原子条件写能力的共享持久存储；
2. 将每个物理账号的并发许可、速率令牌和公平 owner 队列变成全局协调的原子操作（例如带租约、超时和 fencing 的专用协调存储），使多个 Gateway 或同领域 Relay 不会同时发放同一账号的容量；
3. 让 Gateway 与各领域 Relay 的实例无状态地接入该协调层，保持 owner 推导、账本语义和公开 API 不变；队列中断仍依靠幂等查询/重投恢复；
4. Relay 按领域独立扩展。扩大 Image Relay 不得扩大 Video Media Relay 的 Provider 限额，反之亦然；每个实例只能持有被分配账号的最小凭据。

在第 2 步完成前，禁止把同一物理账号的受管流量以多活 Gateway 方式无协调地负载均衡。多实例不是复制内存限流器，也不是把一条请求随机路由到任何账号。

## 7. 实施、合并和部署顺序

以下顺序是依赖顺序，不是对旧名称或现有实现形状的承诺。每一步都须在其真实生产调用链上验证失败路径；不能以接口存在、单元测试或模拟 Provider 代替。

1. **契约先行。** 落地共享非密钥目录、目录投影、账号绑定配置和 owner/账本/任务的类型边界；个人 Key 路线保持本机隔离。验证目录不含密钥，未知/弃用模型和不兼容工作负载被拒绝。
2. **Gateway 治理。** 实现可信身份派生、原子额度保留/结算/释放、Gateway 所属短模型的物理账号调度，以及供两个 Relay 使用的内网 introspection；验证同幂等键不重复扣减、不同 owner 公平、取消/超时释放、账本故障 fail closed，且 Gateway 不接收图片或视频任务/媒体流。
3. **图片边界收口。** 让图片 Sidecar 直连 Image Relay；Relay 只接受图片正式路由，并以独立 service credential 回查 Gateway 身份；验证 generate/edit、重复投递、短时结果 URL、结果 ACK 和本地事务失败后只重试 ACK 的链路。
4. **视频边界独立。** 新建 Video Media Relay 与独立视频任务 API、schema、账号绑定和 introspection audience；验证 Video Sidecar 直连 Relay、Relay 仅向 Gateway 内网 introspection、Gateway 不代理媒体/OSS/长 ASR，且图片请求不能抵达视频 Relay，反之亦然。
5. **small 运营验收。** 用有限、真实的账号配置进行混合负载、故障、重启、账本核对和预算观察；写入明确的上线限制与告警，不给出静态人数结论。
6. **按事实扩容。** 只有达到第 6 节门槛才引入共享协调层和多实例，再以故障切换与全局容量不超发作为发布门槛。

每个阶段应独立合并且可部署：契约与使用它的实现同一变更合并；任何新增/废弃路由、账本语义、密钥归属、Relay 拆分或扩容步骤，都必须在同一批次更新以下文档，使文档描述的正式路径与部署一致：

- `docs/重构/模型与远程能力平台.md`：模型入口、Gateway 与 Relay 的产品边界；
- `docs/重构/生图工作台.md`、`docs/重构/视频工作台.md`：各自领域的提交与结果交接边界；
- `docs/operations/production-servers.md`：真实服务拓扑、路由、健康检查、密钥挂载、部署/回滚与 smoke；
- `docs/重构/迁移与发行.md`：客户端升级次序、旧端点读取/适配退出条件与正式发行验证；
- 共享契约中的版本/弃用说明：客户端与服务端兼容窗口。

现有把「Relay」泛指图片和视频的表述仅可作为迁移兼容描述。只有当生产部署、正式 API、凭据 audience、告警和上述文档都已分离，才可宣布最终分层完成。

## 8. 完成证据与非目标

完成不是目录文件或队列类出现，而是至少具备以下证据：

- 从安装认证到 `scheduler_owner`、`quota_owner` 的不可伪造映射，以及跨 owner 隔离测试；
- 同一物理账号下多 owner 的公平、有界队列、取消、超时、Provider 失败和一次释放的端到端证据；
- 账本保留、结算、释放、幂等重放、未知用量和账本不可用的可审计记录；
- 目录、日志、任务持久化、公开健康/指标投影和桌面包均无不应出现的 Key/Relay secret；
