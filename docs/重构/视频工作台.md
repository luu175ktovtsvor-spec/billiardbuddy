# 视频工作台

视频是 BilliardBuddy 自研领域，和 Codex Agent、图片画布分别拥有独立状态。

面向普通创作者的入口、LLM/Agent 分工及本轮产品反向审计见
[通用视频工作台产品架构](./通用视频工作台产品架构.md)。该产品层不放宽本文件的
素材、权限、预算、Version 或交付合同。

## 后端边界

视频领域拥有素材指纹、探测元数据、转写/视觉证据、编辑方案、时间线版本、预览、渲染、导出和恢复记录。正式服务在 `ts/src/server`；FFmpeg/FFprobe 或同类本机工具执行媒体处理。

```text
导入素材
  -> 探测与证据
  -> 可编辑时间线版本
  -> 预览或渲染操作
  -> 校验后的导出文件
```

模型可以提供带来源的理解或建议，但不能替代真实素材、时间线版本、预览和导出文件。进程退出也不等于成功：输出必须存在并通过媒体元数据与 hash 校验。

## 15.1 视频领域组合根

视频 API 仍接受 `VideoWorkbenchService`，但它仅是 API 兼容门面。正式实例必须由 `createVideoWorkbenchCompositionRoot()` 组合，门面不得重新创建 Repository、Relay client、FFmpeg runner、项目 mutation map、预览/渲染队列或恢复状态。

```text
createVideoWorkbenchCompositionRoot
  -> VideoProjectStore (one SQLite repository and one local mutation coordinator)
  -> ProjectAssets (project shell, source lifecycle, migration reader)
  -> AnalysisIndex (facts, consent/budget, analysis Operation handles)
  -> Editorial (CommandSet-only Timeline Version chain)
  -> FinishingDelivery (Variant Version, Plan, preview/render handles, quality publication)
  -> VideoWorkbenchService (API compatibility facade only)
```

- `VideoProjectStore` is the sole in-process Project read-modify-write coordinator and exposes the one SQLite repository. Its promise map is scheduling only; Project, Fact, Timeline, Variant, Operation, Event cursor and recovery truth are all durable SQLite records.
- `AnalysisIndex` owns only in-memory analysis/fingerprint handles. `FinishingDelivery` owns only preview/render handles and the serialized encoder tail. They are reconstructed from durable Operations on restart and never create a second recovery journal.
- `Editorial` continues to route legacy timeline selection, scene locking and alternative application through typed `CommandSet`; no application may directly create a legacy Timeline projection. `FinishingDelivery` only executes a frozen formal Delivery Variant Version and ExecutionPlan.
- v2 Timeline 条目可带持久化 `linked_av_group_id`。单侧 `split` 会在同一 CommandSet 内联动
  视频和源音频，单侧 `lock` 会锁定整个 A/V group；`trim`、`reorder`、`replace` 仍须
  显式提交两侧，否则一致性校验失败关闭。这样 AVSplit 关系不会随重启或版本回退退化为
  “相同范围猜测”。
- The internal runtime is an implementation port shared by the four applications during this transition. It is not an API service and must not be constructed by server startup code. Low-level fault-injection tests target that runtime explicitly so provider/recovery methods cannot grow back onto the façade.

### 创作与快速创建 API

`Editorial` 还拥有交付意图、范围取舍、Outline/Chapter/Global Review、Quick Create 和 Creative Proposal。`PUT /delivery-intent` 持久化 `natural`、`target` 或 `exact` 意图；`POST /range-decisions`、`/editorial-plans`、`/quick-create`、`/creative-sessions` 及其 message/reject 子路由均要求 `Idempotency-Key`，以 Project 内的不可变 receipt 回放首次资源。创作会话的普通 `messages` 只保存用户备注；只有显式调用 `POST /creative-sessions/:sessionId/suggest` 才会启动证据约束的 `video.analyze` Operation，并把 `creative_session_id` 和安全进度返回给工作台。该 Operation 仍只产生 Evidence/Draft，不能直接写 Timeline/Version；相同幂等键会返回首次 Operation，即使 Project revision 已因证据落库而前进。面向普通创作者，`Creation Brief` 的 `story_structure`、`selection_focus` 与 `creative_direction` 先把 Content Segment 排为可解释的 Storyboard Candidate；`Scene` 只是随后编译出的剪辑装配，并保留 `content_segment_ids`。Quick Create 只创建 1–3 个 Timeline Draft；没有真实取舍差异时只返回一个并说明原因，永远不推进正式 Timeline。`creative_direction` 默认原声优先；旁白必须标为待用户复核，不能由模型或模板静默覆盖用户声音。

Creative Answer/Search Response 只读；带 Draft 或 typed CommandSet 的 Proposal 仍要经 `/creative-proposals/:id/accept` 调用同一个 `applyCommandSet`。Proposal 的接受、旧时间线选择、场景锁定和备选应用不存在第二个 Timeline writer。新 Source 完成的只有本地摘要会留下“规划可更新”记录，不会自动重写已接受版本；任何更深远程分析仍先检查该 Source 的 consent/budget 范围。

普通分析入口 `POST /analyze` 会先创建可恢复的 `video.analyze` Operation，再由同一条链生成 `video.plan` 和 Timeline Draft；它不绕过 Brief、Evidence、Host 校验或用户确认。Draft 与 Operation 都保留规划来源：`provider` 表示已收到并校验 Provider 结果，`local_conservative` 表示本地保守编排，历史记录无法证明来源时显示 `unknown`。这些字段只用于审阅透明度，不是 Timeline 写入权；只有接受 Draft 后的 CommandSet 才能创建正式 Version。

## 远端媒体边界

```text
Video Sidecar
  -> https://zzyppz.cn/video-media/v1/video-media/operations
  -> Video Media Relay
      -> Gateway 私网 /internal/v1/auth/introspect（只验身份）
      -> 北京 OSS / DashScope（媒体与模型执行）
```

Gateway 不代理视频 operation、OSS 字节、长 ASR 轮询或 Provider 结果。Video Media Relay 持有唯一的 DashScope/OSS 凭据，保存短期 object lease、operation、物理账号额度保留、receipt 和清理状态；它不保存 Project、Source Fact、Transcript 修订、Timeline Version 或 Export 事实。

Qwen 视觉、Qwen 规划、Fun-ASR 和 Embedding 可共用同一个 `video-dashscope-account` 逻辑容量池；受限部署配置以 `VIDEO_MEDIA_DASHSCOPE_ACCOUNT_REF + VIDEO_MEDIA_DASHSCOPE_ACCOUNT_BINDING_REVISION` 将其绑定到版本化物理账号。Video Media Relay 必须使用分 workload lane 的公平有界准入，并与 `video-relay.account` 产品额度分开；更换物理账号保留旧账号账本，不把历史额度写到新键。长 ASR 和 OSS 任务是持久 operation，进程内队列只是执行机制，不是恢复事实。

每个已认证安装默认可使用托管视频远程分析，无需先配置 DashScope 或 OSS Key。Video Media Relay 的 owner / 平台日额度耗尽只投影为 `MEDIA_VIDEO_PLATFORM_QUOTA_EXHAUSTED`，不会禁用 Agent 或图片；视频项目自身的确认预算耗尽则是不同的 `MEDIA_VIDEO_PROJECT_BUDGET_EXCEEDED`。队列、对象租约、上传超时和 Provider 短暂故障仍是恢复/重试问题，不能借 429 混成“今日视频额度已用完”。

每次远程分析先按 `video-remote-usage-v2` 策略写入逐 Operation 的正数费用与资源预留；预留绑定素材 fingerprint、Evidence revision、Brief/Delivery revision、授权范围和请求模型，不得用零金额占位。规划请求会把用户目标、分析缺口、获准素材目录以及带 `source_id/in_ms/out_ms` 的 Evidence 锚点一并送入固定 Qwen；约束只作不可引用的上下文，模型不能据此伪造 Scene 证据。Provider 返回的真实 usage/金额 receipt 是结算权威；缺少金额或无法确认的终态保留为 `outcome_unknown`，不能静默按免费调用或释放预算。

Sidecar 到北京 OSS 的字节传输属于独立 transport policy，不与模型目录、Provider 并发或用户额度混写。`BB_VIDEO_MEDIA_UPLOAD_TIMEOUT_MS`、`BB_VIDEO_MEDIA_UPLOAD_RETRIES`、`BB_VIDEO_MEDIA_CONTROL_TIMEOUT_MS` 和 `BB_VIDEO_MEDIA_RESULT_TIMEOUT_MS` 可在桌面运行环境外部调整；跨境分片上传默认单次 240 秒、上限 300 秒。任何超时都先按同一 lease 通过 HEAD/ListParts 对账，再决定是否续传，禁止把未知结果当作普通失败盲目重传。

视频任务不得复用图片 `/v1/images/tasks`、Image Relay token、图片结果对象或泛 `/media` schema。共享治理契约见 [模型资源治理分层](./模型资源治理分层.md)。

视频工作台的“主素材”与“项目资产”是两层边界：`addVideoSource` 只导入并探测真正含有视频流、原始 `primary_video_stream.duration` 和颜色事实的视频文件；PNG/JPEG/WebP 不能伪装成主视频。图片可以作为经过哈希、provenance/license 声明的 `project_asset`，绑定到 `overlay` 轨做 logo、角标、贴纸或画面覆盖，编译器以 `-loop 1` 将静帧延长到冻结时间线范围；音乐和用户确认后的旁白通过 `POST /api/videos/projects/:id/assets` 导入受管项目资产，独立保存完整哈希、音频 PTS、MIME 与许可事实，再由同一条 CommandSet 插入 `music`/`voice_over` 轨。`set_audio_policy` 会创建新的不可变 Export Profile Revision；未被用户选择的音轨不会被静默丢弃。图片工作台的生成/编辑不会被视频时间线隐式调用。该边界由 `videoFinishingDelivery.test.ts` 的多轨资产合同测试、HTTP 资产导入回归和真实 FFmpeg overlay 成片共同验证。

交付 Profile 支持常见 1080p 与 UHD 4K：横向 `1920×1080` / `3840×2160`，竖向 `1080×1920` / `2160×3840`。尺寸、偶数像素、编码器、色彩和输出 hash 仍由同一预检/输出验证链约束；低分辨率源放大到 4K 时必须在质量报告中明确标记，不会伪称为原生 4K。

### 素材输入与导出选择

素材获取不是模型生成步骤。用户可以从本机文件选择器加入自有拍摄、屏幕录制或已获授权的素材，也可以分别导入 B-roll、图片覆盖、音乐和旁白；主视频必须真实含有视频流，图片不能伪装成主视频。工作台不要求用户先理解编码：导入后由 FFprobe 读取实际容器、视频/音频流、PTS、旋转、颜色和原始主视频流时长，扩展名只用于展示 MIME，内容事实不以文件名为准。常见输入容器包括 MP4、MOV、M4V、WebM、MKV、AVI、MPEG/TS、3GP、OGV、FLV 和 MXF；无法读取、没有所需流或事实不完整时失败关闭，不静默转成“可用素材”。

用户需要确认的是成片交付，而不是每个输入编码参数：

- 画幅与分辨率：竖屏/横屏 1080p 或 UHD 4K（分别对应 `1080×1920`、`1920×1080`、`2160×3840`、`3840×2160`）。4K 是目标输出尺寸，不代表原片是原生 4K；放大会在质量报告中明确标记。
- 导出格式：默认且最通用的是 MP4 + H.264 + AAC；需要后续专业调色/剪辑时可选 MOV + ProRes 422 + PCM，或 ProRes 422 HQ + PCM。输出容器、编码、像素格式和音频采样率会写入冻结 Profile 并由实际文件验证。
- 高级选项：帧率（首版白名单）、字幕（不烧录、烧录、SRT/VTT sidecar）和音频策略。普通用户可使用预设，系统负责旋转归一化、缩放/裁切或留白、帧率转换、色彩处理与音频重采样；这些处理不能改写原始素材事实。

## 字幕烧录运行时

正式 Linux Video Media Relay 镜像内置 `ffmpeg`、`libass`、`fontconfig` 和经审查的 `Noto Sans CJK SC` 常规字形。字体不会从宿主机字体注册表或未声明的回退字体中发现：镜像将唯一可用于烧录验证的文件复制到 `/app/runtime-assets/fonts/NotoSansCJKSC-Regular.ttc`，并为该目录生成 application-owned fontconfig 缓存。

Relay 启动时先验证 `subtitles` 过滤器、`Noto Sans CJK SC` 到该受控路径的解析结果，并用 `fontsdir=/app/runtime-assets/fonts` 对包含 CJK 字符的一帧视频执行真实 libass 烧录。任一步失败，入口命令不会启动 Relay，因此也不会接收对象租约或 Provider 操作。受控 production smoke 应保留该启动检查的容器日志与 `readyz` 成功记录；它不需要 DashScope 或 OSS 凭据。

Video Sidecar 仍是 Project、Timeline 和渲染操作的唯一 writer，Relay 不因此取得编辑状态写入权。任何运行在该受控 Linux 环境中的烧录命令都必须显式传入同一 `fontsdir`，并且只能引用视频执行计划中允许的字体族；缺少受控字体、错误字体族或不支持 `subtitles` 的 FFmpeg 构建均按失败关闭处理。

## 第 5 关：完成、交付与质量合同

第 5 关只在视频领域增加可追溯的完成与交付事实；它不把转写、模型回答或界面缓存当作成片事实。字幕、构图、音频、节拍、交付变体和质量报告都属于同一个 Project 的不可变资源，任何一次应用都会通过 `CommandSet` 生成新的正式 Timeline Version 或 Delivery Variant Version。旧接口、草稿或缓存不能绕过这条版本链。

### 字幕、构图、音频与节拍

- 字幕文档修订是交付投影，不会回写或篡改 ASR/Transcript Fact。Cue 必须绑定不可变的 Transcript/Segment（必要时 Word）锚点，并且落在冻结时间线范围内。指定的 Transcript Revision 读不到、跨项目、已变化，或翻译结果缺 Cue、错锚点、拉伸范围时，均拒绝生成或应用候选，不能退回“当前版本”。
- 远端字幕翻译只有 `caption_translation` 的严格结果信封；Relay 只接受与原 Cue ID 一一对应的译文。该调用必须已有同一素材范围的 consent、预算确认、对象租约和 Provider receipt，失败、未知结果或恢复记录不一致时保持 Operation 可恢复/失败关闭，绝不以规划文本冒充字幕结果。
- 字幕交付只允许明确的 `set_caption_revision`。旧式 `caption_document` 时间线轨道不是第二条字幕写入源，会在编译前拒绝。烧录字幕使用冻结 Cue、样式和受控字体目录；sidecar 则连同格式、字节数和 hash 被输出校验绑定。sidecar 预览也必须从同一冻结 Plan 生成，并只以经项目、preview asset 与 hash 校验的受控资源端点提供，绝不向 Renderer 返回本机临时路径。
- 构图计划只提出可审阅的 Delivery Variant Command；主体跟踪不足、事实范围不全、锁定条目或未解决范围必须在计划中显式留下 `unresolved_ranges`，不能静默改镜头。暂未编译的命令（例如 bezier 关键帧）在 CommandSet/编译阶段失败关闭；已支持的 hold、transform、音量、降噪和淡入淡出必须进入同一执行计划。
- 音频计划以本地测量收据为基础，保存响度、真峰值、静音范围和 ducking 意图。语义静音剪辑必须带 Transcript 锚点；没有锚点的历史建议降级为“不建议”，不能成为盲剪。读取原始音频流、Fact 或 PTS 边界失败时不能推断默认流或默认起点，必须拒绝编译。旁白不是隐式 TTS 授权：必须先有用户导入并确认的 `voice_over` 资产，随后由明确的 `set_audio_policy` 选择 `voice_over_with_source`、`voice_over_only` 或包含音乐的组合策略；执行计划会把所有未选择但仍存在的音轨判为错误。
- 工作台当前把“旁白风格”和“实际音色”分开：Creation Brief 的 `voiceover_persona` 只用于叙事建议，交付编辑器现在可以直接选择原声、音乐、旁白的真实组合，并显示项目中已导入的音乐/旁白资产数量和旁白是否已进入时间线。当前没有伪造的 TTS 音色下拉框；要增加可试听的多音色配音，后续只需新增一个受 Video Relay 预算、鉴权、Provider receipt 和生成资产审计约束的语音合成能力，不需要为每种音色重复增加模型。
- 节拍分析使用本地 PCM 证据；Beat Sync 草稿冻结 source fingerprint、evidence basis 和分析器版本。应用时重新核对素材、覆盖范围和 A/V 配对，视频切点会按各自音频 PTS 映射，不能把视频时间戳直接当作音频 seek 位置。

### ExecutionPlan、HDR 与输出验证

`ExecutionPlan` 是预检、预览和正式渲染共同执行的唯一冻结输入。它不仅保存源文件列表，还保存时间线条目的顺序、轨道、位置、源范围、速度、源 fingerprint、视频颜色事实、选定音频流与 PTS 边界、字幕、编码 Profile、映射、滤镜和输出目标。Preview/Render 只能引用已预检的正式 Delivery Variant Version 与此 Plan，不能重新从“当前 head”拼接内容。

- 编译器校验素材边界使用主视频流的真实 duration，不用展示时长；锁定轨道、锁定条目、无效/越界范围、不可用素材和不一致 A/V 映射一律拒绝。
- 输入颜色事实来自 FFprobe 并冻结在 Plan。颜色未知时不能把媒体假定为 SDR；PQ/HLG 要么按 Profile 拒绝，要么在受支持的 FFmpeg 环境中执行真实线性化与 tone-map 到 BT.709 SDR。只改容器/metadata 标签不算 HDR 转换。
- 预检不仅检查领域规则，还以冻结 Plan 构造真实 FFmpeg 参数并探测所需滤镜（包括字幕、降噪、HDR tone-map）；没有可用工具链或滤镜时，不能排队渲染。
- 渲染完成后不信任文件扩展名或进程退出码。输出验证会读取实际 container brand、唯一的视频/音频流布局、视频/音频编码、像素格式、SDR 色彩范围、采样率/声道布局、SAR/DAR、旋转、时长偏差、解码与时间戳证据，并绑定内容 hash。任何一项与冻结 Profile 或 Plan 不符，导出不会发布。

### 预检、后渲染报告与人工发布门槛

质量报告分为 `preflight` 和 `post_render`，均绑定 Project、正式 Timeline/Variant Version、Profile、facts/variant basis 和 ExecutionPlan。报告只记录该阶段确实可做的检查；`passed`、`blocked` 与 `needs_user_decision` 不可互相替代。

- `blocked` 的预检或后渲染报告阻止交付；临时输出和目标导出不能被当成成功版本发布。
- 后渲染出现 warning 且状态为 `needs_user_decision` 时，Render Operation 保持 `committing`，临时媒体与 sidecar 保留，项目仍指向等待确认的冻结 Variant，而不是隐式移动到用户选择的目标位置。
- 人工确认必须明确提交同一 `report_id`、同一输出内容 hash 和报告中完整的 `needs_user_decision` 检查 ID 集合。服务端在发布前重新核对报告、版本、Plan、临时文件 hash 和无 blocked 项；记录不可变 acknowledgement 后才发布。刷新、轮询、重启恢复或 UI 自动重试绝不能代替这一步。

## 第 6 关：桌面产品边界

视频 Renderer 的工作台按项目、导入与授权范围、素材事实、快速创建、编辑、完成与变体、审阅与交付、Operation Center 展示真实视频领域状态。它不是 Agent 对话、图片画布或本地路径浏览器的复用界面。

面向普通创作者的首页额外投影一条只读的引导路径：`导入素材 -> 生成方案 -> 确认时间线 -> 字幕与画面 -> 预览与导出`。引导只根据权威 workspace snapshot、当前 Variant/ExecutionPlan、Operation 和质量报告计算一个“下一步”，不新增写入源，也不替代各领域的 CommandSet、预检或人工确认门槛。素材缺失/变化、事件 reset、后台 Operation 和后渲染质量告警会优先显示对应恢复动作；事实浏览、预算确认、CommandSet 编辑和 Operation Center 仍保留为高级入口。

模板或历史项目只能作为可选参考参数，不能成为普通创作者的必经入口，也不能绕过“用户目标澄清 -> 候选建议 -> 用户确认 -> 正式 CommandSet”这条主路径；任何模板化结果都必须先落为可审查 Draft，再由用户确认后生成新的正式 Version。

当存在 queued/running/committing Operation 时，桌面工作台自动按持久化事件 cursor 续读并显示用户可理解的动作名、当前阶段、状态和百分比；终态或 reset 后停止自动轮询，reset 必须回到权威快照恢复。生成草稿时同时投影已确认的 Creation Brief、候选理由、预计时长和 omissions，候选仍只是建议，只有用户确认后才允许 CommandSet 写入正式 Timeline Version。

候选建议卡还必须显示纳入片段数量、取舍数量、编排依据和模型/事实留下的待确认问题；点击候选卡应默认选中该 Draft 的全部条目，用户再逐项取消即可形成局部接受。不能出现“已选候选但确认按钮仍不可用”的隐式二次选择门槛，也不能把 gaps 静默吞掉后直接写入正式版本。

### 快照与事件续读

桌面端的初次加载和事件 reset 使用 `GET /api/videos/projects/:id/workspace?event_cursor=<n>` 获取单一的安全快照：公开 Project、当前时间线、草稿、当前变体版本、首页事实、字幕/构图/音频/执行计划、质量报告、预览/输出验证、公开 Operation 与事件页。快照不包含本机路径、Relay URL、Provider prompt、密钥、对象签名 URL 或完整 receipt。事实的按 kind/cursor 分页和检索仍走专用只读 API，不能假定初始快照包含所有 Fact。

Operation Event cursor 是持久化续读协议的一部分：客户端必须带回已确认 cursor；服务器返回 `next_cursor` 时才能推进本地游标；返回 `reset_required` 时必须丢弃增量假设并重新取 workspace snapshot，不能继续用旧 cursor 静默漏事件。无效 Facts/Search cursor 必须返回受控的 4xx，而不是 500。

### 正式 Electron 接线的权限原则

视频 UI/Controller 通过一个受控的 `desktop:video:workbench` IPC command union 接到共享 Main/Preload。Main 是唯一可持有视频 UI capability、本机源文件选择结果和导出目标授权的一侧；Renderer 只获得显示名和短期 opaque `selection_id` / `destination_grant_id`，永远不能接收绝对路径、OSS URL、Relay service token、Provider Key 或操作系统权限句柄。

- Main 必须校验 IPC sender、能力、schema、项目归属、grant 用途/MIME/过期时间和一次性/重放规则，再将安全 DTO 转发到视频 API；UI 的按钮禁用不是权限控制。
- Renderer 的创建、编辑、完成、预检、预览、渲染和人工质量确认必须保留 Operation/Version 的真实返回值；调度或生成正式版本的命令带幂等键，不能由本地乐观状态伪造成功或重试入口。
- Review Note、处理事件和 Approval 也走同一个 `desktop:video:workbench` command union。Review 只能锚定冻结 Timeline 的真实时间范围/条目，或绑定到该 Timeline 的 Variant 条目；项目级、素材级或越界锚点均拒绝。Review 本体、处理事件和审批决定分别追加到 SQLite，桌面快照仅投影其当前状态，不能用本地缓存改写结果。
- 原有接受 raw path 的旧视频 IPC 已移除，不得以兼容名义重新引入第二条写入路径。租约与 Main replay receipt 只在当前进程存活期保留；重启后不从磁盘恢复路径，用户必须重新选择素材或导出目标。

## Gate 5/6 部署与真实 smoke（待对应 release 执行）

本节是受控执行清单，不是本次分支已经完成的生产实测记录。既有 Video Media Relay Provider smoke 只证明当时的 OSS/DashScope 基础路径；字幕烧录、ExecutionPlan HDR、交付验证、人工质量确认和正式桌面旅程在改变后必须按下面范围重新取证。

1. 仅从已提交 SHA 打包并发布视频相关 release；记录 release SHA、Video Relay 镜像 digest、`readyz` 的成功结果，以及本次启动日志中的 `video_relay_subtitle_runtime_ready`。不要为此改 Gateway、Nginx、Compose、容量策略或共享部署配置。
2. 使用明确授权、可删除的短测试素材和临时安装 token；若调用翻译/ASR/视觉等真实 Provider，先创建最小 consent 与预算，记录安全的 Operation/receipt 摘要和最终状态，不记录 bearer、DashScope Key、签名 URL、原始媒体或完整 Provider 回执。
3. 覆盖一条 CJK 字幕烧录 Preview/Render、一个受支持的音频/节拍计划、一次预检、一次实际输出验证；如需要覆盖 HDR，素材必须确有 PQ/HLG 色彩事实，并分别证明拒绝策略或真实 tone-map 路径，不能以 metadata 改名代替。桌面 smoke 还须证明 Renderer 只拿 opaque grant，不拿路径。
4. 如需覆盖 `needs_user_decision`，使用经批准的非破坏性 fixture 让报告真实进入等待状态，核对目标文件尚未发布，再由人工显式确认全部告警；若没有实际覆盖此状态，不得在发布记录中把人工门槛标为已 smoke。
5. 结束时 ACK/对账远端操作、删除临时 OSS 对象/租约和本机临时输出（包括 sidecar），复核没有等待确认、未知结果或遗留测试进程。发布记录只保存脱敏日志、检查结果、hash 和清理结果。

### 本地真实 HTTP 端到端演练

`ts/test/videoWorkbenchHttpE2E.test.ts` 会启动临时 loopback HTTP 服务，使用真实 `fetch` 经过视频 API、SQLite Project/Operation/Event 和媒体内容 Range 读取，走完 `Creation Brief -> Delivery Intent -> POST /analyze -> video.analyze/video.plan -> 用户查看建议 -> 用户接受 Timeline Version -> CommandSet 编辑 -> Delivery Variant -> Preflight -> Preview -> Render -> Output Verify`。Provider 不调用公网付费服务，而是使用仓库内真实媒体文件和本地持久化事实；没有 ffmpeg/ffprobe 时，预检必须返回 `MEDIA_VIDEO_FINISHING_UNAVAILABLE`，报告标为 `blocked_by_local_toolchain`，不能伪造渲染成功。`video.analyze` 与 `video.plan` 的公开 Operation 结果还会保存安全的 workflow 阶段、完成单元、当前理解和下一步，桌面据此实时显示“正在做什么/等用户做什么”，不会把建议误投影成已执行。

可复核命令：

```bash
cd ts
VIDEO_E2E_REPORT_PATH="/Users/swl/Desktop/video-workbench-http-e2e-report.md" \
  bun test --preload ./test/setup.ts ./test/videoWorkbenchHttpE2E.test.ts
```

同一测试文件还提供 `VIDEO_E2E_LOAD_CONCURRENCY` 并发的完整用户旅程演练。它用真实 loopback `fetch` 同时建立多个独立 Project，验证 Project/Operation/Event 不串线，并完整走到输出校验；`VIDEO_E2E_LOAD_REPORT_PATH` 可把脱敏结果写到桌面。该演练使用本地确定性 Provider/工具链，不冒充真实 DashScope/OSS 计费结果。生产机上的真实多轮 Provider 旅程由 `deploy/production/video-media-user-journey.ts` 执行，单轮合同 smoke 与多轮用户旅程是两种不同证据。

## 当前前端状态

旧视频前端与旧 Agent 前端已删除。视频 Renderer 的纯领域工作台现只消费视频 API 的真实项目、时间线、操作、Review/Approval 和恢复状态，并已通过正式 Main/Preload grant 接线；它不得复用 Agent Thread、图片候选状态、文件路径或 Sidecar capability。安装包和真实本机/受控 Relay 旅程仍须按上一节单独取证，不能由类型或单元测试替代。

## 迁移

旧泛媒体数据仅保留为支持期内的读取/导入来源。新视频写入只归视频工作台；验证用户数据连续后再移除旧 reader。
