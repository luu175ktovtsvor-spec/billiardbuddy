# 迁移与发行

## 迁移原则

旧自建 Agent、旧 Renderer、ProductTask/Run 账本与旧 Agent API 已删除，不提供兼容运行路径。新 Agent 会话由 Codex Rust Thread Store 保存和恢复。

图片、视频和凭据仍可能有历史用户数据。对应迁移必须是单向、可验证且有明确退出条件：新 writer 只写入所属领域；旧目录只能临时读取或导入；确认数据连续后删除旧 reader。不得用删除用户作品或项目来掩盖迁移失败。

服务端治理以下列顺序发行：先合并无密钥模型目录、capacity/quota/credential 契约和单实例调度；再让 Gateway 与 Image Relay 消费它们；随后让 Video Media Relay 消费同一目录与共享准入原语；最后部署并运行真实 smoke。任一阶段失败都不得让旧、新调度器同时对同一物理账号发放容量。

图片 Relay 的部署名称从泛 `relay` 收口为 `image-relay`，密钥文件从 `/srv/billiardbuddy/secrets/relay.env` 迁移到 `/srv/billiardbuddy/secrets/image-relay.env`，数据目录迁移到 `/srv/billiardbuddy/data/image-relay`。切换顺序固定为：先 `compose config`、构建三个镜像并在无数据卷的临时只读容器中验证三个服务的环境；再人工停止并移除旧 Relay writer；运行迁移脚本完成 WAL checkpoint、快照和原子目录移动；最后由 deploy 创建/检查目标服务目录、启动新服务并切换 Nginx。预构建绝不能创建 `/srv/billiardbuddy/data/image-relay`，因此首次 deploy 即使因旧 writer、旧密钥或旧数据而失败，也已经留下可复用的已验证镜像，不能以启动空目录伪装迁移成功。正式迁移先在同一数据盘创建不覆盖、root-only 的 `/srv/billiardbuddy/data/image-relay-recovery`，逐文件记录 SHA-256/字节数并 fsync；确认快照完整后才用同文件系统原子 rename 把旧目录切到新挂载。快照至少保留到新 release 的图片 submit/poll/result/ACK smoke 和历史结果读取都通过，清理必须是后续显式运维动作，部署脚本不得自动删除。

旧三服务的容量、队列、超时、额度和保留期不是新治理层的权威策略。首次治理切换必须显式给秘密迁移命令传入 `--use-small-production-profile`，用已审核的小规模生产档覆盖这些旧资源参数；Provider 凭据、HTTPS endpoint、物理账号绑定和存储路径仍原样保留，且三个原始 env 都必须进入 root-only 迁移备份。后续普通迁移不使用该一次性参数，继续保留运维人员已经明确设置的有效策略。

切换失败必须受控恢复：预构建失败时不得停旧服务；旧服务仍在时 deploy 必须失败关闭，不替运维人员杀进程；快照建立失败时旧目录原样保留；原子移动后服务启动失败时保留 `image-relay-recovery` 和新目录，先以清单核对、再由运维人员选择恢复，禁止脚本自动覆盖任一目录。Nginx 新配置 reload 失败时，安装器会恢复磁盘上的旧文件、重新执行 `nginx -t` 并显式 reload 旧配置；第二次 reload 仍失败时必须按“运行态未知”处理并中止。

旧图片任务不能在治理切换时变成“免费历史”或丢失已付费结果。新 Relay 首次打开旧库时，按当前 UTC 日把已成功或带 Provider receipt、但没有正式额度保留的任务保守回填到版本化物理账号账本；Provider 无法从旧记录确定时同时占用两个可能账号的安全额度。普通失败、已 ACK 成功和取消任务默认保留 7 天；未 ACK 的成功结果使用独立的 365 天默认保留窗，且不得小于普通任务 TTL。部署 smoke 使用自己的任务并完成 ACK，不得替用户历史未 ACK 结果做 ACK；迁移验收需证明该历史结果在切换前后仍可读取。

同一发行把图片公开路径从 Gateway 代理改为 `https://zzyppz.cn/image-generation/v1/images/tasks`：Nginx 只把 `/image-generation/` 转发到本机 `127.0.0.1:8790`，`/gw/` 仍只到 Gateway。桌面公开配置必须同时包含两个 HTTPS 基址；Sidecar 对 Image Relay 只发送短生命周期安装 bearer。Gateway 与 Image Relay 分别配置同一图片 introspection service secret 的验证端和调用端，结果签名另用 Image Relay 独占密钥；这些值都不得复用旧 `GW_RELAY_TOKEN`。发布验证确认新路径后删除 Gateway 的图片代理变量和路由，禁止新旧两条写路径长期并存。

## 安装包内容

当前 Agent-only Electron 安装包必须包含：空 Renderer 入口、Electron Main/preload、BilliardBuddy Sidecar、锁定构建的 App Server 与同 revision 的 Code Mode Host、锁定源码官方清单对应的 `rg`、BilliardBuddy 本地 Agent 插件市场、第三方许可与完整性清单。Agent-only macOS/Windows 构建不下载、不 staging、不审计 FFmpeg/ffprobe，也不运行 Canvas golden；图片、视频和媒体工具链留给后续独立媒体发行 workflow。两平台 Agent 构建仍必须按目标平台 staging Computer Use、Chrome Control、Browser Use 与 Record & Replay；安装包审计会拒绝旧 Agent 字符串、缺失受管资源和非正式运行入口。

## 发行验证

macOS arm64 与 Windows x64 分别构建和验证。每个平台至少验证：

1. 安装、首次启动和安全存储；
2. Rust App Server 启动、Thread 创建/恢复、Turn、工具、审批和中断；
3. 托管 Responses、个人 Responses 与个人 Chat 路线；
4. Agent-only 包不承担图片、视频 Sidecar 和媒体输出验收；这些能力在媒体发行 workflow 单独验证；
5. 安装包内容审计、升级、更新中断恢复和卸载边界。

构建成功、源码搜索或未签名目录包都不是正式发行完成；但本轮目标不是正式发行，而是确认 Agent-only 软件可安装、可启动、核心 Agent 链路可用。macOS 产出无签名 DMG/ZIP，Windows 产出未签名 Agent 包；签名、公证和正式更新源明确不属于本轮门槛。
