# 模型与远程能力平台

> 施工状态：三个领域共用的能力边界。完整裁决见 [目标架构与施工顺序](./00-目标架构与施工顺序.md)；不把 Gateway 或 Relay 变成业务项目服务。

## 用户结果

用户不必理解 provider、密钥、额度、兼容协议或内部路由。选择 BilliardBuddy 托管模型时，产品可靠地执行、控制用量并说明能力是否可用；用户明确配置个人模型时，Key 只留在本机受信运行时，直连其选定上游，不经过 BilliardBuddy Gateway 或 Relay。

这不是第四个 Agent，也不是图片或视频项目服务。它是三条工作面共同使用的窄远程能力边界。

## 谁拥有什么

| 事实 | 最终拥有者 | 不应拥有它的部分 |
| --- | --- | --- |
| 托管模型的身份、容量、额度、用量和远端操作回执 | BilliardBuddy Gateway / Relay | Renderer、Agent Worker、图片或视频项目 |
| 个人 Key 的原文和当前选择 | Electron Main 与本机受信 Sidecar | Renderer、日志、子进程环境、Gateway / Relay |
| 业务操作的本地身份、是否可重试及最终业务状态 | Agent、图片或视频各自的领域账本 | Gateway / Relay |
| 协议版本、能力名称和安全错误码 | 版本化共享 provider contract | 任一产品页面的临时分支 |

Gateway 的“成功”只代表远程能力收到或完成了某次操作；Agent 的 run、图片的候选操作、视频的分析任务仍由各自领域决定何时提交、何时确认和如何恢复。

## 正式链路

```text
Renderer
  -> 受控 IPC（仅提交配置或用户动作）
Electron Main / 本机 Sidecar
  -> 本地操作账本与协议适配
  -> 托管路由：Gateway -> Relay / 上游
  -> 个人路由：用户选定上游（仅本机直连）
  -> 已持久化的领域结果与公开投影
Renderer
```

任何可能计费、写入外部系统或产生可见结果的请求，都必须先有本地 `operation_id`、幂等键和明确的未知结果处理。网络中断、超时或进程退出不能自动把“是否已被远端接受”猜成失败并重发。远端成功也不是本地业务完成：先持久领域投影，再以同一 `operation_id` 写本地 checkpoint，最后才 ACK Gateway/Relay 或清除本机 direct-call receipt。

## 模型协议

Agent 的文本模型协议至少统一为以下产品级语义，而不是把 provider 流事件泄露到页面或工具。官方 Codex 当前只保留 Responses wire API；BilliardBuddy 的用户需求同时包含 Chat Completions 和 Responses，因此必须保持自己的 `ModelTransportAdapter`，而不是照搬其单协议客户端：

1. **Chat Completions**：流式正文、完整工具调用和明确终态。`stop` 不能携带待执行工具；`tool_calls` 或 `function_call` 没有完整参数时不能执行。
2. **Responses**：输入/输出项、工具参数流和明确完成终态。只有完整的 `response.function_call_arguments.done`（或等价的最终完整输出项）才可把工具调用交给领域；只有 `response.completed` 才是可执行的成功终态。
3. 这两种协议是用户可配置模型的完整边界；不接受 Anthropic Messages 或其他第三种协议。

Agent 的本机持久化由 Rust Codex Thread Store 完成；媒体领域持久化自己的 operation receipt 和终态。不得把上游会话 ID、原始推理内容或 provider 专有状态当作任何一条产品线的业务真相。

## 代码边界

共享 `provider-contract` 只包含版本化 wire schema、能力名、操作回执和安全错误 vocabulary。Gateway、Relay 和桌面 Sidecar 各自实现适配器；桌面运行时不得直接依赖 Gateway 的 provider registry 或业务实现，Gateway 也不得依赖桌面运行时实现。

受管 `TextReasoning` 注册项必须声明 `text_reasoning_transport`。Codex Core 固定使用 Responses：BilliardBuddy 的内置 Agent Key 只使用 `deepseek-v4-flash`，且只经 Gateway 的 `/v1/responses` 路由；Gateway 不提供 `/v1/chat/completions` 或 `/v1/messages` 的 Agent 代理。它只保存身份、额度、用量与受 `operation_id` 约束的 SSE 幂等回放，不能保存或续接 Agent Thread。Responses 额外拒绝 `previous_response_id`、`conversation` 与 provider-side `store`，因为 Rust Codex Thread Store 是 Agent 会话真相。

内置 Agent Key 的额度唯一归属 Gateway 已验证的 `installation_id`：每个安装身份每个 UTC 日最多 **50,000,000 total tokens**（上游实际 input + output），不适用于用户自填的 BYOK。请求开始时用请求字节数加请求输出上限做保守占额；收到 `response.completed` 的上游用量后以 `total_tokens` 结算。没有可靠最终用量或结果未知时保留占额，绝不猜测更低用量。MiMo 不得注册为 `TextReasoning`、不得进入 Agent 模型目录或被环境变量切换进 Agent；它仅保留在图片/视频领域的 `VisualEvidence` 与 `MediaReasoning` 路径。

个人 `openai-responses` 配置仍只在本机直连，不经过 Gateway。个人 Chat Completions 配置只经本机无状态适配器转换到 `/v1/responses`；该适配器没有 Thread、工具、权限、任务或持久化能力。真实受管上游调用仍须在具备合法服务器凭据和明确成本授权时单独验收，本轮不以静态检查伪装该验证。

允许复用的内容：受控凭据传递、operation receipt、幂等/fencing、容量快照、超时和诊断原语。

不允许复用的内容：Agent run、图片候选、视频时间线、泛化 `Project`、泛化 `Task`、或把用户个人 Key 送往托管服务。

## 实施顺序

这不是先于产品做一场大规模“地基重写”。它随第一个消费者 Agent 收口：先固化协议与路由的唯一正式路径，再按需要把图片、视频接到同一窄能力边界。不得为了共享而新建万能工作流、万能项目或第二套状态库。

当前代码中 Gateway 与桌面互相直接 import 的部分，必须在不改变托管额度和本机个人 Key 语义的前提下，逐步收敛到单向的共享 contract；这项替换应有明确消费者迁移和旧 import 退出条件。

## 完成验收

- 托管文本模型仅经 Gateway，且可展示能力/额度的安全快照；
- 个人 Key 不进入 Renderer、Gateway、Relay、日志或 Worker 子进程环境，并只请求用户选定上游；
- Chat Completions 与 Responses 的完整工具调用、成功、长度截断、取消、网络未知结果都映射为同一份可靠业务语义；
- 远端成功只有在本地领域结果和同 operation_id 检查点持久化后才被确认；
- Gateway、Relay、Sidecar 能各自发布或演进，不再直接 import 对方的运行时业务代码；
- 图片和视频接入时不会获得或污染 Agent 的会话、任务账本或权限状态。
