# 生图工作台

## 用户结果

用户以一个图片作品项目开始：导入参考、角色和品牌素材，编辑创作 Brief，发起真实图片任务，比较候选，在确定性画布中继续编辑、排版、放大或组合，保存版本并导出可校验文件。关闭或重启应用后，项目、资产、版本和任务仍是同一份事实。

交互与工作流研究 InvokeAI 这类成熟创作工具的项目、画布、工作流、候选与版本思路，但 BilliardBuddy 只采用满足本产品的部分；不把其源码、品牌或运行时作为依赖。

## 领域边界

图片项目拥有：参考资产、Brief、生成/编辑操作、候选、画布图层/蒙版、已选作品、版本、质检证据和导出记录。图片任务拥有自己的操作身份、事件、取消、失败恢复和远端回执。

多模态模型可帮助理解素材、规划 Brief 和检查已生成的图片；图片 provider 才能产生图片字节；画布才决定最后的排版。文字、提示词、分镜或“生成成功”的模型回复都不能代替真实候选或导出文件。

## 正式链路

```text
图片项目与参考资产
  -> Brief / 编辑意图
  -> 持久图片操作和远程能力请求
  -> 候选文件与来源回执
  -> 确定性画布、版本和质检
  -> 校验后的图片导出
```

图片项目不能借用 Agent 消息或视频时间线作为状态来源。Renderer 只保存当前选择、缩放、拖拽等视图状态；服务器拥有项目修改、资产元数据、版本和任务终态。

## 完成范围

1. 导入、校验并管理参考图、角色、品牌素材与约束；
2. 可编辑 Brief，以及可追溯到参考和用户修改的生成/编辑请求；
3. 持久生成、编辑、重试、取消与恢复任务；
4. 多个真实候选的比较、选择和版本化；
5. 画布图层、蒙版、局部修改、排版、放大和组合；
6. 对真实像素结果的视觉质检及其证据；
7. 文件、MIME、尺寸、hash 都经过验证的导出。

## 重构要求

图片领域从泛媒体服务中拆出独立服务、持久仓库、任务调度和 API；它可以复用共享的安全存储、远程能力、操作回执、资产引用和诊断，但不得与视频共享一份项目状态机。被替代的图片调用路径在完成迁移后删除，不做永久双轨。

## 完成验收

从真实参考与 Brief 建立项目，获得真实候选，完成选择和画布编辑，保存多个版本并在重启后恢复，模拟失败后继续，最终导出并验证文件。只有按钮、静态画布、mock 候选或单次 API 返回都不算完成。
