# 生图工作台

生图是 BilliardBuddy 自研领域，不属于 Codex Agent 内核，也不使用 Codex 原生 image-generation 工具。

## 后端边界

图片领域拥有自己的项目、参考资产、Brief、操作、候选、画布、版本、导出和事件记录。正式本地服务位于 `ts/src/server` 的图片工作台服务与 API；Image Relay 只承接付费生成的异步任务、Provider receipt 与待 ACK 结果，不拥有图片项目事实。

```text
图片项目 / 资产 / Brief
  -> 可恢复 ImageOperation
  -> Image Relay /v1/images/tasks 付费异步任务
      -> Gateway 私网身份内省（不转发图片）
  -> 候选组
  -> 用户采纳
  -> 画布版本与校验导出
```

候选生成成功不等于用户作品完成；只有明确采纳、版本保存和导出文件校验后才形成领域结果。Agent 的文本、Thread 或工具结果不能替代图片候选、画布或版本。

应用层由 `MediaRuntime` 只公开一组五个按完整用例边界组织的 Application（Project、Generation、Canvas、Delivery、Recovery）。它们由唯一的 `ImageWorkbenchRuntime` 组成受限 port；Compatibility `ImageWorkbenchService` 仅供既有直接调用面，不进入生产 `MediaRuntime`，也不创建第二个 Repository、CAS writer、恢复循环或 HTTP 路径。正式 API 和启动恢复分别只从对应 Application 进入；媒体字节在 Application 中重验，HTTP `Response` 只在 API 边界构造。所有 Application 共享同一 SQLite metadata store、CAS 和 writer fence，事务与事件提交仍由图片 runtime/repository 的单一写路径完成。

## 远端能力治理

- 图片建议是 `image_advice`，不得占用或改写通用 `media_reasoning` 协议；其模型选择、`qwen-account` 容量池与图片建议额度由共享模型目录绑定。
- 图片生成是 `image_generation`，OpenAI 与 Seedream 各有独立物理容量池；Image Relay 从自己的受限密钥存储读取 Provider Key，并使用独立 introspection service token 回查 Gateway。Gateway 不持有图片 Provider Key，也不代理 submit/poll/result/cancel/ACK。
- 两个图片账号分别以受限部署配置中的 `ACCOUNT_REF + ACCOUNT_BINDING_REVISION` 形成版本化账号键；容量许可和 Provider 侧日成本按该键隔离。切换物理账号不得复用旧键，单纯轮换同一账号的 Key 不得制造一份新的日额度。
- 受理队列、Provider 并发/RPM、单 owner 公平与产品付费额度是不同限制，不得用一个“并发数”同时表示。默认 small 档仅是可调起点，不是固定用户数承诺。
- 每个已认证安装默认可使用托管图片生成，无需预先填写图片 Provider Key。图片 owner / 平台额度独立于托管 Agent 和视频额度：Relay 的 allow-listed 日额度 429 必须投影为 `MEDIA_IMAGE_QUOTA_EXHAUSTED` 并给出 UTC 重置时间；队列满、上游限流和临时故障仍是可重试的 `MEDIA_IMAGE_UNAVAILABLE`，不得误报为额度耗尽。
- Round 在远端 POST 前必须持久化 operation id、请求 hash、预算保留和策略版本；重启只以原幂等键查询/恢复，不自动重提未知付费结果。
- Provider 成功后必须先验证字节和 hash，再于同一事务写入 CAS、Candidate/Version、current pointer、receipt 与 Outbox，之后才 ACK；ACK 恢复不能重新生成。

共享治理契约见 [模型资源治理分层](./模型资源治理分层.md)。

## 当前前端状态

旧前端已经删除。图片专用 Shell 位于 `ts/desktop/src/image-workbench`，通过类型化的 `ImageWorkbenchClient` 消费图片领域 API，覆盖快速建项、Brief 与灵感输入、受控参考图、候选审核与派生、显式采纳、画布预检/渲染/导出、素材复用、Brand Kit/Template、Campaign、操作与恢复状态。它只持久化面板、选择、拖拽草稿和事件游标；项目、候选、画布、操作与资产只能由公开 `GET /api/images/projects/:id/projection` 重载，不能从 Renderer 本地状态重建。

Campaign 不是第二套图片事实或自动排版器。每个已启动项目通过固定 Quick Create 幂等键成为普通图片 Project；Round/Operation 入库后、首次付费 POST 前，Campaign 项目与不可变的 `campaign_project_intent` 收据在同一 Campaign 锁和 SQLite 事务中绑定。收据锁定 Campaign revision、Brand/Template revision 与文字/二维码 Slot 值，但不会把变量拼进 Provider prompt，也不会自动采纳候选或改写 Canvas。用户明确采纳候选后，Shell 才以该收据调用标准 `apply_template` 或 `apply_brand_kit` Canvas Command。

Campaign 重试必须先获得逐项目 estimate 并确认费用回执，随后才可创建新 attempt。仍有效且未消费的 retry confirmation 会随 `GET /api/images/campaigns/:id` 返回；Shell 重启、刷新或断线恢复后从该公开投影重建操作入口，不依赖 Renderer 内存。恢复只能重取同一 Round/Operation 和原幂等键，旧 attempt 不得覆盖或重新提交较新的 attempt。

Campaign 列表是本地索引分页读取，单页最多 50 条，详情和远端状态刷新只针对当前页/选中项目；不会因列出历史 Campaign 而无界轮询 Image Relay。开始和重试的完整 quote 会保留项目、revision、付费 Operation 数、并发、价格上界和有效期，Shell 必须在有效 quote 上执行独立确认；派生同样先展示 estimate，再允许付费提交。

候选和正式 Version 都可以作为 Edit/Inpaint 的唯一来源。Candidate 派生在 Operation 上锁定 `base_candidate_id`，正式 Version 派生锁定 `base_version_id` 与已验证的基础资产 hash；二者都必须先取得短期 estimate，再创建一个方向的 Generation Round 和可恢复的正式 Operation。局部重绘蒙版必须是 PNG，且像素尺寸与锁定来源一致。远端结果只会生成新的 Candidate Group，不会覆盖来源；Version 派生组在 Group 上保留 `base_version_id`，而 Candidate 不会伪造 `derived_from_candidate_id`。

取消回执在逐项处理前先持久化。queued 且尚未跨过远端提交边界的 formal Operation、transport 和 Campaign attempt 由同一项目锁与 SQLite 事务原子改为取消；事务失败后恢复先消费 prepared cancellation receipt，再扫描普通 Operation，确保不会把用户已取消的任务首次 POST。running 或提交竞态只记录 `cancellation_too_late` 终态并返回稳定 409，绝不把它显示为取消成功。

该 Shell 不持有密钥、能力令牌或 Provider 访问路径，也不直接发 HTTP/Relay 请求。每个受保护的图片请求由 Main 签发一次性、短期 HMAC ticket，绑定 method、path/query、body hash、Range、Host、Origin、项目和资源标识；Sidecar 在读取 JSON 前验证 ticket 并拒绝重放。候选和正式 Version 预览只能由共享 schema 所定义的受限 data URL 桥接载入，Renderer 绝不把受保护的媒体路径塞入 `<img>`。普通 Operation 仅在 `queued` 时可请求取消；在轮询与取消之间已启动的 409 是预期竞态，`running` 不得展示为“可取消成功”。当前正式入口已接入 `imageWorkbenchInvoke` 图片专用 Main/Preload 通道：方法 payload、HTTP 响应和 Renderer 信封都由共享 schema 校验，候选字节由 Main 验证 hash、尺寸和 MIME 后才转换为有上限的 data URL；Renderer 入口挂载 `createElectronImageWorkbenchClient` 与 `ImageWorkbenchShell`，不再直接请求 HTTP。无论接入何种壳，图片界面都不能把图片操作塞进 Codex Thread 或重新引入泛化 ProductTask。

用户文件在 Renderer 进入 `FileReader` 前先检查 MIME、单文件字节上限和可用的解码尺寸：Reference/灵感图单张最多 8 MiB、同一命令累计最多 20 MiB；PNG 蒙版最多 32 MiB；所有输入的边长最多 12,000 像素且最多 1 亿像素。Sidecar 对原始请求体使用有上限的流读取，不调用无上限 `req.text()`：48 MiB 以上会在 JSON 解析和 ticket 的 body-hash 校验前以稳定的图片输入过大错误拒绝。CAS 的完整解码校验仍是所有环境下的最终权威。

需求编排保持“建议与事实分离”：用户主动请求图片理解建议时，才调用受额度治理的 Qwen 理解模型；这一步不启动图片生成，也不产生图片生成费用。Qwen 只能返回有边界的可见事实、构图建议、风险和待确认项；建议会以同一 Project revision 的 receipt 持久化并在重启后重新显示。公开 Creative Plan 只读取当前修订已有的建议，没有建议时直接生成不含模型意见的确定性方向，不因点击 Plan 偷偷发起新的计费请求；若当前修订已有建议，则必须绑定用户确认收据。Gateway 为 ImageAdvice 提供绑定完整的只读结果查询：桌面端丢失响应、收到在途 409 或重连时，只能查询同一 operation/fingerprint，不能以超时为理由再次 POST 或再次预留额度；结果未知时明确停在 `outcome_unknown`，不假装成功也不盲目重试。Candidate/Version 视觉评估同样以项目修订、目标字节 hash 和 Brief 形成稳定远端幂等键，并复用已有评估收据，避免换一个 UI 调用句柄产生第二次 Qwen 费用。用户修改 Brief、参考图 role/influence/preservation/priority 或输出规格后，旧建议自动过期；没有被用户确认的建议不能进入付费 Provider 请求。公开 `/api/images/quick-create` 与桌面 Quick Create 只持久化 Project、Brief 和参考输入并返回 `prepared`，不会直接创建付费 Round 或请求 Provider；只有 Creative Plan、有效 estimate 和显式付费确认齐备后，Generation Round 才能入库并跨过付费边界。Campaign/兼容内部路径如需一次性启动，必须显式传入 `mode: 'start'`，不能作为 Renderer 公共入口。Template/Brand Kit 是可选的复用工具，不是生图前置条件，也不会自动套用或替用户决定版式；用户可以完全不使用它们而直接生成，再在 Canvas 中手动调整。Operation Center 通过 durable event cursor 投影 queued/running/committing/succeeded 等状态、阶段和百分比，断线或重启先恢复事实再继续订阅，不能只显示一个无解释的“生成中”。Export 在入队事务中冻结 delivery spec id/revision 和 Version map，恢复时继续使用这个不可变快照，不会因为项目后来改了尺寸或格式而换规格。

## 验证边界

图片回归至少覆盖固定 legacy migration、CAS/SQLite/ACK 崩溃恢复、Round 入库到首次 POST 的恢复、Candidate 与 Version 派生、Canvas/Export、Campaign、Qwen 降级和 typed IPC。Provider smoke 只验证显式、预算受控的真实协议构造，不在常规测试中发起付费请求。Sidecar socket、Main Action 和 Preload 合同 E2E 可以证明本地图片调用链，但不能代替真实打包 Electron 安装验证；macOS arm64 与 Windows x64 的当次金图/安装 artifact 必须对将要发行的提交单独产生和审阅，不能用历史 artifact 替代。

## 迁移

旧泛媒体目录只可作为受控的历史数据读取/导入来源。新图片写入只归图片工作台；待支持期结束并验证迁移后，再删除旧 reader，而不是让两套 writer 长期并行。

Campaign 迁移按项目逐行可断点续跑：v11 保留不可变 Project intent，v12 以绑定命令回执修复历史 revision，并校验实际存在且归属同一子 Project 的 Generation Round、formal Operation 和 transport。每次迁移完成后再写 schema marker；缺少任一事实会使该次迁移失败而不会生成伪造 attempt。v12 为每个 `(Campaign, Item, attempt)` 保留精确 Round/Operation 映射，恢复可继续处理未完成的项目而不会重提旧尝试。
