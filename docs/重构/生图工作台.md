# 生图工作台

## 用户结果

用户以一个图片作品项目开始：导入参考、角色和品牌素材，编辑创作 Brief，发起真实图片任务，比较候选，在确定性画布中继续编辑、排版、放大或组合，保存版本并导出可校验文件。关闭或重启应用后，项目、资产、版本和任务仍是同一份事实。

交互与工作流研究 InvokeAI 这类成熟创作工具的项目、画布、工作流、候选与版本思路，但 BilliardBuddy 只采用满足本产品的部分；不把其源码、品牌或运行时作为依赖。

## 源码参考与适配边界

本模块参考 [InvokeAI 公开源码](https://github.com/invoke-ai/InvokeAI/tree/93fd9ae16e60069d0b78f04720b3c5b0fd0f57d5) 的 Canvas Projects、工作流输出暂存和持久队列设计；该仓库根目录为 [Apache-2.0](https://github.com/invoke-ai/InvokeAI/blob/93fd9ae16e60069d0b78f04720b3c5b0fd0f57d5/LICENSE)。固定只读参考已放在本机 `invokeai-reference/`，HEAD 必须为 `93fd9ae16e60069d0b78f04720b3c5b0fd0f57d5`；它被 `.gitignore` 排除，不进入产品构建、运行时或提交。

可以学习的是：素材字节、素材元数据、作品归属、画布状态和队列操作分别拥有事实；一次生成先形成可比较候选，再由用户显式采纳进画布或版本；画布持久的是组合文档和资产引用，而不是缩放、选中、拖拽等 Renderer 视图状态。

不复制 InvokeAI 的 Python 推理栈、节点工作流、全局图库、品牌、模型运行时或 `.invk` 工程格式。BilliardBuddy 第一阶段只建立自己的“图片操作 → 候选组 → 采纳 → 画布版本 → 导出”正式路径。

从源码得到的具体约束是：画布项目保存时要能恢复其层、蒙版、参考图和生成参数，而不是依赖当前页面；队列记录只描述一次可恢复的执行，输出文件和项目采纳是两份独立事实。BilliardBuddy 保留这两个原则，但使用自己的 JSON/CAS 文件和 Gateway/Relay，不引入 InvokeAI 的图执行、全局 gallery 或 `.invk` 格式。

## 领域边界

图片项目拥有：参考资产、Brief、生成/编辑操作、候选、画布图层/蒙版、已选作品、版本、质检证据和导出记录。图片任务拥有自己的操作身份、事件、取消、失败恢复和远端回执。

正式对象至少分为 `ImageProject`、`ImageAsset`、`ImageBrief`、`ImageOperation`、`ImageCandidateSet`、`ImageCanvasDocument`、`ImageVersion`、`ImageExport` 和 `ImageEventJournal`。这些是领域事实而非必须照搬的类名：候选未被采纳前不等于作品；画布文档能形成不可变快照；导出必须重新读取文件并验证 MIME、尺寸和 hash。

多模态模型可帮助理解素材、规划 Brief 和检查已生成的图片；图片 provider 才能产生图片字节；画布才决定最后的排版。文字、提示词、分镜或“生成成功”的模型回复都不能代替真实候选或导出文件。

## 正式链路

```text
图片项目与参考资产
  -> Brief / 编辑意图
  -> 持久图片操作和远程能力请求
  -> 候选文件与来源回执
  -> 确定性画布、版本和质检
  -> 校验后的图片导出
```

图片项目不能借用 Agent 消息或视频时间线作为状态来源。Renderer 只保存当前选择、缩放、拖拽等视图状态；服务器拥有项目修改、资产元数据、版本和任务终态。

## 完成范围

1. 导入、校验并管理参考图、角色、品牌素材与约束；
2. 可编辑 Brief，以及可追溯到参考和用户修改的生成/编辑请求；
3. 持久生成、编辑、重试、取消与恢复任务；
4. 多个真实候选的比较、选择和版本化；
5. 画布图层、蒙版、局部修改、排版、放大和组合；
6. 对真实像素结果的视觉质检及其证据；
7. 文件、MIME、尺寸、hash 都经过验证的导出。

## 重构要求

图片领域从泛媒体服务中拆出独立服务、持久仓库、任务调度和 API；它可以复用共享的安全存储、远程能力、操作回执、资产引用和诊断，但不得与视频共享一份项目状态机。被替代的图片调用路径在完成迁移后删除，不做永久双轨。

### 当前代码到正式模块的迁移

当前 `mediaProjectService.ts` 同时保存图片项目、图片操作、视频时间线、FFmpeg 队列和删除回收；它可以作为迁移期间的事实读取来源，但不能继续成为图片正式状态机。图片模块按以下边界落位：

| 现有职责 | 正式归属 | 切换条件 |
| --- | --- | --- |
| `createImageProject`、参考图、Brief、候选、版本、画布和导出 | `ImageWorkbenchService` + `ImageProjectRepository` | 项目和版本只读/写入都不再经过视频类型或视频锁 |
| `submitImageProject`、`startImageOperation`、`refreshImageTask`、Relay ACK | `ImageOperationService` + `ImageOperationRepository` | 操作 ID、未知结果、候选落盘和 ACK 在图片领域 journal 内闭环 |
| 图片字节、蒙版和导出文件 | `ImageAssetStore` | 每个资产都有 MIME、尺寸、hash 和项目归属；画布只存 asset 引用 |
| 项目删除、回收与恢复 | `ImageProjectRepository` 的图片回收区 | 项目、图片操作 journal 与项目资产作为一个可恢复单元移动；恢复时先还原依赖，最后发布项目 |
| HTTP/IPC 的 `/images/*` 入口 | 图片 API 适配层 | 页面只访问图片投影，不能获得 `MediaProject` 或视频任务对象 |
| Gateway/Relay、通用安全文件读写、诊断 | 共享远程能力/基础设施 | 不拥有图片项目、候选选择或版本语义 |

视频迁出后，旧泛媒体服务和其图片分支必须删除；不能以“新图片类转发旧 `MediaProjectService`”冒充完成。迁移先保持既有用户路径可读，再以一次受控切换让图片写入只落新目录；新写入开始后旧目录只作为有期限的导入来源。当前启动迁移不得再改写旧图片或视频记录：两域各自独立导入，泛媒体目录只保留兼容读取职责。

### 当前正式入口（2026-08-01）

图片桌面页面现在只读取 `imageWorkbenchStore`，通过 `imageWorkbenchApi` 访问 `/api/images/*`，并经 `DesktopHost.images` 的窄 IPC 能力提交、编辑、确认未知结果和导出。图片项目、操作、事件回放、删除恢复和资产 URL 都不再穿过 `/api/media/images/*`；旧图片 URL 会被明确拒绝，不能形成第二条写入路径。

视频仍暂时使用自己的媒体入口和 Store；本轮没有把视频状态迁进图片，也没有把两域抽成一个泛化工作流。`MediaProjectService` 仍只作为旧目录导入/兼容读取的候选，尚未因本次路径切换而宣布删除。真实上游候选、恢复和导出旅程仍需要在受控能力可用时验证，不能以此路径收口或本地构建代替。

## 完成验收

从真实参考与 Brief 建立项目，获得真实候选，完成选择和画布编辑，保存多个版本并在重启后恢复，模拟失败后继续，最终导出并验证文件。只有按钮、静态画布、mock 候选或单次 API 返回都不算完成。
