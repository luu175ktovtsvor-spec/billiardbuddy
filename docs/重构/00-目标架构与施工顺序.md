# 当前目标架构与施工顺序

> 本文是重构期的总导航。产品愿景和完成定义以仓库根目录的 [BilliardBuddy-重构合同](../../BilliardBuddy-重构合同.md) 为准；Agent 的源码边界以 [Codex 原生 Agent 路线](./Codex原生Agent路线.md) 为准。此前的 TypeScript `ProductTask` / Run 账本方案和宿主管理工具面方案均已退役，不再是可选实现。

## 产品由三个平行领域组成

```text
BilliardBuddy 桌面产品
├─ Agent 工作台
│  └─ 锁定的 Codex Rust App Server / Core / Tools / Sandbox
├─ 生图工作台
│  └─ 图片项目、资产、画布、版本与持久 ImageOperation
└─ 视频工作台
   └─ 素材、时间线、预览、渲染与导出
```

三者共享 Electron 宿主、品牌、登录、用户设置、安全存储、诊断和远程能力接入；它们不共享 Agent Run、媒体 Job 或万能 `Task` 账本。

## 当前正式后端形态

```text
Renderer（仅显示与提交意图）
  └─ Electron Main（受信 IPC、系统安全存储、窗口归属）
       ├─ Rust Codex App Server（stdio JSON-RPC）
       │    ├─ Thread Store / Core / Context / Tools
       │    ├─ Exec / sandbox / approval / MCP / Skills / Hooks / collaboration
       │    └─ Responses 模型 provider
       ├─ 托管模型：本机 loopback → BilliardBuddy Gateway /v1/responses → DeepSeek
       ├─ 用户 Responses Key：Rust 直接请求用户 endpoint
       └─ 用户 Chat Completions Key：本机无状态适配器 → 用户 endpoint

Bun Sidecar
  └─ 图片、视频、语音、设置、能力快照和历史目录只读投影

远程 Gateway / Relay
  ├─ 账户鉴权、套餐/额度、限流、路由、用量与安全审计
  ├─ 模型调用幂等键与终态 SSE 回放
  └─ 图片/视频领域需要的独立异步任务与结果交接
```

### 唯一状态拥有者

| 状态 | 唯一拥有者 | 不允许保存的位置 |
| --- | --- | --- |
| Agent Thread、Turn、Item、上下文、工具、审批、沙箱、MCP、Skills、Hooks、协作、恢复 | 私有 `CODEX_HOME` 中的 Rust Codex Thread Store、rollout 与 state database | Gateway、Bun Sidecar、Renderer、旧 ProductTask/Run 账本 |
| Agent 进程连接、背压、活跃请求 | Rust App Server | Renderer 推断的终态或 Bun Worker |
| 用户 API Key 与个人 provider 配置 | Electron Main 的系统安全存储 | Renderer、Gateway、Codex 配置文件、日志、模型回放 |
| 托管账户、授权、额度、用量、模型调用幂等与终态流回放 | BilliardBuddy Gateway | Agent Thread、工具执行、审批、沙箱或恢复语义 |
| 图片项目/资产/候选/版本/ImageOperation | 图片工作台自己的仓库和 Relay 结果交接 | Agent Thread、视频时间线 |
| 视频素材/证据/时间线/预览/渲染/导出 | 视频工作台自己的仓库和本机媒体进程 | Agent Thread、图片画布 |

“对齐 Codex”不等于网关不保存任何东西：开源 Codex 的本地 Thread Store 本来就保存会话与恢复资料，Gateway 也必须保存账户、额度和调用结果回放。禁止的是把 Agent 状态复制到 Gateway 或重新造一套外层 Agent 调度器。

## 模型与凭据规则

- Rust Codex Core 只说 Responses；它不直接支持 Chat Completions wire API。
- BilliardBuddy 托管模型是 DeepSeek V4 Flash，固定经自有 Gateway 的 `/v1/responses`；Gateway 因协议不符会拒绝请求。
- 用户在设置中自填 Key 后仍可选两种协议：Responses 直连，或由本机无状态适配器转换的 Chat Completions。
- 每个 App Server 子进程只得到短生命周期的模型能力；用户明文 Key 不进入 Renderer、Gateway、持久 `config.toml`、Thread、日志或 SSE 回放。
- 内嵌 App Server 明确关闭其上游分析、反馈和自动更新检查，不能在已选模型路线之外自行联网。

## 固定施工顺序

1. **完成 Agent 后端证据**：保持 Rust 为唯一执行内核；在成本与凭据获授权后，做受控真实模型 Turn、工具、审批、停止和崩溃恢复验收；安排低负载或 CI 重建，移除剩余的无效源码兼容补丁。
2. **全盘后端审计**：逐项检查无消费者服务、旧 HTTP/IPC、重复状态、凭据流和远程网关边界。发现旧 Agent 平行路径即删除或明确退役，不把它迁回新架构。
3. **生图后端**：只在图片领域内对照成熟图片工作台源码，审计图片项目、资产、候选、画布、异步 Job、结果 ACK、恢复和导出；不把图片状态放入 Agent。
4. **视频后端**：只在视频领域内对照成熟视频编辑源码，审计素材证据、时间线、预览、渲染、取消、恢复和输出校验；不把视频状态放入 Agent。
5. **前端最后进行**：所有后端状态和失败边界稳定后，才从 Codex 的信息架构推导 BilliardBuddy 页面。前端只投影 Rust Thread/Item 与媒体领域状态，不能再创建任何 Agent 账本或模拟执行结果。
6. **发行最后进行**：真实用户旅程稳定后再进入 Windows/macOS 打包、安装、升级、签名和发布验证。

每个小模块保持独立提交：先读真实调用链与参考源码，明确唯一状态拥有者，修改正式路径，运行与改动相称的验证，检查 diff，再提交。临时进程、测试服务和打包进程在验证后立即停止。
