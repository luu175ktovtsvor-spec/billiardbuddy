## 四、确认 bug（按严重度排序）

> 排序：致命 → 一般 → 吹毛求疵。**本次无致命 bug。**

### 【一般 · 真功能 bug】#1 内容生成旁路漏注入店脑

- **位置**：`server/services/content_service.py` 的 `generate_workbench`（:859）/`generate_copywriting`（:622）/`generate_activity`（:698）/`generate_operation`（:772）四个非流式函数。
- **复核结论**：✅ **确认属实**。复核员逐个读了四个函数体——它们各自**手搓**一套管道（`prompt_engine.render` → `_append_guardrails` → `get_brand_voice_context` → `provider.generate`），**全程没有 `with_store_brain`/`load_store_memory` 调用**。店脑注入只在 `run_generation`（:70）和流式 `stream.py`/`agent.py` 里有。这四个函数**不走 `run_generation`**，所以店脑确实漏了。
- **触发**：
  - REST `/api/v1/generate`（workbench/copywriting/activity/operation 卡片，`generate.py:31/57/84/110`）；
  - 主动出击 `proactive.generate_daily_drafts` → `generate_workbench`（`proactive.py:52`）。
  - 这两条**没有外层 Agent system prompt 兜底**，产出内容看不到老板的店脑记忆（含 manual 亲定店规矩/改价纠错）。
- **矛盾点**：`proactive.py:9` 与 `agent.py` 端点 docstring 明写「走 generate_workbench 管道，配额/落库/**店脑**/合规全生效」——**代码不兑现 docstring**。
- **Agent 主循环工具路径不受影响**：`tools.py:190` 的 `write_operation_content` 也调 `generate_workbench`，但 Agent 的 system prompt 已含店脑（`agent.py:517` `compose_agent_system_prompt(..., format_memories_for_prompt(memories))`），所以 Agent 对话里产出能看到店脑。漏的只有 **REST 卡片 + 主动草稿**两条独立入口。
- **后果**：违背 CLAUDE.md 核心契约「店脑让所有走统一管道的生成都懂这家店」「manual 优先级最高」。老板改了价/定了规矩，从工作台卡片或「帮我备好今天的」生成时**不生效**。**不影响能不能跑，影响生成质量。**
- **建议修法**：在四个 `generate_*` 函数里、`provider.generate` 之前补 `prompt = with_store_brain(prompt, await load_store_memory(db, store.id), intent=...)`。**注意顺序契约**：店脑必须追加在 prompt 末尾（近因效应压旧画像），其后不再 append——而当前 brand_voice/concise_directive 都在末尾追加，需把店脑排到这些之后（或把这三者排序统一）。
- **严重度**：**一般**（真功能缺口，但故障安全方向无害——漏注入只是少了上下文，不崩不泄）。

### 【一般】#2 流中途断连则该轮成品卡/审批卡全丢

- **位置**：`web/src/hooks/use-agent-chat.ts:130-147`。
- **复核结论**：✅ 属实。`finalText`/`steps`/`approval`/`question` 都只在 `onDone`（:133）里才 `setMessages` 落地。若后端已发 `final`/`tool_result`/`approval_request` 但连接在 `done` 前断开，reader 抛非 Abort 异常走 `onError`（:142），只追加一条 `⚠️` 错误气泡，**已生成的成品/待审批卡全部丢弃**。
- **触发**：网络抖动/后端中途异常，在 `done` 事件前断流。审批卡丢失尤其要紧——本该弹的确认卡没了。
- **建议修法**：`onError` 兜底时若已攒到 `steps`/`approval`/`finalText`，也落一条 assistant 消息再追加错误提示，而不是直接丢。
- **严重度**：**一般**（真机网络不稳时体验明显受损，但不崩、不误执行）。

### 【一般】#3 Electron 起子进程缺 `'error'` 监听，二进制缺失可崩主进程

- **位置**：`desktop/src/backend.js:97/101`、`frontend.js:61`、`publish.js:89` 的 `spawn(...)` 只挂了 `stdout/stderr/close`，**没挂 `child.on("error", ...)`**。
- **复核结论**：✅ 属实（grep 确认 backend/frontend/publish 的 spawn 后无 error 监听，只有 http req 上有）。spawn 失败时 Node 在 ChildProcess emit `'error'`，无监听器 → **冒泡为未捕获异常可崩主进程**；且 spawn 失败 `_proc.stdout` 为 null → `_proc.stdout.on("data", ...)`（backend.js:103）**直接 TypeError**。
- **触发与真机相关性**：
  - **dev 路径**（`spawn("uv", ...)`）：`uv` 未装 / `python3` 不在 PATH → 崩。
  - **prod 路径**（`spawn(packedExe, ...)`）：line 95 先 `fs.existsSync(packedExe)` 守了一道，存在才 spawn，**打包后正常机器上这条被守住**；但 exe 损坏/被杀软隔离/权限不足时 spawn 仍可能 emit error → 崩，且无重启兜底。
- **建议修法**：每个 spawn 后加 `child.on("error", e => { onLog(...); /* 走与 close 同样的失败/重启路径 */ })`；并在挂 `stdout.on` 前判 `_proc.stdout` 非 null。
- **严重度**：**一般**（打包版正常机器有 existsSync 兜底，但杀软隔离/权限/exe 损坏等真机现场常见情况下会崩且不自恢复 → 列入真机必修）。

### 【一般】#4 端口被占用静默失败，回落到打不开的页面

- **位置**：`desktop/src/backend.js:15`（端口 8077 写死，可 env 覆盖）、`frontend.js:20`（3100 写死）。
- **复核结论**：✅ 属实。无「端口占用就换口」逻辑。若 8077/3100 被占，`_waitReady` 轮询拿不到 200 → 超时后 `ok=false`，main 回落 `localhost:3000`（dev 才有，prod 必空白页）。且前端反代目标 8077 是**打包期烘进 server.js 的**，后端换口前端也连不上 → 端口是硬约束。
- **触发**：用户机器 8077/3100 被别的程序占用（真机现场不罕见）。
- **建议修法**：至少在 health 探活失败时把「端口可能被占用，请关闭占用 8077/3100 的程序后重启」**明确报给用户**，而非静默回落到打不开的页面。
- **严重度**：**一般**（真机端口冲突时表现为「装好了打不开还不知道为啥」，列入真机必修——至少给可诊断的报错）。

### 【吹毛求疵】#5 侧栏「正在用：xxx」模型标识改配置后不刷新

- **位置**：`web/src/components/desktop/chat-shell.tsx:75-99`，拉 BYOK 配置的 effect 依赖数组是 `[]`（只挂载跑一次）。
- **复核结论**：✅ 属实。改模型/切供应商档/改门店名/产生新花费后，侧栏 `liveModel`/`liveStoreName`/`liveSpend` 仍显旧值，直到 app 重载。
- **建议修法**：设置 Sheet 关闭后回调刷新，或监听路由返回重拉。
- **严重度**：吹毛求疵（陈旧数据，不影响功能正确性）。

### 【吹毛求疵】#6 edit_excel 选错工作表名抛裸 KeyError，报错不友好

- **位置**：`server/services/agent/local_tools.py:159` `ws = wb[ch["sheet"]] ...` 在 try 块**之外**（try 从 161 起）。

## 五、误报排除（读码后判定不成立 / 被既有机制兜住）

### 【误报 → 降级】首轮对话拒绝/确认不计数（denial_tracker key 为 null）

- **审计原判**：一般。新会话第一条消息弹审批卡时前端 `conversationId` 仍为 null，点拒绝传 `conversation_id=null` → `_bucket(None)` 返回 None → 计数 no-op，SH-8 首轮失效。
- **复核结论**：**大部分场景误报，仅极窄竞态成立**。读码核实：
  - 后端**始终知道** conv_uuid（`agent.py:377`：conversation_id 为空时从 gen_id 现造一个），`done` 事件携带 `conversation_id`（:433）。
  - 关键：loop 遇审批时（`loop.py:919-931`）emit `approval_request` 后 **`continue` 继续循环**，不停流，最终仍 emit `final`+`done`。前端 `onDone`（`use-agent-chat.ts:138`）即把 conversationId 设上。
  - 用户点审批卡是**流结束之后**的独立动作 → 点的时候 conversationId 基本已被 onDone 设好，传给 execute/reject 的不是 null。
  - 仅当用户在 `done` 事件到达前**抢先**点卡，或流在 done 前异常断开（即 bug #2 场景），才会传 null。
- **判定**：**误报（降级为吹毛求疵·待核）**。不列入必修。若将来发现首轮拒绝偶发不计数，再查这条竞态。
