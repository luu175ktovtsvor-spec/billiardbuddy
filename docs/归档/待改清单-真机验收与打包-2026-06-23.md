## P0-1 · 附件选择器不能选整个文件夹

- **现状**:聊天框 📎 附件按钮只弹"选单个文件 + 类型过滤"模式 → `.py` 等非白名单类型变灰、文件夹整个选不了。
- **影响**:用户想把"测试台球运营管家"整个文件夹授权给 AI(让它跑里面的 .py、读写 xlsx),做不到;只能一个个挑表格/文档。
- **根因证据**:`web/src/components/desktop/chat-shell.tsx:159-166` 的 `pickFiles` 只调 `electron.files.pick({ multi: true })`,没传 `directory`。默认过滤白名单(`desktop/src/main.js` files:pick handler ~121行)= xlsx/xlsm/csv/txt/md + 图片/视频,不含 .py。
- **底层其实支持**:`desktop/src/main.js` files:pick 支持 `{directory:true}`→openDirectory;沙箱 `server/services/agent/local_tools.py:35,47,59` 明确"用户选定的文件夹(或其子文件)→放行" → **选了文件夹AI就能读改里面一切**。端到端通,只差前端入口。
- **改法**:① `chat-shell.tsx` 加 `pickFolder`(调 `electron.files.pick({ directory: true })`),路径塞进 `selectedFiles`;② UI 加"选文件夹"入口(或 macOS 用 `["openFile","openDirectory"]` 同弹窗允许选文件或文件夹);③ 顺手放开/默认"所有文件",别让 .py 灰。
- **涉及**:`web/src/components/desktop/chat-shell.tsx`、`desktop/src/main.js`(files:pick)、可能 composer 组件加按钮。
- **临时办法(用户当下可用)**:弹窗里把类型筛选切到"所有文件"→ 能选 .py(但仍单文件、整文件夹还得改)。

## P0-2 · 任务慢/卡(根因已锁定)

- **现象**:一个任务转 147 秒还没完;但后端此刻 CPU 0.1%、无子进程、无外部连接(空闲),前端却在转圈。
- **根因①(杀手) 系统代理**:macOS 系统级代理(Clash Verge,127.0.0.1:7897)全局开着(`scutil --proxy` 显示 HTTP/HTTPS/SOCKS 全指 7897)。后端联网工具(web_fetch/web_search)的请求走了这个翻墙代理 → 访问**国产模型/国内站**时,代理连不上就 `ConnectError`(实测抓 tianqi.com 耗 5.3s 失败)、或挂死等满超时(抓到 `→7897 CLOSE_WAIT` 死连接)。**直连模型 api.xiaomimimo.com 仅 148ms**(绕过代理实测),所以模型不背锅,是代理在拖。多个联网工具叠加 → 几十秒到两分钟。
- **根因②(次因) 每轮固定开销**:每条消息把 系统提示+_SAFETY_REDLINE+25技能清单+工具/MCP定义 全量注入 ≈ **13000 tokens**(实测"1+1"也吃13076 tokens),`server/api/v1/agent.py:247` `compose_agent_system_prompt`。无前缀缓存 → 模型每轮重嚼,单轮~3-6s,多轮累加。
- **证据**:计时复现 —— 无工具简单题 6.26s(其中6.1s首响应);联网题20.6s/5轮,卡在 web_fetch tianqi.com ConnectError 5.3s,换 weather.com.cn 0.3s秒通。
- **改法 B(治本·代码)**:后端联网工具 + 模型 HTTP 客户端**绝不走系统/环境代理**(国产服务本就该直连)。httpx 用 `trust_env=False` 或显式 `proxies=None`;或设 `no_proxy` 覆盖。注意:web_fetch 抓**境外站**时可能反而需要代理 → 方案可做"国内域名直连、其余允许走代理"或给个开关,别一刀切断了境外抓取。
  - 涉及:`server/services/agent/web_tools.py`(web_fetch ~131 / web_search ~284 的 client)、模型 provider 的 httpx 客户端(`server/services/ai/` 下)。
- **改法 A(用户侧·零代码,先验证用)**:关掉 Clash 系统代理 或设国内直连。用来先证实就是代理的锅。
- **改法 C(提速·优化)**:前缀缓存 / 精简每轮上下文,压掉每轮13K的固定开销。工作量较大,见 `docs/完整优化清单.md`。

## A.2 目标架构(已定 · 依据见 A.4)

> 已按 2025 生产/大厂标准把方向定死(不再留待拍板)。**一句话**:学 Claude Code 的"薄索引 + 按需明细",但后端**沿用 SQLite**;写入走 **hybrid**(后台自动抽取 + 模型 hot-path 主动记);召回按 **相关性 + 近因 + 重要性** 取 top-k,语义用预置 **bge-small-zh**;注入**缓存友好**(薄索引进可缓存前缀、相关记忆每轮单独注入);防膨胀靠**写时取代矛盾 + 空闲整合**;**不上 mem0/Letta 重框架**(收益=范式本身,几百行可自建;Letta 会接管我们的 ReAct 循环)。

**七条目标(全部经查证,见 A.4)**:
1. **载体 = SQLite**(现状沿用)。结构学 Claude Code:一份薄"记忆索引"(摘要+指针)+ 明细按需取。非技术用户不手编文件,SQLite 给事务/可查询/去重/审计——正是 sqlite.org 官方力荐的"设备本地·单用户·低写并发"场景。
2. **分层 = 两条正交轴**:短期(对话 buffer + 滚动摘要,窗口内)/ 长期(SQLite,窗口外按需召回);长期内按 **semantic(事实/偏好)· episodic(成功范例)· procedural(行为规则)** 标类型(LangMem 官方共识)。现有 `store_memories.type` 接近,对齐即可。
3. **写入 = hybrid**:① **hot-path 工具**(模型对话中主动 remember/update,Anthropic Memory-Tool 风格)记"必须马上记住"的事;② **background 抽取**(会话结束/空闲异步,现有 `remember` 即是)做跨会话综合。
4. **召回 = relevance + recency + importance 三因子 top-k**(Stanford Generative Agents 范式,α 各=1、recency 指数衰减、importance 让模型打 1–10 分)。现有 `select_relevant_memories` 只有 relevance+confidence,补 recency/importance。
5. **语义 = 预置 bge-small-zh**(~90MB,fastembed/ONNX,不依赖 PyTorch),替掉词面哈希;精确词(乔氏/美团/追分/星牌)再加 FTS5 关键词 + RRF 合并(hybrid)。
6. **注入缓存友好**:薄索引进可缓存系统前缀(随三段式系统提示一起顶过最小缓存阈值),相关记忆放缓存断点之后/附用户消息(Anthropic + OpenAI 官方"静态在前·动态在后")。
7. **防膨胀 = 写时取代矛盾(mem0 ADD/UPDATE/DELETE/NOOP)+ 空闲周期整合(reflection)+ 衰减只降可检索性、不物理删**(保审计),配软删。

# 专题C · 台球知识库:用「导航式」让强模型自己取知识(2026-06-24 owner 提出 + 本窗口验证定案)

> **缘起**:owner 听到一个观点——"大模型够强了,台球知识库该瘦身;前置 RAG 检索虽必要,但强模型前提下这套架构要不要调?"(讨论以 MiMo v2.5 为参照模型)。本专题 = 结合现状代码 + 2026 行业研究的评估与待办。

> **调研依据(2026-06-24,已查证)**:
> - **现状代码(子代理挖透,带行号 · 含本窗口验证更正)**:开 `@台球` 只把 **3 个 L0 核心 YAML 正文**(约 6k 字)进系统提示(`server/api/v1/agent.py:111-130,273-276`);其余 **57 knowledge + 72 operation(约 28 万字)不进对话**。`look_up_knowledge`(`tools.py:92-127` → `rank_knowledge_for_topic` `content_service.py:417`)**只回名字+描述+硬数字索引、不回正文**(原作者**故意省 token**,因单条 template 中位 1155 字/最大 5641 字,回 top-5 全文≈5800~26600 字会爆)。**验证更正三点**:① 查(`rank_knowledge_for_topic`)与写(`_select_knowledge_keys` `:481`)**早已共享 `_semantic_scores`+同一 bge embedder**(`:449/:504`),不是「两套互不相干」;② bge 默认没插电(`RAG_EMBEDDER=fastembed` 才开)→ 默认退回关键词;③ `generate_operation()` 是**孤儿**(全 server 零调用),但其全文注入 `_load_knowledge_for_role` 仍**活着**——藏在 `_append_guardrails`(`:586→:611`),被写作工具/`generate_workbench` 用着。
> - **行业研究(2026,已查证 · 这步是定案关键)**:① **大厂收敛到「渐进披露(Agent Skills)」、不是向量RAG**——先给名字+一句话(~200token)、模型按需读全文;有论文标题就叫《Don't Retrieve, Navigate》([Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)、[SwirlAI 渐进披露](https://www.newsletter.swirlai.com/p/agent-skills-progressive-disclosure))。② **小而精的策展知识库:别上 RAG、整篇加载**(<20万token 就别切块向量;咱整库约 17~20 万 token、单条才千把字,正在线上)([Anthropic Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)、[Karpathy LLM Wiki 模式](https://www.mindstudio.ai/blog/karpathy-llm-wiki-pattern-knowledge-base-without-rag))。③ GitHub 活跃生态全是 Skills/渐进披露(pydantic-ai-skills 319★、OpenSkills…),没人给小库上向量RAG。④ 旧结论仍成立:长上下文不取代检索、Context Rot「少而精」([arXiv 2501.01880](https://arxiv.org/pdf/2501.01880)、[Chroma 解读](https://www.understandingai.org/p/context-rot-the-emerging-challenge)、[RAGFlow 2025](https://ragflow.io/blog/rag-review-2025-from-rag-to-context))。
> - **MiMo v2.5 = 1M 上下文**(小米官方,[mimo.xiaomi.com](https://mimo.xiaomi.com/mimo-v2-5)),理论塞得下整库(~20 万 token),但据上 ②③ **不该塞**,且会冲掉刻意为前缀缓存做的设计(连日期头都不敢进核心层,见 P0-2 改法 C)。

> **✅ 本窗口最终结论(已验证,2026-06-24)—— 最好的做法 = 方案④「导航式 / 渐进披露」**:
> - **怎么做**:`look_up_knowledge` 保留当「菜单」(给名字+描述,或直接给某运营域的 L1 `_index` 目录页);**新增 `read_knowledge(key)`**,模型挑中哪条就读**那 1–2 条的整篇正文**(单条才千把字、自包含,不切块);据整篇作答,数字只引用读到的内容。靠强模型自己导航,**不上向量、不切块、不打包 bge**。
> - **为什么是它**:① 最贴 owner 本意(模型够强→放手让它找,机器越少越好);② 大厂已收敛到这条路(见下「外部研究」);③ 代码里**已有骨架**(L0 模块地图分五域 + L1 `_index` 目录页 + look_up 都在),只差「读整篇」这一步,改动最小;④ 最不过度设计(无重依赖)。
> - **评估并否决的其它方案**:**①向量RAG**(把 look_up 改语义+切块回正文)= 对「小策展库」是**错的工具**,还要多塞 ~90MB bge + 切块管线;**②纯核心不检索** = 硬料那半受伤(owner 明确「具体料和思路都要」);**③统一两套系统** = 验证发现查/写**早已共享同一套语义内核**(`_semantic_scores`+同一 embedder),「两套互不相干」是高估了,多余。
> - **⚠️ 方法教训**:本窗口我前两版(先③后①)**跳过了「外部」这步**、只凭本地代码推,越推越偏;补查大厂(Anthropic Skills)+ GitHub 生态后才定到方案④。**改架构前先看大厂怎么做,别闭门推**(全局 CLAUDE.md 第9条「本地→外部→判断→假设→验证」、项目第8条「先看大厂 harness」)。

> **🎯 核心设计取舍(owner 观点本体 · 这条链路要回答的根本问题)**:模型够强的前提下,知识库给 AI 做回答的核心链路,本质是一道选择题——**约束给多少?** 两个方向直接决定最终生成质量:
> - **方向①:小知识库 + 放手让模型自由发挥** —— 只给精炼核心,靠模型自身能力延伸场景。**优点**=发挥充分、贴用户具体情况、不像背模板;**风险**=可能偏离 PPT 在册的真实打法/硬数字,甚至越安全红线(本产品铁律:PPT-only、不杜撰、守红线)。
> - **方向②:给很多约束(预建场景 / 死模板 / 穷举规则)** —— 话术、场景、步骤都写死喂进去。**优点**=可控、口径稳;**风险**=正是 owner 担心的:**框太死,强模型发挥不出来,产出僵硬像填空,质量反而更差**。
> - **本产品其实早已选定方向①**(CLAUDE.md/memory 在册:"大厂标准 B = 精炼核心 + 让模型自己延伸场景,**不替模型穷举预建场景**";铁律 "**不做鸡肋死模板**,功能用 AI 真智能")。owner 这轮观点 = **再次确认走方向①、并要求据此动手**。
> - **关键纠偏:①不是"越空越好"。** 真正的解 = **瘦掉"约束类"内容(死模板/穷举场景),但把"事实类"内容(PPT 硬数字/在册真实打法)让模型按需读整篇喂回** —— 给模型**表达的自由**,同时**钉住事实的接地**,既不僵硬也不跑偏、也不越红线。**这正是方案④(C.2 导航让模型按需读整篇)+ 瘦身(C.1 去约束)要服务的同一目标:落地"方向①"的两只手。**

> **⏱️ 现在要不要动手?(优先级定调 · 2026-06-24 owner 拍板)**:**先记录、暂不抢做 —— evidence-gated。** 现 @台球 对话已经很"方向①"(只塞 ~6k 核心,没框死模型),owner 担心的"约束压制模型"在 agent 路径上基本没发生;真正的弱点是「查回来只有目录、没有读整篇的下一步」(方案④/C.2 补的就是这步),但**它拖累生成质量的程度要用真实问答验证、别凭代码推断**(见 memory"别凭代码猜真机行为")。**决策步骤**:① 先花 ~30 分钟拿 5–10 个真实台球问题走一遍 `@台球` 对话,肉眼看回答是否真的弱/泛/跑偏 PPT;② 真弱 → 做 C.2(方案④导航,最高杠杆)+ C.1 瘦身顺手 + C.3 单独议;③ 已经答得不错 → 专题C 原样待命,等 `@台球` 用量上来或出现真实差评再启。**排序:整体让位于 P0(代理慢/选文件夹)与专题D(全内置 key),不插队。**

## D.1 内置 key 的现实 + 两类模型分治(核心 · owner 二次拍板后必读)
owner 定:key 直接内置壳子、不走服务器。技术上要把**两件不同的事**分清——

**(1) 藏 key:owner 已拍内置,但"二进制看不到"是误解(提醒一次,然后照办)**
- Electron `app.asar` **不加密**(Electron 官方明说它不是安全边界),`npx asar extract` 几秒解包、key 明文可见;PyInstaller 后端也能解包反编译;**即便混淆,用户对自己机器抓包(mitmproxy)也能从请求里读出 key**。→ 内置的 key 早晚被扒走盗刷。
- owner 已知仍要内置 → 照办,但**必做缓解**:provider 控制台给每个 key **设消费上限**(见 D.4),泄漏也只烧到上限。

**(2) 翻墙出海:跟 key 放哪无关,内置解决不了(物理事实)**
- **国内模型(Seedream / Seedance / MiMo)**:内置 key → app **直连**火山方舟/小米 → 成。**完全不用服务器**,完美符合"直接内置"。✅
- **GPT Image-2(在国外)**:**内置 key 也连不上**——国内本地程序直连 `api.openai.com` 被墙挡死,与 key 在哪无关。要它在国内能用,网络上**必须经过一个"国外出口"**;那东西本质就是中转/代理,**不管叫不叫"服务器"**。
- 所以 "**GPT Image-2 + 纯内置 + 无任何出口 + 国内可用**" 四个**不能同时成立**。"中间转代理能否实现"——能(你那台美国机现在就在干、~80ms),但它就是个出口。**二选一**:
  - **路线①(留 GPT)**:国内模型全内置直连(无服务器);**GPT Image-2 仅借你已有的美国机 `zzyppz.cn` 做网络出口**(只这一个借道,key 可放该机 .env)。细节见 D.2/D.3。

**Seedream(火山方舟生图 · 同步接口 `POST /api/v3/images/generations`)**
- 尺寸两种传法(不可混):① 档位 `size="1K/2K/3K/4K"` + prompt 描述比例;② 精确像素 `size="2048x2048"`(默认),总像素 + 比例 [1/16,16] 内。
- **无独立画质参数,分辨率档=画质档**。最大 **16.7M 像素(4096x4096)**,非 1:1 单边更长(4K 16:9 推荐 5504x3040)。
- 各模型档不同:`doubao-seedream-5.0-lite`(2K/3K/4K)、`4.5`(2K/4K)、`4.0`(1K/2K/4K)、`3.0-t2i`(仅精确像素 ≤2048)。

**Seedance 2.0(火山方舟视频 · 异步任务 `POST /api/v3/contents/generations/tasks` → 轮询)**
- ⚠️ 用户说的"1K/2K/3K"是**图片**叫法;**视频档 `resolution` = `480p/720p/1080p/4k`**(4k 仅满血 2.0;默认 720p)。
- 比例 `ratio` = `16:9/4:3/1:1/3:4/9:16/21:9` + `adaptive`(默认)。例:1080p 16:9=`1920x1080`、9:16=`1080x1920`、1:1=`1440x1440`;4k 16:9=`3840x2160`;720p 16:9=`1280x720`。
- 时长 `duration` **4~15 秒**整数(默认 5,-1 自选);**24fps**。参数 `model`/`content[]`/`resolution`/`ratio`/`duration`/`generate_audio`/`watermark`;`camera_fixed`/`seed` 2.0 暂不支持;仅在线推理、不接受真人人脸参考图。
- model id `doubao-seedance-2-0-260128`(已可调),Mini 预计 6/25——**以火山方舟控制台「查询 Model ID」为准**。

## E.0 目标与数据流

一句话:**老板说"给我做个国庆活动短视频" → 大脑写分镜 → 调生图模型出关键帧 → 老板过目确认 → 即梦基于关键帧图生视频 → 前端播放。**

```
用户输入(可带店照)
  → [大脑] 写分镜脚本(镜头/景别/运镜/时长)            ← LLM 推理,不是工具
  → [工具] generate_image 逐镜出关键帧(GPT Image-2/Seedream,同步秒级)
  → [确认] 把分镜+关键帧摊给老板过目(自然对话,不是硬审批闸)  ← 质量+成本双闸
  → [工具] generate_video 逐镜图生视频(即梦 Seedance 2.0,异步分钟级)
  → [机制] 提交任务拿 job_id 立即返回(不阻塞循环)→ 后台轮询 → 前端占位卡轮询变播放器
  → (可选)ffmpeg 拼接多镜为一条
```

**核心单点 = 关键帧图质量**:即梦 2.0 主打**图生视频**,关键帧烂→视频必烂。所以"先出好图、先给老板确认"是整条链的命门,不是可选步骤。

## E.1 选型与已查证的硬事实(执行依据,别再凭记忆)

**生图(出关键帧)**:GPT Image-2(海外·需出口,见专题D路线①)或 Seedream(国内直连·中文海报更强,路线②)。二者已接通,见 E.3.0 复用现有 `generate_image`。
- GPT Image-2 `images.edit` 支持**最多 16 张参考图**合成(用于"把店照改成更好的关键帧");尺寸宽高均须 16 整除、比例 1:3~3:1、最大 3840x2160;质量 low/medium/high/auto。来源:[OpenAI GPT Image 2 docs](https://developers.openai.com/api/docs/models/gpt-image-2)。

**视频(图生视频)= 即梦 Seedance · 火山方舟原生异步任务**
> ✅ **以下全部来自火山引擎官方 API 文档**(`api.volcengine.com/api-docs` 的 `CreateContentsGenerationsTasks` / `GetContentsGenerationsTask`,2026-06-24 用浏览器实抓官方正文)。**之前清单里来自第三方中转站(apifox/laozhang)的写法已纠正——它们把 `role` 和 task id 字段写错了,别再用。**

- **创建任务**:`POST https://ark.cn-beijing.volces.com/api/v3/contents/generations/tasks`,头 `Content-Type: application/json` + `Authorization: Bearer $ARK_API_KEY`。
- **官方请求体**(原生 `content[]` 数组;**图、视频、音频都用 `role:"reference_*"`,首帧/尾帧靠 text 文字描述**,这是 Seedance 2.0 多模态的官方写法):
  ```json
  {
    "model": "doubao-seedance-2-0-260128",
    "content": [
      {"type": "text", "text": "镜头描述……;首帧为图片1;……;尾帧定格为图片2。"},
      {"type": "image_url", "image_url": {"url": "https://<公网URL>/pic1.jpg"}, "role": "reference_image"},
      {"type": "image_url", "image_url": {"url": "https://<公网URL>/pic2.jpg"}, "role": "reference_image"}
    ],
    "ratio": "adaptive",
    "resolution": "720p",
    "duration": 5,
    "generate_audio": false,
    "watermark": false
  }
  ```
  - ⚠️ **`role` 官方枚举是 `reference_image` / `reference_video` / `reference_audio`**,**不是** `first_frame`/`last_frame`(那是旧 1.0 pro 经典图生视频的玩法)。Seedance 2.0 把"哪张当首帧、哪张当尾帧"**写在 text 里**("首帧为图片1""尾帧定格为图片2")。
  - `ratio`/`resolution`/`duration`/`generate_audio`/`watermark` 是**独立顶层字段**,不是 prompt 里的 `--flag`。
- **官方创建返回**:`{"id": "cgt-2025****-**"}` —— 任务 id 字段名是 **`id`(前缀 `cgt-`)**,**不是 `task_id`**。
- **轮询**:`GET https://ark.cn-beijing.volces.com/api/v3/contents/generations/tasks/{id}`(同样 Bearer 头)。官方成功返回:
  ```json
  {"id":"cgt-…","model":"doubao-…","status":"succeeded",
   "created_at":"…","updated_at":"…",
   "content":{"video_url":"https://xxx"},
   "usage":{"completion_tokens":35800,"total_tokens":35800}}
  ```
  失败返回:`{"status":"failed","error":{"code":"OutputVideoSensitiveContentDetected","message":"…"}}`。
  - **`status` 官方枚举:`queued|running|succeeded|failed|expired`**;**视频 URL 在 `content.video_url`**(临时链接,必须立刻落盘转存)。
- **官方参数(执行时按需用)**:
  - `resolution`:`480p|720p|1080p`(2.0 默认 720p;1080p 在 2.0 fast 不支持)。
  - `ratio`:`16:9/4:3/1:1/3:4/9:16/21:9/adaptive`(文生默认 16:9、**图生默认 adaptive**)。
  - `duration`(整数秒)**或** `frames`(小数秒,frames=秒×24,须按 25+4n 取值,frames 优先级高于 duration)。
  - `generate_audio`(仅 2.0/2.0fast/1.5pro 支持,会自动配人声/音效/BGM,对话放双引号里效果更好);`watermark`;`seed`(2.0 暂不支持)。
  - **`return_last_frame`**:返回视频尾帧图 → **官方推荐的"连续多镜"做法 = 上一镜尾帧当下一镜首帧**(E.5 多镜拼接直接用它,比硬 ffmpeg 拼更连贯)。
  - **`draft`(样片模式)**:出便宜的预览草稿、消耗 token 少 → **可用于 E.5 关键帧确认前先出草稿视频压成本**。
  - `execution_expires_after`:任务超时阈值,默认 172800 秒(48h),范围 [3600,259200]。
- **内容安全拦截(店照真人脸/敏感被拒的真实机制)**:官方错误码 `InputImageSensitiveContentDetected`(输入图敏感)、`InputTextSensitiveContentDetected`(输入文本敏感)、`OutputVideoSensitiveContentDetected`(产出视频敏感)。E.6 的店照人脸处理要按这个兜。
- **model id**:官方示例用 `doubao-seedance-1-0-pro-250528`;2.0 用 `doubao-seedance-2-0-260128`(D.4-附)。**以火山方舟控制台[模型列表](https://www.volcengine.com/docs/82379/1330310)实测可用 id 为准**(E.9)。
- 官方来源:[创建视频生成任务 API](https://api.volcengine.com/api-docs/view?action=CreateContentsGenerationsTasks&version=2024-01-01&serviceCode=ark)、[查询视频生成任务 API](https://api.volcengine.com/api-docs/view?action=GetContentsGenerationsTask&version=2024-01-01&serviceCode=ark)、[Seedance 2.0 API 参考](https://www.volcengine.com/docs/82379/1520757)。

> ⚠️ **会害"一遍过"翻车的头号坑**:`image_url.url` **必须是火山服务器公网能拉到的地址**(官方示例图全是火山自家 `ark-project.tos-cn-beijing.volces.com` 的公网 TOS URL,**通篇没有 base64 示例**)。本地 `/uploads/...` 是 localhost,**火山取不到**。→ **最稳妥:把关键帧(GPT/Seedream 出的图、或店照)先上传火山 TOS 拿公网 URL 再传**;能否用 `data:image/...;base64,` data URI 省掉上传,**执行时实测一次**(官方没承诺,别假设)。**绝不能传 localhost 地址。**

## E.2 核心设计原则(别焊死 · 与本项目"通用 Agent 不锁死模型"一致)

**不要做一个 `make_marketing_video` 大工具把"分镜→出图→生视频"全焊死。** 拆三层:

| 层 | 落地物 | 性质 |
|---|---|---|
| 原子工具 | `generate_image`(已有,复用)+ **新增 `generate_video`**(含图生视频) | 模型自由调,各自单独可用 |

|---|---|---|
| 直接当首帧 | 店照URL → generate_video | ⚠️ **即梦 2.0 不收真人脸参考图(D.4-附 第359行)**,有真人脸大概率拒/糊 |

## G.0 总原则(本窗最重要结论 · 作全局心智,所有 harness 改动都按这个判)
