# 使用事件采集 / 产品分析（喂版本迭代）

> 2026-06-16 新增（migration 020）。后端先行、不碰前端、**故障安全**（绝不影响生成）。
> 行业背景：SaaS 埋点 + AI 产品可观测性（记录每次生成/失败/反馈/token）是驱动迭代的标准做法，
> 对 AI 产品已是 2025 起的基线要求。本项目原来只在生成**成功**时落 `generations`，**失败直接抛异常不留痕**——
> 失败/卡点不可见。本模块把"看不见的失败"和耗时捞回来，按场景聚合，告诉我们**下一版该先改哪儿**。

## 一句话

每生成一次内容，后端就在 `usage_events` 表记一笔（哪个场景、成功/失败、耗时）；admin 接口按场景聚合，
变成"该优先改哪个 prompt/功能"的数据清单。**不是给门店用户看的，是给我们做版本迭代看的。**

## 数据在哪 / 记了什么

- **表**：`usage_events`（`models/usage_event.py`，migration 020）。**append-only 事件日志**。
  - 字段：`id` / `event`(事件名，如 `generation`) / `store_id`(可空，**无外键**) / `user_id`(可空) / `props`(JSONB 小上下文) / `created_at`。
  - **刻意无外键、解耦**：不随门店/用户删除而级联，保留历史；跨店只做**统计聚合**，不参与租户自动过滤
    （归入 `test_coupling_guards._MANUAL_FILTER_TABLES`）。
- **目前记的事件**：`generation`（统一管道 `content_service.run_generation` 打点）。`props` 含：
  - `scenario`：场景（`sub_type` 或 `gen_type`，如 `copywriting.moments`）
  - `gen_type`：大类
  - `outcome`：`success` / `failure`
  - `latency_ms`：耗时
  - `tokens`：成功时的 token 数
  - `error_type`：失败时的异常类型（如 `AIServiceError`）

## 怎么写入（铁律：故障安全，绝不影响生成）

- 入口：`services/usage_event_service.log_event(event, store_id, user_id, props)`。
  - **独立 `async_session()`**（与生成的 db 事务解耦）+ **吞掉一切异常**（失败只 log、不抛）。
- `run_generation` 里由 `_safe_log_generation()` 调用，**本身再包一层 try/except**（双层兜底）：
  - 成功路径：主 `db.commit()` 之后记 `outcome=success`；
  - 失败路径：AI 调用异常时记 `outcome=failure` + `error_type`，**再按原映射抛出原异常**（不掩盖）。
- ⚠️ **改 `run_generation` 时务必保持这条故障安全契约**：打点绝不能拖垮/阻断生成，绝不能在重抛前自己抛异常盖住原错误。`test_security_guards.py` 已加 guard 锁住打点不被删。

## 怎么看（喂迭代）

- **admin 接口**：`GET /api/v1/admin/usage/scenarios?days=30`（`require_admin`，跨店聚合、不暴露任一店内容）。
  返回按场景：`attempts` / `failures` / `failure_rate` / `avg_latency_ms`，按失败数倒序。
  → 一眼看出**哪个场景最常失败、最慢** = 下一版优先改哪。
- 现在是 **JSON 接口**，还没做后台页面（见下方"下一步"）。

## 隐私

跨店只做**统计聚合**给我们（开发方）看，不把 A 店内容暴露给 B 店；按店下钻时由 admin 显式 `.where(store_id)`。

## 现状 & 下一步

- **现状**：代码已合并/待部署。部署（`deploy_us.sh` 跑 `alembic upgrade head`）后表才建好、开始记录；
  之后**用户一用就攒数据**。无新增 env/配置。
