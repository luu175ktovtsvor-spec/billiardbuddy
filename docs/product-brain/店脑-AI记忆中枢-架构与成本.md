# 店脑（AI 记忆中枢）— 架构、成本与上下文澄清

> 状态：**设计稿（已调研 + 逻辑推演确认，未开始编码）**
> 日期：2026-06-13
> 目标：让球房从业者用这个软件时，**明显感觉它很聪明**——而且不只是表面，深处真的在"长脑子"。
> 注意：本文的"店脑"指**给单家门店的 AI 长期记忆**，和 `docs/product-brain/` 里的"产品大脑（行业知识/Prompt 规则）"不是一回事。

---

## 0. 一句话定位

把现在"**一堆各自聪明、用完即忘的功能**"，升级成"**一个持续生长、被所有功能共享的店脑**"——每次交互都在读它、写它，于是越用越懂这家店。

---

## 1. 为什么要做：把"智能感"拆开看

老板不会评估"模型好不好"，他只凭**感觉**判断聪不聪明。智能感 = 这几种具体感觉：

> 懂我的店 · **记得我** · 主动想到我没想到的 · 给的能直接用 · 像个懂行的人 · **越用越准**

现在产品已经做到的：懂我的店（注入门店资料）、主动（今日推荐/节日）、懂行（行业知识库）、能直接用。

**还没做好、最伤智能感的两条，恰恰都靠"记忆"：**
- **记得我** —— 对话不记得你上次聊过啥、做过啥，每次像新的。
- **越用越准** —— 👍👎 和"效果好"沉在后台，你感觉不到它在学。

店脑就是补这两条的唯一机制。表面打磨给不了"复利智能"。

## 2. 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│              用户交互（任意入口 / 任意窗口 / 任意员工）            │
│      工作台卡片 · AI 对话 · 协作 · 海报 · 👍👎 反馈              │
└───────────────┬──────────────────────────────┬────────────────┘
            写  │                          读   │
                ▼                              ▼
        ┌────────────────┐            ┌──────────────────┐
        │ ① 抽取 extract  │            │ ③ 注入 inject     │
        │ DeepSeek JSON 模式           │ 整本店脑放进       │
        │ 从这次交互挑"值得记的"        │ prompt 的固定前缀  │
        └───────┬────────┘            │ （吃 KV 缓存）     │
                ▼                     └────────▲─────────┘
        ┌────────────────┐                    │
        │ ② 整合 consolidate                   │
        │ ADD / UPDATE / MERGE / NOOP          │
        │ 改价→更新、矛盾→覆盖、重复→合并        │
        │ ⇒ 让店脑保持"稳定大小"，不越长越大     │
        └───────┬────────┘                    │
                ▼                              │
   ╔════════════════════════════════════════════════════╗
   ║   store_memory  (Postgres, 按 store_id 自动隔离)     ║
   ║   语义事实 · 情景 · 偏好 · 运营模式                   ║
   ╚════════════════════════╤═══════════════════════════╝
                            │ 摊开 / 可改
                            ▼
                  ┌────────────────────┐
                  │ ④「AI 眼里的你的店」 │
                  │   页面（可编辑·人在环）│
                  └────────────────────┘
```

### 四个部件

| 部件 | 落在代码哪 | 干什么 |
|---|---|---|
| **① 抽取 extract** | 新 `services/memory_service.py`；在生成/对话/反馈完成后**异步**触发 | 一次 DeepSeek（JSON 模式）从交互里挑出值得记的，输出结构化 `{类型, 内容, 置信度}` |
| **② 整合 consolidate** | 同上，定期/按量触发 | 新事实和旧记忆对账：没见过→ADD、变了→UPDATE、矛盾→覆盖、重复→MERGE、已知→NOOP。**这步是成本不随时间膨胀的关键** |
| **③ 注入 inject** | `prompt_engine` 组装处 | 把整本店脑放进 prompt 的**固定前缀**（最大化 KV 缓存命中），所有功能读同一本 |
| **④ 可编辑页** | 新页 `/dashboard/store-brain` + GET/PATCH API | 把店脑摊给老板看、可改。既显得聪明，又是"人在环"纠错 + 评估器 |

### 数据模型（一张表，零新基建）

```
store_memory(
  id, store_id,           -- 按 store_id，天然吃 core/tenant.py 的租户隔离
  type,                   -- semantic 语义事实 / episodic 情景 / preference 偏好 / procedural 运营模式
  content,                -- 记忆内容（文本）
  confidence,             -- 置信度
  updated_at
)
```

记忆四类（借认知科学通用分法）：
- **语义（事实）**：台型/价格/位置 + 推断的（"主力金腿银腿""客群偏熟客"）
- **情景（发生过的事）**：上次端午做了 X、效果好
- **偏好（风格）**：文案要熟人口吻、不爱表情、标过的"效果好"都是搭子局类
- **运营模式**：周末靠散客、工作日靠助教

## 3. DeepSeek 上下文澄清（专门回答你的疑问）

你的疑问：「上下文只有 1MB（或 128K）？是不是开新对话窗口就从头开始？」

### 先纠正三个概念

1. **不是 1MB**。MB 是文件体积单位，上下文按 **token** 算。
2. **当前 deepseek-v4-flash 上下文 = 1M tokens**（≈100 万 token，约几十万到上百万汉字）。
   （已验证：抓 `api-docs.deepseek.com/quick_start/pricing`，"CONTEXT LENGTH = 1M"。你说的 128K 是更老的 deepseek-chat/V3，已不是现在用的型号。）
3. **上下文 ≠ 对话记忆**，这是关键——

### 真相：模型是"无状态"的，它什么都不记得

每次调用，模型只能看到**这一次请求里塞进去的内容**。所谓"对话窗口里有上下文"，是**应用每次把整段历史重新塞进去**造成的错觉，不是模型记住了。

```
   窗口 A 第1句 ─┐
   窗口 A 第2句 ─┼─► App 每次把【整段历史 + 店脑】重新塞进 messages ─► DeepSeek(1M)
   窗口 A 第3句 ─┘                                                      │
                                                                        ▼
   窗口 B（新开）─► 没有历史了！但 App 仍然注入【店脑】─────────────────► DeepSeek
                   └── 这正是你直觉到的"别的办法"：
                       店脑跨窗口/跨会话持久存在，每次都注入 ⇒ 换个窗口它照样"记得你"
```

### 所以你的理解：对了一半
- ✅ 对：开新窗口，**这次对话的历史**确实从头开始（因为 App 没把旧历史塞进去）。
- ❌ 不对的部分：这不是"上下文太小"导致的（1M 很大）；是因为模型无状态、App 没传旧内容。
- **方案就是店脑**：把"关于这家店该记住的东西"持久化在数据库里，**每个窗口、每次请求都注入**。于是无论开第几个窗口、哪个员工登录，它都"记得这家店"。**你担心的跨窗口失忆，店脑天生就解决了。**

## 4. 成本分析（按 DeepSeek v4-flash 真实定价）

**定价（已验证）**：输入 cache-miss `$0.14/1M`、cache-hit `$0.0028/1M`、输出 `$0.28/1M`。
**假设一家店月活**：~30 次生成（配额）+ ~20 次对话/反馈 ≈ **50 次交互**。

| 动作 | 频次/月 | 单次 token | 月成本 |
|---|---|---|---|
| ① 抽取 | 50 | 输入~1.5k + 输出~0.2k | ~$0.013 |
| ③ 注入 | 30 | ~1.5k（多为**缓存命中**$0.0028/1M） | ~$0.001 |
| ② 整合 | ~30（每天1次） | 输入~3k + 输出~0.5k | ~$0.017 |
| **合计** | | | **≈ $0.03–0.04 / 店 / 月 ≈ ¥0.3 / 店 / 月** |

> 这是店脑**额外**增加的成本（在原有生成成本之外）。一家店一个月**三四毛钱**。

### 1) 规模类比（按店数，线性）
| 店数 | 店脑月成本（增量） |
|---|---|
| 1 家 | ~¥0.3 |
| 2 家 | ~¥0.6 |
| 100 家 | ~¥30 |
| 1000 家 | ~¥300 |

### 2) 人头类比（按使用人数）
店脑是**按门店共享的**（一家店一个脑，老板/店长/助教/前厅共用）。成本由**交互次数**驱动，不由人头驱动。
- 5 个员工共用 1 个店脑，每人每月 10 次交互 = 50 次 = 还是 ~¥0.3/店。
- **每多一个人的边际成本 ≈ 他自己那几次抽取调用（每次约 ¥0.002）**，几乎为零。
- 结论：人头不是成本变量，**交互量才是**。

### 3) 增长趋势（会不会越用越贵？）
**不会——前提是做了"整合"这一步。**
- 若像 mem0 那样"只增不改"，记忆会无限堆积 → 注入越来越大 → 慢慢变贵、最终撑爆。
- 我们的设计有 **② 整合**：改价就更新、矛盾就覆盖、重复就合并 → 店脑稳定在一个**有限大小**（它是门店的"摘要"，不是"流水账"，本质就几十到一两百条、1–3k token，长期持平）。
- 唯一会自然累积的是**情景记忆（发生过的事）**——对策：只留最近 N 条 + 定期把旧情景**压缩**成语义事实。
- **所以成本是平的，不随时间上涨。这正是"整合"步骤的核心价值，也是和 mem0"只增不改"路线最关键的区别。**

## 5. 怎么测（用业界基准 LongMemEval 的五项能力）

> 已验证：LongMemEval 是测长期记忆的现行基准，测 5 项核心能力。逐项翻译成球房店脑 + 可自动化的 golden 测试（TDD）。

| LongMemEval 能力 | 店脑要过的测试 |
|---|---|
| ① 信息抽取 | 对话说"我们没包厢了" → 断言店脑记下"无包厢" |
| ② **知识更新**（命门） | 改价/助教数变 → 店脑**更新旧值、不留两条打架** |
| ③ 时序推理 | "上次端午做了啥" 能带时间答对 |
| ④ 多轮综合 | 跨几次对话的信息能合起来用 |
| ⑤ **Abstention 弃权**（防幻觉） | 问店脑里没有的事 → 答"不知道/请补充"，**不瞎编**（信任底线） |

两层评估：
- **记忆质量层（自动）**：一组"门店对话 → 期望记忆"golden 案例进 pytest，每次改动回归。
- **端到端层（人评）**：同需求 喂店脑 vs 不喂 → 老板更认可哪版。
- **可编辑页本身就是持续评估器**：老板每改一次 = 一个抽取错误信号，长期看纠错率下降 = 越来越准。

## 6. 和现有架构的关系（不是外挂，是补上缺的一层）

1. **正好插在已有护城河上**：对话/卡片/协作都走同一条 `free_intent` 管道，店脑注入放这个咽喉点一次 → 所有功能一起受益。架构早就为它留好了位置。
2. **收编碎片**：现在 `operation_profile`（静态）+ `behavior_service`（算的）+ `feedback`（👍👎）各管一摊；店脑给它们统一读写口。
3. **天然吃多租户隔离**：`store_memory` 按 `store_id` 存 → `core/tenant.py` 自动过滤覆盖。
4. **分层更干净**：数据层(PG) → **记忆层(店脑·新)** → 生成层(PromptEngine)。
5. **为什么是 DeepSeek 的近乎最优解**：记忆方案分两派——mem0 派靠 embedding+向量检索（DeepSeek 没 embedding，要额外接模型）；load-whole 派靠大上下文整本注入（DeepSeek 1M 上下文 + 便宜 + KV 缓存，原生就够）。**顺着 DeepSeek 的能力曲线，就该选 load-whole，正是本架构。**

## 7. 落地节奏（先证明记得对，再证明记得多）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **第一版（最小可信闭环）** | 只做 偏好 + 几条关键事实的 抽取 → 注入生成 → 可编辑页 | golden 测试绿 + 老板看页面觉得"记对了" |
| 第二版 | 加整合（知识更新/抗矛盾）+ 情景记忆 | 改价不留旧值；跨会话"记得" |
| 第三版 | 主动层（店脑发现缺口/矛盾就追问）+ 跨场景串 campaign | 智能感拉满 |

**不 big-bang。** 最大风险不是 token，是**记错的记忆比没记忆更蠢**——先用第一版把抽取质量这个闭环验证靠谱，再扩规模。可编辑页是全程的安全阀。

## 8. 诚实的边界

- 产品定位不碰收银/实时数据，所以店脑**学不到"这条朋友圈到底带来几个客"**这种真实经营结果——它能学的是"你做了什么、你说哪条好、你的偏好"。这是天花板，但已足够让它从"聪明工具"变"懂你店的伙伴"。
- 单店记忆量小（几页纸），**不需要**向量库/知识图谱那套重型检索；真到了跨门店百万级记忆，再单独挂小 embedding 模型即可，不影响现在的选型。

## 9. 实测后的 as-built 调整（2026-06-13 第一版落地）

第一版已落地并通过真实 DeepSeek 评估（`server/tests/eval_store_brain.py` 5/5 + 端到端实跑）。相对上面设计的两处修正：

1. **注入位置：放 system prompt 末尾，不是前缀。** 设计原想放前缀吃 KV 缓存，但实测发现**店脑与门店 profile 冲突时（如"金腿75"vs profile"金腿60"），放前缀压不过后面的 profile**。改放末尾（近因效应）+ 措辞"如与其他资料/价格冲突一律以店脑为准"后，店脑正确覆盖冲突项、互补其余项。**取舍：放弃了店脑那 1~2k token 的缓存命中，换取覆盖正确性——值得。**
2. **整合返回"最终列表"而非 ADD/UPDATE 操作。** 实测 ADD/UPDATE/MERGE/NOOP 标签边界模糊、模型不稳定贴标签，但"无重复+改价生效"这个目标始终达成。故 `consolidate_memories` 直接返回整合后的完整列表，按结果对错衡量。
3. **评估是统计性的**：抽取召回允许 6 条抖动 ≤1，防幻觉必须 0；记忆操作 temperature=0 求稳。

落地清单：`models/store_memory.py` + 迁移 017、`services/memory_service.py`(extract/consolidate/load/remember/format)、`stream.py`(注入+`BackgroundTask`后台学习)、`api/v1/store_memory.py`(CRUD)、前端 `/dashboard/store-brain`「AI 眼里的你的店」。**钩子后台学习不计用户配额。**

### 9.1 生产耐用加固（为"人多了、以后不再改"一次做到位）

1. **并发安全（根治丢记忆）**：`remember()` 取**每店事务级咨询锁** `pg_advisory_xact_lock(hashtext("store_memory:{store_id}"))`，把同一家店的并发学习串行化——解决"读现有→整合→删全部再插入"在多员工同时使用时的丢更新竞态。只锁同店、不锁跨店，不影响整体吞吐。已用并发 e2e 验证（两条并发学习都不丢）。
   - 取舍：锁在 consolidate(LLM ~3-5s) 期间持有连接；单店学习不频繁、连接池 20+40 足够，realistic SaaS 规模无碍。极端规模再考虑队列化（当前不做，避免过度设计）。
2. **防膨胀上限**：`_cap_memories` —— 耐久类(事实/偏好/运营模式)全留，**情景类(会累积)只留最近 25 条**，总数封顶 150；同时 consolidate prompt 要求"旧情景合并成简短总结"。双保险，多年使用也不会无限胀大。已有上限单测覆盖。
