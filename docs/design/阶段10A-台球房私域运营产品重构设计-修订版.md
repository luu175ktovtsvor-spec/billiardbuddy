# 阶段 10A 修订版：台球房私域运营产品重构设计 + AI 能力底座规划

---

## 1. 产品重新定位

### 1.1 定位升级

```
旧定位：台球房 AI 文案 / 海报生成器
新定位：台球房私域运营与助教管理工作台
```

旧定位的问题：当前产品本质是"选场景→AI 输出文案/海报"，和把豆包/ChatGPT 包了一层皮没有本质区别。台球房老板试用后会觉得"挺好玩，但不知道每天打开干什么"。

新定位要解决的核心问题：**让球房里的每个人每天打开系统，就知道今天该干什么、该发什么、该联系谁。**

### 1.2 产品一句话定义

> 球房 AI 店长是一个帮助台球房完成"日常运营动作"的工作台——它不管钱，管的是每天该发什么、该联系谁、该推什么、该做什么。

### 1.3 核心价值转变

| 维度 | 旧产品 | 新产品 |
|------|--------|--------|
| 用户打开的理由 | "我想生成一条文案" | "我看看今天该干什么" |
| 核心驱动 | 用户主动想到要生成内容 | 系统主动告诉用户该做哪些运营动作 |
| 内容来源 | 通用 AI 场景 | 围绕球房经营逻辑的具体场景 |
| 用户粘性 | 偶尔用一下 | 每天打开，像打卡工具 |
| 差异化壁垒 | 无（任何 AI 工具都能做） | 台球房经营场景库 + 角色化任务 + 助教管理 |

## 2. 和收银系统 / 通用 AI 的区别

### 2.1 和收银系统的区别

```
收银系统管"钱的流转"：开台、计费、上钟、收银、会员余额、充值、退款、报表
本系统管"人的动作"：每天发什么、联系谁、推什么活动、怎么转化客户、怎么管理助教日常
```

| 收银系统做的事 | 本系统做的事 |
|-------------|-------------|
| 客户到店 → 开台计费 | 客户到店 → 接待话术、加微信话术、推卡话术 |
| 助教上钟 → 计时扣费 | 助教每天 → 发朋友圈、跟进客户、内容推广 |
| 会员充值 → 余额变动 | 老会员唤醒 → 私聊邀约、专属福利、生日关怀 |
| 收银报表 → 营收分析 | 运营日报 → 今天发了什么、联系了谁、转化了几个 |

**本系统不碰收银系统的任何功能。**

### 2.2 和豆包 / ChatGPT 等通用 AI 的区别

| 通用 AI | 本系统 |
|---------|--------|
| 用户自己想 Prompt | 系统按经营场景直接给任务 |
| "帮我写一条朋友圈" | "今天下午空台，给你生成一条下午促活朋友圈，门店价格已自动带入" |
| 不知道你是台球房 | 知道你几张台、什么价格、有没有助教、最近在推什么活动 |
| 输出通用文案 | 输出带门店名、价格、地址、二维码的可直接发布内容 |
| 没有角色概念 | 老板看全局、店长管运营、助教做推广、前厅搞接待 |
| 没有任务驱动 | 每天登录就有待办事项和运营建议 |

## 3. 用户角色设计

### 3.1 老板

| 维度 | 说明 |
|------|------|
| **主要痛点** | 不在店里不知道店长和助教在干什么；团购客户来了就走不知道有没有转化；助教招不到留不住 |
| **每天需要做的事** | 看今天店里运营了什么、助教发没发朋友圈、有没有新活动在推 |
| **系统能帮什么** | 今日运营总览、助教工作状态一览、经营建议 |
| **对应模块** | 今日运营工作台（管理视角）、助教管理概览 |

### 3.2 店长

| 维度 | 说明 |
|------|------|
| **主要痛点** | 每天不知道发什么、活动不会策划、团购客户不知道怎么转化、助教管不好、群里没人说话 |
| **每天需要做的事** | 发朋友圈、发群公告、跟进重点客户、检查助教工作、安排今日活动 |
| **系统能帮什么** | 每日运营待办、一键生成各场景内容、团购转化话术、助教任务分配 |
| **对应模块** | 今日运营工作台（执行视角）、团购转化助手、助教管理、内容生产中心、前厅 SOP |

### 3.3 助教

| 维度 | 说明 |
|------|------|
| **主要痛点** | 不知道怎么获客、不会写朋友圈、不知道怎么跟客户聊天、店里给的素材少 |
| **每天需要做的事** | 发 1-2 条朋友圈、给老客户发消息邀约、在群里露个脸、跟进意向客户 |
| **系统能帮什么** | 每日发圈任务和文案、客户跟进话术、个人推广海报、人设包装建议 |
| **对应模块** | 助教工作台、助教推广内容 |

### 3.4 教练 / 赛事负责人

| 维度 | 说明 |
|------|------|
| **主要痛点** | 周赛月赛报名人数不够、赛事宣传不会做、学员转化率低 |
| **每天需要做的事** | 赛事报名推广、赛前提醒、赛后战报、教学课推广 |
| **系统能帮什么** | 赛事全套内容（方案/报名/海报/提醒/战报）、教学课推广素材 |
| **对应模块** | 教练赛事运营助手、搭子局运营助手 |

### 3.5 前厅

| 维度 | 说明 |
|------|------|
| **主要痛点** | 团购客户核销后不知道说什么、不会推会员卡、客户嫌贵不知道怎么应对 |
| **每天需要做的事** | 接待客户、核销团购、推荐会员卡、加客户微信、处理投诉 |
| **系统能帮什么** | 各场景标准接待话术、推卡话术、加微话术、投诉处理模板 |
| **对应模块** | 前厅 SOP 助手、员工话术库 |

### 3.6 运营人员

| 维度 | 说明 |
|------|------|
| **主要痛点** | 内容产出跟不上、不会做海报、抖音/小红书不知道发什么 |
| **每天需要做的事** | 批量产出朋友圈/群公告/海报、规划内容日历 |
| **系统能帮什么** | 批量内容生成、多渠道适配、内容素材库 |
| **对应模块** | 内容素材生产中心 |

## 4. 客户分类与转化路径

### 4.1 客户分类

| 客户类型 | 特征 | 对门店的价值 | 运营重点 |
|---------|------|-------------|---------|
| **团购客户/散客** | 美团/抖音团购第一次到店，价格敏感 | 利润极低甚至亏损 | 加微信、进群、转化为私域客户 |
| **新客户** | 第一次或第二次到店，在观望 | 低但有潜力 | 良好体验、二次邀约、推荐助教体验课 |
| **老客户** | 来过 3 次以上，有习惯但没充值 | 中等 | 促进充值、推荐周赛、引导带朋友来 |
| **助教客户** | 预约过助教，愿意为陪练付费 | 高（客单价翻倍以上） | 持续预约、推荐更多课时、节日关怀 |
| **竞技/搭子客户** | 喜欢约局、打比赛、社交需求强 | 中高（频次高） | 搭子群运营、周赛通知、竞技氛围维护 |
| **轻度台费局客户** | 偶尔来打一两局，频率低 | 低 | 下午促活、搭子群引导、助教体验推荐 |
| **大客户/充值客户** | 充值会员、高频到店、经常带人 | 极高 | 专属维护、生日关怀、VIP 活动、防流失 |

### 4.2 转化路径

```
路径 1：团购引流 → 私域沉淀 → 复购转化
  团购客户到店 → 前厅接待+加微信+进群 → 二次到店邀约 → 推荐会员卡/充值 → 成为老客户

路径 2：团购客户 → 助教客户
  团购客户到店 → 推荐新人助教体验课 → 助教跟进+复约 → 客单价从50元→150-300元

路径 3：单人练球 → 搭子局 → 复购
  单人练球客户 → 店长/教练撮合凑局 → 引导进搭子群 → 形成自约习惯 → 高频复购

路径 4：老客户 → 高价值客户
  老客户 → 推荐充值 → 邀请参加周赛 → 引导预约助教 → 推荐带朋友来 → 成为大客户

路径 5：大客户 → 专属维护
  大客户 → 生日祝福+专属福利 → 充值续费 → VIP赛事邀请 → 转介绍激励 → 防流失
```

### 4.3 转化关键节点（系统必须提供内容支持）

1. 团购核销时 → 加微信话术 + 进群引导
2. 第一次离店时 → 二次到店邀约话术
3. 第二次到店时 → 推卡话术 + 助教体验推荐
4. 加入搭子群后 → 约球接龙 + 竞技局引导
5. 第一次预约助教后 → 助教跟进话术 + 复约邀请
6. 办卡/充值后 → 充值感谢 + 权益说明
7. 30 天未到店时 → 回访话术 + 专属福利
8. 生日/节日时 → 个性化祝福 + 到店优惠

## 6. 当前 MVP 能力复用分析

| 已有能力 | 新产品中的复用方式 | 需要升级的地方 |
|---------|-------------------|--------------|
| **门店资料** | 所有内容生成的基础上下文 | 新增助教资料字段或独立表 |
| **AI 文案生成 (TextProvider)** | 团购话术、助教朋友圈、搭子局文案、赛事文案 | 新增 15-20 个场景 Prompt 模板 |
| **活动方案生成** | 周赛方案、充值活动、搭子局活动 | 新增赛事/助教/搭子场景活动模板 |
| **海报生成 (Pillow)** | 助教海报、赛事海报、招聘海报 | 新增 3-5 个海报模板，视觉升级 |
| **生成历史** | 素材库雏形 | 后续加标签/分类筛选 |
| **Dashboard** | 今日运营工作台框架 | 升级规则引擎，按角色推荐 |
| **Prompt Engine (YAML)** | 所有新场景通过 YAML 扩展 | 无需修改引擎 |
| **AI Provider 抽象** | TextProvider 直接复用 | 无需修改 |
| **本地 uploads** | StorageProvider 本地实现 | 后续切 OSS 时替换实现 |

**结论：新产品方向 70% 的工作量是"新增 Prompt 模板 + 新增前端场景入口"，核心引擎和架构不需要重写。当前 MVP 是地基，不是废稿。**

## 7. AI 能力底座规划

### 7.1 为什么需要规划 AI 能力底座

当前已接入 DeepSeek 文本模型，能生成文案/活动方案/海报文案。但未来产品方向会扩展到 AI 图片背景、助教宣传图、视频素材包等。需要提前把能力抽象设计好，避免以后接图片、视频时推翻重来。

核心原则：

```
架构一次性想清楚，功能分阶段落地。
```

### 7.2 TextProvider：文本模型能力

**当前状态**：DeepSeek 是 TextProvider 的第一个实现，已服务朋友圈文案、群公告、活动方案。

**未来扩展场景**（只增加 Prompt 模板，不改 Provider）：

```
团购客户转化话术      助教推广文案          助教招聘文案
助教每日任务          助教客户邀约话术      搭子局/竞技局话术
教练赛事文案          周赛/月赛报名文案     大客户维护话术
前厅 SOP 文案         短视频标题            抖音/小红书文案
视频号文案            拍摄脚本              封面文案
```

**设计原则**：
- TextProvider 统一封装文本模型调用
- 业务层不直接依赖 DeepSeek，只通过 ProviderFactory 获取 TextProvider
- 不同经营场景通过 PromptBuilder 生成不同 Prompt，Provider 本身不变
- 未来替换或增加模型（OpenAI/Claude/通义/豆包）只需新增 Provider 实现，注册到工厂

### 7.3 ImageProvider：图片模型能力

**当前状态**：已有抽象基类但未接入真实模型。海报使用本地静态背景图 + Pillow 合成。

**未来可接入模型**：

```
GPT Image / DALL-E          即梦 / 火山引擎
通义万相                     Midjourney API
Stable Diffusion             其他图片生成/编辑模型
```

**未来服务场景**：

```
海报背景生成          门店活动背景图        赛事海报背景图
招聘海报背景图        助教照片美化          助教宣传图背景
朋友圈配图            短视频封面图          门店氛围图
```

**关键原则：不让 AI 图片模型直接生成完整商业海报。**

```
正确策略：
  AI 图片模型生成背景/氛围图/美化图
  + 程序叠加真实中文、Logo、二维码、价格、门店地址、电话
  = 最终可发布素材
```

原因：
- 中文容易出错字/变形
- 价格数字绝对不能错
- 二维码必须可扫描，AI 无法生成
- Logo 必须是门店真实 Logo
- 助教姓名、标签、预约信息必须准确

**当前 Pillow 海报合成引擎不废弃，继续作为最终合成层。** ImageProvider 只负责背景图/美化图，Pillow 负责叠加所有准确商业信息。

### 7.4 VideoProvider：视频模型能力

**先做规划，不近期开发。**

#### 短期（只做文本，不做视频生成）

不做 AI 视频生成。只做"视频发布素材包"——用户上传门店视频/助教视频后，系统用 TextProvider 生成：

```
视频标题              朋友圈视频配文        抖音文案
视频号文案            小红书标题            封面标题
话题标签              拍摄建议              下一条视频选题
```

#### 中期

```
视频封面图生成（用 ImageProvider）
视频脚本文案
分镜建议
素材归档
视频素材库
```

#### 长期

```
AI 视频生成
AI 自动剪辑
多平台发布辅助
```

**为什么视频不能太早做**：
- 生成成本高、速度慢
- 稳定性不够，商业场景不可控
- 人物一致性难（助教形象不能乱变）
- 真人肖像和授权风险高
- 视频文件大，存储和带宽压力大
- 内容审核风险更高
- 当前球房运营优先靠图文，视频是锦上添花

### 7.5 PromptBuilder：经营场景 Prompt 编排层

**当前状态**：按内容类型生成（生成朋友圈 / 生成群公告 / 生成活动方案）。

**升级方向**：按经营场景生成。

```
当前：按内容类型                    升级后：按经营场景
┌─────────────────┐               ┌─────────────────┐
│ 生成朋友圈       │               │ 团购转私域       │ → 朋友圈 + 话术 + 群公告
│ 生成群公告       │               │ 助教推广         │ → 朋友圈 + 海报 + 话术
│ 生成活动方案     │               │ 搭子局/竞技局    │ → 群公告 + 话术 + 海报
│ 生成话术         │               │ 周赛/月赛        │ → 方案 + 海报 + 群公告 + 战报
└─────────────────┘               │ 大客户维护       │ → 话术 + 福利通知
                                   │ 门店视频发布     │ → 标题 + 配文 + 封面
                                   └─────────────────┘
```

每个经营场景可以输出多种内容：朋友圈、群公告、私聊话术、海报文案、视频标题、执行 SOP、店长待办。

**PromptBuilder 的职责**：

```python
# 伪代码，只表达设计意图

class PromptBuilder:
    """根据经营场景 + 门店资料 + 用户输入，编排出一组 Prompt 任务"""

    def build(self, scene: str, store: Store, params: dict) -> list[PromptTask]:
        """
        scene = "团购转私域" / "助教推广" / "搭子局" / ...
        返回一组 PromptTask，每个 task 对应一个内容产物
        """
        scene_config = self._load_scene_config(scene)
        tasks = []
        for output_type in scene_config.outputs:
            template = self.prompt_engine.load(output_type.template_key)
            prompt = template.render(store=store, **params)
            tasks.append(PromptTask(
                prompt=prompt,
                output_type=output_type.name,  # "朋友圈" / "群公告" / "海报文案"
                provider_type="text",           # 或 "image"
            ))
        return tasks
```

**这样做的价值**：
- 不再像普通 AI 文案工具
- 用户不需要自己写 Prompt
- 围绕台球房经营目标生成内容
- 方便未来接图片/视频能力（一个场景可以同时触发文本+图片生成）
- 方便做"经营场景一键生成"（选一个目标，输出一套完整物料）

**当前 PromptEngine（YAML 模板 + 变量替换）是 PromptBuilder 的底层能力**，PromptBuilder 在 PromptEngine 之上增加了"场景编排"层——知道一个经营场景需要调用哪几个模板、生成哪几种内容。

### 7.6 StorageProvider：素材存储抽象

**当前状态**：`server/uploads/` 本地目录存储。

**未来可接入**：

```
阿里云 OSS          腾讯云 COS          AWS S3
Cloudflare R2       其他对象存储
```

**StorageProvider 统一管理**：

```
门店 Logo            微信二维码           海报合成结果
AI 生成背景图        助教照片             助教宣传图
门店照片             门店视频             视频封面
视频发布素材包
```

**设计原则**：

```python
# 伪代码

class StorageProvider(ABC):
    @abstractmethod
    async def upload(self, file_bytes: bytes, filename: str, content_type: str) -> str:
        """上传文件，返回可访问 URL"""
        ...

    @abstractmethod
    async def delete(self, file_url: str) -> None:
        ...

class LocalStorageProvider(StorageProvider):
    """当前实现：存到 server/uploads/"""
    ...

class OSSStorageProvider(StorageProvider):
    """未来实现：存到阿里云 OSS"""
    ...
```

**演进策略**：
- 当前 MVP 继续使用 `uploads/`，即 LocalStorageProvider
- 上线试用期也可以先本地持久化
- 商业化后替换为 OSSStorageProvider
- 业务层通过 StorageProvider 接口调用，切换存储不改业务代码
- **本阶段只规划，不开发**

## 8. 未来 AI 工作流设计

### 工作流 1：AI 海报背景生成

```
选择经营场景（充值活动/周赛/搭子局/招聘/助教预约）
→ PromptBuilder 生成图片 Prompt（无文字、无 Logo、预留文字区域）
→ ImageProvider 生成背景图
→ Pillow 叠加标题、正文、Logo、二维码、门店信息
→ StorageProvider 保存
→ 写入 generations 表
→ 前端预览 + 下载
```

**当前替代方案**（ImageProvider 未接入前）：使用本地预置的高质量静态背景图，其余流程不变。

### 工作流 2：助教宣传图生成

```
选择助教 → 读取助教资料和照片
→ 选择用途：朋友圈/群推荐/预约海报/封面
→ ImageProvider 美化照片或生成背景
→ Pillow 叠加助教昵称、标签、预约话术、门店二维码
→ StorageProvider 保存
→ 写入历史
```

**注意**：
- 使用真实助教照片，不凭空生成虚构助教
- 涉及真人照片需门店获得授权
- AI 只负责美化/背景/风格，不篡改关键信息

**当前替代方案**：不做 AI 美化，直接用助教照片 + Pillow 合成海报模板。

### 工作流 3：视频发布素材包

```
上传门店视频/助教视频
→ 系统读取视频基本信息（时长/文件名/上传者备注）
→ TextProvider 生成：标题、配文、话题标签、封面文案、拍摄建议
→ 可选 ImageProvider 生成封面背景
→ 保存为视频素材发布包
→ 用户复制各平台文案发布
```

**短期只做标题和配文（纯 TextProvider），不做 AI 视频生成。**

### 工作流 4：经营场景一键生成

```
选择经营目标：团购转私域 / 助教推广 / 搭子局 / 周赛
→ PromptBuilder 编排多内容任务
→ TextProvider 生成文案和话术（多条并行）
→ ImageProvider 生成海报背景（如已接入）
→ Pillow 合成海报
→ StorageProvider 保存全部素材
→ 前端展示"内容包"：朋友圈 + 群公告 + 话术 + 海报，一次性复制/下载
```

**这是产品的终极形态**：用户选一个经营目标，系统输出一套完整的可执行运营物料。但它建立在所有基础能力之上，不急于一步到位。

## 13. 风险点

| 风险 | 严重性 | 规避方案 |
|------|--------|---------|
| **场景做太多每个都浅** | 🔴 高 | 每个阶段只做 1-2 个场景做深做透 |
| **Prompt 质量决定体验** | 🔴 高 | 每个 Prompt 找真实球房场景测试 |
| **助教模块复杂度膨胀** | 🟡 中 | 第一版只做资料卡+内容生成，不做排班/绩效/考勤 |
| **和收银系统边界模糊** | 🟡 中 | 一旦涉及金额/余额/支付立即停止 |
| **角色系统过早复杂化** | 🟡 中 | MVP 不做权限分离，先用同一套页面 |
| **AI 图片接入时合成流程断裂** | 🟡 中 | 保持 Pillow 合成层不变，ImageProvider 只替换背景图来源 |
| **PromptBuilder 过度设计** | 🟡 中 | 第一版 PromptBuilder 可以只是"一个场景对应几个 YAML 模板的映射表"，不做复杂编排引擎 |
| **StorageProvider 迁移时数据丢失** | 🟢 低 | 文件名用 UUID，URL 字段统一存储，迁移时只换实现不换接口 |
