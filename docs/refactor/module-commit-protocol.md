# 模块施工与提交协议

## 目的

本协议把重构合同变成可执行的模块施工节奏。一次只处理一个 active work unit；附属文档只记录证据，不拥有产品架构或代码状态。

## 权威顺序

1. `BilliardBuddy-重构合同.md`：产品结果、长期边界和完成定义。
2. `docs/refactor/refactor-roadmap.md`：全局依赖顺序、当前游标和唯一下一步。
3. 当前模块总纲：该模块的内部边界、状态所有者、失败/恢复规则和退出条件。
4. 当前正式源码与实际生产调用链：当前实现事实。
5. 专题参考文档、核验账本和工作树盘点：证据与记录，不得单独宣布完成。

文档中的历史“已完成”、提交数量、类型检查或页面存在，都不能替代当前源码证据。文档互相冲突时，修正文档并保留真实源码作为裁决依据。

## 每个模块的固定施工单

进入模块前，路线图必须只保留一张施工单：

```text
Work-unit: R?/A?/M? — 单点名称
Outcome: 唯一可观察产品结果
Evidence: 当前入口、状态权威、消费者和参考证据
Constraints / Non-goals: 本轮必须守住和明确不改的内容
Allowed scope: 可修改的代码、合同和记录文件
Verification / Exit: 类型、生产构建、静态审计和失败/恢复证据
Next cursor: 唯一下一工作单元
```

施工中发现其他缺口，只登记到对应后续模块。只有错误结果、数据丢失、重复副作用、权限越界或无法恢复，才能中断当前游标。

## 脏工作树处理

现有脏工作树是候选资产池，不是一个可直接提交的模块。开始代码模块前：

- 记录 `git status`、暂存区、未跟踪文件和当前基线；不重置、覆盖或删除用户已有改动。
- 按差异块而不是文件名确认模块归属；一个共享文件的不同差异块可以属于不同模块。
- 锁文件、共享合同和应用壳跟随实际消费者所在模块，不能组成“杂项提交”。
- 没有消费者、无法证明归属或已经被替代的代码，保留到 R8 清理裁决，不提前删除或提交。

必要时在独立 `codex/` 分支或干净 worktree 中重建模块；原脏工作树继续保留，作为待审阅参考，不把它当作完成证据。

## 模块提交门禁

模块退出前依次完成：

1. 只暂存该模块已经裁决的文件和对应证据记录。
2. 检查 `git diff --cached --name-status`、`git diff --cached --check` 和模块边界，确认没有跨模块差异。
3. 运行该模块需要的服务端/桌面类型检查、生产构建和源码可达性审计；不编写或运行测试、smoke、模拟请求或安装验收。
4. 在核验账本记录已证明的结果、未验证事实、残余缺口和下一游标。
5. 使用清楚的中文提交信息，只提交一次；提交不等于推送，除非用户另行要求推送。

提交后，工作树里其余改动继续保留，不得用 `git add -A`、宽泛目录或“顺手整理”混入下一模块。

## 完成定义

一个模块只有在其 Outcome、Constraints、Allowed scope 和 Verification 全部有当前证据时才算完成。不能因为改动很多、构建通过或附属文档写了“完成”就推进游标。
