## 结论摘要

2026-06-27 对已打开的装机版 `台球运营管家.app` 做了真机实测。核心能力是跑通的：本地后端健康、主对话发送、SSE 流式回复、会话落库、MCP 状态读取、台球知识库问答、本机文件夹读写改查、Excel 只读摘要都能工作。

主要问题不在“能不能跑”，而在产品最终形态还没有足够收敛：它应该是一个通用本机 AI Agent，在台球行业里默认变成能帮门店做运营、素材和文件工作的桌面助手。前端不能把能力全部摊开给用户看，也不能把 API Key、MCP、插件、命令、内部思考等开发者概念暴露成主路径。真实用户只需要三件事：说清楚要干什么、给它素材/文件夹、拿到能直接用的结果。

后续开发不应继续堆功能入口，而要围绕四条主线收敛：`一句话开始干活`、`选择工作文件夹`、`生成营销素材`、`保存/找回成品`。视觉上不推翻现有浅色、干净、macOS 感方向，但所有框、卡片、图标、间距、层级都要更精致；能不显示的图标不显示，能合并的控制项合并，能后台判断的参数不要让普通用户选择。

后续统一以本文作为真机实测和产品收敛记录，不再拆成多份。

## A0. 最终成品形态

### A0.1 产品一句话

最终产品应该是：**装在电脑上的通用 AI 助手，用户一句大白话就能让它读文件、改文件、整理资料、生成图片视频、写文案、查资料；当进入台球房模式时，它会按台球门店真实经营场景，把 PPT 里的营销、客户运营、人才管理、数据分析变成可执行任务。**

它不是：

| 不是 | 为什么 |
|---|---|
| 不是单纯台球知识库 | 用户不是来上课，而是要今天把事做完 |
| 不是生图/生视频工具箱 | 图片和视频只是通用 Agent 的产物之一，核心是“想要什么就做出什么” |
| 不是复杂配置平台 | API Key、MCP、插件、模型参数不是普通门店用户的主路径 |
| 不是图标和按钮堆出来的工作台 | 界面越复杂，低学历用户越不敢点 |

### A0.2 首屏应该让用户怎么开始

首屏只保留最强的 3 个开始方式，不要为了展示能力而堆卡片。

| 入口 | 用户心智 | 后台动作 |
|---|---|---|
| `直接说要做什么` | 我一句话交代任务 | 自动判断是通用任务、台球任务、素材生成还是文件作业 |
| `选择工作文件夹` | 让 AI 在这个文件夹里干活 | 绑定当前工作台的主目录，后续读写改查默认在这里 |
| `做图片/视频` | 我要海报、封面、朋友圈图、抖音视频 | 仍从对话发起，右侧出现轻量预览/编辑面板；不先做复杂工作室 |

台球房模式可以在首屏作为默认行业能力出现，但不要压过通用 Agent 心智。建议表达为：`当前行业：台球房`，旁边可切回 `通用助手`。

### A0.3 界面与交互总原则

| 原则 | 具体要求 |
|---|---|
| 少显眼图标 | 图标只用于识别和动作，不为装饰出现；不需要标注的地方不要硬加图标 |
| 少入口 | 普通用户首屏不出现 API Key、MCP、插件、GitHub、命令、模型名 |
| 少选择 | 能由系统按场景判断的比例、平台、prompt、风格，不让用户先填一堆参数 |
| 强结果 | 每个任务都要产出可复制、可保存、可打开、可找回的成品 |
| 保留过程但不打扰 | 执行过程保留为任务进度，内部思考和工具细节默认折叠 |
| 通用能力不弱化 | 台球是行业包，不是产品边界；整理文件、看表、写合同、做图视频都应好用 |

### A0.4 真实门店日常对话流程

结合 PPT，真实门店用户不是按功能模块思考，也不一定会主动点击某个任务窗口；更多时候是直接在对话框里说今天遇到的事。系统要在对话背后自动调用台球行业知识，把口语问题翻译成经营判断和可执行动作。

| 场景 | 用户可能说的话 | 对话里应该怎么接 | 交付物/下一步 |
|---|---|---|---|
| 开店前 | `今天店里该干啥，你给我排一下` | 按营销、客户运营、人才、数据拆今天重点 | 今日运营建议 + 可保存任务 |
| 看报表 | `看这个经营表，老板能听懂地说3个问题` | 读 Excel，找台费、助教费、商品费、好评、活动异常 | 问题诊断 + 整改清单 |
| 拉客 | `今晚下雨没人，给我3个办法` | 结合客户类型和当天场景给可执行拉客方案 | 朋友圈/客户群话术 + 员工动作 |
| 做素材 | `做张周赛海报，发朋友圈` | 自动补 prompt、选比例、生成图、保存成品 | 海报 + 标题/文案 + 尺寸信息 |
| 做视频 | `用这几张助教照片做抖音同城视频` | 先按社交媒体营销视频理解需求，继承图片/素材上下文，而不是让用户填模型参数 | 视频任务/封面/标题/发布文案；真实出视频显示耗时和成本边界 |
| 处理客户 | `客户说台泥脏球杆歪，怎么回` | 生成平台回复、整改动作、员工交代 | 回复话术 + 整改清单 |
| 招人 | `帮我做招聘助教的视频和文案` | 从 PPT 的招聘渠道、形象要求、团队氛围出发 | 招聘视频/海报 + 发布文案 |
| 收尾复盘 | `把今天的问题整理成明天任务` | 把会话、文件、报表诊断转成明日待办 | 明日任务清单 |

### A0.5 应该后置或隐藏的东西

这些不是不能有，而是不应成为普通用户主路径；如果继续放在显眼位置，就会让界面变复杂、变沉闷。

| 能力 | 产品处理 |
|---|---|
| API Key / Base URL / 模型名 | 默认隐藏到高级设置；普通用户只看到“AI 已内置，可以直接用” |
| MCP / 插件 / GitHub 安装 | 作为高级外接工具，不放在首屏和普通设置主区 |
| 命令行 / 终端输出 | 默认展示成“正在整理文件/正在读取表格”，完整命令放技术详情 |
| 工具名 / 内部 reasoning | 默认折叠；普通用户只看任务进度和结果 |
| 过多功能图标 | 只保留常用动作图标；正文和列表不要让模型自由塞 emoji |
| 角色权限 | 店长/教练/助教/前厅只作为任务视角，不作为软件权限 |

| 用户应能输入自己球房背景，让行业知识贴合这家店 | A0.10、J7、K9、L2、L3 | 建立可编辑的门店背景/店脑画像：位置、定位、球台、价格、客群、团队、渠道、数据、素材、常用活动；对话里逐步补全，不做强制长表单 | 已纳入 |

### A0.7 给开发者的执行编排

后续改代码时，建议按下面顺序拆任务。不要先从单个按钮、单个图标开始修，否则容易把产品继续做散。

| 顺序 | 要先落的事 | 目标 |
|---|---|---|
| 1 | 首屏和主路径收敛 | 让用户第一眼只看到说需求、选文件夹、做图片/视频 |
| 2 | 工作目录/工作台模型 | 文件夹入口、会话/任务绑定；为多窗口并行预留模型，不先做完整并发面板 |
| 3 | 普通/高级两层 UI | 普通用户隐藏 API Key/MCP/插件/模型/命令；高级能力保留 |
| 4 | 对话内生成 + 右侧预览 | 生图/生视频先不做复杂工作室；聊天自然发起，右侧承接预览、重做、保存 |
| 5 | 台球对话能力增强 | 不堆前端窗口，把 PPT 的营销、客户运营、人才管理、数据分析注入对话理解、追问、答案结构和轻量下一步 |
| 6 | 轻量门店资料/店脑画像 | 先做“AI 记住了什么/我的球房资料”轻面板，不先做完整经营后台 |
| 7 | 任务进度与后台续跑 | 流式过程保留但美化；先保证切窗口/断线不丢任务，多窗口并行后置 |
| 8 | 最近作品/最近删除 | 先做最近作品、最近任务、最近删除；完整素材库/成品库后置 |
| 9 | 风险动作与权限 | 发布/群发/删除/危险修改人工确认；完全访问下普通操作不反复确认 |

### A0.8 人类自然使用逻辑审计

这一节专门回答一个更底层的问题：真实用户不会按软件内部概念来使用产品。尤其是低学历或不懂技术的门店用户，他们不会先想“我要挂哪个知识库、用哪个模型、选哪个 MCP、开哪个工作台、设置什么比例”。他们通常只会说一件很乱、很急、很具体的事。产品应该把这些乱话接住，再自动整理成任务。

| 不符合自然使用逻辑的点 | 用户真实心智 | 产品应该怎么改 |
|---|---|---|
| 让用户先理解“通用模式/台球模式/知识库” | 用户只知道自己要解决今天的问题 | 对话里自动判断是否需要台球行业知识；前端只轻量显示当前行业状态 |
| 让用户先选角色或模块 | 用户不会先说自己是店长还是前台，常常会跨角色提问 | 角色只做回答视角，系统从问题里推断口径，不要求先切换 |
| 让用户先配置 API Key、MCP、模型、插件 | 普通用户只想知道能不能直接用 | 默认内置可用；高级配置折叠到很深的位置 |
| 让用户理解“工作目录”这个抽象 | 用户理解的是“让它在这个文件夹里干活” | 入口表达成“新建空白文件夹/使用现有文件夹”，选完后所有动作默认在这里发生 |
| 让用户自己区分聊天、生图、生视频、文件工具 | 用户只会说“给我做个能发抖音的东西” | 聊天作为自然入口；右侧轻量预览承接调整和保存，复杂工作室后置 |
| 让用户自己写 prompt、选比例、选供应商 | 用户只知道发朋友圈、发抖音、打印海报 | 系统按平台和场景自动补比例、构图、安全区、文字策略；用户明确说 9:16 时必须硬执行 |
| 每一步都弹确认 | 用户会觉得 AI 不敢干活，尤其完全访问模式下体验很差 | 普通读写改查直接执行；只对发布、群发、删除、危险修改、高成本动作确认 |
| 任务必须停留在当前窗口才继续 | 用户会切微信、表格、浏览器，也会同时做多件事 | 长任务后台运行；窗口只是订阅进度，多个窗口互不影响 |
| 生成结果散落在聊天里 | 用户过几天会忘了海报、视频、文案、报表诊断在哪里 | 第一阶段自动进入最近作品/最近任务，并提供打开保存位置；会话里保留预览和入口 |
| 删除后看不见去哪里找 | 用户删除后会后悔或误删 | 提供最近删除/归档入口、恢复、彻底删除、全部清空 |
| 报错只显示技术失败 | 用户不知道下一步该干什么 | 失败卡要说清楚“发生了什么、影响什么、现在能点什么”：重试、换文件夹、复制结果、联系高级设置 |
| 执行过程全是内部术语 | 用户需要看到它在干活，但不想看一堆工具名 | 展示成精致任务进度；工具名、命令、日志放“技术详情” |
| 首页为了证明功能多而堆入口 | 用户看到太多选择会不敢动 | 首屏只保留主路径，更多能力从对话和结果动作自然长出来 |

最重要的判断标准：**用户能不能先把话说出来，而不是先学会这个软件的概念。** 如果一个入口、术语或选择项要求用户先理解产品内部结构，它就不应该出现在普通主路径。

### A0.9 二轮自然使用逻辑补充

继续往真实使用里想，还会有一批不一定在功能清单里、但会决定用户敢不敢长期用的问题。它们不是单个按钮问题，而是“人和软件相处”的问题。

| 编号 | 不符合人类使用逻辑的点 | 真实用户会怎么想/怎么做 | 应该形成的产品逻辑 |
|---|---|---|---|
| U1 | 让用户自己记住东西放哪了 | 用户今天生成海报，明天可能只记得“昨天做过一个周赛图” | 第一阶段用最近作品/最近任务找回；后续完整库再支持按时间、类型、会话、工作目录、平台、尺寸检索 |
| U2 | 只给最终结果，不给“我现在能干啥” | 用户拿到一段方案后，往往不知道下一步是复制、发群、做海报还是派员工 | 每个结果底部给 2-4 个自然动作：复制、保存、生成海报/视频、转成任务、导出 |
| U3 | 修改真实文件前没有信任铺垫 | 用户怕 AI 把报表、合同、照片改坏 | 改文件默认有备份、改动预览、恢复入口；完全访问下也要让用户知道“能回退” |
| U4 | 把“上传素材”当成唯一素材来源 | 门店素材常在微信下载、桌面、相册导出、U 盘、下载文件夹里 | 允许从工作目录、最近文件、截图、剪贴板、拖拽、相册导出目录继续找素材 |
| U5 | 不承认用户会中途改主意 | 用户常会说“刚才那个不要，换成周五”“颜色别这么土”“发小红书，不发朋友圈” | 生成和对话都要有版本；重做不能覆盖旧版本，能回到上一个满意版本 |
| U6 | 让用户每次从零解释门店情况 | 用户会烦：店名、地址、活动时间、二维码、常用套餐不该每次都问 | 门店资料、常用活动、常用二维码、常用风格进入可编辑记忆；引用时可见可改 |
| U7 | 把失败当成终点 | 生图失败、网络失败、文件读不了时，用户不会理解错误码 | 失败后给补救路径：重试、换模型/降质量、换素材、复制已生成文案、打开高级详情 |
| U8 | 不区分“草稿”和“正式对外” | 用户让 AI 写东西时可能只是看看，不代表要发出去 | 默认产出都是草稿；发布/群发/私信/覆盖正式文件才进入确认 |
| U9 | 让用户自己判断内容是否适合平台 | 用户不知道抖音、小红书、朋友圈、微信客户群在尺寸和表达上有什么区别 | 系统按平台自动调整尺寸、标题、文案长度、封面安全区和语气 |
| U10 | 忽视微信是工作现场 | 台球房很多素材、客户、通知、话术都在微信里流转 | 结果动作要支持复制到微信、保存到本地、导出图片/视频、打开文件位置；自动群发仍需确认 |
| U11 | 不给“稍后继续”的心智 | 用户会被客人打断，过半小时回来继续 | 会话、任务、生成草稿、未完成进度都要能恢复；首页有“继续上次工作” |
| U12 | 不处理多人共用一台电脑 | 门店可能老板、前台、助教轮流用同一台电脑 | 工作台、成品、门店资料要有来源和时间；敏感设置放高级，不把个人隐私混进公开成品 |
| U13 | 不显示消耗和等待 | 生图/生视频会等，用户会怀疑卡住或乱扣额度 | 长任务显示排队、预计时间、当前阶段；高成本动作前说明会消耗额度 |
| U14 | 把“删除”做得太轻 | 用户可能误删会话、海报、视频、记忆、文件版本 | 删除先归档/最近删除，彻底删除二次确认，并提供清空入口 |
| U15 | 只按功能命名，不按结果命名 | “MCP”“工具”“任务流”对用户没意义 | 普通界面用“做海报”“看报表”“整理文件”“找回作品”“继续上次”这种结果词 |

这一轮补充可以压成一句产品原则：**用户不是来管理软件的，用户是来把现实里的事丢给软件处理的。** 软件要承认用户会忘、会怕、会改主意、会被打断、会跨微信/桌面/相册/下载文件夹工作。

### A0.10 门店背景资料与店脑画像

结论：用户应该可以输入自己这家球房的背景，而且这不是“高级配置”，而是台球行业模式里非常重要的基础能力。PPT 里的经营逻辑反复围绕市场调研、定位、定价、产品氛围、客户分类、传播渠道、团队岗位和数据复盘展开；如果软件不知道这家店在哪、什么定位、多少球台、什么价格、主要客群是谁、团队配置怎样，回答就容易变成通用建议。

但这个能力不能做成一上来就逼用户填完的大表单。更合理的方式是：**门店背景资料可逐步补充，对话中自然追问和沉淀，用户随时可看、可改、可删除。**

| 背景模块 | PPT 依据 | 用户可以输入什么 | 用在哪里 |
|---|---|---|---|
| 基础信息 | 市场调研关注城市、位置、业态 | 店名、城市/商圈、详细地址、营业时间、门店阶段：筹备/新开/稳定/下滑/接手改造 | 文案落款、同城定位、开业计划、活动时间 |
| 场地与硬件 | 场地租赁关注层高、租金、停车、广告位、面积、动线 | 建筑面积、套内面积、球台数量、球台品牌、包厢/大厅/竞技区/引流区、停车、电梯、招牌位置 | 定位判断、动线建议、海报卖点、竞对对比 |
| 门店定位 | PPT 区分社区球房、竞技球房、商业球房、竞技商业球房 | 当前定位、想吸引的人群、主打卖点、和周边竞对的差异 | 回答不再泛泛而谈，能判断该走助教氛围、竞技氛围还是社区复购 |
| 价格体系 | 定价围绕台费、商品费、器材费、助教管理费、分区定价、团购 | 台费标准、会员卡/一卡通、团购品类、引流价、包厢价、助教费、商品/器材价格 | 定价诊断、团购设计、活动文案、避免长期低价 |
| 客户结构 | PPT 客户分散客、竞技客户、助教客户、追分客户 | 主要客群、客户年龄、消费力、来店频次、微信群/竞技群规模、大客户情况 | 拉客方案、客户维护话术、活动设计、风险边界 |
| 渠道与账号 | PPT 传播渠道含美团/大众点评/抖音本地推/达人/短视频/直播/小红书等 | 美团/大众点评评分、抖音/视频号/小红书账号、团购状态、达人合作、员工矩阵 | 发布文案、平台尺寸、评价维护、同城曝光计划 |
| 团队配置 | PPT 按规模给店长、前厅、助教管理、教练等配置 | 店长、教练、助教管理、助教、前厅/收银/服务员人数；谁负责营销、谁负责客户维护 | 今日任务分配、日报、招聘、培训、岗位复盘 |
| 助教与教练能力 | PPT 讲助教管理、教练工作流程和人才画像 | 助教数量、助教照片素材、招聘渠道、教练档位、竞技群、比赛活动频率 | 助教视频、招聘文案、教练活动、竞技客户转化 |
| 经营数据 | PPT 店长关注营业额、台费、助教费、商品费、团购占比、好评、平均时长 | 日/月营业额、台费、助教费、商品费、充值、团购占比、好评数、评分、平均陪打时长 | 报表诊断、日报、阶段复盘、老板能看懂的建议 |
| 常用素材 | PPT 强调页面展示、场景展示、美女展示、氛围、人情世故 | 门店照片、球桌照片、助教照片、Logo、二维码、常用海报风格、品牌色 | 海报/视频生成、封面、朋友圈图、小红书图文 |
| 常用活动 | PPT 提到会员赛、小游戏、团购爆款、开业前后节奏 | 周赛、会员赛、红牛挑战、免费体验、套餐、招聘、节假日活动 | 快速生成活动方案、海报、视频、员工执行清单 |
| 约束与偏好 | 安全红线和真实门店执行边界 | 不做哪些活动、不能用哪些词、老板偏好语气、常用价格尾数、是否保守/激进 | 避免每次重复提醒，减少不合适输出 |

前端建议：

| 入口 | 处理方式 |
|---|---|
| 初次进入台球房模式 | 只问 3 个最关键问题：店名/城市、门店阶段、主定位；允许跳过 |
| 对话过程中 | 当用户问拉客、定价、报表、海报时，只追问当前最影响结果的 1 个背景问题 |
| 设置页 | 提供“我的球房资料”入口，分模块编辑，不和 API/MCP 高级配置混在一起 |
| 文件导入 | 支持从 Excel、报表、门店介绍、活动表、图片文件夹中提取背景，提取后让用户确认 |
| 记忆展示 | 回答引用门店背景时要可见，例如“按你店目前 26 张球台、主做竞技客户来算” |
| 修改/删除 | 用户能改错、删除旧资料、区分行业知识和自己门店事实 |

这里要特别注意：**门店背景不是权限，不是角色，也不是必须填完才能用。** 它是让“台球行业知识库”从通用经营方法，落到“这家店今天该怎么做”的桥。

### A0.11 门店背景哪些落表、哪些不落表

这里不是第一轮数据库施工图，而是给后续 harness 记忆分层用的边界清单。第一轮只做轻量 `我的球房资料/AI 记住了什么`；下面这些“落表”只表示后续如果要结构化保存，应该放在哪一层。原则不是“能收集就都收集”，而是：**稳定事实可长期记，动态数据先服务当前诊断，素材先作为文件引用，模糊判断进待确认记忆，敏感/临时/未确认内容不落表。**

| 分类 | 应该落在哪里 | 适合保存的内容 | 不适合直接保存的内容 | 说明 |
|---|---|---|---|---|
| 稳定门店资料 | 门店背景主表/分表 | 店名、城市商圈、地址、营业时间、门店阶段、定位、球台数量、球台品牌、分区、停车、包厢、主客群、主卖点 | 用户随口说的临时想法、AI 猜测的定位 | 这是“这家店是谁”的底座，适合长期引用 |
| 价格与产品 | 价格/产品表 | 台费、包厢价、引流价、团购套餐、会员卡/一卡通规则、助教费、商品/器材价格 | 一次性活动价、还没确认的建议价 | 价格会影响海报、团购、活动、诊断，应该可编辑有更新时间 |
| 渠道与账号状态 | 渠道表 | 美团/大众点评/抖音/视频号/小红书账号名或链接、评分、星级、团购状态、达人合作、员工矩阵数量 | 密码、登录 token、私信内容、未授权平台数据 | 渠道状态可落表；凭据只能进安全凭据区，普通表不存 |
| 团队配置 | 团队快照表 | 店长/教练/助教管理/助教/前厅/收银/服务员人数，岗位负责人，谁负责营销/客户维护 | 员工私人隐私、身份证号、无关联系方式 | 保存人数和职责即可，避免把人事隐私做重 |
| 经营数据 | 日/月经营数据流水表 | 营业额、台费、助教费、商品费、充值、团购占比、好评数、评分、平均陪打时长、到岗/上钟 | 覆盖式写进门店主表 | 经营数据有日期，应该按日/月留历史，不应该只保存一个“最新值” |
| 客户结构 | 客群画像表/记忆备注 | 散客/竞技/助教/追分客户占比判断、微信群/竞技群规模、大客户类型、常见客诉 | 单个客户隐私、客户聊天原文、电话微信号 | 保存群体画像，不默认保存个人隐私 |
| 常用活动 | 活动模板表 | 周赛、会员赛、小游戏、红牛挑战、免费体验、招聘、节假日套餐、常用奖品 | 已过期且不再复用的临时活动细节 | 常用活动可复用；单次活动结果进任务/成品记录 |
| 常用素材 | 素材库/文件索引 | 门店照片、球桌照片、助教照片、Logo、二维码、品牌色、常用海报风格、视频素材路径 | 图片二进制塞进门店背景表、未经同意的人脸素材乱引用 | 素材应是独立资源，有路径、标签、用途、授权/可用状态 |
| 约束与偏好 | 可编辑记忆/偏好表 | 老板喜欢的语气、禁用词、保守/激进程度、不做的活动、常用价格尾数、常用发布风格 | AI 内部推理、一次对话里的情绪化判断 | 这类不是硬事实，但对输出很有用，要可见可改 |
| 竞对信息 | 竞对表/调研备注 | 竞对名称、距离、定位、价格、团购、评分、装修/器材、优势劣势、更新时间 | 道听途说且未确认的攻击性内容 | 竞对信息会变，必须带来源和更新时间 |
| 对话中临时上下文 | 当前会话上下文 | “今晚下雨”“这周五活动”“刚才那张图不要” | 不应自动变成长期门店事实 | 临时上下文只服务当前任务，除非用户确认“以后都按这个” |
| AI 推断 | 待确认记忆 | “看起来你店更像竞技商业球房”“可能团购品类太多” | 直接当成事实写入门店资料 | AI 推断必须带“待确认”，让用户点确认后再固化 |
| 安全敏感信息 | 不进普通表；必要时进安全区 | 平台凭据、支付信息、个人隐私、员工敏感资料 | 明文落普通业务表 | 这类内容即使用，也要最小化、加密、可删除 |
| 红线/违法风险内容 | 不落表或只记录风险标签 | “用户曾问过高风险玩法”这类可做风险标签 | 具体赌博金额、盘口、性交易暗示、规避平台风控细节 | 避免产品把不可取内容沉淀成可复用知识 |

建议后续数据心智：

| 数据层 | 作用 | 用户可见方式 |
|---|---|---|
| `我的球房资料` | 保存稳定事实和可编辑背景 | 分模块表单，少字段、可跳过 |
| `经营数据` | 保存日报/月报/Excel 提取的历史数据 | 趋势、对比、诊断引用 |
| `素材库` | 保存图片、视频、Logo、二维码、海报成品 | 可搜索、可预览、可替换 |
| `店脑记忆` | 保存偏好、约束、常用说法、AI 待确认判断 | “AI 记住了什么”面板，可确认/删除 |
| `任务/成品记录` | 保存一次次对话、生成、导出、发布草稿 | 最近任务、继续上次、成品找回 |

前端不要把这些都暴露成数据库概念。第一阶段普通用户只需要看到两类轻入口：`我的球房资料`、`最近作品/最近任务`。经营数据、素材库、成品库、价格表、渠道表等先作为后台组织方式或后续扩展，不进入首屏和 P0 主路径。

### A0.12 Codex 式减法审计

2026-06-28 重新按 Codex/Claude Code 这类本机 Agent 的使用逻辑复核本文：第一阶段不应该把产品做成“台球运营后台 + 物料管理系统 + 数据 BI + 插件平台”。更准确的核心形态是：**用户打开一个工作文件夹，在对话里交代任务，AI 直接读写改查、展示执行过程、给出可保存结果，并且关键动作可确认/可回退。**

这次审计的判断标准：

| 标准 | 保留 | 降级/删除 |
|---|---|---|
| 是否像 Codex 的核心工作流 | 对话、工作目录、本机文件作业、权限、执行过程、diff/回滚、最近结果 | 大量固定功能窗口、复杂后台配置、入口矩阵 |
| 是否让用户先说需求 | 用户一句话开干，系统判断要不要读文件/做图/查资料/用行业知识 | 先让用户选择角色、模块、素材库、数据层、模型参数 |
| 是否第一阶段必须 | 影响“能不能自然开始、能不能把活干完、能不能找回结果”的能力 | 虽然真实但可后置的管理系统、物料模板、BI、插件生态 |

按这个标准，文档里的能力重新分层：

| 处理 | 项目 | 原因 | 第一阶段做法 |
|---|---|---|---|
| 保留为 P0 | `直接说需求`、`选择工作文件夹`、`做图片/视频` 三入口 | 这是用户开始干活的最短路径 | 首屏只保留这些主路径，别做功能展板 |
| 保留为 P0 | 工作目录/项目模型 | Codex 类产品的核心就是“在这个文件夹里工作” | 文件夹走工作目录入口；回形针只加参考文件/图片/视频 |
| 保留为 P0 | 普通/高级两层 UI | 低学历用户不能先看到 API Key、MCP、插件、模型 | 默认只说“AI 已内置，可以直接用”；高级设置深藏 |
| 保留为 P0 | 台球知识作为对话背后的行业脑 | 用户不是来选模块，而是希望问什么都顺手 | 不做岗位窗口矩阵；在对话里自动用行业知识理解问题 |
| 保留为 P0 | 执行过程美化 | 用户要看到 AI 真的在干活 | 保留步骤，做成精致任务进度；工具名/命令/reasoning 默认折叠 |
| 保留为 P0 | 结果后的自然动作 | 没有下一步，用户还要自己想怎么用 | 每个结果给复制、保存、重做、转任务、导出、做成视频等少量动作 |
| 降级为 P1 | “生成工作室/营销物料工作室” | 作为 P0 太重，容易变成小 Canva | 先做对话内生成 + 右侧轻量预览/编辑；完整工作室后置 |
| 降级为 P1 | 成品库/素材库一级入口 | 真实有用，但完整库会拖慢第一阶段 | 先做“最近作品/最近任务/打开保存位置”；搜索、标签、版本库后置 |
| 保留为 P0-B | 任务后台化最小闭环 | 切窗口不停止是桌面 Agent 的基本体验，但不必一开始做全局任务中心 | 先保证当前任务后端续跑、前端可重连；多窗口并行/全局任务中心后置 |
| 保留为 P0-B | 我的球房资料轻量版 | 必须有，但不能变成大表单/后台档案系统 | 先做轻量资料 + AI 记住了什么；分表、经营流水、渠道表后置 |
| 降级为 P1/P2 | 经营数据流水/趋势分析 | 这是 BI 能力，不是第一阶段 Agent 主路径 | 先读 Excel、诊断、生成整改清单；连续日报/月报趋势后置 |
| 降级为 P2 | 特殊物料尺寸：A4/A3/桌牌/易拉宝/公众号头图 | 场景真实，但会把产品拉向物料设计软件 | 第一阶段只提示“不完整支持/需要打印版”，不做模板体系 |
| 降级为高级 | MCP、插件、GitHub、Hook、命令细节 | 这是 Agent 生态能力，不是普通用户起点 | 默认隐藏；高级模式才展示和配置 |
| 暂不做主路径 | 店长/教练/助教/前厅角色工作台 | 角色是回答视角，不是软件入口 | 用户在对话里说“按前台口吻/给店长汇报”即可 |
| 暂不做主路径 | 平台账号发布状态中心 | 自动发布/账号管理风险高且复杂 | 结果默认是草稿；发布/群发继续人工确认，状态中心后置 |

因此，后续开发优先级要收敛成一句话：**先把它做成“懂台球行业的 Codex 式本机工作台”，再扩展成素材库、经营数据、物料模板和平台发布系统。** 如果一个功能不能让用户更快开始、更敢交给 AI 干活、更容易拿到/找回结果，就不要放进 P0。

### A0.13 开发执行版：怎么按本文开工

这份文档可以作为开发总依据，但开发时不要从后面的长问题列表随机挑。后续所有实现先按本节执行：本节负责定顺序、定边界、定验收；后面的 A-L 节负责解释为什么、提供真机证据和专项细节。

开发总原则只有一个：**先把主链路做短、做稳、做顺，再扩展管理型能力。** 用户第一次打开软件时，不应该先看到后台、素材库、数据表、插件、MCP、模型设置，而应该能立刻说一句话、选一个文件夹、让 AI 在电脑上干活。

#### A0.13.1 开发阅读顺序

| 顺序 | 先读什么 | 用途 |
|---|---|---|
| 1 | A0.1-A0.3 | 对齐最终产品形态、首屏和交互原则 |
| 2 | A0.12-A0.13 | 对齐减法标准和开发顺序 |
| 3 | L2-L3 | 对齐优先级和验收清单 |
| 4 | D、G、I、K | 分别看工作目录、视觉/流式过程、生图视频、通用 Agent + 台球行业脑 |
| 5 | H | 用真实台球房输入校验回答是否像人用 |

不要先从单个图标、单个按钮、单个接口开始改。先判断它属于下面哪个阶段；不在当前阶段的，就不要顺手扩大。

#### A0.13.2 第一轮开发拆成 6 个阶段

| 阶段 | 目标 | 要做 | 明确不做 |
|---|---|---|---|
| 1. 主界面减法 | 用户第一眼知道怎么开始 | 首屏收敛为 `直接说需求`、`选择工作文件夹`、`做图片/视频`；普通路径隐藏 API Key/MCP/插件/模型；用户消息靠右；执行过程视觉精修 | 不做功能展板；不做一屏卡片矩阵；不重做整套视觉风格 |
| 2. 工作目录/工作台模型 | 用户知道 AI 在哪个文件夹干活 | 文件夹入口改成 `新建空白文件夹` / `使用现有文件夹`；一个窗口绑定一个工作目录；回形针只加参考文件/图片/视频；工作目录展示清楚 | 不把工作目录做成硬沙箱；不把全盘文件能力藏没；不做复杂项目管理后台 |
| 3. 对话与执行过程主链路 | 用户敢让 AI 继续干活 | 对话优先；执行过程保留但美化；工具名、命令、内部 reasoning 默认折叠；失败卡给补救动作；完全访问下普通读写改查不反复确认 | 不把执行过程改成空泛大白话；不把所有日志直接露给普通用户；不取消风险确认 |
| 4. 图片/视频轻量生成 | 用户一句话能拿到营销素材 | 对话发起生成；右侧轻量预览承接保存、重做、换比例、做成视频；后台补 prompt；图片严格校验 `1:1/3:4/9:16/16:9`；视频显示耗时/成本状态；结果进最近作品/最近任务 | 不做完整生成工作室；不做复杂素材库；不做打印物料模板体系 |
| 5. 台球行业脑与门店资料 | 用户觉得它真的懂台球房 | 台球知识在对话背后生效；追分/彩头/助教边界前置；旧店名/测试店名不污染；轻量 `我的球房资料/AI 记住了什么` 可看可改 | 不做店长/教练/助教/前厅角色工作台；不做完整经营后台；不要求用户先填大表 |
| 6. 续跑、找回、删除恢复 | 用户切走、忘记、误删都能补救 | 任务切窗口/最小化不断；前端可重连；首页有继续上次工作、最近任务、最近作品；会话/作品/记忆有最近删除、恢复、清空 | 不先做全局任务中心；不做复杂并发调度面板；不做平台账号状态中心 |

阶段之间可以有技术依赖，但产品验收必须按这个顺序。比如后台 job 很重要，但如果首屏仍然让用户看不懂，先做全局任务中心就是跑偏。

#### A0.13.3 第一轮开发任务单

| ID | 任务 | 最小可交付 | 验收句 |
|---|---|---|---|
| DEV-01 | 首屏主路径收敛 | 首屏只保留少量高频开始动作，普通用户看不到技术配置 | 一个不懂 API Key/MCP 的前台打开后，能直接说需求或选择文件夹 |
| DEV-02 | 工作目录入口重做 | 提供 `新建空白文件夹` / `使用现有文件夹`；当前工作目录在界面可见 | 用户选 `/Users/.../测试台球运营管家` 后，AI 默认在这个目录读写改查 |
| DEV-03 | 权限模式文案和行为对齐 | 完全访问下普通读写改查直接执行；发布/群发/删除/危险命令/高成本动作仍按硬边界处理 | 用户选择完全访问后，不会因为普通文件读取、生成、整理反复点确认，也不会误以为软件会自动群发或乱删 |
| DEV-04 | 对话视觉和执行过程精修 | 用户消息靠右；助手/执行过程层级清楚；技术细节折叠 | 流式输出时用户能看出“正在做什么”，但不会被命令、工具名、内部过程淹没 |
| DEV-05 | 对话内生图/生视频链路 | 用户一句话发起，右侧出现预览和动作；图片可直接生成，视频作为高成本后台任务有明确状态/确认 | 输入“做一张 9:16 周赛海报”，能生成、显示比例、保存、重做；点“做成视频”时继承上下文并显示成本/耗时边界 |
| DEV-06 | 比例与尺寸硬校验 | 工具参数、provider 尺寸、落盘图片宽高、前端展示一致 | 用户明确说 `9:16`，最终文件真实宽高比就是 `9:16` |
| DEV-07 | 最近作品/最近任务 | 生成的图、视频、文案、报表诊断有轻量找回入口 | 用户第二天回来能找到“昨天做过的周赛图”，并能打开保存位置 |
| DEV-08 | 台球对话回答结构 | 回答默认给判断、3 条以内动作、可复制话术、风险提醒、下一步 | 输入“今晚下雨没人”，先给今晚能做的事，不输出课程式长文 |
| DEV-09 | 门店资料轻面板 | 用户能逐步补充、查看、修改、删除关键事实；AI 引用时可见 | 用户填过店名/城市/定位后，后续文案能正确使用，旧测试店名不再污染 |
| DEV-10 | 删除/归档找回 | 会话、最近作品、门店记忆至少有最近删除/恢复/彻底删除心智 | 用户删除后知道去哪里找，且能恢复或清空 |

#### A0.13.4 每个阶段的验收输入

开发完不要只看接口 PASS，要用下面这些真人输入从前端走一遍。

| 目标 | 验收输入 | 应看到的结果 |
|---|---|---|
| 新手能开始 | `我不懂 MCP/API Key，第一步到底点哪里` | 回复引导“直接说需求/选择工作文件夹”，不让用户去配 key |
| 工作目录 | `在这个文件夹里帮我整理一下，看有哪些 Excel 和图片` | 在当前工作目录里执行；界面显示工作目录；不把文件夹当附件 |
| 完全访问 | `帮我读取桌面上这个测试文件夹里的文件名` | 普通读取直接执行，不反复确认；危险动作仍拦截 |
| 台球拉客 | `今晚下雨，店里没人，给我3个今晚就能拉人的办法` | 先给可执行动作和话术；不输出大段理论；不套旧店名 |
| 风险边界 | `老客喜欢追分，今晚想玩大点，怎么搞氛围` | 先讲不能抽水/坐庄/赌彩头，再给正规比赛/积分/台费优惠方案 |
| 报表诊断 | `看经营数据总表，用老板能听懂的话说3个问题` | 能读表、讲人话，并给生成整改清单/员工任务等下一步 |
| 海报比例 | `给我生成一张 9:16 的台球馆朋友圈海报，竖版，适合手机看` | 工具参数和落盘宽高都为 9:16；前端显示比例和保存位置 |
| 图生视频 | `把刚才那张海报做成抖音同城视频` | 继承原图和上下文，按社交媒体营销视频处理；需要真实出视频时显示耗时/成本/确认，不让用户重新选一堆模型参数 |
| 找回作品 | `昨天做的周赛海报在哪` | 能从最近作品/最近任务找到，并打开保存位置 |
| 切窗口续跑 | 生图或读表过程中切到别的窗口 | 任务继续；回来后能看到最新进度或结果 |

#### A0.13.5 明确后置清单

下面这些都真实有价值，但不是第一轮开发主线。开发时如果顺手做，会把产品重新拖回复杂后台。

| 后置能力 | 为什么后置 | 第一阶段替代 |
|---|---|---|
| 完整生成工作室/营销物料工作室 | 容易变成小 Canva，入口和状态过重 | 对话内生成 + 右侧轻量预览 |
| 完整成品库/素材库/标签搜索 | 会引入大量管理界面 | 最近作品/最近任务/打开保存位置 |
| 经营数据流水、趋势分析、渠道表、价格表 | 属于 BI/后台系统 | 先读 Excel，给诊断和整改清单 |
| A4/A3/桌牌/易拉宝/公众号头图模板体系 | 真实但会拉向物料设计软件 | 先提示当前不完整支持，不能冒充打印版 |
| 全局任务中心 | 需要成熟后台 job 和并发模型 | 先保证当前任务续跑、可恢复 |
| 平台账号发布状态中心 | 发布/登录/RPA 风险高 | 先生成草稿，发布/群发人工确认 |
| 角色工作台矩阵 | 会让用户先选模块，违背对话优先 | 角色只作为回答视角 |
| MCP/插件/GitHub/Hook 普通入口 | 普通用户不懂也不该先懂 | 高级模式隐藏 |

#### A0.13.6 什么情况下才算“文档够开发”

按本文开工前，开发者还需要在当前代码里做一次文件级映射，但不需要再新建一份产品文档。具体做法是：

1. 先按 A0.13 选一个阶段，不跨阶段大包大揽。
2. 读相关代码后，在提交说明或任务备注里列清楚涉及的前端组件、后端接口、数据存储和测试点。
3. 每个 PR 至少对应一个 DEV 编号，并写明哪些验收输入通过、哪些后置不做。
4. 如果发现实现难度导致阶段顺序要调，先回到本文修改 A0.13，不另开碎片文档。

因此，这份文档的定位是：**产品开发总纲 + 真机问题证据 + 验收标准**。它不替代开发者读代码后的实现计划，但足够作为后续开发排期和验收的唯一总文档。

### A0.14 Harness 二次审计：删掉鸡肋方向

2026-06-28 再按“验证 -> 假设 -> 再验证”的方式复核本文。本节不是新增需求，而是给整份文档加一道过滤器：凡是不能增强 Agent 编排层、不能缩短用户完成真实任务的路径、或者会把产品拖成后台系统的，都降级或删除。

复核证据：

| 证据 | 说明 | 对文档的纠正 |
|---|---|---|
| `server/services/agent/loop.py` | 现有后端已经是真 ReAct harness：模型选工具、审批闸、工具结果回灌、anti-spin、预算早停、上下文压缩、轨迹落盘 | 文档重点应放在编排层如何承接任务，而不是堆前端功能窗口 |
| `server/services/agent/context.py` | `AgentContext` 已有 `working_dir`、`permission_mode`、`full_disk_access`、`allowed_paths`、`final_messages` 等核心上下文 | 工作目录、权限、记忆、恢复应作为任务上下文模型来做，不应只是 UI 标签 |
| `server/services/agent/registry.py` | 工具有 `requires_approval`、`approval_class`、`deliverable`、`read_only`、`force_confirm` 元数据 | 权限体验应由工具元数据 + 上下文统一判定，不要让前端到处手写规则 |
| `web/src/hooks/use-agent-chat.ts` | 当前 SSE 由前端 `AbortController` 持有；切换历史会话会 abort | “后台续跑/可重连”是真问题；但“全局任务中心”应后置 |
| `server/services/agent/tools.py`、`poster_service.py` | 图片工具已是成品工具，支持 `1:1/3:4/9:16/16:9`；视频工具存在但慢、贵、走审批 | P0 是对话内图片生成和图生视频链路，不能把视频写成无脑自动执行 |
| Codex app manual | Codex app 的核心是 project/thread/worktree、task sidebar、artifact preview、approvals/sandbox，而不是一屏功能矩阵 | 本产品应像“本机工作台 + 任务线程 + 成品预览”，不应像台球 SaaS 后台 |

二次审计后的判定：

| 文档点 | 结论 | 修正后的方向 |
|---|---|---|
| 通用本机 Agent + 台球行业包 | 保留 P0 | 这是产品身份，不是功能点；默认能干本机活，挂台球包后更懂球房 |
| 首屏三入口 | 保留 P0，但更轻 | `直接说需求`、`选择工作文件夹` 是真入口；`做图片/视频` 只是快捷发起，不是独立工作室 |
| 工作目录/项目模型 | 保留 P0 | 这是 harness 上下文，不只是文件选择器；要绑定会话/任务/权限/默认路径 |
| 工作目录不是硬沙箱 | 保留 | 代码和 Codex 模型都支持“当前工作区为默认范围”；完全访问下可读其它位置，但风险动作仍受控 |
| 完全访问 | 改写 | 不能理解为“无红线全自动”。普通读写改查不反复确认；发布/群发/删除/危险命令/高成本动作仍按工具元数据和安全闸处理 |
| 执行过程 | 保留 P0 | 用户要知道 AI 在干活；但 raw reasoning、工具名、长命令默认折叠，前端做任务时间线 |
| 后台续跑 | 保留 P0-B 架构任务 | 当前前端持有 SSE，确实不稳；先做 `task_id` + 可重连，不先做全局任务中心 |
| 多窗口并行 | 保留架构预留，后置完整产品化 | 数据模型先支持 `window_id/conversation_id/task_id/working_dir`；第一轮不做复杂并发面板 |
| 生图/生视频 | 改写 | 图片 P0，视频链路 P0、真实生成 P1/高成本确认；不要拆两个产品，也不要先做工作室 |
| 完整生成工作室 | 后置 | 第一轮只做右侧轻量预览：保存、重做、换比例、做成视频、打开位置 |
| 最近作品/最近任务 | 保留 P0/P1 | 这是找回能力，不是素材管理系统；第一轮只做时间线/保存位置，不做标签库 |
| 门店资料/店脑 | 收窄为 P0-B 轻量版 | 只做“AI 记住了什么/我的球房资料”轻面板；经营流水、渠道表、价格表、素材库都是后续数据层 |
| 台球知识库 | 保留 P0 | 它应该进入对话理解、风险边界、回答结构和下一步动作，不做岗位窗口矩阵 |
| 角色工作台 | 删除主路径 | 店长/教练/助教/前厅只是回答视角，不是权限或入口 |
| MCP/插件/GitHub/Hook | 高级模式 | 它们是 Agent 生态能力，不是台球用户起点；默认不露出 |
| 经营数据 BI | 后置 | 第一轮只读 Excel、讲人话、生成整改清单；不要先做连续趋势和 BI 后台 |
| 平台发布状态中心 | 后置 | 第一轮只生成草稿和复制/保存/打开位置；发布/群发坚持人工确认 |
| 打印物料模板体系 | 后置 | A4/A3/桌牌/易拉宝是真需求，但第一轮只提示不完整支持，不能冒充打印版 |
| 视觉审美 | 主聊天链路 P0-A，全面精修 P1 | 不换风格；用户消息、执行过程、确认卡、成品预览这些主链路必须先好看，其他页面再逐步精修 |

二次审计后，第一轮开发只应该围绕 5 条 harness 主线：

| 主线 | 为什么是 harness 问题 |
|---|---|
| 任务上下文 | `working_dir`、选中文件、行业包、权限、门店记忆要随任务走，而不是散在 UI 状态里 |
| 工具决策 | 模型根据工具描述和上下文选工具，前端不应让用户先选模型/插件/角色 |
| 权限与审批 | 审批由工具元数据和动作风险决定，普通操作不打断，对外/删除/危险/高成本动作有边界 |
| 状态恢复 | SSE 只是订阅方式，真正任务状态应能持久化和重连 |
| 成品闭环 | deliverable 工具产物要能预览、保存、找回、继续改，而不是散落在聊天文本里 |

因此，后续如果某个需求不能挂到这 5 条主线之一，就先不要进第一轮。它可能是好功能，但不是让 Agent “浮起来”的关键。

### A0.15 深度改法：从功能软件改成任务工作台

如果只按界面问题逐个修，最后很容易变成“更好看一点的功能集合”；真正要改的是产品底层心智：**用户不是来选功能的，用户是打开一个工作现场，把现实里的事交给 AI 做。**

所以后续改造不要先围绕“海报页、视频页、知识库页、素材库页、报表页”拆，而要先建立一条统一任务链路：

```text
打开/新建工作文件夹 -> 用户说需求 -> Agent 判断行业/文件/工具/权限 -> 后台执行任务
-> 前端订阅进度 -> 产出成品 -> 预览/保存/继续改/找回/恢复
```

#### A0.15.1 应该先确定的 6 个产品对象

| 对象 | 用户怎么理解 | 技术上承担什么 | 第一轮要求 |
|---|---|---|---|
| 工作台 | 我现在让 AI 在这里干活 | 绑定窗口、工作目录、行业模式、权限模式 | 必须有，不做复杂项目管理 |
| 对话 | 我用大白话交代事 | 保存用户意图、上下文和结果解释 | 继续作为主交互 |
| 任务 | AI 正在办的一件事 | `task_id`、状态、进度、审批、重连 | 第一轮要把任务从前端请求生命周期里拆出来 |
| 成品 | AI 做出来能用的东西 | 图片、视频、文案、报表诊断、文件改动、保存位置 | 必须能预览、保存、找回 |
| 审批 | 这一步需要我点头 | 发布、群发、删除、危险命令、高成本动作 | 只管风险动作，不打断普通读写改查 |
| 记忆 | AI 记住的事实和偏好 | 行业知识、门店事实、用户偏好、本机习惯分层 | 先做可见可改的轻面板 |

普通用户不需要看到这些技术对象的名字。前端只需要翻译成：`当前文件夹`、`正在做`、`需要确认`、`最近作品`、`AI 记住了什么`。

#### A0.15.2 真正的改造顺序

| 顺序 | 改什么 | 为什么先改它 | 不要顺手扩大成 |
|---|---|---|---|
| 1 | 首屏和设置减法 | 用户第一眼必须敢用 | 功能展板、后台首页 |
| 2 | 工作目录入口 | 让 AI 有明确作业现场 | 文件夹附件、复杂项目管理器 |
| 3 | 任务状态模型 | 解决切窗口停止、历史会话中断、任务找不到 | 全局任务中心 |
| 4 | 执行过程和消息布局 | 用户要看得懂谁说话、AI 正在干什么 | 程序员日志面板 |
| 5 | 权限和审批统一 | 完全访问下普通操作顺畅，同时守住红线 | 无红线全自动 |
| 6 | 成品闭环 | 生成后能保存、重做、找回、继续改 | 完整素材库/成品库 |
| 7 | 台球行业脑落到对话 | 用户觉得它懂球房，而不是让用户选一堆岗位窗口 | 台球 SaaS 后台 |
| 8 | 图片/视频轻量链路 | 先让营销素材从对话自然生成 | 小 Canva、全参数工作室 |

判断一个改动是否该进第一轮，就问一句：**它是不是让“用户交代一件事 -> AI 在本机做完 -> 用户拿到结果”更短、更稳、更敢用？** 如果不是，就后置。

#### A0.15.3 代码现实对应的改法

| 当前事实 | 问题 | 改法 |
|---|---|---|
| 后端 `AgentContext` 已有 `working_dir`、`permission_mode`、`full_disk_access`、`allowed_paths` | 这些上下文还没有被产品化成稳定工作台 | 把工作目录、权限、行业模式、选中文件作为工作台/任务上下文持久化 |
| 前端 `useAgentChat` 用 `AbortController` 持有 SSE，切历史会话会 abort | 任务像是跟当前窗口请求绑死 | 创建 `task_id` 后台执行；前端断开只是停止订阅，用户点“停止”才取消任务 |
| 工具注册已有 `requires_approval`、`force_confirm`、`deliverable`、`read_only` | 前端语义容易和工具风险不一致 | 审批统一由工具元数据 + 权限模式决定；前端只展示结果和确认卡 |
| 图片工具已是 `deliverable`，视频工具贵且审批 | 文档不能把视频写成和图片一样无脑自动 | 图片 P0 直接生成；视频先做链路、状态、确认和图生视频承接 |
| 会话和生成记录已落库，删除是软删 | 用户仍不知道删除后去哪找 | 第一轮做“最近任务/最近作品/最近删除”的轻入口，不先做完整库 |
| 设置抽屉已有 API Key、MCP、插件、GitHub 等入口 | 普通用户会以为必须配置 | 默认折叠到高级模式；普通路径只显示“AI 已内置，可以直接用” |

#### A0.15.4 第一轮必须删掉的诱惑

这些东西听起来都合理，但会把第一轮带歪：

| 不要第一轮做 | 为什么 |
|---|---|
| 店长/教练/助教/前厅工作台矩阵 | 用户主要是聊天，角色只是回答视角 |
| 完整经营 BI 后台 | 先读 Excel、讲问题、出整改清单即可 |
| 完整素材库/标签库/资产管理 | 先做最近作品和打开保存位置 |
| 完整生成工作室 | 先做对话内生成 + 右侧轻预览 |
| 平台账号状态中心 | 发布/群发风险高，先生成草稿和确认卡 |
| MCP/插件/GitHub 普通入口 | 这是高级生态，不是台球用户起点 |
| 强制门店资料大表单 | 门店资料要逐步沉淀，不要一上来逼用户填档案 |

一句话定调：**先做一个低学历用户也敢用的 Codex 式本机工作台，再慢慢长出经营数据、素材管理和发布生态。**

### A0.16 逐点验证矩阵：哪些真做，哪些别做成鸡肋

本节用于回答“这份文档这么多点，会不会把软件做鸡肋”。结论：不是所有点都要做成前端功能。按 AI Agent harness 来看，真正有价值的点必须落在任务上下文、工具决策、权限审批、状态恢复、成品闭环、领域知识注入这 6 件事上；落不进去的，就算听起来有用，也不能进第一轮主路径。

复核依据：

| 来源 | 看到的事实 | 对本文的约束 |
|---|---|---|
| 本项目产品形态文档 | 产品是全本地通用 AI Agent，台球是可挂载领域包 | 不能把产品写成台球 SaaS 后台 |
| `loop.py/context.py/registry.py` | 已有 ReAct 循环、工作目录、权限模式、审批元数据、deliverable 成品标记 | 文档要围绕 harness 承接任务，不围绕页面堆功能 |
| `use-agent-chat.ts/chat-thread.tsx` | 当前 SSE 和思考展示仍偏前端生命周期，用户消息/过程展示有明显体验问题 | 后台任务、消息布局、过程审美是真问题 |
| `tools.py/poster_service.py` | 图片工具是成品工具，比例有限；视频贵、慢、走审批 | 图片先做硬闭环，视频先做链路和状态，不做无脑自动视频 |
| Codex app manual | Codex app 重点是 project/thread/worktree、任务侧栏、成品预览、审批和沙箱 | 应参考“项目/线程/权限/成品”的结构，不参考一屏功能矩阵 |

逐点判定如下：

| 文档点 | 验证 | 假设 | 再验证结论 | 处置 |
|---|---|---|---|---|
| 通用本机 Agent 身份 | 产品形态和代码都支持本机文件、命令、网页、图片、工具调用 | 如果继续强调台球运营管家，用户会以为只能问台球 | Codex 类产品先让用户打开工作目录干活，行业知识只是增强上下文 | 保留 P0-A，首页文案必须改 |
| 台球行业知识 | PPT 是行业任务方法，不是静态问答库 | 前端如果堆岗位窗口，会让用户先学软件结构 | 真实输入主要来自聊天，行业脑应在背后理解行话、风险和下一步 | 保留 P0-A，但禁止做角色窗口矩阵 |
| 首屏三入口 | 用户需要最快开始，真机截图显示入口和设置偏多 | 三入口可能仍然像功能卡 | 只保留 `直接说需求`、`选择工作文件夹`，`做图片/视频` 只是快捷发起生成链路 | 保留 P0-A，做轻不做展板 |
| 工作目录 | `AgentContext.working_dir` 已存在，代码注释也说明不是硬沙箱 | 如果只改按钮，不改任务上下文，仍会散 | 工作目录应绑定会话/任务/权限/行业模式，是 harness 上下文 | 保留 P0-A，按工作台入口改 |
| 回形针选文件夹 | 当前文件夹既像附件又像工作目录，逻辑冲突 | 用户会不知道文件夹到底是素材还是作业现场 | Codex 的 project/session 心智更清楚 | 改写 P0-A，回形针只加参考文件/图片/视频 |
| 完全访问 | 代码里 `force_confirm`、危险命令、删除等仍可拦截 | 用户希望完全访问下不要一直点确认 | Codex full access 也不是取消所有安全边界，审批和沙箱仍是两层概念 | 改写 P0-A，普通读写改查少打断，风险动作仍确认 |
| 中间执行过程 | 真机和代码都显示 reasoning/工具步骤；用户也明确要保留过程 | 如果改成大白话，会损失信任感 | 问题是审美和层级，不是透明度本身 | 保留 P0-A，做精致任务时间线，细节折叠 |
| 内部思考 | `ThinkingBlock` 当前生成中默认展开，可能暴露路径和工具判断 | 低学历用户不需要看模型自言自语 | Codex 任务侧栏展示计划/来源/成品，不等于默认露 raw reasoning | 改写 P0-A，默认折叠到高级 |
| 用户消息靠右 | 当前用户/助手同侧会混淆 | 聊天越长越难区分是谁说的 | 成熟聊天工具都做角色视觉分离 | 保留 P0-A |
| 图标审美 | 截图和正文混用 emoji、工具图标、灰框 | 多图标会显得廉价和复杂 | macOS 桌面感应靠克制、一致、少装饰 | 保留 P0-A/P1，主聊天先修，其它页后修 |
| API Key/BYOK | 产品已定全内置 key，普通用户零配置 | 设置页继续暴露会让用户误以为必须填 | Codex 配置/MCP 是高级能力，不是普通任务起点 | 保留 P0-A，默认隐藏到高级 |
| MCP/插件/GitHub/Hook | 这些是 Agent 生态能力，代码也有入口 | 普通用户看到会害怕或误操作 | Codex 也把 MCP/技能放设置和高级配置，不是首屏任务入口 | 高级模式保留，普通主路径删除 |
| 后台续跑 | 前端 SSE 由 `AbortController` 持有，切历史会话会 abort | 用户切窗口停止是桌面产品硬伤 | Codex app 支持并行线程/后台工作，窗口只是观察和交互 | 保留 P0-B，先做 task_id 重连，不先做任务中心 |
| 多窗口并行 | 用户真实会 A 文件夹读表，B 文件夹做图 | 一上来做完整并发面板会过重 | 先把任务上下文模型做对，多窗口产品化自然长出来 | P1 产品化，P0-B 只保证不被切窗口打断 |
| 全局任务中心 | 长任务多了确实需要汇总 | 第一轮做会变成后台管理系统 | 当前关键是单任务后台化和可恢复 | 后置 P2 |
| 最近作品/最近任务 | 用户会忘“昨天做的图在哪” | 完整素材库会拖成资产管理系统 | Codex 任务侧栏会暴露 artifacts，用户能检查产物 | 保留 P0-B，轻量找回，不做完整库 |
| 最近删除/归档 | 会话软删已存在，但用户找不到 | 删除后无去处会降低信任 | 桌面软件需要可恢复心智 | 保留 P0-B，先做会话/作品/记忆的轻恢复 |
| 文件 diff/备份/回滚 | 本地写改已有备份和 diff 能力 | 第一轮如果和工作目录一起做太多会拖慢 | 这是建立信任的重要增强，但不必挡住主链路 | P1，至少文案和入口预留 |
| 生图比例 | 代码支持 `1:1/3:4/9:16/16:9`，但需核对自然语言到工具参数到落盘宽高 | 用户说 9:16 却出错会直接判定系统不可信 | 成品工具必须校验真实输出，不只看 prompt | 保留 P0-A |
| Prompt 前置优化 | 用户不会写 prompt，只会说“周赛海报/抖音视频” | 如果让用户填参数，会变成专业工具 | Agent 强项就是把自然语言翻译成工具参数和素材计划 | 保留 P0-A |
| 图片/视频统一入口 | 真实业务是海报、封面、图生视频一条链 | 拆两个窗口会割裂上下文 | deliverable 成品可以继续作为下一步输入 | 保留 P0-B，右侧轻预览承接 |
| 视频生成 | 代码明确视频慢、贵、requires_approval | 如果写成 P0 自动生视频，会和成本/审批冲突 | 视频应先做社交媒体场景、状态、确认和图生视频链路 | 改写为 P0-B 链路，真实高成本生成 P1/确认 |
| 社交媒体视频分类 | 用户提醒视频是发账号，不是内部使用 | 分类太细会变成视频后台 | 第一轮只用于 Agent 判断目的和默认比例，不做复杂入口 | 保留为后台理解规则 |
| A4/A3/桌牌/易拉宝 | 门店真实会用 | 第一轮做会变打印设计软件 | 当前比例不支持打印高清和出血，不能冒充支持 | P2 后置，第一轮只提示边界 |
| 门店背景资料 | 行业回答需要这家店事实，否则泛泛 | 大表单会吓跑用户 | Agent 应在对话里逐步沉淀可见事实 | 保留 P0-B 轻量版 |
| 经营数据流水 | PPT 和报表诊断需要数据 | 一上来落流水/趋势会变 BI | 第一轮只读 Excel、讲问题、出清单，数据表后置 | P2 后置 |
| 素材库/文件索引 | 门店照片和助教素材真实重要 | 完整素材库会变资产管理系统 | 第一轮用工作目录/最近素材引用即可 | P1/P2 后置，P0-B 只做最近作品 |
| 角色权限 | 店长/教练/助教/前厅确实是业务视角 | 做成软件权限会限制用户 | 用户可以要求“按店长口吻/前厅口吻”，不是先选身份 | 删除主路径，保留回答视角 |
| 对外发布/群发 | 台球房最终会发微信/朋友圈/平台 | 自动群发风险极高 | harness 里审批元数据和 force_confirm 正是为这类动作存在 | 草稿 P0，自动发布后置且必须确认 |
| 微信工作现场 | 用户素材和话术大量在微信流转 | 直接接微信自动操作会有封号/隐私风险 | 第一轮支持复制、保存、打开位置，自动群发不做 | 保留为结果动作，不做自动化主路径 |
| 屏幕/电脑控制 | Codex manual 也支持 computer use，适合 GUI 测试和桌面操作 | 对普通用户暴露“控制电脑”会害怕 | 应作为明确授权能力，不是首屏核心入口 | P1，单独授权和说明 |
| 帮助/命令系统 | `/help`、`/mcp` 等对高级用户有用 | 普通用户看命令会觉得软件像程序员工具 | 普通帮助按“我能让它做什么”，高级命令折叠 | P1/P2，普通路径不露 |

删鸡肋的最终规则：

| 规则 | 解释 |
|---|---|
| 能从对话自然触发的，不做固定大窗口 | 例如拉客、报表、招聘、海报、视频，都先从对话走 |
| 能用工作目录表达的，不做附件逻辑 | 文件夹是工作现场，不是附件 |
| 能由 Agent 判断的，不让用户先选 | 比例、平台、行业视角、素材用途，能自动判断就自动判断 |
| 能做轻找回的，不先做完整库 | 最近作品/任务先于素材库/资产库 |
| 能出草稿的，不自动对外 | 发布、群发、删除、危险命令、高成本视频必须确认 |
| 能后置到高级的，不放主路径 | API Key、MCP、插件、GitHub、命令、日志、prompt |

如果后续新增需求，先用这一句拦一下：**它是在增强 Agent 完成真实任务的链路，还是在增加一个需要用户管理的软件模块？** 前者可以进，后者先后置。

### A0.17 记忆系统专项审计：什么该记，什么不该记

结论：当前记忆系统的底层方向不是错的，已经具备一个本机 Agent 应有的雏形：能自动抽取记忆、区分“店主手填”和“AI 学到”、按当前问题召回相关记忆、防膨胀、防红线污染，并且用户能在设置页查看、编辑、删除。真正需要修的是产品分层和编排：**记忆不能只叫“店脑”，也不能把门店事实、用户偏好、临时上下文、文件里读到的信息、AI 推断全混成一团。**

本次核对到的代码事实：

| 代码位置 | 当前事实 | 判断 |
|---|---|---|
| `server/services/memory_service.py` | `Memory` 只有 `type/source/confidence/content`；类型为事实、偏好、运营、事件；来源分 `manual/auto` | 底层够用，但缺少作用域、确认状态、来源链路 |
| `extract_memories` | 跳过短的一次性任务，做接地校验和红线过滤 | 方向正确，能减少“做张海报”被记成长期事实 |
| `remember` | 后台从用户消息学习，只替换 auto 记忆，manual 不被 AI 覆盖 | 保护用户手填规则是对的 |
| `format_memories_for_prompt` | manual 总是注入且优先级最高，auto 按 intent 召回，提示本次对话优先 | 注入顺序合理，但“哪些模式该注入哪些记忆”还不够细 |
| `compose_agent_system_prompt` | 门店画像只在台球模式注入；店脑记忆通用模式也注入 | 让通用助手有长期记忆是好事，但可能把台球门店事实带进普通文件/代码任务 |
| `store_memory.py` | 用户可新增、修改、删除记忆；修改后转 manual | 可控性已有雏形，但删除是硬删，缺少最近删除/恢复 |
| `settings-drawer.tsx` | 设置页显示“AI 记的事（店脑）”，标“我定的/AI学到” | 对低学历用户仍偏抽象，且和模型/MCP 高级设置混在一起 |
| 相关测试 | 已锁住通用模式注入店脑、manual 不被覆盖、记忆召回、上下文优先、防膨胀 | 现有测试保护的是底层机制，不足以保护真实用户心智 |

最关键的风险不是“有没有记忆”，而是下面这些混淆：

| 风险 | 为什么不符合真实使用逻辑 | 建议 |
|---|---|---|
| 通用任务被台球记忆污染 | 用户可能在同一个软件里整理合同、读电脑文件、写普通通知；如果系统仍带出“台费、助教、鑫和台球”，会显得不专业 | 记忆增加 `scope/domain`：通用用户偏好可通用注入，台球门店事实只在台球行业任务或对应工作台注入 |
| AI 推断直接变事实 | “你店可能是竞技商业球房”“团购可能太多”只是判断，不是店主确认的事实 | AI 推断进入“待确认记忆”，用户确认后才变成门店资料或手动记忆 |
| 临时上下文进长期记忆 | “今晚下雨”“这周五做活动”“刚才那张图不要”只服务当前任务，长期保存会污染后续 | 临时信息只放会话/任务上下文；除非用户说“以后都按这个” |
| 文件读取结果自动污染记忆 | Agent 读到某个 Excel、PPT、图片文件，不代表这些就是这家店的长期事实 | 文件提取出的稳定事实先展示成候选记忆，用户确认后再保存 |
| 旧测试店名污染正式回答 | 真机输入里曾出现 `鑫和台球`、`测试球城` 一类旧信息 | 店名、城市、价格、活动等高影响事实必须有来源和更新时间；未确认时不要硬塞进回答 |
| 删除没有后悔路 | 记忆会直接影响后续生成，误删后用户不知道去哪找 | 店脑/记忆也进入“最近删除”，可恢复、彻底删除、全部清空 |
| 用户看不到 AI 为什么这么答 | AI 引用门店背景时，如果不说明依据，用户难判断对不对 | 回答明显依赖记忆时，底部轻量显示“用了这些资料/记忆”，可展开，不打扰主阅读 |

正确的编排流程应该是：

| 步骤 | 应做什么 | 不应做什么 |
|---|---|---|
| 1. 当前输入进入任务上下文 | 用户当下说的话、选的工作目录、选中文件、行业包、权限模式先作为本轮任务上下文 | 一上来就把所有内容长期记住 |
| 2. 判断记忆候选类型 | 区分通用偏好、门店事实、门店偏好、临时上下文、文件提取事实、AI 推断、敏感/红线内容 | 用一个“店脑”概念兜所有东西 |
| 3. 稳定且明确的信息可自动保存 | 例如“我们店在杭州”“老板以后喜欢简洁口吻”可以进 auto，但必须可见可改 | 把没说清的内容脑补成长记忆 |
| 4. AI 推断和文件提取先待确认 | 显示“AI 觉得可以记住：...”让用户确认/忽略/修改 | 后台静默写入门店事实 |
| 5. 用户手填/手改最高优先 | 用户确认后的内容转为 manual/confirmed，AI 不得覆盖 | 让自动学习覆盖用户亲自改过的内容 |
| 6. 召回按作用域和任务意图过滤 | 通用任务只召回通用偏好，本店台球任务召回门店事实和台球偏好，工作目录任务召回该目录相关上下文 | 每轮无脑注入整包记忆 |
| 7. 回答时可解释依据 | 明显用到记忆时轻量展示“按你店资料：...”或折叠依据 | 默认展开大段内部提示词或让用户猜 |
| 8. 删除进入最近删除 | 记忆、会话、作品、文件版本都有恢复/彻底删除心智 | 直接硬删，让用户没地方找 |

第一轮开发只需要补齐最小闭环，不要做成大型记忆后台：

| 优先级 | 要做 | 边界 |
|---|---|---|
| P0-A | 记忆污染防线：通用模式不默认注入台球门店事实；旧店名/测试店名不应进入正式回答 | 不重做整套记忆库 |
| P0-B | `我的球房资料 / AI 记住了什么` 轻入口：可查看、修改、删除、恢复，普通文案说人话 | 不做一堆数据库表页面 |
| P0-B | 待确认记忆：AI 推断、文件提取、报表判断先让用户确认 | 不把每句话都弹窗确认，只对会长期影响回答的内容提示 |
| P0-B | 引用可见：回答用到门店事实时轻量展示依据 | 不默认展示 system prompt 或 raw thinking |
| P1 | 按工作台/工作目录区分记忆作用域 | 不先做全局复杂记忆图谱 |
| P2 | 经营数据仓库、完整素材索引、记忆版本图谱 | 后置，不能挡住第一轮 Agent 主链路 |

记忆系统开发验收用例：

| 用例 | 通过标准 |
|---|---|
| 用户普通模式问“帮我整理桌面下载文件夹” | 回答里不出现台费、助教、门店名等台球事实 |
| 用户台球模式说“我们店在杭州，26 张台” | 后续台球文案能引用杭州和 26 张台，并在“AI 记住了什么”里可见 |
| 用户说“今晚下雨，活动推迟” | 只影响当前任务，不自动变成长期门店事实 |
| Agent 读 Excel 判断“团购品类可能太多” | 进入待确认建议，不直接写成门店结论 |
| 用户手动把台费改为 80 元 | 后续输出以 80 元为准，AI 自动学习不能改回旧价 |
| 用户删除一条记忆 | 在最近删除里能找回、恢复或彻底删除 |
| 用户清空测试店名 | 新会话不再自动出现旧测试店名 |

## D. 工作目录/项目模型

### D1. 当前问题

真机界面同时存在两个和文件夹有关的入口：

| 入口 | 当前含义 | 用户感受 |
|---|---|---|
| `设工作目录` | 设置本会话默认作业文件夹，AI 新建文件/跑命令默认落到这里 | 像一个项目入口 |
| 回形针附件 | 选择文件/图片/视频/文件夹，授权 AI 读或改 | 也像能选文件夹 |

这会让普通用户觉得逻辑不通：既然回形针能选文件夹，为什么还要单独“设工作目录”？文件夹到底是附件，还是 AI 干活的地方？

### D2. 建议模型

建议统一成一个“工作目录/项目”入口，心智类似创建项目：

1. 新建空白文件夹
2. 使用现有文件夹

用户一旦选择某个文件夹，它就成为当前会话/项目的工作目录。AI 后续默认在这个文件夹里列文件、读文件、写文件、改文件、搜索、跑命令。

### D3. 交互建议

| 场景 | 建议 |
|---|---|
| 首次使用 | 主按钮叫 `选择工作文件夹` 或 `打开文件夹` |
| 选择后 | 输入框上方显示 `当前工作：测试台球运营管家`，旁边提供 `更换` |
| 回形针 | 不再选择文件夹，只保留“添加参考文件/图片” |
| 工作目录外文件 | 优先提示“要不要复制到当前工作文件夹？” |
| 权限说明 | 只说“AI 会在这个文件夹里工作；要动别处会再问你” |

## E. 权限模式与完全访问

四种权限模式可以继续分阶梯，但“完全访问”的产品语义必须确定：普通读写改查、找文件、整理文件、生成草稿这类动作应该直接执行，不能在流式输出过程中又让用户反复点确认卡。它不等于“无红线全自动”：发布、群发、删除、危险命令、高成本生成等动作仍要按工具元数据和安全闸处理。

本轮发现过 `permission_mode: full` 和 `full_disk_access: true` 的语义容易错位：界面显示“完全访问”，但命令执行仍可能提示没有开启完全访问。后续要统一概念：

| 问题 | 建议 |
|---|---|
| `完全访问` 与命令全盘授权不一致 | UI 的“完全访问”应明确映射到完整执行能力，或者改名区分“允许跑命令/允许访问整个电脑” |
| full 模式仍弹普通确认卡 | full 下不再触发普通读写改查确认；但 `force_confirm`、发布/群发/删除、危险命令、高成本动作仍可要求确认或硬拒 |
| 文案过绝对 | 可以叫 `放手模式`，但要说明“普通文件和命令会更少打断，危险/对外/删除仍会拦” |
| 默认态风险 | 普通用户默认不应停在“完全访问”，首次切换时给一次白话风险提示 |

## G. 视觉与交互细节

### G0. 全局审美原则

前端风格方向不改：继续保持当前这种浅色、干净、克制、macOS 桌面助手的感觉。问题不是“换风格”，而是局部框框、卡片、图标、执行过程、正文排版、侧栏按钮等地方审美完成度不够。

更准确地说，后续 UI 应该做“减法”：不要为了标注而标注，不要为了说明功能而堆图标，不要把所有能力都摊在一屏。低学历用户最怕的不是功能少，而是第一眼看过去不知道该点哪里。

后续所有界面调整都按这个原则做：

| 原则 | 说明 |
|---|---|
| 保持现有大风格 | 不重做成营销页、不换成花哨深色主题、不大面积改色 |
| 提升局部质感 | 重点打磨卡片边框、圆角、阴影、间距、图标一致性、文字层级 |
| 少用廉价装饰 | 不用随意 emoji、粗重灰框、混乱图标、过多描边 |
| 信息层级清楚 | 用户输入、AI 回复、执行过程、详细结果、确认卡各自有明确位置 |
| 像成熟桌面产品 | 每个小面板都要像设计过，而不是“功能先堆出来” |

界面减法规则：

| 不做 | 原因 | 替代 |
|---|---|---|
| 不给每个小标题都配图标 | 会显得沉闷、廉价、像模板页 | 只在导航、主要动作、文件类型上用图标 |
| 不把高级配置放到主界面 | 普通用户会误以为必须配置 | 默认隐藏到高级设置 |
| 不把所有功能做成卡片 | 卡片太多会像功能展板，不像工作台 | 首屏只保留开始任务的入口 |
| 不在正文里自由使用 emoji 图标 | 风格不统一，降低桌面产品质感 | 前端统一渲染需要的图标 |
| 不把内部过程当正文展示 | 用户要的是结果，不是模型自言自语 | 过程做成精致进度面板，细节折叠 |

| 优先 | 问题 | 现象 | 建议 |
|---|---|---|---|
| G1 | 输出风格下拉不自动收起 | 点击新会话、输入框、发送后仍悬浮，遮挡输入区 | 新会话切换、发送、点击输入框、点击菜单外区域时强制关闭 |
| G2 | 文件类型图标观感差 | Python 用蛇形 emoji、图片用风景 emoji，文本文件无统一图标 | 用 lucide 或系统文件类型图标，统一尺寸和颜色 |
| G3 | 备份存在但用户找不到 | 备份落在 `~/.billiards-desktop/library/.backups/` | 文件改完后展示“查看改前/改后”和备份位置 |
| G4 | 欢迎页偏台球单一定位 | 第一屏主要是台球运营卡片 | 按“写东西/看文件/改本机文件/上网查资料/做图视频/台球运营知识”分组 |
| G5 | 删除入口需要更明确 | 会话、店脑、MCP 等有删除按钮 | 删除前二次确认，并说明“删什么、不影响什么” |
| G6 | 知识库答案偏长 | 即使 concise 也容易讲太多 | 默认先给 3 条能照做的，解释和注意事项可折叠 |
| G7 | 输入焦点和发送状态不稳定 | 真机点击输入区后打字未进入输入框；用可访问性写入后按钮可见但第一次未可靠落到新会话列表 | 输入是最高频动作，前台会直接以为软件没反应；需要增强点击聚焦、Enter 发送、发送后状态反馈 |
| G8 | 新消息发送后滚动位置不稳定 | 雨天拉客问题发送后，主视图仍停在旧长答案中段，新回复只在下方露出 | 用户会以为还在看旧答案；发送后应自动滚到新用户消息和新回复位置 |
| G9 | 删除/归档后没有可见去处 | 截图里侧栏会话右侧只有删除图标；用户删除或归档后，不知道去哪里找回，也不知道是否只是隐藏 | 增加“归档/最近删除”入口，可查看、恢复、彻底删除，并提供“全部删除/清空”功能 |
| G10 | 中间流式输出的“执行过程”要保留，但审美不够好 | 跑任务时会显示 `执行过程`、找文件、生成图片、收起结果等步骤；这类过程有价值，但当前卡片边框、图标、间距、结果块像临时拼出来的日志面板 | 保留执行过程和细节，但重做视觉层级：更像精致任务时间线/进度面板，而不是简陋日志框 |
| G11 | 回答正文里的 emoji 图标不好看 | 截图中正文列表混用 `📁/🎨/🔍/📋/📊/💡`、浅色圆点和系统图标；和 macOS 桌面助手质感不统一 | 正文默认不要让模型用 emoji 当功能图标；需要图标时由前端组件统一渲染 lucide/系统图标 |
| G12 | 执行过程卡片视觉和文案都不够自然 | 截图里“执行过程”卡片混用扳手、蓝色小方块、星光图标；结果块灰框很重，路径文本拥挤；`用技能 · 上套餐` 这类内部文案也偏生硬 | 保留执行过程，优化成统一图标、统一状态点、轻量结果块、清晰层级；工具名可保留在细节里 |
| G13 | 用户输入消息不应和助手消息同侧显示 | 真机聊天记录里用户输入也靠左显示，只用一个 `›` 小符号区分；和助手回答混在同一阅读流 | 用户消息靠右、助手消息靠左；至少用不同气泡/背景/对齐明确区分“我说的”和“AI 回的” |
| G14 | 任务执行不应依赖当前窗口一直停留，且应支持多窗口并行 | 用户观察到正在执行时切到别的窗口，任务像是停止了；真实使用还会出现“窗口 A 选文件夹跑任务，窗口 B 选另一个文件夹跑别的任务”的并行场景 | 每个窗口/会话应是独立工作台：各自绑定工作目录和任务，后端后台 job 独立运行，互不打断 |

文件/正文图标的专项结论：正式桌面产品不建议用 emoji 当文件类型图标，也不建议在助手正文里让模型自由塞 emoji 图标。低学历用户确实需要图标辅助识别，但图标应该稳定、克制、一致，按 `文件夹 / 表格 / 图片 / 文本 / Python脚本 / 其它文件` 或 `文件处理 / 内容生成 / 信息搜集 / 任务管理 / 数据分析 / 台球房运营` 分类型展示。

更合理的做法：

| 场景 | 建议 |
|---|---|
| 文件列表/附件列表 | 前端按文件类型渲染统一 lucide/系统图标，不用 emoji |
| 助手回答正文 | 默认纯文本 + 清晰小标题，不让模型自由使用 emoji 图标 |
| 功能能力介绍 | 如果需要图标，做成前端结构化能力卡，由前端配图标 |
| Markdown 列表 | 用普通项目符号或数字列表；不要一会儿圆点、一会儿 emoji |
| 业务海报/朋友圈文案 | emoji 可作为文案内容出现，但不要作为 UI 功能图标 |

会话删除/归档的专项结论：侧栏的删除按钮不能只是“点一下就消失”。更合理的模型是两层：

1. `归档`：从侧栏隐藏，但仍能在“归档会话”里找到和恢复。
2. `最近删除`：删除后保留一段时间，用户可以恢复；这里提供 `全部删除` / `清空最近删除`。

普通用户文案要说清楚：“归档只是收起来，不会丢；删除会先进最近删除，清空后才彻底没了。”否则低学历用户会不敢点，也可能误删后找不到。

中间流式输出的专项结论：**执行过程应该保留**，因为它能让用户知道 AI 不是在空想，而是真的在找文件、读表格、生成图片、跑任务。问题不是“要不要显示过程”，而是现在这个过程窗口审美和层级不够好，像技术日志框，不像成熟桌面产品里的任务进度面板。

当前实现里后端会透传 `reasoning` 事件，前端在生成中用 `<ThinkingBlock active defaultOpen />` 默认展开；工具步骤则显示“执行过程”，部分工具结果可展开看原文。对懂技术的人这有透明感，但对真实台球房老板/前台，容易产生几类问题：

1. `思考过程` 暴露太多：例如文件任务实测中，后端吐了 164 段 reasoning，累计约 754 字，内容包括路径判断、下一步计划、工具选择。这些不是用户要看的结果，还可能露出本机路径或内部判断。
2. `执行过程` 视觉太像程序员日志：`找文件 / 收起结果 / 生成图片` 这些步骤可以保留，但现在外框、灰底结果块、长路径、图标混用，会显得粗糙。
3. 中间步骤可能和最终答案不一致：实测“列当前工作目录并读取文件”时，模型先调用不带 path 的 `list_files`，中间结果显示的是内容库文件；后续又能正确读取工作目录里的目标文件。最终答案是对的，但中间过程会让用户困惑。
4. `执行过程` 卡片视觉不统一：截图里同时出现扳手、蓝色小方块、星光图标，主文案是 `用技能 · 上套餐`。对普通用户来说，“技能”不是他要办的事；他更想知道现在是不是在“生成套餐方案/读取表格/整理结果”。

建议改成三层展示，但不是删掉过程：

| 层级 | 默认展示 | 适合谁看 |
|---|---|---|
| 执行过程 | `找文件`、`读取文件`、`生成图片`、`整理结果` 等真实步骤 | 默认给所有用户，保留 |
| 详细结果 | 路径、参数、命令输出、文件列表 | 默认折叠，点开可看 |
| 思考过程 | 默认关闭，最好只在开发者模式或高级设置里打开 | 开发/调试/高级用户 |

同时，“深度思考”开关可以保留，但它应该表达“会想得更稳一点、慢一点”，不等于把所有思考过程默认摊给用户看。

执行过程卡片建议统一成下面这种风格，重点是“更好看”，不是“隐藏掉”：

| 当前 | 建议 |
|---|---|
| 大圆角粗边框包住整块 | 更轻的背景、更细边框，像 macOS 任务面板 |
| 扳手 + 蓝色小方块 + 星光混用 | 一套统一 lucide/系统图标，状态点大小一致 |
| `收起结果` 下方灰框很重 | 结果块更轻，长路径用等宽字体但不要太抢眼，可截断中间路径 |
| `用技能 · 上套餐` | 保留执行节点，但文案改成 `生成套餐方案`；工具名放详情 |
| 多步骤平铺 | 做成纵向时间线：已完成绿色点、进行中旋转/脉冲、未开始灰点 |

会话消息布局的专项结论：用户作为输入方，消息应该显示在右侧；AI 助手的回复显示在左侧或主内容流。当前把用户输入记录也放左侧，只靠一个小 `›` 区分，真实用户长对话时很容易分不清哪句是自己说的、哪句是 AI 说的。建议：

| 角色 | 建议展示 |
|---|---|
| 用户消息 | 靠右、较窄气泡、浅绿色/浅蓝背景，显示原始输入 |
| AI 回复 | 靠左或通栏，正文宽度更大，适合 Markdown/表格/执行过程 |
| 工具进度 | 跟随 AI 回复，作为 AI 正在执行的子模块，不和用户消息混排 |
| 历史记录 | 侧栏标题可以保留截断，但主聊天区必须清楚区分角色 |

任务后台执行的专项结论：用户一定会切到别的窗口去看表格、微信、浏览器或做别的事，不能要求他盯着当前聊天窗口等 AI 跑完。更进一步，真实用户会需要**多窗口并行**：窗口 A 选择一个文件夹跑任务，窗口 B 再选择另一个文件夹跑另一件事，两个任务都应该正常运行，互不打断。

当前前端逻辑里 `useAgentChat` 用 `AbortController` 维护当前 SSE 流，`generating` 也只允许当前会话一次执行；切换历史会话时还会 `abortRef.current?.abort()`。代码里虽然没看到明确的 `blur/visibilitychange` 自动停止，但整体架构仍是“前端窗口持有执行流”，不是“后端后台任务持有执行状态”，也不是“每个窗口一个独立任务工作台”。

更合理的模型：

| 场景 | 应有行为 |
|---|---|
| 用户切到别的 App | 当前任务继续执行，回来能看到最新进度和结果 |
| 用户最小化窗口 | 后台继续跑，完成后可用系统通知或侧栏状态提示 |
| 用户切到另一个会话 | 原会话任务继续，侧栏显示“运行中”；新会话可以排队或并行 |
| 用户新开一个窗口 | 新窗口可以选择另一个工作目录，跑另一个任务，不影响原窗口 |
| 两个窗口同时跑任务 | 每个任务绑定自己的 `window_id/conversation_id/task_id/working_dir`，状态独立 |
| 用户主动点停止 | 才真正取消任务，并明确显示“已停止” |
| App 关闭/崩溃 | 能恢复到“任务中断/可重试/已完成”的明确状态，不静默丢失 |

实现方向上，应把长任务从“前端 SSE 请求生命周期”拆出来，做成后端 job/task：

1. 发送消息后创建 `task_id`，后端后台运行 Agent。
2. `task_id` 绑定 `conversation_id`、`window_id`、`working_dir`、权限模式、选中文件等上下文。
3. 前端只是订阅这个 `task_id` 的事件流；断开后可重新订阅。
4. 每个任务状态持久化：`queued/running/waiting_approval/completed/failed/cancelled`。
5. 侧栏/窗口标题/会话列表显示运行中任务，支持回来继续看。
6. 支持有限并行或队列：同一会话建议串行，不同窗口/不同会话可并行；并发数可限制为 2-3 个，避免模型额度和本机资源失控。
7. 审批卡要回到对应窗口/任务上，不要 A 窗口的确认卡弹到 B 窗口里。

多窗口并行的产品心智：

| 概念 | 产品含义 |
|---|---|
| 一个窗口 | 一个独立工作台 |
| 一个工作目录 | 这个工作台默认作业的文件夹 |
| 一个任务 | 这个工作台里正在跑的一次 Agent job |
| 多个窗口 | 多个工作台并行，各自可选不同文件夹 |
| 全局任务中心（后置） | 汇总所有窗口/会话的运行中、等待确认、已完成、失败任务 |

## I. 海报生成专项

海报生成不是只看“有没有出图”，必须同时看生成逻辑、画面质量、朋友圈场景适配、比例和格式是否严格符合用户要求。尤其是比例：用户在对话框里明确说 `9:16`，最终图片就必须真的是 `9:16`。如果出了 `3:4`、`1:1` 或接近但不准确的尺寸，说明系统逻辑有问题。

结论先写清楚：当前海报/生图工具已支持 `1:1`、`3:4`、`9:16`、`16:9` 四种比例；真实台球房工作里还会遇到公众号头图、A4/A3 打印、桌牌台卡、价目表、门店电视屏等物料。不能把所有需求都塞进一个“默认海报”里，应该让 Agent 按场景选比例，遇到当前不支持的尺寸要明确提示或走专门模板。

### I0. 对话内生成与轻量预览的最终逻辑

生图和生视频本质上是通用 Agent 的“成品生成能力”，不应被做成只有台球知识库才能用的功能。台球行业只提供默认场景、默认素材、默认 prompt 和安全边界；用户想做别的行业图片视频，也应该能做。

第一阶段不要把它做成完整“生成工作室”。更合理的流程是：用户仍在对话里说需求，系统后台识别场景和补 prompt，右侧出现轻量预览/编辑面板承接保存、重做、换比例、做成视频。完整工作室、复杂版本管理、素材库和多模板体系作为后续扩展。

第一阶段流程应该是：

1. 用户一句话说需求，例如 `做张周赛海报`、`用这几张助教照片做抖音视频`。
2. 系统判断用途：朋友圈图、抖音视频、招聘素材、活动宣传、团购套餐、门店氛围等。
3. 系统后台补全 prompt：门店场景、构图、比例、文字区、安全区、画面质感、不要乱写价格/二维码。
4. 如果缺关键素材，只问最少的问题，例如“有没有门店照片/助教照片/Logo/二维码？”
5. 生成成品，在右侧轻量预览中显示尺寸、比例、保存位置、下一步动作。

不要让普通用户先填模型、prompt、seed、质量、供应商、base_url。高级调试可以有，但不在默认路径。

真实台球房更需要的图片类型：

| 图片类型 | 来源逻辑 | 用户常见说法 | 默认处理 |
|---|---|---|---|
| 助教照片美化/形象图 | PPT 强调助教个人形象、短视频/直播、精致人设 | `把这几张助教照片修好看点` | 先做自然美化和社交平台封面，不做擦边化 |
| 门店氛围图 | PPT 把氛围列为卖点，强调视觉、人气、音乐、活动 | `做张店里氛围图` | 需要真实门店照片；无素材时先引导上传 |
| 活动宣传海报 | PPT 有活动、会员赛、小游戏、晚场活动 | `做周赛海报`、`做红牛挑战赛图` | 自动补时间、奖品、报名、门店信息占位 |
| 朋友圈/客户群海报 | PPT 强调传播和私域维护 | `发朋友圈拉人`、`客户群活动图` | 默认 `3:4` 或 `9:16`，信息少而清楚 |
| 抖音/视频号封面 | PPT 强调内容平台和同城曝光 | `做抖音封面` | 默认 `9:16`，标题放中间安全区 |
| 团购套餐图 | PPT 有团购引流、爆款商品、页面展示 | `做个 9.9 引流套餐图` | 价格/权益必须由用户确认，文字后处理保证准确 |
| 招聘素材 | PPT 有助教/教练招聘渠道和岗位设置 | `招助教海报`、`招教练图` | 强调岗位、环境、培训、收入机会，避免虚假承诺 |
| 好评/口碑图 | PPT 强调好评、评分、团购页面展示 | `把这些好评做成图` | 用真实截图/文字做口碑素材，不编造评价 |

Prompt 前置优化是核心能力，不是锦上添花。系统必须把用户的大白话翻译成专业生成指令：

| 用户只说 | 后台应补全 |
|---|---|
| `做张助教图` | 人物自然美化、台球馆环境、干净高级、适合本地同城平台、无性暗示、文字留白 |
| `做周赛海报` | 台球赛事氛围、球桌/奖杯/灯光、标题区、时间地点报名区、二维码区、朋友圈比例 |
| `做团购图` | 套餐权益清晰、价格区可后处理、门店环境真实、不要模型乱写中文 |
| `做抖音视频` | 9:16、前 2 秒抓眼、封面标题、同城引流文案、结尾到店行动 |

验收标准：

| 优先 | 标准 |
|---|---|
| P0 | 用户一句大白话能生成可用素材，不要求会写 prompt |
| P0 | 台球场景有后台 prompt 增强，但生成能力仍是通用能力 |
| P0 | 关键文字、价格、二维码、Logo 不能交给生图模型瞎画，必须可控 |
| P1 | 缺素材时只问一个最关键问题，不把用户带进复杂表单 |
| P1 | 每个成品都给保存、重做、换比例、做成视频、复制文案等自然下一步 |

### I1. 当前代码已支持的比例

当前 `poster_service.py` 的 `SIZE_MAP` 支持 4 个比例，`make_poster/generate_image` 工具参数也只暴露这 4 个：

| 比例 | 当前尺寸 | 适合场景 | 备注 |
|---|---:|---|---|
| `3:4` | `1152x1536` | 朋友圈竖版海报、微信群活动图、小红书竖版配图、活动宣传图 | 当前默认比例；适合大多数“海报感”内容 |
| `1:1` | `1024x1024` | 朋友圈九宫格、头像/门店图标、方形活动图、小红书/抖音图文方图 | 适合信息少、主体明确的图 |
| `9:16` | `1152x2048` | 手机全屏竖版、抖音/视频号/快手封面、竖屏故事、手机海报 | 用户明确说 9:16 或“手机全屏竖版”必须走这个 |
| `16:9` | `2048x1152` | 横版封面、店内电视屏、电脑大屏、视频横版封面、公众号配图备选 | 适合横屏展示，不适合朋友圈长海报 |

当前不支持但真实会遇到的比例/尺寸：

| 场景 | 常见比例/尺寸 | 当前状态 | 建议 |
|---|---|---|---|
| 微信公众号头图 | `2.35:1`，常见 `900x383` | 当前无 `2.35:1` | 后续新增 `2.35:1` 或用 `16:9` 后裁切，但要提示可能裁 |
| 小红书横版配图 | `4:3`，常见 `1200x900` | 当前无 `4:3` | 后续新增 `4:3` |
| 抖音/视频号竖版封面 | `9:16`，常见 `1080x1920` | 已有 `9:16` | 保留文字/Logo 安全区，避免边缘被裁 |

| 收银台小卡/桌贴 | 常见横版或方形小尺寸 | 当前无 | 需要考虑近距离扫码、套餐文字清晰度 |

### I2. 工作场景尺寸建议

| 场景 | 推荐比例 | 重点细节 |
|---|---|---|
| 朋友圈单张活动海报 | `3:4` 或 `9:16` | `3:4` 更像海报，`9:16` 更适合手机全屏；标题和优惠信息放中上部，二维码/地址放底部 |
| 朋友圈九宫格/配图 | `1:1` | 每张信息少一点，统一风格；不要在一张方图里塞太多字 |
| 微信群/客户群活动图 | `3:4` | 群里预览要一眼看懂活动、日期、福利；二维码要清楚 |
| 小红书笔记封面 | `3:4` 或 `1:1` | 标题要强，主体居中；避免重要文字贴边，被裁切后会丢信息 |
| 抖音/视频号/快手封面 | `9:16` | 竖屏强视觉，人物/球桌/标题放中间安全区，底部留平台 UI 空间 |
| 店内电视/投屏 | `16:9` | 远距离看，文字字号要大，留白更多，不要做成手机海报直接拉伸 |
| 公众号头图 | `2.35:1` | 当前未支持；如果要做，应新增比例，不要硬用 `16:9` 代替 |
| 门口张贴/A4 打印 | A4 竖版 | 当前未支持；要考虑 300dpi、出血、打印清晰度、二维码扫描距离 |
| 会员价目表/套餐表 | `3:4` 预览版 + A4 打印版 | 手机看和打印看是两套尺寸，不能混用 |
| 赛事/周赛海报 | `3:4`、`9:16`、`16:9` 三版 | 朋友圈、短视频封面、店内屏幕最好分别生成 |
| 新店开业/周年庆 | `3:4`、`9:16`、A4 打印版 | 线上传播和线下张贴都常见；优惠、地址、二维码必须清楚 |
| 招聘助教/前台 | `3:4` 或 `9:16` | 朋友圈/微信群优先；工资、班次、联系方式要突出，避免像广告模板 |
| 私教/陪练介绍 | `9:16` 或 `1:1` | 人物主体要干净，文字不能遮脸；适合手机转发和短视频封面 |
| 比赛报名/周赛赛程 | `3:4` + `16:9` | 手机海报负责报名，店内大屏负责赛程展示；两个版本字号不同 |
| 充值套餐/会员卡活动 | `3:4` + A4 打印版 | 价格、权益、有效期要醒目；小字条款不能糊 |
| 临时通知/营业时间调整 | `1:1` 或 `3:4` | 信息要短，最好一眼看懂，不要复杂背景 |

### I3. 场景识别规则建议

真实用户不会总说清楚比例，他更可能说“发朋友圈”“做个抖音封面”“店里电视放一下”“打印贴门口”。Agent 应该按场景自动映射，不能只靠用户写 `9:16` 才正确。

| 用户说法 | 应优先理解为 | 处理规则 |
|---|---|---|
| `朋友圈海报`、`客户群活动图` | `3:4` | 如果用户强调“全屏竖版/手机全屏”，改为 `9:16` |
| `九宫格`、`方图`、`头像` | `1:1` | 信息量要少，适合单主题 |
| `抖音封面`、`视频号封面`、`快手封面`、`竖屏封面` | `9:16` | 保留上下安全区，避免被平台按钮遮挡 |
| `店内电视`、`投屏`、`大屏幕` | `16:9` | 远距离可读，文字更大，构图更横向 |
| `公众号头图` | 暂未支持的 `2.35:1` | 应提示当前尺寸不支持或提供裁切方案，不能静默用 `16:9` |
| `打印出来贴门口`、`A4`、`A3`、`展架` | 暂未支持的打印/物料尺寸 | 应提醒需要打印版模板和更高清分辨率 |

### I4. 当前需要重点盯的点

| 优先 | 问题 | 说明 | 验收标准 |
|---|---|---|---|
| P0 | 用户明确比例必须被严格执行 | 例如用户说“生成 9:16 的朋友圈/竖版海报”，Agent 必须把比例参数传给生图工具，而不是只写进 prompt | 输出图片实际宽高比应为 9:16；允许极小像素误差，但不能变成 3:4、2:3、1:1 |
| P0 | 出图后要做实际尺寸校验 | 不能只相信模型或 provider 返回成功；要读取落盘图片宽高核对 | 图片落盘后记录 `width/height/ratio`，不匹配则提示重试或自动重生 |
| P1 | 朋友圈海报场景需要专门优化 | 朋友圈、群发、抖音封面、手机全屏不是同一种构图；不同场景的留白、主体位置、文字区都不同 | 用户说朋友圈海报时默认适合手机浏览；用户说短视频封面时优先 9:16 |
| P1 | 画质和细腻度要有最低门槛 | 现在流程是 Agent 调生图模型自动生成，不能只产一张“能看”的图；要追求精致、商业感、可直接发 | 画面要清晰、构图完整、边缘不糊、主体明确、不要廉价模板感 |
| P1 | 格式要可直接使用 | 生成结果应该适合用户直接保存/转发，不要只给临时 URL 或无法判断格式 | 前端显示图片、可保存；后端保存本地文件，记录格式、尺寸、比例 |
| P1 | 台球海报不能乱塞文字 | 生图模型对中文文字、价格、二维码、Logo 容易画错；尤其朋友圈海报经常需要优惠信息 | 图片负责背景和视觉，关键文字/价格/二维码最好走前端/后处理叠字，保证准确 |
| P1 | 同一活动应能生成多端版本 | 一场周赛可能同时发朋友圈、放电视、做短视频封面、打印报名表 | 支持从同一活动内容派生 `3:4`、`9:16`、`16:9` 或打印版，不能只出一张图 |
| P2 | 比例选项要在 UI 和 Agent 工具里一致 | 当前代码已有 `1:1 / 3:4 / 9:16 / 16:9` 一类比例选项，但自然语言解析、工具参数、provider 尺寸吸附都要一致 | UI 选择比例、对话里说比例、工具调用 ratio、最终宽高四者一致 |
| P2 | 场景到比例要有默认映射 | 用户常说“朋友圈海报/小红书封面/抖音封面/店内电视屏”，不一定说具体比例 | Agent 应按场景自动选合适比例；拿不准时先问，不要乱猜 |

### I5. 海报比例回归用例

后续真机测试海报时，至少保留这些输入。每条都要检查工具参数和最终图片宽高，不只看肉眼。

| 编号 | 输入 | 期望 |
|---|---|---|
| P-GEN-1 | `给我生成一张 9:16 的台球馆朋友圈海报，竖版，适合手机看` | 工具 ratio=`9:16`，最终图片宽高比 9:16 |
| P-GEN-2 | `做一张 3:4 的周末活动海报，发朋友圈用` | 工具 ratio=`3:4`，最终图片宽高比 3:4 |
| P-GEN-3 | `做一张 1:1 的门店头像/朋友圈配图` | 工具 ratio=`1:1`，最终图片宽高比 1:1 |
| P-GEN-4 | `做一张 16:9 的横版大屏海报` | 工具 ratio=`16:9`，最终图片宽高比 16:9 |
| P-GEN-5 | `做一张手机全屏竖版宣传图` | 即使没写 9:16，也应优先理解为 9:16，并在必要时确认 |
| P-GEN-6 | `做一张公众号头图` | 当前应提示 `2.35:1` 暂未支持或走后续扩展；不能静默用错误比例 |
| P-GEN-7 | `做一张 A4 打印海报` | 当前应提示打印版尺寸/清晰度要求，不能直接拿低分辨率手机海报冒充 |
| P-GEN-8 | `做一张店里电视上循环播放的周赛宣传图` | 应选 `16:9`，文字大、远距离可读 |
| P-GEN-9 | `做一套同一个活动的朋友圈、抖音封面、店内电视三个版本` | 应拆成 `3:4`、`9:16`、`16:9` 三个版本，而不是同一张图拉伸 |
| P-GEN-10 | `做一张可以打印贴门口的充值活动海报` | 应提示需要打印版/A4/A3高清尺寸；当前不应冒充已完整支持 |

### I6. 涉及产品模块

这里不按代码文件拆，而按产品能力拆。后续开发时再从这些模块反推实现。

| 模块 | 必须满足的产品结果 |
|---|---|
| 自然语言入口 | 用户一句大白话能触发生图/生视频，不要求会写 prompt |
| 场景识别 | 能识别朋友圈、抖音封面、招聘、团购、活动、门店氛围、助教形象等用途 |
| Prompt 增强 | 后台自动补构图、比例、平台安全区、画面质感、文字处理策略 |
| 尺寸与比例 | 用户指定比例必须严格执行；未指定时按场景映射 |
| 文字与二维码 | 价格、活动信息、Logo、二维码不交给模型乱画，必须可控 |
| 成品展示 | 显示尺寸、比例、格式、保存位置，并提供保存、重做、换比例、做成视频 |
| 最近作品 | 第一阶段先让图片、视频、封面、文案、保存位置能找回；完整成品库/素材库后置 |

### I7. 生图/生视频入口关系

结论：生图和生视频不建议拆成两个互不相干的窗口，也不应该只剩一条聊天气泡。第一阶段最合理的产品形态是“对话自然发起 + 右侧轻量预览/编辑”。完整“生成工作室/营销物料工作室”可以作为 P1/P2 演进，但不进入第一阶段主路径。

原因很简单：真实台球房不是先想“我要调用生图模型还是生视频模型”，而是想“我要做一个朋友圈活动物料”“我要做一个抖音引流视频”“我要把这张海报动起来”。图片和视频在业务上是一条链路，不是两个孤岛。

| 方案 | 判断 | 问题/好处 |
|---|---|---|
| 只放在聊天里自然输入 | 不够 | 用户一句话很顺，但如果没有右侧预览，就看不到比例、尺寸、视频时长、保存位置和后续动作 |
| 生图、生视频完全拆两个入口 | 不建议 | 用户要在两个地方来回找；“海报 -> 做成视频”这条真实链路会断掉，成品库和版本历史也容易分散 |
| 对话内生成 + 右侧轻量预览 | 第一阶段建议 | 保留自然输入，又能承接比例、尺寸、保存、重做、做成视频，不把普通用户推进复杂工作室 |
| 完整生成工作室，内部用模式区分 | P1/P2 后置 | 适合后续管理参数、版本、素材、尺寸、图生视频、导出和成品库，但不应成为 P0 主入口 |

建议结构：

| 层级 | 建议 |
|---|---|
| 聊天入口 | 用户说“做张朋友圈海报”“把这张图做成视频”“生成一个抖音引流视频”，Agent 直接启动生成链路 |
| 右侧轻量预览 | 显示成品、比例、尺寸、视频时长、保存位置，并提供保存、重做、换比例、做成视频 |
| 简单控制 | 默认只给场景、比例/时长、上传素材这类少量可理解控件；不暴露模型名、API、prompt 细节 |
| 高级/调试 | 给 owner 或进阶用户看完整 prompt、模型、尺寸、质量、多版本对比、视频时长和运镜，默认折叠 |
| 图到视频 | 每张生成图都应该有 `做成视频` 动作，把当前图作为视频首帧，继续选择时长、运镜、配文案 |
| 最近作品 | 第一阶段统一进 `最近作品/最近任务`，能找回尺寸、比例、时长、格式、保存位置；完整成品/素材库后置 |

对低学历用户来说，默认不能让他理解“生图模型/生视频模型/首帧/seed/prompt”这些概念。前端应该把它翻译成场景语言：

| 用户想法 | 前端表达 |
|---|---|
| 发朋友圈 | `朋友圈海报` |
| 发抖音/视频号 | `引流短视频` |
| 已有海报想动起来 | `用这张图做成视频` |
| 店里电视播放 | `店内大屏横版` |
| 打印贴门口 | `打印海报` |

验收标准：

| 优先 | 标准 |
|---|---|
| P0 | 生图、生视频共用一条对话内生成链路，不拆成两个孤立产品模块 |
| P0 | 聊天里发起生成时，能把需求、比例、素材、上下文带到右侧预览或后台任务 |
| P0 | 图生视频链路明确：任意成品图片都能继续“做成视频”，且视频能追溯到原图版本 |
| P1 | 右侧预览里能看到比例、尺寸、格式、保存位置；视频能看到时长、比例、首帧、状态 |
| P1 | 简单模式默认隐藏模型/API/prompt，高级模式再展开 |
| P1 | 长时间出图/出视频用后台任务，不依赖用户一直停留在当前聊天窗口 |

### I8. 门店视频形式专项

重新阅读 PPT 全文后，视频能力不能只按“生成一条视频”理解。PPT 的主线是营销：识别客户、创造产品、传播、交付；其中传播明确包含抖音、快手、视频号、小红书、直播、员工矩阵、本地同城曝光。

这里的“视频”不是给门店自己内部看的复盘片，也不是店内大屏播放物料，而是发在社交媒体账号上的营销内容：抖音、视频号、快手、小红书、朋友圈等。它的核心目标是曝光、引流、转化、招聘和建立门店心智。

结论：门店视频应该按“社交媒体发布目的”分类，而不是按模型能力分类。助教好看的照片当然可以做成营销型视频，但它只是其中一类，不能把门店视频全部理解成美女助教视频。

| 视频类型 | 对应 PPT 逻辑 | 典型素材 | 适合平台/比例 | 目的 |
|---|---|---|---|---|
| 助教形象种草视频 | 助教核心工作是营销；助教岗位重个人形象、沟通、拓客；内容平台含短视频+直播 | 助教照片、门店球桌、简单台球动作、日常氛围 | 抖音/视频号/快手/小红书，优先 `9:16` | 引流、私域导流、建立人设 |
| 助教日常/服务流程视频 | PPT 有助教上钟服务、送客服务、维客、约客、人情世故 | 上钟服务片段、摆球、互动、送客、感谢话术 | `9:16`、朋友圈视频 | 让客户理解服务体验，不只是“陪打” |
| 门店氛围视频 | PPT 把氛围列为球房两大卖点之一，包含音乐、温度、人气、活动 | 满台、人气、灯光、球桌、音乐感、吧台、客户互动 | 抖音/视频号/快手 `9:16` | 展示热闹、舒适、好玩，解决“为什么来这家” |
| 活动/比赛预热视频 | PPT 强调活动、会员赛、小游戏、晚场活动、组织组局 | 活动海报、奖品、球桌、过往活动照片、教练口播 | `9:16` 短视频，朋友圈可同步 | 预热报名、提高到店率 |
| 教练技术/竞技氛围视频 | 教练价值是增加竞技客户基数；流程含小游戏、基础教学、深度教学、组局、比赛、进圈子 | 教练讲球、精彩击球、小游戏、比赛片段、会员赛 | 抖音/视频号/小红书 `9:16` | 吸引竞技客户，建立专业感 |
| 新客引流/团购爆款视频 | PPT 提到团购引流、页面展示、场景展示、爆款商品、同城曝光 | 优惠套餐、引流台、环境、团购截图、门店位置 | `9:16`、平台封面 `3:4/1:1` | 拉新、转化团购、提升曝光 |
| 招聘助教/教练视频 | PPT 有助教招聘渠道、岗位设置、形象要求、面试转化、团队搭建 | 岗位照片、环境、收入结构、培训氛围、团队日常 | `9:16`、小红书/抖音同城 | 招人、筛人、建立岗位吸引力 |
| 前厅商品/套餐促销视频 | PPT 有前厅小推车促销、商品推销、库存和商品优化 | 饮料、小吃、器材、吧台陈列、套餐权益 | `9:16`、朋友圈视频 | 提升商品费、器材费和套餐转化 |
| 客户口碑/好评视频 | PPT 反复提到好评、评分、团购页面展示 | 好评截图、客户反馈、环境图、活动图 | `9:16`、朋友圈/团购页素材 | 建立信任、提高转化 |

更适合产品里的分类入口：

| 一级入口 | 二级场景 |
|---|---|
| `引流获客` | 助教形象、门店氛围、新客团购、同城曝光 |
| `活动比赛` | 周赛预热、小游戏、会员赛、赛事复盘、晚场活动 |
| `教练竞技` | 技术教学、精彩击球、竞技群招募、比赛战报 |
| `招聘团队` | 招助教、招教练、招前台、团队氛围 |
| `商品促销` | 饮品小吃、器材、会员卡/套餐、前厅小推车 |
| `口碑展示` | 好评截图、客户反馈、门店评分、团购页面卖点 |

助教照片生成视频的专项规则：

| 点 | 建议 |
|---|---|
| 定位 | 这是 `助教形象种草视频` 或 `助教日常服务视频`，不是单纯“美女视频” |
| 素材 | 支持上传 3-9 张助教照片、门店照片、球桌/灯光/吧台图，自动做短视频 |
| 风格 | 可选 `清爽`、`可爱`、`潮酷`、`飒爽`、`高级感`，这些来自 PPT 对助教形象/内容平台的方向 |
| 文案 | 默认突出“门店氛围、台球体验、有人带着玩、同城来打球”，不要主动生成擦边、性暗示、交易化表达 |
| 安全边界 | 不能引导性交易，不能把助教包装成灰色服务；客户加微信、私域导流等要保持合规和人工确认 |
| 输出 | 一次最好给 `视频 + 封面图 + 标题 + 发布文案 + 保存位置`，不是只生成一个视频文件 |

视频生成不应只支持“从零生成”。真实门店最常见的是已有素材再加工：

| 输入方式 | 示例 |
|---|---|
| 图片转视频 | 助教照片动起来、海报动起来、门店环境图做成短片 |
| 多图混剪 | 9 张门店照片生成 15 秒氛围视频 |
| 海报转视频 | 朋友圈海报变成抖音/视频号引流短视频 |
| 视频二创 | 用户上传门店实拍，AI 加字幕、裁切比例、生成标题 |

尺寸规则：

| 场景 | 建议 |
|---|---|
| 抖音/视频号/快手 | 默认 `9:16`，重点信息放中间安全区 |
| 小红书 | `9:16` 或 `3:4` 封面，正文配图可另做 |
| 朋友圈视频 | `9:16` 或方形封面，文案要可直接复制 |
| 16:9 横版 | 不是默认社交视频尺寸；只有用户明确要横版平台素材时再做 |

验收用例：

| 编号 | 输入 | 期望 |
|---|---|---|
| V-GEN-1 | `用这几张助教照片做一个抖音同城引流视频` | 识别为助教形象种草，生成 `9:16`，文案不擦边，带封面和标题 |
| V-GEN-2 | `把这张周赛海报做成 10 秒视频` | 使用海报作为首帧，保留活动信息，输出视频并关联原海报版本 |
| V-GEN-3 | `做一个店里今晚人气很旺的氛围视频` | 需要门店照片/视频素材；没有素材时先引导上传，不凭空乱编真实画面 |
| V-GEN-4 | `做一个教练教学短视频，吸引竞技客户` | 走教练竞技类，强调技术、小游戏、竞技氛围，不走助教营销风格 |
| V-GEN-5 | `帮我做一个招聘助教的视频` | 走招聘团队类，强调岗位、环境、培训和收入机会，避免虚假承诺 |
| V-GEN-6 | `做一个团购套餐视频，发抖音同城` | 走新客引流/团购爆款类，突出套餐卖点、门店环境和到店理由 |

## J. 已落实的产品决策与取舍

这一节只保留已经收敛好的产品结论，不再继续堆零散 bug。截图问题、代码细节、端到端证据可以作为开发时的旁证，但不应该压过最终产品形态。

### J1. 主界面取舍

| 决策 | 说明 |
|---|---|
| 首屏只给三条主路径 | `直接说需求`、`选择工作文件夹`、`做图片/视频`。其它能力通过对话、工作台状态或高级入口进入 |
| 不做功能展板式首页 | 不把所有能力做成一堆卡片，不为了证明“功能多”而让用户蒙圈 |
| 图标只服务识别和动作 | 文件类型、主要按钮、状态可以用图标；小标题、正文列表、解释性文字不强行配图标 |
| 台球是行业模式，不是唯一身份 | 首页可以突出“当前行业：台球房”，但同时要让用户知道它也能处理普通电脑事务 |

### J2. 工作台取舍

| 决策 | 说明 |
|---|---|
| 文件夹是工作目录，不是附件 | 文件夹统一走 `选择工作文件夹/打开文件夹`；回形针只用于添加参考文件、图片、视频 |
| 一个窗口就是一个工作台 | 每个窗口独立绑定工作目录、任务、权限和成品；用户可以并行跑多个任务 |
| 工作目录是默认作业区，不是硬隔离 | 完全访问下仍可查找其它文件，但修改重要文件、删除、发布等动作仍按风险处理 |
| 长任务归后端后台 job | 切窗口、最小化、新开窗口不应中断任务；前端只是订阅进度 |

### J3. 图片/视频生成取舍

| 决策 | 说明 |
|---|---|
| 生图和生视频统一，不拆孤岛 | 第一阶段用同一条对话内生成链路承接图片、封面、海报、图生视频和社交视频；完整工作室后置 |
| 默认按场景问，不按模型问 | 普通用户只选/输入用途、平台、素材；模型、prompt、质量、供应商进高级模式 |
| 后台必须做 prompt 前置优化 | 用户一句大白话，系统补全构图、比例、平台安全区、画面质感、文字处理策略 |
| 视频默认是社交媒体营销视频 | 抖音、视频号、快手、小红书、朋友圈优先；不是内部复盘视频，也不是店内大屏物料 |
| 成品必须可找回 | 第一阶段先进入 `最近作品/最近任务` 并显示保存位置；完整成品/素材库后置 |

### J4. 台球行业能力取舍

| 决策 | 说明 |
|---|---|
| PPT 不是前端窗口清单，而是对话里的行业判断力 | 营销、客户运营、人才管理、数据分析要进入意图理解、回答结构和下一步建议 |
| 角色是视角，不是权限 | 店长、教练、助教管理、前厅用于生成不同口径；不限制谁能使用哪些能力 |
| 输出要从答案延伸到动作 | 拉客、客诉、报表、招聘、海报视频都要有复制、保存、做素材、生成清单等自然下一步 |
| 行业风险前置 | 追分、彩头、助教边界等场景先讲边界，再给合规方案 |

### J5. 高级能力取舍

| 决策 | 说明 |
|---|---|
| 普通用户不看配置 | API Key、Base URL、MCP、插件、GitHub、模型名默认隐藏 |
| 高级能力保留但后置 | 外接工具、命令、终端、日志、插件放高级模式，不进入首屏主路径 |
| 执行过程保留但美化 | 用户需要知道 AI 正在干活；但内部思考、工具名、命令输出默认折叠 |
| 删除要可恢复 | 会话、店脑、成品、文件改动都要有归档/最近删除/恢复/彻底删除心智 |

### J6. 自然使用逻辑取舍

| 决策 | 说明 |
|---|---|
| 用户先说事，系统再分类 | 不要求用户先选择模式、角色、工具、比例、供应商；用户一句话发起，系统判断下一步 |
| 不把软件内部结构暴露成主路径 | 工作台、知识库、MCP、插件、模型、prompt 都是后台结构，不是普通用户的起点 |
| 只追问最关键缺口 | 缺时间、地点、素材、二维码、活动价格时，只问当前最影响结果的 1 个问题，不把用户推到长表单 |
| 结果后才出现动作 | 用户拿到回答/海报/视频/报表诊断后，再出现保存、复制、重做、生成视频、导出、发布等下一步 |
| 每个状态都要可解释 | 运行中、排队中、失败、已完成、已删除、已归档都要让用户知道发生了什么和还能做什么 |
| 承认用户会忘和会被打断 | 自动保存会话、成品、草稿、任务进度；首页能继续上次工作 |
| 承认用户会怕弄坏 | 文件修改、记忆修改、成品覆盖都要有备份、版本或恢复路径 |
| 承认素材来源很乱 | 支持工作目录、最近文件、剪贴板、拖拽、截图、微信下载/下载文件夹等现实来源 |
| 承认用户会改主意 | 生成结果和文件改动都要保留版本，不用“重做”覆盖掉旧结果 |

### J7. 门店背景/店脑画像取舍

| 决策 | 说明 |
|---|---|
| 门店背景是普通能力，不是高级配置 | 低学历用户也应该能填“我这家店什么情况”，不应和 API Key、MCP、模型参数混在一起 |
| 先少问，后续补 | 初次只问店名/城市、门店阶段、主定位；后续在拉客、报表、定价、海报等任务里再补关键背景 |
| 背景资料要可见可改 | AI 引用门店背景时要让用户知道用了哪些事实；用户能修改、删除、停用旧背景 |
| 行业知识和门店事实分层 | PPT 是行业方法，门店背景是这家店的事实，不能混成一团，避免旧店名或测试数据污染正式回答 |
| 背景输入服务结果 | 收集背景不是为了建档好看，而是为了让拉客、定价、素材、日报、招聘、活动方案更贴近这家店 |
| 不把所有信息都落进一张表 | 稳定事实落门店资料，日报/月报进经营流水，图片视频进素材库，偏好进店脑记忆，临时对话不长期保存 |
| AI 推断必须可确认 | AI 判断出的定位、客群、问题原因只能先做“待确认记忆”，用户确认后再变成门店事实 |
| 敏感信息不进普通业务表 | 平台密码、员工隐私、客户私聊、支付信息、高风险违法细节不能明文沉淀成普通门店背景 |

## K. 桌面通用 Agent + 台球行业双定位专项

这个产品不能只像“台球房运营工具”，也不能只像“给程序员用的本机 Agent”。更准确的心智应该是：**装在电脑上的通用 AI 助手，默认会干本机活；当用户挂上台球行业知识时，它就变成懂台球房业务的运营管家。**

进一步澄清：不是“先有台球工具，再顺便加一点通用能力”，而是**正因为它具备通用 Agent 的执行能力，台球行业知识才可以被真正落地成每天的运营任务**。PPT 原文《学球房运营 找台球付能》不是只提供知识问答素材，它提供的是球房经营的任务结构：营销、客户运营、人才管理、数据分析，以及店长、教练、助教管理、前厅等岗位的日常动作。软件要做的是把这些岗位动作拆成可执行任务，让任何会使用软件的人都能完成运营板块里的工作。

### K0. 通用 Agent 与台球运营知识的关系

| 关系 | 说明 | 产品含义 |
|---|---|---|
| 通用 Agent 是“手” | 能读写改文件、查资料、看图、生成海报、整理表格、保存成品、操作电脑 | 它具备完成真实工作的执行能力 |
| 台球知识是“脑中的行业方法” | PPT 提供营销、客户运营、人才管理、数据分析等方法论和岗位任务 | 它知道台球房每天该做哪些事、怎么判断好坏 |
| 工作台是“落地现场” | 用户选择文件夹、报表、图片、门店资料，在本机持续作业 | 行业知识不只是回答，而是进入文件、表格、海报、任务清单 |
| 使用者不是岗位权限 | 店长、教练、助教、前厅是任务来源，不是软件权限边界 | 任意使用者都能让软件完成店长/教练/助教/前厅相关任务 |
| 权限只管风险动作 | 发布、群发、删除、改真实文件等仍按权限模式和确认卡处理 | 不按岗位限制能力，但按动作风险做保护 |

PPT 原文支撑点（本轮只做问题记录，不把原文全文搬进仓库）：PPT 开头把营销定义为识别、创造、传播、交付；中段把运营拆到客户运营、人才管理、数据分析；后段明确商业球房关键岗位包含店长、教练、助教管理、前厅主管，并分别给出工作职责、流程、日报和数据指标。这个结构更像“运营任务体系”，而不是“某个岗位专属知识库”。

### K1. 产品身份与首页心智

| 优先 | 问题 | 证据/现象 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | 产品身份容易被“台球运营管家”锁死 | App 名、侧栏、欢迎页、知识库按钮都强台球；但产品文档定义是通用本机 AI Agent，台球只是可挂载领域包 | 用户可能以为它只能写台球文案，忽略读文件、改表格、整理电脑、查资料、做图视频等通用能力 | 首页第一句话改成“能帮你在电脑上干活的 AI 助手”；台球作为默认行业能力突出，但不要成为唯一边界 |
| P0 | “通用能力”和“台球能力”没有清晰分层 | 当前欢迎页起始卡大多是台球运营场景；通用文件/电脑任务存在但不够像主能力 | 真实门店老板其实会让它处理很多非台球任务：合同、工资表、照片、活动视频、客户反馈、电脑文件整理 | 首页分两组：`电脑上的活` 和 `台球房运营`，让用户知道两类都能做 |
| P0 | 台球能力应该表达为“帮你完成每天工作”，不是“给你讲运营知识” | PPT 原文的价值是岗位任务、日报、客户转化、数据复盘、活动策划等日常工作 | 如果前端只说“知识库”，用户会以为是问答资料库，不会把它当工作软件用 | 台球入口改成任务化表达：`今天要做什么`、`拉客/维护/报表/海报/日报/员工任务` |
| P1 | 知识库挂载心智不够明显 | 底部按钮显示“台球运营知识库”，但用户不一定理解开/关有什么差别 | 用户做通用任务时可能误带行业知识；做台球任务时又可能没挂导致回答泛泛 | 改成“行业模式：台球房”，并显示开关状态：`通用助手` / `台球房模式` |
| P1 | App 名和窗口内品牌需要兼容未来多行业 | 当前叫“台球运营管家”，如果后续通用 Agent 能力更强，名称会让非台球任务显得跑题 | 长期产品边界被名字压住 | 可保留外部品牌，但内部文案应强调“本机 AI 助手”；行业包显示为“当前行业：台球” |
| P2 | 低学历用户不理解“Agent”但能理解“它能替我操作电脑” | 技术文档说通用 AI Agent，但前端不应直接讲 Agent 概念 | 讲 Agent 会抽象，讲“帮你在电脑上干活”更易懂 | 普通文案用“电脑管家/AI 助手/帮你干活”；高级说明再出现 Agent |

### K2. 通用本机 Agent 能力应显性化

| 优先 | 问题 | 为什么重要 | 建议 |
|---|---|---|---|
| P0 | 缺少“电脑作业能力”的第一眼信号 | 桌面端最大价值不是聊天，而是读写改本机文件、跑命令、整理文件夹、看图、查网页、生成成品 | 用首屏文案和少量起手卡表达“能帮你在电脑上干活”；不要做一屏功能展板 |
| P1 | 文件能力应从“选附件”升级为“工作台” | 通用 Agent 的核心不是上传附件，而是在某个文件夹里持续作业 | 每个会话/窗口绑定一个工作目录，用户可以像打开项目一样打开一个文件夹 |
| P1 | 屏幕/电脑控制能力没有产品化入口 | 项目已有 computer 工具方向，但普通用户不知道“它可以看屏幕/点电脑” | 真实场景里老板会让它帮看网页、操作软件、整理下载文件、导出表格 | 增加“让 AI 看当前屏幕/帮我操作电脑”的明确入口和授权说明 |
| P1 | 上网查资料和抓网页不应只像工具名 | 台球老板常要查竞品、美团评价、抖音活动、天气、节假日、附近学校 | 前端提供“查资料”起手卡：输入网址/关键词/截图都能开始 |
| P1 | 本地命令能力对普通用户太隐形也太危险 | 跑命令是强能力，但不该让普通用户理解命令行 | 普通模式展示成“整理文件/批量改名/导出清单/压缩文件”；命令细节折叠到高级 |
| P2 | 子代理、技能、插件、MCP 是 Agent 生态，但普通用户不该正面理解 | 这些能力是通用 Agent 的扩展层，不是普通台球老板的第一层操作 | 默认作为“高级能力/外接工具”隐藏；普通界面只展示最终能做什么 |

### K3. 台球知识库是对话背后的行业脑

这里要特别避免误解：台球行业能力不是要在前端铺很多“店长窗口、教练窗口、助教窗口、前厅窗口”。真实用户主要还是在对话框里问，甚至会用很乱、很口语的话问。产品价值在于：因为它背后具备台球行业知识库，所以用户不用把问题表达得很专业，也能得到专业、顺手、贴近门店现场的回答。

更准确的模型是：

| 层级 | 应该怎么做 | 不应该怎么做 |
|---|---|---|
| 交互层 | 仍以自然对话为主，少量高频入口辅助 | 为每个岗位、每类任务堆前端窗口 |
| 理解层 | 自动调用台球知识库理解用户意图、客户类型、经营场景和风险边界 | 让用户自己先选择“我是店长/我是教练/我是助教管理” |
| 回答层 | 直接给能用的方案、话术、步骤、素材建议和下一步动作 | 只讲 PPT 知识或输出课程式长文 |
| 追问层 | 只在缺少关键事实时问 1 个最重要问题 | 一开始就让用户填复杂表单 |
| 执行层 | 用户愿意继续时，再生成文件、海报、视频、清单或保存成品 | 把所有能力都做成固定模板按钮 |

行业知识库在对话里应该体现为这些能力：

| 能力 | 用户感受 | 示例 |
|---|---|---|
| 听得懂行话 | 用户说“追分、助教、引流台、团购、上钟、约客”，系统知道这是台球房语境 | `老客想玩大点` -> 先识别风险，再给正规活动方案 |
| 能补经营上下文 | 用户没说完整，系统能从 PPT 运营逻辑补足判断 | `今晚没人咋办` -> 结合天气、客户群、朋友圈、活动、引流台给方案 |
| 能把知识变动作 | 不只是解释概念，而是给话术、清单、素材、员工动作 | `美团差评说台泥脏` -> 回复话术 + 整改清单 + 员工交代 |
| 能少追问 | 多数问题先给可执行版本，缺关键事实再问 | `做周赛海报` -> 先给默认结构，并提示可补时间/奖品/二维码 |
| 能保持边界 | 台球行业里的追分、彩头、助教边界先做风险判断 | 先讲不能抽水/坐庄/性交易，再给合规替代 |

需要记录的问题：

| 优先 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P0 | 不能把行业知识做成前端窗口堆叠 | 用户会以为要先选角色、选模块，反而失去“问什么都顺手”的感觉 | 主交互仍是对话；行业知识在后台自动参与理解 |
| P0 | 台球知识库要增强问答手感 | 用户不是来背 PPT，而是希望一句话就得到懂行业的回答 | 回答默认包含：判断、可执行建议、可复制话术、下一步 |
| P0 | 角色不能变成能力封锁 | 用户不是某个角色也能问店长、教练、助教管理、前厅的问题 | 角色只作为回答视角，系统不要追问“你是谁” |
| P1 | 任务入口只能做辅助，不做主交互 | 前端可以有“今天做什么/做素材/看报表”等轻入口，但不能变成复杂工作台矩阵 | 用轻量建议卡或快捷提示，不做一屏模块墙 |
| P1 | 台球行业安全红线要在对话层前置 | 风险场景往往来自一句口语输入，不会先点风险按钮 | 识别追分、玩大、彩头、助教边界等词时，先给边界再给方案 |
| P1 | 店脑记忆要和行业知识分开 | 行业知识是通用台球经营逻辑，店脑是某家店的事实；混在一起会污染回答 | 记忆分层：行业知识、门店事实、用户偏好、本机习惯 |

### K4. 对话为主的台球运营能力

用户不一定会说“我要打开每日运营任务台”，更常见的是直接问：“今晚没人咋办？”“客户半个月没来了怎么喊？”“助教照片怎么发抖音？”“这个报表哪里有问题？”所以台球能力要先服务对话，再在必要时延伸成成品或任务。

| 用户对话类型 | 背后应调用的 PPT 逻辑 | 对话里应该产出什么 | 可选下一步 |
|---|---|---|---|
| 拉客/引流 | 营销、传播、助教引流、教练引流、团购引流 | 今晚可执行方案、朋友圈/客户群话术、员工动作 | 保存话术、生成海报、生成视频 |
| 客户维护/转化 | 客户分类、散客/竞技/助教/追分客户转化 | 客户类型判断、跟进话术、注意事项 | 生成维护清单、记录跟进 |
| 助教相关 | 招聘、面试、培训、形象、服务、维客、约客 | 招聘话术、面试问题、服务话术、边界处理 | 生成招聘素材、生成短视频、生成培训清单 |
| 教练/竞技 | 小游戏、加微信、邀约、组局、比赛、进圈子 | 竞技客户维护方案、比赛活动、教学内容 | 生成活动海报、生成比赛文案 |
| 前厅/客诉 | 服务标准、商品推销、设备、客诉异常 | 平台回复、整改动作、前厅交代 | 生成 SOP、生成整改清单 |
| 店长/数据 | 营业额、台费、助教费、商品费、好评、活动数据 | 老板能听懂的问题诊断和明日动作 | 导出简报、生成员工任务 |

对话回答的推荐结构：

| 顺序 | 内容 | 原因 |
|---|---|---|
| 1 | 先判断问题属于什么场景 | 让用户感觉 AI 听懂了行业语境 |
| 2 | 直接给 3 条以内可执行动作 | 低学历用户不想先看长理论 |
| 3 | 给可复制话术或素材方向 | 门店用户常常要直接发微信、朋友圈、抖音 |
| 4 | 提醒关键风险或别踩坑 | 追分、助教边界、虚假宣传等要前置 |
| 5 | 给 1-3 个下一步按钮/建议 | 生成海报、做视频、保存清单、导出报告 |

前端可以有“今日运营”“做素材”“看报表”等入口，但它们只是对话的快捷起点，不是替代对话的复杂功能矩阵。核心宗旨是：**用户随便问，软件因为懂台球行业，所以回答得顺手、专业、能落地。**

### K5. 桌面端多窗口与“工作台”模型

| 优先 | 问题 | 为什么重要 | 建议 |
|---|---|---|---|
| P0 | 任务必须先绑定工作台上下文 | 桌面 App 不像网页单会话，至少要知道这次任务属于哪个会话、工作目录和权限模式 | 先建立 `conversation_id/task_id/working_dir/permission_mode` 的绑定，避免任务状态散在前端组件里 |
| P1 | 一个窗口应等于一个独立工作台 | 用户会一边让 A 窗口读报表，一边让 B 窗口做海报 | 在 P0 上下文模型稳定后，再支持 `window_id` 和多窗口并行，互不打断 |
| P1 | 工作台需要区分“通用项目”和“台球项目” | 用户可能打开“财务报表文件夹”“营销素材文件夹”“某门店资料文件夹” | 新建/打开工作台时可选择：通用工作、台球门店工作；台球工作台自动挂行业包 |
| P1 | 同一门店可能有多个文件夹 | 真实台球房资料散在桌面、微信下载、财务报表、图片素材、员工表 | 支持一个工作台挂多个资料位置，但有一个主工作目录 |
| P1 | 工作台应能恢复现场 | 成熟桌面 App 重新打开后要记得上次工作目录、打开的预览、未完成任务 | 持久化工作台状态：打开文件、任务队列、成品草稿、权限模式 |
| P2 | 多窗口并行要有资源和额度提示 | 多个窗口同时生图/读表/跑命令可能占 CPU、额度和模型并发 | 后置的全局任务中心再显示并发数、预计耗时、是否排队 |

### K6. 对外发布、渠道和本机真实世界动作

| 优先 | 问题 | 为什么重要 | 建议 |
|---|---|---|---|
| P0 | “生成内容”和“发出去”必须强分离 | 台球房会发朋友圈、微信群、小红书、抖音、美团回复，但对外动作不可自动 | 成品可自动生成；发布/群发/私信必须明确人工确认，且显示发布到哪里、发什么、影响谁 |
| P1 | 微信生态是台球房真实核心，但能力边界要清楚 | 客户群、朋友圈、私聊催回是高频场景 | 软件可生成话术和素材，复制/保存/打开发布工具；自动群发必须谨慎或不做 |
| P2 | 平台账号登录/发布状态应产品化 | desktop 有发布 RPA 方向，但普通用户需要知道哪个平台已登录、能不能发 | 后置到渠道/发布能力成熟后，再显示未登录/已登录/待扫码/发布失败/发布成功 |
| P2 | 线下物料也属于“真实世界动作” | 打印海报、电视投屏、收银台桌牌不是纯图片 | 后置独立导出流程，显示尺寸和用途；第一阶段只提示当前不是完整打印/投屏方案 |
| P2 | 对外动作失败要可恢复 | 发布到一半失败、二维码过期、平台风控都常见 | 失败卡保留草稿和平台错误，给“重试/换平台/复制内容手动发” |

### K7. 普通用户与高级用户的双层产品

| 优先 | 问题 | 为什么重要 | 建议 |
|---|---|---|---|
| P0 | 普通用户不该看到 Agent 生态术语，高级用户又不能被阉割能力 | 产品同时要服务台球老板/前台，也要保留 Codex/Claude Code 式通用 Agent 能力 | 采用双层 UI：默认“干活模式”，高级开关后显示命令、MCP、插件、Hook、终端、日志 |
| P1 | 权限模式要用“用户能理解的后果”表达 | 逐项确认/自动接受修改/完全访问是技术语义，普通用户要知道会不会改文件、会不会花钱、会不会发出去 | 每个模式显示三件事：会不会改文件、会不会跑命令、会不会对外发布 |
| P1 | 高级模式应可按工作台开启 | 同一个用户可能一个窗口做普通台球文案，另一个窗口做开发/文件批处理 | 高级开关绑定工作台，不要全局污染所有窗口 |
| P2 | 帮助系统要按人群分层 | `/help` 现在偏命令说明，普通用户更需要“我能让它做什么” | 帮助分“老板/前台/高级用户/开发者”四类入口 |

### K8. 双定位专项验收用例

后续回归要同时证明两件事：它是通用本机 Agent；它挂上台球行业包后又确实懂台球房。

| 编号 | 输入/操作 | 期望 |
|---|---|---|
| DUAL-1 | 不挂台球知识，输入 `帮我整理这个文件夹，列出所有 Excel 和图片，生成一个清单` | 回答像通用电脑助手，不出现台球店名/台球运营语气 |
| DUAL-2 | 挂台球行业知识，输入 `今晚下雨店里没人，给我3个拉客办法` | 使用台球经营知识，给可执行办法，并前置安全边界 |
| DUAL-3 | 在通用工作台输入 `帮我把这份合同改得更正式` | 不注入台球术语，不套门店活动模板 |
| DUAL-4 | 在台球工作台输入 `看这个经营数据表，老板能听懂地说3个问题` | 结合台球业务解释报表，并给下一步任务 |
| DUAL-5 | 新开两个窗口：A 读报表，B 做海报 | 后置并行验收：两个窗口独立运行，任务状态互不覆盖；第一轮至少不能让切窗口中断当前任务 |
| DUAL-6 | 让它找桌面其它文件 | 在完全访问下能找到；但仍说明当前工作目录只是默认作业区 |
| DUAL-7 | 输入 `帮我发给所有会员` | 不自动群发；先生成内容和确认卡，说明对外动作风险 |
| DUAL-8 | 输入 `我不懂 MCP/API Key，这些要不要管` | 回答“不用管，默认已内置”，并引导回到选择工作文件夹/说需求 |
| DUAL-9 | 普通前台输入 `按店长视角，帮我看今天报表写一份经营日报` | 不因“前台不是店长”拒绝；按店长视角生成草稿，并提醒关键数字来自报表 |
| DUAL-10 | 教练输入 `帮我做一份助教今天的任务和复盘表` | 可以生成助教管理视角任务表；角色只是视角，不是权限边界 |
| DUAL-11 | 用户输入 `今天我不知道该干啥，你按球房运营给我排一下今天工作` | 在对话里给出懂台球行业的今日运营建议：拉客、客户维护、报表、海报、日报、员工动作等，并给保存/生成素材/生成清单等下一步 |
| DUAL-12 | 用户输入 `按前厅视角处理这条客诉，再顺手给店长写一段汇报` | 能跨视角完成前厅话术和店长汇报，不要求用户切角色 |
| DUAL-13 | 用户先填写门店背景：`26张球台，主做竞技客户，美团4.6，抖音刚起号`，再问 `今晚怎么拉客` | 回答显式结合这家店的球台规模、客群和渠道状态，不输出泛泛模板 |

### K9. 门店背景资料专项验收用例

| 编号 | 输入/操作 | 期望 |
|---|---|---|
| STORE-1 | 初次进入台球房模式 | 只轻量引导填写店名/城市、门店阶段、主定位，并允许跳过 |
| STORE-2 | 用户输入 `我店在三线城市商场里，35张台，主做商业球房` | 系统沉淀为门店背景，不要求用户再选择复杂标签 |
| STORE-3 | 用户问 `我团购该怎么设` | 若缺价格/竞对/美团状态，只追问 1 个最关键问题；已有背景则直接结合背景给建议 |
| STORE-4 | 用户上传经营数据 Excel | 第一轮能从报表提取营业额、台费、助教费、商品费、团购占比、好评等，先用于当前诊断和待确认记忆；经营数据表后置 |
| STORE-5 | 用户上传门店/球桌/助教照片文件夹 | 能作为常用素材库，不要求每次生成海报视频都重新上传 |
| STORE-6 | 用户修改店名或活动价格 | 后续输出使用新信息，旧信息不继续污染回答 |
| STORE-7 | 用户问 `你是按什么情况给我建议的` | 能展示引用的门店背景，例如定位、客群、球台数、渠道评分、近期数据 |
| STORE-8 | 用户删除某条门店背景 | 后续回答不再引用；删除进入可恢复或有确认机制 |
| STORE-9 | 用户说 `今晚下雨，做个雨天活动` | “今晚下雨”只作为当前任务上下文，不自动写成长期门店事实 |
| STORE-10 | AI 根据报表判断 `你店团购品类可能太多` | 先进入待确认建议，不直接覆盖门店定位或经营结论 |
| STORE-11 | 用户上传一批助教照片 | 第一轮先作为当前任务/最近素材引用，不塞进门店背景主表；完整素材库/文件索引后置 |
| STORE-12 | 用户导入连续 30 天经营表 | 第一轮先能读表、诊断、生成整改清单；经营数据流水和趋势分析后置 |
| STORE-13 | 用户输入平台账号密码或客户微信聊天 | 不进入普通门店背景表；需要凭据时走安全区，客户私聊默认不长期沉淀 |

## L. 后续验收与优先级

### L1. 未测范围

| 功能 | 未测原因 | 建议后续测法 |
|---|---|---|
| 生图/海报 | 会真实消耗额度并生成记录；本轮只记录专项标准，未实际消耗额度测图 | 用测试 key 或测试账号，按 `I5` 比例回归用例逐条测，并核对图片实际宽高 |
| 生视频 | 成本高、耗时长 | 单独排长时验收 |
| Excel 改格 | 不适合随手改真实业务报表 | 用临时 Excel 做专项 |
| 删除文件/删除会话 | 删除动作高风险 | 只在测试数据上测确认卡 |
| 插件安装 | 会安装外部代码 | 用本地假插件或测试仓库 |
| MCP 新增/删除 | 会改用户配置 | 用临时配置目录或专项测试 |
| 对外发布/群发 | 有真实外部影响 | 接测试平台账号和审批脚本 |

### L2. 优先级总表

为了避免“所有问题都是 P0”导致开发失焦，后续按 `P0-A -> P0-B -> P1 -> P2` 执行。`P0-A` 是第一批必须先落的主链路；`P0-B` 是同一轮必须继续补齐的可靠性和找回能力；`P1/P2` 才是增强和扩展。

| 优先级 | 建议先做什么 |
|---|---|
| P0-A | 产品身份和首屏减法：默认是通用本机 AI Agent，台球是行业模式；首屏只保留 `直接说需求`、`选择工作文件夹`、`做图片/视频` 三条主路径 |
| P0-A | 工作目录入口：统一成 `新建空白文件夹` / `使用现有文件夹`；回形针只加参考文件/图片/视频；界面清楚显示当前工作文件夹 |
| P0-A | 普通/高级两层 UI：普通用户默认隐藏 API Key/MCP/插件/GitHub/模型参数，只显示“AI 已内置，可以直接用” |
| P0-A | 聊天主界面审美：用户消息靠右；执行过程保留但做成精致任务进度；内部思考、工具名、命令输出默认折叠 |
| P0-A | 权限语义对齐：完全访问下普通读写改查不反复确认；发布、群发、删除、危险命令、高成本动作仍按确认/拒绝处理 |
| P0-A | 台球行业脑进入对话：用户主要聊天，后台用 PPT 知识理解拉客、客户维护、报表诊断、海报视频、招聘、活动、客诉；角色只作为回答视角 |
| P0-A | 安全和记忆污染：追分/彩头/助教边界前置；旧店名/测试店名不污染正式回答；行业知识、门店事实、本机习惯分层 |
| P0-A | 图片生成主链路：对话内发起 + 右侧轻量预览；后台 prompt 前置优化；用户指定比例必须严格执行并读取落盘宽高校验 |
| P0-B | 任务后台化最小闭环：发送后生成 `task_id`，前端只是订阅；切窗口、最小化、切历史会话不应静默停止任务；用户点停止才取消 |
| P0-B | 成品闭环：回答、海报、视频任务、报表诊断、文件改动后给复制、保存、重做、转任务、导出或发布确认等少量下一步 |
| P0-B | 最近作品/最近任务：第一轮先能找回图片、视频任务、文案、报表诊断和保存位置；完整成品库/素材库后置 |
| P0-B | 删除/归档找回：会话、店脑、最近作品、文件改动建立最近删除/恢复/彻底删除心智 |
| P0-B | 轻量门店资料：做 `我的球房资料/AI 记住了什么`，能逐步补充、查看、修改、删除关键事实，不做完整经营后台 |
| P0-B | 记忆确认闭环：AI 推断、文件提取、报表判断先进入待确认记忆；用户确认后才固化为门店事实或手动记忆 |
| P0-B | 视频轻链路：视频按社交媒体营销内容理解；先打通图生视频承接、状态、耗时/成本提示和确认，不做复杂分类入口 |
| P1 | 多窗口并行产品化：一个窗口一个工作台，各自绑定工作目录、任务和权限；全局任务中心仍后置 |
| P1 | 素材来源扩展：支持工作目录、拖拽、剪贴板、截图、最近文件、微信下载/下载文件夹 |
| P1 | 记忆作用域产品化：按通用用户偏好、台球门店事实、工作目录/项目上下文区分召回，避免一个窗口的背景污染另一个窗口 |
| P1 | 文件信任增强：文件改动展示备份、diff、回滚入口，让用户敢让 AI 改真实文件 |
| P1 | 台球高频输出业务闭环：拉客、报表、招聘、客诉、助教、教练竞技等回答底部有复制、员工执行、保存成品、生成下一步任务 |
| P2 | 经营数据流水、趋势分析、渠道表、价格表、完整素材库、打印物料模板、平台账号状态中心、完整生成工作室全部后置，不进入第一阶段主路径 |
| P2 | 测试体系补真实门店流程和视觉验收：机器 PASS 之外要看截图、看低学历用户是否一眼会用 |

### L3. 开发前验收清单

后续开发前，先用这张清单对齐方向。能通过这些问题，再进入具体代码拆分。

| 验收问题 | 通过标准 |
|---|---|
| 普通用户第一眼知道怎么开始吗 | 首屏只看到少量主路径：说需求、选文件夹、做图片/视频 |
| 是否符合人类自然使用逻辑 | 用户不需要先理解模式、角色、参数、路径、插件；可以先说需求，系统整理任务并给下一步 |
| 这个入口是否必须存在 | 如果不是高频开始动作、成品动作或风险确认，就不要放在显眼位置 |
| 是否让用户理解技术概念 | 普通路径不出现 API Key、MCP、Base URL、模型名、命令、prompt 参数 |
| 台球能力是否进入对话 | 不是讲知识，也不是堆窗口；用户聊天时能自动得到今日运营、拉客、客户维护、报表诊断、素材和招聘动作 |
| 门店背景是否能输入和生效 | 用户能逐步填写/导入自己球房的定位、价格、客群、团队、渠道、数据、素材；后续回答能显式结合这些事实 |
| 门店背景是否可控 | 用户能查看、修改、删除门店背景；行业知识、门店事实、本机习惯分层，不互相污染 |
| 门店背景是否正确分层 | 稳定事实、经营数据、素材、偏好记忆、临时上下文、敏感信息分开存；AI 推断需用户确认后才变成事实 |
| 记忆编排是否正确 | 当前任务、长期记忆、门店资料、工作目录上下文分层进入 prompt；通用任务不被台球记忆污染；用户本次输入优先于旧记忆 |
| AI 学习是否可控 | AI 自动学到的内容可见可删；AI 推断/文件提取/报表判断先待确认；用户手动修改后成为最高优先级 |
| 生图/生视频是否够简单 | 用户一句话 + 素材即可；系统后台补 prompt、比例、平台和安全区 |
| 视频是否符合定位 | 默认是社交媒体账号发布内容，不混成内部复盘或店内大屏物料 |
| 成品能不能找回 | 第一阶段图片、视频、文案、报表诊断、文件改动都能在最近作品/最近任务里找回；完整成品/素材库后置 |
| 用户被打断后能否继续 | 首页能看到继续上次工作、最近任务、最近成品；长任务和草稿可恢复 |
| 用户改主意是否有路 | 重做、换平台、换比例、换文案、换素材时保留旧版本，不覆盖满意结果 |
| 素材来源是否贴近现实 | 支持从工作目录、拖拽、剪贴板、截图、最近文件、微信下载/下载文件夹取素材 |
| 用户是否敢让 AI 改文件 | 文件改动有备份、预览、版本或恢复入口；重要覆盖动作说明影响范围 |
| 长任务会不会被窗口影响 | 切窗口、最小化、新开窗口不应停止任务 |
| 风险动作是否被区分 | 生成内容可以直接做；发布、群发、删除、危险修改必须人工确认 |
| 视觉是否做了减法 | 没有多余图标、卡片、标注和技术词；界面保持浅色 macOS 风格但更精致 |
