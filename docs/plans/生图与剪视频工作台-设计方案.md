# B. 剪视频工作台设计(含 owner 点名的预览研究)

## B.1 owner 重点问题的结论:视频工作台右边要不要预览板?

**结论:要,但形态与生图不同 —— 视频的"预览板"= 一块「时间线预览播放器」(播源片 + 播放头 scrubber + trim 手柄 + 片段拖拽重排 + DOM 字幕浮层),外加一条可视化时间线轨道条。用户在时间线上直接拖/裁/删/排来调整视频,每次操作即时反映在预览播放器上;真正 ffmpeg 出片只在点"出片"时发生一次。**

### 依据(联网调研 + 自家契合,来源见 §D)

1. **主流 web 视频编辑器一致做法 = 时间线 + 实时预览播放器分离**:Twick(React 时间线 SDK)、OpenReel(浏览器端 CapCut 替代,WebCodecs 多轨时间线 + 实时预览 + 帧级 scrub)、designcombo/react-video-editor(Remotion 内核,多轨拖放/split/trim/snap + 实时视口预览)、react-timeline-editor(xzdarcy)都是这套。**Remotion `<Player>` 的关键点:预览 = 运行时按时间线合成播放,edit 立即反映,不重渲;最终 render 是另一步 export**。这正对我们"预览别每次调 ffmpeg"的需求。
2. **预览"实时反映编辑"= 客户端播放引擎按 EDL 播源片,不重渲**:预览播放器读时间线(EDL)、按 clip 边界 seek 各源片、DOM 叠字幕/播放头;这条我们**已有地基** —— `localFileResponse`(`videoEditProjects.ts` L923)已支持 `GET /api/v1/video-edit/localfile?path=` 的 **Range 分段播放**,客户端秒级 seek 源片就靠它。
3. **Descript 式"编辑像编文档"= 转写驱动**:改/删转写里的字 → 视频同步变,点某个词 → 跳到那一帧。这是"音频优先"的最高级形态,和我们 video-use 研判的 transcript-first 完全同源。**但它依赖真词级转写,我们现在是占位** —— 所以这条降级放到 §B.5 诚实缺口,不作 P0。
4. **自家天然契合(最强依据)**:我们 `TimelineDoc` 是**唯一真相源**,`applyOne`(L265)已实现 `add_media/add_track/add_clip/add_caption/remove_clip/trim_clip/reorder_clip/edit_caption/set_music/set_grade` 十种原子操作,`applyOperations`(L574)**克隆→逐条 apply→validateDoc 不过整体回滚**。**时间线 UI 上的每一次可视化拖拽,本质就是发一条原子操作**——工作台前端只是把这份文档"暴露成可点可拖的界面",后端骨架早就位。

## B.2 用户如何基于预览板调整视频(可落地交互方案)

```
┌ 剪视频工作台(整页 Tab) ───────────────────────────────────┐
│                  [预览播放器 · 上]                          │
│         ┌────────────────────────┐                        │
│         │   播当前时间线合成      │  ▶ ⏸  00:07 / 00:16     │
│         │   (seek 源片+DOM字幕)  │  [撤销↺][重做↻][出片]   │
│         └────────────────────────┘                        │
│  [时间线轨道条 · 下]  ├─播放头(scrubber,可拖)             │

│   字 ┈┈"高光1"┈┈"高光2"┈┈           ← 字幕轨,双击改字      │
```

**每个交互 → 原子操作,即时预览(纯 seek,不 ffmpeg):**

| 用户操作(可视化) | 触发的原子操作 → `POST /projects/:p/ops` | 预览如何反映 |
|---|---|---|
| 拖片段**左/右 trim 手柄** | `trim_clip {id, src_in?, src_out?}` | 前端拿回新 `docView`,预览重算 clip 时长、seek 边界立即变 |
| 拖片段**改前后顺序** | `reorder_clip {id, order}` | 播放顺序即时重排 |
| 选中片段**删除** | `remove_clip {id}` | 该段从预览消失 |
| 从**素材库抽屉拖新片段**进轨道 | `add_media {src,duration}` + `add_clip {track,media,src_in,src_out}` | 新片段进预览 |
| **双击字幕块改文字**/拖字幕改时间 | `edit_caption {id, text?/start?/end?/style?}` | DOM 字幕浮层文字/时间即时变 |
| 轨道空白处**加字幕** | `add_caption {track,text,start,end}` | 新字幕浮层出现 |
| **选 BGM** | `set_music {media}` | 音乐轨标记(预览可选混音,近似) |
| **选调色档** | `set_grade {grade}` | 预览可 CSS 近似;精确以出片为准(见缺口) |
| **拖播放头 scrubber** | 不发后端,纯前端 seek | 预览跳到该时刻 |
| **撤销/重做** | 前端维护操作栈;或每次 ops 前端存一份 docView 快照回滚 | 回到上一状态(后端本身每次 ops 已"失败整体回滚",但"成功后撤销"要前端存栈) |
| **出片** | `POST /projects/:p/render`(ffmpeg) | 出成片 `/uploads/videos/*.mp4`,进对话/下载 |

**要点**:预览播放器负责"所见",时间线轨道条负责"可操作",两者都读同一份 `docView`。**验证闸(video-use strategy confirmation)= "出片"按钮就是那一步显式确认**:调之前用户已在预览里审过。

# D. 联网调研(来源 + 关键结论)

**做了联网调研(内置 `WebSearch`)**,三轮,聚焦"web 视频编辑器怎么做预览 + 可视化调整"。关键结论:

1. **时间线 + 实时预览播放器是行业标配,且二者分离**:多个开源 React 方案(Twick、OpenReel、designcombo/react-video-editor、react-timeline-editor、Remotion Timeline)都是"多轨时间线(scrubber/trim 手柄/拖拽重排/snap)+ 实时预览"。**Remotion `<Player>` 明确:预览 = 运行时按时间线合成播放、edit 立即反映、不重渲;最终 render 是独立 export 步**。→ 支撑我们"预览别每次调 ffmpeg,只在出片调一次"。
2. **预览"实时反映编辑"靠客户端按 EDL 播源片**(seek 各 clip + 叠 DOM 字幕/播放头),不做服务器渲染。→ 我们 `localFileResponse` 的 Range 播放已备好这条地基。
3. **Descript = 转写驱动的文档式编辑**(改字=改视频、点词跳帧),是"音频优先"的最高级形态,和我们 video-use transcript-first 同源;**但依赖真词级转写**,我们现是占位 → 降级、标缺口。
