# 右侧预览 + "基于此调整"(Codex Canvas 式)· 完整设计

> 📌 owner 要:对话里的图片/网页/Word 等内容,点开→右侧预览;预览里**分模块呈现**,用户**框选某段 + 给指令 → 那段被改**。设计交互 + 后端逻辑(owner 全权给我),前端照 owner 的 Codex 壳子接。
> ⚠️ **参考现实**:cc-haha 的 `ReviewArtifactTool` 是 ant 内部 gated 的**空 stub**(开源版没真实现),抄不了。真正范式 = **Codex/ChatGPT Canvas**(owner 前端正照它做)。本设计 = Canvas 范式 + 我们**两条现成管线**。

## 一、核心洞察:"基于此调整"复用两条现成管线,后端新建极少

| 内容类型 | "基于此调整"走哪条线 | 是否回主 LLM | 复用什么(已有) | 要新建 |
|---|---|---|---|---|
| **图片**(海报/生图) | **B 线·确定性媒体管线** | ❌不经主 LLM,直接图片模型 | `/studio/edit`:source_generation_id + mask + edit_type + 指令 → edit_image 局部重绘 | 框选区域(bbox)→遮罩的转换(便利,可后端做) |
| **HTML/网页** | **A 线·作用域受限的 agent 编辑** | ✅回 LLM | 现有 edit_file/patch 工具改文件 + 预览重读 | 把"选中块+指令"craft 成作用域 prompt(可后端 helper) |
| **Word/docx** | **A 线·同上** | ✅回 LLM | 现有 docx 编辑工具 | 同上 |
| **Markdown/代码/文本** | **A 线·同上** | ✅回 LLM | 现有 edit_file | 同上 |

**答 owner 的问"是不是得把请求返回给大模型":分内容类型**——
- 图片调整**不回主 LLM**,回**图片模型**(edit_image,快、确定性、B 线);这正是 owner 说的"生图编辑台/看板"的后端。
- 文本/HTML/文档调整**回主 LLM**(语义改写"改得活泼点/去掉这句/换个说法"需模型),但只是一条**作用域受限的普通 agent 消息**,agent 用 edit_file 改文件那一段,现有能力就够。

## 二、交互模型(Canvas 式,三步)

```
① 对话里出现内容(图片/生成的 HTML/文档)
   → 点击 → 右侧预览面板打开、渲染内容
② 预览"分模块呈现"(前端渲染):
   - 图片:整张是画布,用户拖框选一块区域(bbox/套索)
   - HTML:按 DOM 结构/标题拆成可选块,用户点选一个块 or 框选文字
   - 文档:按段落拆,用户选一段
③ 用户在选区上敲指令("这块改成…/这段更活泼/去掉这句")
   → 提交 → 后端按内容类型路由 → 内容更新 → 预览刷新
```

**"分模块化呈现" = 前端渲染职责**(把内容拆成可选块),后端只需支持"给一个选区引用,改那部分"。

## 三、后端契约(前端照 Codex 壳子发这些)

### 3.1 图片调整(B 线,媒体 job)
复用 **`POST /api/v1/studio/edit`**(已存在),前端发:
```jsonc
{
  "source_generation_id": "<之前生图的 id>",   // 或 source_image_path
  "region": { "x": 0.3, "y": 0.2, "w": 0.4, "h": 0.3 },  // 归一化 bbox(0~1),新增便利:后端转遮罩
  // 或前端自造遮罩:"mask_path": "<白区=选区的PNG>"
  "edit_type": "content",   // 改画面内容;改字用 "text_fix"
  "prompt": "把这块的灯换成暖色射灯"
}
```
→ 后端把 region 转成遮罩(选区白、其余黑)→ edit_image 局部重绘 → 返回 job_id → 前端轮询 → 新图替换预览。
**要新建**:`region(归一化bbox) → 遮罩PNG` 的转换(纯确定性,sharp/canvas 或纯像素写)。不新建则前端自造遮罩(也行)。

### 3.2 文本/HTML/文档调整(A 线,作用域 agent 编辑)
两种接法(推荐 B):
- **接法 A(前端 craft)**:前端直接把选区+指令拼成普通对话消息发 `/agent/run`:「把文件 `<path>` 里这段『<选中>』按指令调整,其余不动。指令:<用户指令>」。零新后端,但 craft 逻辑散在前端。
- **接法 B(后端 helper·推荐)**:新增 **`POST /api/v1/preview/adjust`**,前端发结构化选区,后端 craft 作用域 prompt 再喂 createTurnStream:
```jsonc
{
  "content_type": "html|markdown|doc|code|text",
  "file_path": "<预览的文件绝对路径/uploads 路径>",
  "selection": { "text": "<选中原文>", "start_line": 12, "end_line": 18 },  // 或 anchor/selector
  "instruction": "<用户指令>",
  "conversation_id": "<当前会话>"
}
```
后端 craft:`「只修改 <file_path> 中 <start_line>-<end_line>(或匹配这段原文:『…』)的内容,按指令『<instruction>』调整,不动其它任何部分。改完用 edit_file 落盘。」` → 跑一轮 agent(edit_file 精确改那段)→ SSE 回改动 → 前端重读文件刷新预览。
**要新建**:`/api/v1/preview/adjust` 这个 craft+dispatch 薄端点(逻辑小,把选区变成作用域 prompt)。

## 四、为什么这么分(对齐"两条线"铁律)
- 图片是**生成物、像素级**,局部重绘是确定性媒体操作(遮罩 inpaint),不该塞进模型 ReAct 循环 → B 线,直连图片模型。
- 文本/HTML/文档是**语义内容**,"改这段"是语义改写 → A 线,交模型;但**作用域受限**(只动选中段),避免模型乱改全文。
- 两条都**复用已有能力**(edit_image 遮罩 / edit_file),新建的只是"选区→遮罩"和"选区→作用域prompt"两个薄转换层。

## 五、要新建的后端(小,本轮做)
1. **图片**:`region 归一化bbox → 遮罩PNG` 转换 + `/studio/edit` 接受 `region`(不改现有 mask_path 契约,新增可选参数)。
2. **文本类**:`POST /api/v1/preview/adjust` 薄端点(选区+指令→作用域prompt→createTurnStream)。
3. **预览刷新契约**:调整完成后,前端凭 file_path 重读(文件类走现有 fs/read)、图片凭新 generation_id 换图(现有)。

## 六、前端接线点(owner 的 Codex 壳子,后续接)

- 选区工具条:框选后浮出"输入指令"小框 → 提交调用上面端点。
- 调整中态:图片显 job 进度、文本类显 SSE 流式;完成刷新预览。
