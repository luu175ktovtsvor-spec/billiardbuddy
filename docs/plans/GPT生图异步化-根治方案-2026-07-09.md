# GPT 生图大陆超时 · 异步化根治方案(已落地代码)

> 📌 状态:✅现行 · 落地 2026-07-09 · 取代《待改-GPT出图从大陆超时-异步化方案-2026-07-03》(旧稿只提案未落地、部分数字漂移,已移历史标注)

这份是 GPT Image 2 生图链路的**单一权威口径**。回答"图在哪生成/为什么走美国/怎么根治超时",并记录已落地的 A2 异步方案(代码 + 测试 + 部署 + 激活)。

## 1. 定论:图在哪生成、为什么必须走美国

- **图在 OpenAI 自己的服务器(美国)生成。** GPT Image 2 = OpenAI Images API 的 `images.generate/edit`,是**同步**调用、**没有 task 概念**。既不是"我们服务器生成再下载",也不是"用户本地生成"——OpenAI 生成,我们只负责把请求送进去、把图接回来。
- **请求必须从美国 relay 出口。** 原因:① 大陆直连不了 OpenAI;② 真 OpenAI key 只放在美国 relay(`zzyppz.cn` / 47.77.237.250),客户端只带可吊销的令牌(藏 key 白标铁律)。
- **对照:豆包 Seedream**(火山方舟 `ark.cn-beijing`)是大陆直连、又快又稳,不受本文任何问题影响。默认生图走 Seedream,只有"复杂创意/西文为主/写实人像·高保真改图/用户显式手选"才路由到 GPT。

## 2. 根问题:跨境长连接约 60 秒被掐

GPT Image 2 单张耗时严重取决于 quality(联网核实,2026-07-09):

| quality | 单张耗时 |
|---|---|
| low | 3–8 秒 |
| medium | 20–40 秒 |
| **high(写实人像/改图)** | **2.5–4.5 分钟** |

若大陆客户机 / 大陆网关**直接握一条到美国 relay 的跨境长连接死等**,这条连接会被网络在**约 60 秒物理掐断**(实测:大陆 Mac 直连 relay `curl images/edits` 整 60 秒 Empty reply,同调用挪到美国机上秒成)。掐断在网络层,relay/网关配的 900s/1800s 超时根本用不上。结果三连:**图在 OpenAI 已生成并扣了费 + 结果传不回来 + 客户一脸懵**。因为断了可能已扣费,所以不能盲目重试(会重复扣费)。

⚠️ 关键:项目 §13 主场景「门店助教照片优化」= 写实人像 / 高保真改图,恰好路由到 GPT 的 **high 质量档(2.5–4.5 分钟)**,是最容易踩 60 秒墙的那条路。所以这不是边角,是生图主场景的拦路石。

## 3. 方案:A2 异步 submit/poll(慢调用挪到美国本地)

```
客户端(大陆) --短-- 大陆网关(39.106.214.21) --短-- 美国 relay 任务服务 --US→US ~80ms-- OpenAI
```

- 客户端只发"提交(短)+ 每隔几秒轮询一次(短)"。
- 真正那次几分钟的 OpenAI 调用**在美国 relay 本地跑**(美→美 ~80ms,完全不跨境)。
- **任何一跳都不再有跨境长连接**,60 秒墙结构上被绕开。
- 为什么不是 A1(状态放大陆网关):A1 里"网关→relay"那跳仍是大陆→美国跨境,同样可能 60 秒被掐,未验证。只有 A2(慢调用由美国端发起)能保证不跨境。

## 4. 已落地(代码 + 测试)

三层,均单测覆盖(注入 fetchImpl,mock 上游):

| 层 | 落点 | 干什么 | 测试 |
|---|---|---|---|
| **美国 relay 任务服务** | `relay/app.ts`(新)+ `relay/app.test.ts` + `relay/deploy.sh` + `relay/README.md` | 收提交→后台在美国本地调 OpenAI(generate JSON / edit multipart)→存结果→供轮询;并发闸 + TTL 清理 + 鉴权 | 6 pass:提交→后台调→轮询成功、multipart 改图、失败捕获为 failed(不抛)、鉴权、未知/过期 404、TTL 清理 |
| **大陆网关** | `gateway/app.ts` `POST /v1/images/tasks` + `GET /v1/images/tasks/:id` | 提交/轮询转发到美国 relay 任务服务(注入 relay 令牌);提交计入生图 IPM 限速+每日配额,短请求不占在途并发信号量;缺 `GW_RELAY_TASKS_BASE` 返回 503 | 2 pass:配置后转发到 relay tasks base 且注入 relay 令牌;未配置返回 503、零上游调用 |
| **桌面客户端** | `ts/src/media/mediaJobs.ts` `submitOpenAiImageTask` + `QF_GPT_IMAGE_ASYNC` 开关 | GPT(openai-compatible)路径按开关走 submit/poll;返回 OpenAI 形状 `{data:[...]}` 复用 persist;尊重 ctx.signal 取消 | 1 pass:开关开时 GPT 走 `/images/tasks` 提交+轮询,全程不走同步 `/images/generations` |

**契约**(三层一致):
- `POST /images/tasks` `{mode:'generate'|'edit', model, prompt, n, size, response_format?, images?:string[](data-uri), mask?, input_fidelity?}` → `202 {task_id, status:'queued'}`
- `GET /images/tasks/:id` → `{status:'queued'|'running'|'succeeded'|'failed', data?:[{b64_json|url}], error?, created}`

**顺带修的两个真机会失败的同步路径 bug**(提交 `62a9951`,与本方案同批相关):
- Seedream 默认尺寸低于火山像素下限 3,686,400 → 默认生图必失败(已补等比放大)。
- gpt-image-2 传 input_fidelity 会 400(已改成只对非 gpt-image-2 的 gpt-image 系列设)。

## 5. 激活(部署 + 开关)——根治的最后一步(owner 操作)

代码全建全测,**激活只差部署**:

1. **美国服务器**:按 `relay/README.md` 部署 `relay/app.ts`(systemd `qfrelay` :8790 + 真 OpenAI key)+ nginx 加 `location /relay/imgtasks/`。
2. **大陆网关** `gw.env`:`GW_RELAY_TASKS_BASE=https://zzyppz.cn/relay/imgtasks`,重启 `qfgw`。
3. **桌面客户端** `bundled.env`:`QF_GPT_IMAGE_ASYNC=1`(打进安装包)。
4. 关掉任一个即退回同步路径(仍带上面两个 bug 修复,适合快请求或未部署 relay 的场景)。

## 6. 剩余风险 / 未验证

- **真机端到端未验**:上面全是单测(mock OpenAI)。部署后需真机用生产 key 跑一次 high 质量 gpt-image-2,确认不再丢图。(owner 说测试 key 将废,用生产 key。)
- **relay 重启丢任务**:任务状态在内存 Map;relay 进程重启会丢在途任务,客户端轮询得 404 后需重新提交(可接受;要更稳可加 sqlite 持久化)。
- **不涉及 Seedream**:Seedream 直连火山、无跨境问题,本方案只动 GPT 路径。
- **来源诚实**:美国 relay 的 nginx 现行配置不在本仓库(只在服务器),proxy_read_timeout 等以 `relay/README.md` 建议值为准,部署时以服务器实际为准。
