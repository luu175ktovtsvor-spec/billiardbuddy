# 门店信息处理方案：A 自动记忆 vs B 设置填写

## 0. 一句话总览

- **A（纯 cc 自动攒）** = 模型在聊天里自己把门店事实存本地、每轮自动读回。**已实现**，owner 的理解基本对，只有一处要往"更强"的方向纠正（不是"循环里碰运气找到"，而是"每轮必读、确定性读到"）。
- **B（设置界面填门店信息）** = 让老板主动一次性填清门店画像。**现状最大的坑：门店数据后端早就有了，但只喂给"生图"，聊天大脑一个字都读不到 —— 这就是"填了变鸡肋"的病根。** B 的真正工作不是"存哪"（存的地方现成），而是"给它接一条模型每轮必读的通路"。
- **推荐：A + B 结合**。A 兜底自动攒细颗粒事实，B 给老板掌控、一次填清主画像；两者写进**同一套记忆池、同一条注入通路**，不新造第二套系统。

## 1. A 机制说明（确认 owner 的理解 + 一处纠正）

### 1.1 owner 的理解：对，大方向完全正确

owner 说"模型聊天时自己攒数据、存本地、循环里会找到"——**前半段完全正确**：

- **模型自己攒**：给模型装了一把 `save_memory` 工具（`ts/src/tools/saveMemoryTool.ts`）。聊天中只要听到"值得长期记的门店事实"（黄金档台费、会员规则、常办活动、旺淡季、店主偏好），模型**自己主动**调它记下来，老板不用点任何按钮。
- **存本地**：每条事实存成一个"带标题的小 Markdown 文件"，同时往一个 `MEMORY.md` 索引清单加一行 `- [标题](文件名) — 一句话摘要`。全在用户本机 `~/.billiardbuddy/projects/<门店>/memory/`，按工作区分区（白标铁律走 `.billiardbuddy`，绝不 `.claude`）。
- 分四类：`user`（店主是谁/偏好）、`feedback`（对你做事的纠正/肯定+原因）、`project`（门店事实与近况，**门店信息大多归这类**）、`reference`（资料在哪）。
- 有安全红线写死在工具里：**只记店主明说过或纠正过的，拿不准就不记，禁止凭空补全/推测/编造**；不记密钥隐私；`forget=true` 可删。

### 1.2 要纠正的一点：不是"循环里碰运气"，而是"每轮必读、确定性读到"（比 owner 想的更强）

真实读回机制（`ts/src/harness/claudemd.ts` 的 AutoMem 段）：

> **那份 `MEMORY.md` 索引（每条一行：标题+摘要）是每一轮对话都被直接塞进系统提示词、当成"必读指令"强推给模型看的**，前面还带一句"以下是必须遵守、优先级高于默认行为的指令"。

所以：

- 模型**每轮都必然看到**"这家店记过哪些事"这份清单，**不存在"没找到/漏掉"的运气成分**。
- 要用某条的**完整细节**时，模型再按需 `read_file` 去读那个具体 `.md`。

**一句话给 owner：这套是"索引常驻必读（强推）＋ 详情按需读取"，确定性的、可靠的，不是循环里撞大运。** 这一点比原本理解更值得放心 —— A 在"模型一定读得到已记的门店事实"这件事上是有保证的。

**唯一的小边界**：A 靠模型自觉判断"这条值不值得记"，且只记店主明说过的、不编造 —— 覆盖全不全，取决于聊天里有没有聊到。**这正是 B（让老板一次性主动填全）要补的缺口**，两条路互补、不冲突。

（技术出处：这套是照抄 cc 的 AutoMem/memdir 机制做的白标版；读写两侧按同一个 `workspace.root` 派生同一目录，保证"写进去的下次一定读得到"。）

## 2. B 完整方案（正面回答 owner 三连问：填写 → 后端接 → 模型怎么读到）

### 2.0 先看现状最大的坑（B 不鸡肋的命门就在这）

调研发现一个已存在的大坑，必须先讲清：

- 门店信息的**后端数据早就有了** —— `ts/src/server/services/desktopDataStore.ts:28-76` 的 `defaultStore()` 已定义约 40 个字段（店名/城市/地址/电话/营业时间/台数/台种/价格/会员卡/助教数/助教价/器材品牌/客单价/高峰时段…），存在 `desktop-data.json` 的 `store` 对象里，还自带一个 `completeness`（完整度）字段。
- 填写/修改的 **API 也早就有了** —— `GET/PUT/PATCH /api/v1/stores/me`（`ts/src/server/index.ts:3158-3175`）。
- **但是：这份门店数据只喂给了"生图"。** 全项目 `getStore()` 只被三处调用（生图品牌约束 `index.ts:2602`、备份导出 `3135`、GET 接口 `3164`）。**聊天的大脑 `buildSystemPrompt`（`index.ts:1513`）从头到尾没读过它。**

> 也就是说：**现在就算老板把门店填得满满当当，聊天时模型也一个字看不到。** 这就是"填了没人看 = 鸡肋"的病根。所以 owner 三连问里，前两问（填写/后端存）基本现成，**第三问（模型怎么读到）才是 B 真正要新建的部分。**

（附带发现文档漂移：根 `CLAUDE.md` 声称已落地"门店画像层"注入，但代码里那层已下线（`index.ts:3137` 注释"自造店脑记忆已下线，改用 cc AutoMem"）。B 本质就是**把这层用真数据、按 cc 的读路径重新接回来**。）

### 2.2 设置界面怎么做（抄 WorkBuddy）

抄 WorkBuddy 两块（逆向档案 `docs/references/WorkBuddy逆向档案/14-补:设置-个性化.md` + `13-补:设置-记忆.md`）：

- **抄链路（§14 个性化面板）**：这是"设置里填 → 存 config → 后端 Collector 渲染 → 注入系统提示变量"最干净的完整样板。分工 = **填写面板只管"填 + 存"；另有一个后端 Collector 专门把它读出来、渲染成模型能读的文本、注入系统提示**。填写与注入解耦。我们门店信息是结构化字段，所以填写形态换成**结构化表单 + 字段分组折叠 + 底部确认按钮 + 脏检查**（交互抄 cc、颜色文案抄 WorkBuddy，项目前端铁律），但接法链路一模一样。
- **抄管理 UX（§13 记忆面板管理弹窗）**：一张卡展示当前记忆全文 + 编辑/清空两个图标按钮。对应到 B = 面板里放**"预览模型看到的门店档案"折叠区 + "清空重填"入口**，让老板肉眼确认"模型到底记着我店里啥"——这本身就是不鸡肋的信任感来源。
- 务实取舍照抄：桌面单机版**隐藏远程门控、去埋点、开关常开**，别做云端那套。

### 2.3 后端怎么接 + 模型怎么读到（命门）

**存哪（复用地基，零新增存储）**：结构化真相源 = 沿用已存在的 `desktop-data.json → store` + 现成的 `PUT /api/v1/stores/me`。这份**可编辑、可回改、可备份**的结构化档案当"数据库"，设置面板直接读写它。

> 为什么不直接把门店信息塞进 memdir 当一条 project 记忆就完？因为 memdir 是"一条条离散事实"的池子，适合模型零散攒（A）；而门店档案是**一张要整体覆写、带完整度、逐字段可改**的结构化档案，用 `store` 当真相源、再投影成模型可读文本，比让老板去编辑 memdir 的 markdown 更顺手、也更好统计完整度。

**模型怎么读到（B 唯一要新建的部分，抄 WorkBuddy 的 Collector 角色）**：加一个后端**"门店档案投影器"**——每次保存后，把结构化 `store` 渲染成一段人类可读的 Markdown「门店档案」，**写进模型每轮必读的地方**。

两条读路径的差别必须讲清（这是 owner 关心的核心）：

| 读法 | 常驻什么 | 是不是"每轮全文必读" | token 成本 |
|------|---------|------------------|-----------|
| **memdir 索引式**（cc AutoMem） | 只有**一行索引**常驻，详情靠模型按需 `read_file` | ❌ 只保证看到指针 | 极省 |
| **主指令常驻式**（`BILLIARDBUDDY.md` 家族 / SessionStart） | **全文**常驻 | ✅ 填了模型一定读到全文 | 一段文字的量 |

证据：`ts/src/harness/claudemd.ts:748-758`（AutoMem 只注入 `MEMORY.md` 索引本身）vs `811-830`（主指令层全文注入）；系统提示**每次聊天请求都重建**（`index.ts:1513` → `loadMemoryInjection` 现读文件），所以主指令层"每轮拿最新、改完下一轮即生效"。

**→ owner 要的"填了模型一定读到" = 主指令常驻式（全文），不能只用索引式。** 具体落点二选一（见第 4 节拍板点）：

- **落点 A（推荐 · 全文每轮常驻、跨模式）**：投影器把门店档案 Markdown 写进 User 层主指令 `~/.billiardbuddy/BILLIARDBUDDY.md` 的一个**带标记托管区块**（`<!-- STORE_PROFILE_START -->…<!-- END -->`，投影器只覆写标记块内、用户手写内容不动），或用 `@门店档案.md` 引入（User 层 `@import` 外部文件永远放行，`claudemd.ts:721`）。→ 走 cc 现成读路径，**每轮全文注入、改完即刷新、不新开注入通道**。语义也对：单店老板全局就一家店，门店档案属"跨项目的用户级事实"，放 User 层正合适（memdir 是按 workspace 分区的，换工作目录各自一份，反而不适合当唯一门店真相）。
- **落点 B（备选 · domain 感知、会话级）**：门店档案改由**台球领域包的 SessionStart hook 动态读 `store` 渲染注入**（把 `CLAUDE.md` 说的"门店画像层"用真数据接回；现在 `packs/billiards/pack.ts:108` 的 `sessionStartContext` 是静态字符串，改成挂载时现读渲染）。→ 只挂台球包才注入、通用模式干净；缺点是会话中途改门店要开新会话才刷新。
- **两者都叠加一份 memdir 兜底（强烈建议）**：无论选 A/B，投影器**同时**在 memdir 落一份 `门店档案.md` + `MEMORY.md` 一行索引（复用 A 的写路径 `saveMemoryTool.ts:94-97`）。好处：任何模式模型都能主动 `read_file` 取到；和模型自己攒的门店事实**同池**、能被统一"忘掉/更新"；A 与 B 读路径归一、不打架。

**完整链路（填 → 存 → 投影 → 注入 → 读）**：

```
老板在设置「门店档案」面板填/改字段
      │ PUT /api/v1/stores/me
      ▼
DesktopDataStore.updateStore() → desktop-data.json 的 store   ← 结构化真相源(已存在)
      │  【B 唯一新增:门店档案投影器】保存后触发
      ▼
把 store 渲染成 Markdown「门店档案」
      ├─(落点A) 写进 ~/.billiardbuddy/BILLIARDBUDDY.md 托管区块
      │        └─ 每次 buildSystemPrompt 全文重读 → 模型每轮读到全文 ✅
      ├─(落点B) 台球包 SessionStart hook 动态注入(domain 感知)
      └─(兜底) memdir/门店档案.md + MEMORY.md 索引一行 → 模型可主动 read_file,与 A 同池
```

一句大白话：**老板在设置里填的门店信息，后端存进原来那个 store；新加一个"投影器"，每次一保存就把它翻译成一段模型能读的文字，塞进"模型每轮开口前必读的那份指令"里。这样填了就一定被读到，改了下一轮就变。**

### 2.4 不鸡肋三要点

1. **字段从 PPT 提炼**（不拍脑袋）：字段集 = 通读 PPT 运营底本提炼的十大板块（见 2.1）；前端用**完整度进度条**（复用现成 `completeness` 字段）逼着"别只填一半"。
2. **写进"每轮必读"处**（命门）：走**主指令常驻式全文注入**（落点 A/B），不是只挂个 memdir 索引 —— 直接根治现状"填了模型看不到"的病根（把只喂生图的 store 接进聊天大脑）。
3. **用户可改**：真相源是结构化 `store`，逐字段可改；每次保存投影器重渲染、主指令层每轮重读 → 改完下一轮即生效；再加"预览模型看到的门店档案 + 清空重填"入口，让老板看得见、改得动、信得过。

## 3. A vs B 对比 + 推荐

| 维度 | A（纯模型自动攒） | B（自动攒 + 设置填） |
|------|-----------------|---------------------|
| 谁来写 | 模型聊天时自己判断、`save_memory` 写 | 老板在设置里主动填，后端投影写 |
| 覆盖 | 取决于聊没聊到，可能漏 | 一次填清主画像，不漏命脉 |
| 掌控感 | 老板看不见、改不动（无掌控感） | 看得见、逐字段改、有进度条（有掌控感） |
| 数据形态 | 离散小事实（适合细颗粒 ops） | 结构化整档（适合整体覆写、完整度统计） |
| 成本 | 最省、已实现、不用做字段 | 要认真做字段（PPT 提炼）+ 新建投影器注入，否则鸡肋 |
| 鸡肋风险 | 低（模型自觉，但可能不全） | **高**——字段拍脑袋 or 只存不注入就废 |

**推荐：A + B 结合（不是二选一）。**

- **A 兜底**：细颗粒、随聊随记的门店事实交给 A 自动攒，已实现、最省、确定性读回。
- **B 补掌控**：MVP 的 11 个命脉字段用 B 让老板一次填清、看得见改得动，字段严格从 PPT 提炼、投影进"每轮必读"、进度条防填一半。
- **两条路归一**：B 的投影副本落在**同一个 memdir 池**、读路径都收敛到 cc 的 `getMemoryFiles`，**不新开第二套记忆系统**，避免"老板填的"和"模型攒的"两份门店信息各说各话。冲突处理：门店档案（B，结构化、权威）优先级高于模型零散攒的同类事实（A），渲染时在门店档案段标注"以下为店主在设置中确认的门店事实，优先采信"。

## 4. 给 owner 的拍板点

1. **主指令落点 A vs B？**
   - **A（User 层主指令全文常驻，推荐）** = 跨模式都读到 + 改完即刷新 + 实现最轻；代价：通用助手模式下也会带上门店那几行（噪音很小）。
   - **B（台球包 SessionStart 动态注入）** = 只挂台球包才注入、通用模式绝对干净；代价：会话中途改门店要开新会话才刷新，`sessionStartContext` 要从静态改成动态读。
   - 建议 **A + memdir 兜底**，最贴"填了一定读到"的诉求、实现也最轻；若你更在意"通用模式绝对不带门店噪音"，选 B。

2. **MVP 字段范围拍板**：认可这 11 个命脉字段作为 v1 的 B 表单吗？（尤其"门店定位类型对齐 PPT 四类球房"这个关键口径改动，会动到老字典的 `positioning` 枚举。）

3. **管理弹窗做到哪一层？** 建议 v1 从简：**结构化表单本身就是编辑器 + "预览模型看到的门店档案" + "清空重填"** 即可，不必再抄 WorkBuddy §13 那套内联提交建议的记忆弹窗。
