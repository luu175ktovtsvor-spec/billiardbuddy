# 门店信息处理方案：统一走 cc AutoMem 常驻注入（自动攒 + 设置填，同一条通路）

## 0. 一句话总览

- **门店信息统一走 cc AutoMem 常驻注入**：模型在聊天里自己把门店事实存本地、每轮自动读回。**已实现**，owner 的理解基本对，只有一处要往"更强"的方向纠正（不是"循环里碰运气找到"，而是"每轮必读、确定性读到"，详见 1.2）。
- **现状最大的坑**：门店数据后端早就有了，但只喂给"生图"，聊天大脑一个字都读不到 —— 这就是"填了变鸡肋"的病根（详见 2.0）。设置表单要补的，就是把它接进"模型每轮必读的那条通路"。
- **收敛口径（纯 cc）**：不搞 A/B 二选一、也不新造第二套系统 —— 门店信息一律走 cc AutoMem 常驻注入；**设置表单只负责把老板填的内容写进 memdir（.md）/主指令**，和模型对话增量攒的门店事实**同池、同一条注入通路**，不另立结构化 store 真相源、不做门店档案投影器。老板一次填清主画像、模型随聊随补细节，两个入口喂同一套记忆。

## 1. A 机制说明（确认 owner 的理解 + 一处纠正）

### 1.1 owner 的理解：对，大方向完全正确

owner 说"模型聊天时自己攒数据、存本地、循环里会找到"——**前半段完全正确**：

- **模型自己攒**：聊天中只要听到"值得长期记的门店事实"（黄金档台费、会员规则、常办活动、旺淡季、店主偏好），模型**自己主动**把它写进 memdir，老板不用点任何按钮。（⚠️现状走自造的 `save_memory` 工具 `ts/src/tools/saveMemoryTool.ts`；按核心思想应**并回 cc 原生做法**——cc 无 save_memory 工具，是给 agent 注入 `Write`/`Edit` 直接写 memdir，与下文 2.3 口径统一，见《内核A线对齐差异总清单》记忆条。）
- **存本地**：每条事实存成一个"带标题的小 Markdown 文件"，同时往一个 `MEMORY.md` 索引清单加一行 `- [标题](文件名) — 一句话摘要`。全在用户本机 `~/.billiardbuddy/projects/<门店>/memory/`，按工作区分区（白标铁律走 `.billiardbuddy`，绝不 `.claude`）。
- 分四类：`user`（店主是谁/偏好）、`feedback`（对你做事的纠正/肯定+原因）、`project`（门店事实与近况，**门店信息大多归这类**）、`reference`（资料在哪）。
- 有安全红线写死在工具里：**只记店主明说过或纠正过的，拿不准就不记，禁止凭空补全/推测/编造**；不记密钥隐私；`forget=true` 可删。

### 1.2 要纠正的一点：不是"循环里碰运气"，而是"每轮必读、确定性读到"（比 owner 想的更强）

真实读回机制（`ts/src/harness/claudemd.ts` 的 AutoMem 段）：

> **那份 `MEMORY.md` 索引（每条一行：标题+摘要）是每一轮对话都被直接塞进系统提示词、当成"必读指令"强推给模型看的**，前面还带一句"以下是必须遵守、优先级高于默认行为的指令"。

所以：

- 模型**每轮都必然看到**"这家店记过哪些事"这份清单，**不存在"没找到/漏掉"的运气成分**。
- 要用某条的**完整细节**时，模型再按需 `read_file` 去读那个具体 `.md`。

**一句话给 owner：这套是"索引常驻必读（强推）＋ 详情按需读取"，确定性的、可靠的，不是循环里撞大运。** 这一点比原本理解更值得放心 —— A 在"模型一定读得到已记的门店事实"这件事上是有保证的。

**唯一的小边界**：A 靠模型自觉判断"这条值不值得记"，且只记店主明说过的、不编造 —— 覆盖全不全，取决于聊天里有没有聊到。**这正是 B（让老板一次性主动填全）要补的缺口**，两条路互补、不冲突。

（技术出处：这套是照抄 cc 的 AutoMem/memdir 机制做的白标版；读写两侧按同一个 `workspace.root` 派生同一目录，保证"写进去的下次一定读得到"。）

## 2. B 完整方案（正面回答 owner 三连问：填写 → 后端接 → 模型怎么读到）

### 2.0 先看现状最大的坑（B 不鸡肋的命门就在这）

调研发现一个已存在的大坑，必须先讲清：

- 门店信息的**后端数据早就有了** —— `ts/src/server/services/desktopDataStore.ts:28-76` 的 `defaultStore()` 已定义约 40 个字段（店名/城市/地址/电话/营业时间/台数/台种/价格/会员卡/助教数/助教价/器材品牌/客单价/高峰时段…），存在 `desktop-data.json` 的 `store` 对象里，还自带一个 `completeness`（完整度）字段。
- 填写/修改的 **API 也早就有了** —— `GET/PUT/PATCH /api/v1/stores/me`（`ts/src/server/index.ts:3158-3175`）。
- **但是：这份门店数据只喂给了"生图"。** 全项目 `getStore()` 只被三处调用（生图品牌约束 `index.ts:2602`、备份导出 `3135`、GET 接口 `3164`）。**聊天的大脑 `buildSystemPrompt`（`index.ts:1513`）从头到尾没读过它。**

> 也就是说：**现在就算老板把门店填得满满当当，聊天时模型也一个字看不到。** 这就是"填了没人看 = 鸡肋"的病根。所以 owner 三连问里，前两问（填写/后端存）基本现成，**第三问（模型怎么读到）才是 B 真正要新建的部分。**

（附带发现文档漂移：根 `CLAUDE.md` 声称已落地"门店画像层"注入，但代码里那层已下线（`index.ts:3137` 注释"自造店脑记忆已下线，改用 cc AutoMem"）。B 本质就是**把这层用真数据、按 cc 的读路径重新接回来**。）

### 2.2 设置界面怎么做（抄 WorkBuddy）

抄 WorkBuddy 两块（逆向档案 `docs/references/WorkBuddy逆向档案/14-补:设置-个性化.md` + `13-补:设置-记忆.md`）：

- **抄外观（§14 个性化面板）**：借它填写面板的**外观/交互**——结构化表单 + 字段分组折叠 + 底部确认按钮 + 脏检查（交互抄 cc、颜色文案抄 WorkBuddy，项目前端铁律）。⚠️**只抄外观、不抄后端接法**：WorkBuddy 那套"存 config → 后端 Collector 渲染 → 注入系统提示变量"的 Collector，正是门店档案投影器的等价物、也正是 2.3 与核心思想要砍掉的"结构化 store 真相源 + 渲染注入投影器"。我们的接法按 2.3 走纯 cc：表单填的内容**直接写进 memdir 的 `.md`/主指令**，注入复用 cc AutoMem 常驻注入，不存 config 真相源、不做 Collector 渲染层。
- **抄管理 UX（§13 记忆面板管理弹窗）**：一张卡展示当前记忆全文 + 编辑/清空两个图标按钮。对应到 B = 面板里放**"预览模型看到的门店档案"折叠区 + "清空重填"入口**，让老板肉眼确认"模型到底记着我店里啥"——这本身就是不鸡肋的信任感来源。
- 务实取舍照抄：桌面单机版**隐藏远程门控、去埋点、开关常开**，别做云端那套。

### 2.3 后端怎么接 + 模型怎么读到（纯 cc：直接写进 memdir/主指令，不另立真相源）

**统一走 cc AutoMem 常驻注入**：门店信息**不再**沿用 `desktop-data.json → store` 那套 structured store 当"第二套真相源"，也**不做**"门店档案投影器"管道。设置表单填/改字段后，把内容**直接落成 cc AutoMem memdir 里的门店事实 `.md`（+ `MEMORY.md` 一行索引），或写进 User 层主指令** —— 走的就是 1.2 讲过的"索引常驻必读 + 详情按需读取"现成通路，不新开注入通道。

**为什么不并立第二套**：门店信息和模型对话攒的门店事实是同一类东西，理应进同一个记忆池、被同一条常驻注入喂给模型。单独再养一份结构化 `store` + 投影器，就是并立第二套门店真相源，正是 owner 拍板"纯 cc"要砍掉的。设置表单是确定性代码（B 线），它的活只有一件：把老板填的字段整理好写进 memdir/主指令；对话里模型也能自己往同一个 memdir 补写门店事实（回合内写记忆 = 主模型直接 `Write`/`Edit` 往 memdir 落 `.md`）。两条写入落**同一池**、被同一条常驻注入读到，不打架。

**这就根治了 2.0 的病根**：填的内容落进 memdir/主指令后，模型每轮必读、改完下一轮即生效，不再是"只喂生图、聊天读不到"。证据：系统提示**每次聊天请求都重建**（`index.ts:1513` → `loadMemoryInjection` 现读文件），所以"改完下一轮即生效"是确定性的。

### 2.4 不鸡肋三要点

1. **字段从 PPT 提炼**（不拍脑袋）：字段集 = 通读 PPT 运营底本提炼的十大板块（见 2.1）；前端用**完整度进度条**逼着"别只填一半"。（⚠️完整度改由前端按 memdir 里已写门店字段的覆盖数现算，不再依赖已作废的 `desktopDataStore.store` 的 `completeness` 字段——那套 structured store 按 2.3 不再当真相源。）
2. **写进"每轮必读"处**（命门）：走 **cc AutoMem 常驻注入**（内容落进 memdir/主指令那条每轮必读的通路，见 1.2 / 2.3），不是填了没人看 —— 直接根治现状"填了模型看不到"的病根（把只喂生图的 store 接进聊天大脑）。
3. **用户可改**：填的内容逐条可改；memdir/主指令每轮重读 → 改完下一轮即生效；再加"预览模型看到的门店信息 + 清空重填"入口，让老板看得见、改得动、信得过。
