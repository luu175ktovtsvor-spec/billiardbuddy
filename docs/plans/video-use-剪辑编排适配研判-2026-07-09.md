# browser-use/video-use 剪辑编排适配研判

> 📌 状态:✅现行 · 最后核对 2026-07-09

> **这份是研判(adoption judgment),不是实现计划。** 逐条判断 `browser-use/video-use` 的剪辑编排方法本项目要不要吸收、现在有没有、落在哪、后续怎么走。所有"现状"结论都真读了当前 TS 代码(`ts/src/media/videoEditProjects.ts`、`ts/src/media/mediaJobs.ts`、`ts/src/server/index.ts`),引了真实方法名和行号。对应阶段目标 §3.3 / §8 / §12 与完成标准 §17.8。
>
> **口径提醒**:`server/`(老 Python 线,含 `server/services/video_edit/*`)已于 2026-07-09 整体退役删除(见根 `CLAUDE.md` 顶部 banner)。因此 `docs/plans/视频创作工作区-V2开发文档-2026-07-02.md` 里标"✅真机验通"的那套(director/VLM/whisper/template_render/recaption/BGM)**已不在代码库里**,属历史。当前真正在跑的视频能力,只有下文引用的这套 TS 本地实现。
>
> **参考来源**(2026-07-09 核对):video-use 官方 [README](https://github.com/browser-use/video-use/blob/main/README.md) / [SKILL.md](https://github.com/browser-use/video-use/blob/main/SKILL.md)。其管线 = **Transcribe → Pack(`takes_packed.md`)→ LLM Reasons → EDL → Render → Self-Eval**,自检不过最多重渲 3 次;核心信条"音频优先、画面跟随,LLM 不看视频、只读两层摘要(`takes_packed.md` 文本 + `timeline_view` PNG)"。

---

## 一、结论先行(大白话)

1. **video-use 的骨架思想,本项目其实已经有一半**:它把"时间线文档当唯一真相源、用原子操作改、渲染前先校验、成品和中间产物都堆进项目目录"这套做扎实了——我们 `videoEditProjects.ts` 里的 `TimelineDoc` + `applyOperations` + `validateDoc` + `edits/<项目>/timeline.json` 就是同一套路,这块已经落地,不用重造。

2. **video-use 真正的看家本领——"先把素材转写成文字、LLM 只读压缩摘要来剪"——我们目前是空的**。现在 TS 的转写/字幕/换段全是**占位文案**(代码里明写"真实转写、VLM 挑高光和智能换段仍需媒体后端"),而那个媒体后端(老 Python)已经删了。所以 transcript-first、`takes_packed.md`、按词边界剪口播这几条,现在是"想法认可、实现为零"。

3. **几条低成本的剪辑手艺我们还没做**:剪口播不切断单词、片段两侧留 30–200ms、切点加 30ms 淡入淡出防"啪"声、渲染完再自检画面/音频/字幕——这些不依赖大模型,是纯工程细节,`renderProject` 现在是硬切、无 padding、无 fade、只在**渲染前**校验结构、**渲染后不复查成品**。这批最值得优先补,而且和"删除 AI 生成视频"铁律毫无冲突(全是真实素材剪辑)。

4. **没有任何一条 video-use 方法会碰到红线**:video-use 是纯"真实素材 + 转写驱动剪辑",不生成视频,和我们"删掉 CD/Seedance 文生图生视频、只保留真实素材剪辑"的方向完全同向。吸收它不会把生成视频能力带回来。

5. **一句话**:编排骨架(时间线真相源/原子操作/渲染前校验/项目目录/响度归一)已进方案;transcript-first 那条智能主线要等"媒体后端或 TS 内做转写"补齐;padding/fade/不切词/渲染后自检是可立即排期的工程增量;可视 `timeline_view` 和前端工作台归前端窗口。

## 三、已进入本项目方案的编排思想(有代码为证)

video-use 的"素材理解 → 策略 → 时间线 → 渲染 → 自检"里,**骨架和确定性那半**已经在 TS 内核落地:

1. **时间线文档 = 唯一真相源 + 原子操作 + 回滚**
   - `TimelineDoc`(`videoEditProjects.ts:34`)是分轨(video/audio/caption)、稳定 ID 的结构化文档;`applyOperations`(`:574`)先 `cloneDoc` 再逐条 `applyOne`(`:265`),任一步失败或 `validateDoc` 不过就整体不落盘、返回旧文档(`:579–591`)。这正是 video-use "对 EDL 发原子编辑、消费文档确定性出片"的同构实现。

2. **渲染前结构自检**
   - `renderProject`(`:802`)入口即 `validateDoc`(`:233` / 调用点 `:806`):校验 clip 是否引用了存在的轨道/媒体、`src_in < src_out`、区间是否超出源素材、字幕时间是否合法;不过关直接 `VideoEditError` 不出片。这是 video-use self-eval 的**前置一半**(结构层)。

3. **项目目录集中化**
   - 每个剪辑项目一份 `uploads/edits/<项目>/timeline.json`(`docPath` `:958`);成片/字幕统一落 `uploads/videos/`(`:813–816`)。素材来源经 `resolveMediaSource`(`:964`)规范化 + 越界护栏(`:972`)。对齐 video-use"所有产物进 edit 目录"。

4. **异步任务化 + 大白话进度**(编排落地形态)
   - `mediaJobs.ts` 定义 `video_inventory`/`video_auto_plan`/`video_render` 三种 job kind(`:18–20`),`startVideoJob`(`:678`)统一起任务;有媒体后端走代理轮询、没有则 `localVideoJobFallback`(`:1454`)本地跑(inventory/auto_plan→`createLocalPlan`,render→`renderProject`),全程 `ctx.progress` 吐大白话阶段。路由在 `server/index.ts` `handleVideoEditRoute`(`:2937`)。这让 video-use 那套"分阶段管线"在本项目以异步 job 形态承接。

5. **出片工程标配**:响度归一(`LOUDNESS_FILTER` `:95`)、字幕烧录 + 降级(`:883–896`)、scale/pad 到目标画布 + fps 归一(`:849`)——都已在 `renderProject` 内。

## 四、暂不吸收或降级的(理由)

1. **老 V2 的"AI 导演 + VLM 挑高光 + 花哨模板逐帧渲染 + 程序化 BGM"整套——降级/不恢复原实现**
   - 那套只存在于已删除的 `server/services/video_edit/*`(Python),`docs/plans/视频创作工作区-V2开发文档-2026-07-02.md` 里的"✅真机验通"是历史。**当前不主张照原样恢复 Python 实现**;若要,应在 TS 侧或新后端按需重写,且以 video-use 的"转写驱动"为主线,而非重堆模板特效。这不违反红线(不是 AI 生成视频),只是产品阶段优先级问题。

2. **`timeline_view` 后端可视合成(波形/filmstrip PNG)——降级为可选**
   - 本项目前端是桌面工作台,客户端播源片 + DOM 字幕浮层的预览体验优先级更高(见五 5);后端再渲一张 PNG 摘要属锦上添花,近期不做。

3. **render 后自检的"最多重渲 3 次"自动循环——先只做自检、暂不做自动重渲**
   - 自动重渲会显著拉长任务、增加不确定性;当前阶段先做"渲染后体检 + 给出可读问题",是否自动重渲留给 owner 决策。

4. **与红线的边界确认(不是要吸收、是要守住的)**
   - video-use 全程真实素材剪辑,**不涉及**文生视频/图生视频/`generate_video`。吸收它的任何方法都**不得**顺带引入生成视频链路(阶段目标 §3.2/§11 已删且禁止恢复)。转写用的 provider(whisper 本地 / 云转写)是**语音转文字**,不是视频生成,不触红线。

## 五、后续路径(可执行项 · 标注归属)

> 归属:**内核** = `ts/` 后端;**前端** = ts-desktop 工作台;**owner** = 需 。

1. **【内核】补真转写(transcript-first 的地基)** — 最高价值、当前最大缺口
   - 现状:`createLocalPlan`/`autoCaption` 全占位,`phrases:[]`、`used_vlm:false`,依赖已删的媒体后端。
   - 做法二选一:① 内置 whisper 作为 **Node 子进程 sidecar**(`.node`/二进制塞不进 `bun build --compile`,按 `ts/CLAUDE.md` 铁律 8 走 sidecar);② 接一个云转写 provider(走网关藏 key)。产出**词级** transcript(时间戳),写进 `edits/<项目>/`,把 `candidates.phrases` 填真值。
   - 依赖它才能解锁:`takes_packed.md`、按词边界剪口播、口播线字幕用"说的话"。

2. **【内核】`takes_packed.md` 类素材摘要** — 依赖(1)
   - 转写就绪后,把词级结果 + `footage_health` 压成一份给 LLM 读的紧凑 Markdown/结构化摘要,进项目目录。让编排 LLM"只读摘要不看视频"。

3. **【内核】剪辑工程细节三件套(不依赖大模型,可立即排期)**
   - **padding**:切段时对 `src_in/src_out` 做参数化安全外扩(默认 30–200ms,clamp 到素材范围),改 `createLocalPlan`/`renderProject` 的取段逻辑。
   - **30ms fades**:`renderProject` 段边界加 `afade`(音频优先)、可选 `xfade`;注意现在是 `-c copy` 硬拼(L871),加 fade 要改成重编码合成路径,权衡耗时。
   - **不切断单词**:依赖(1),口播切点吸附最近词边界。
   - **render 后自检**:出片后 ffprobe 复验时长/音轨/分辨率,加基础成片体检(黑帧/静音/字幕存在性),失败给可读原因(先不自动重渲)。

4. **【内核 + 会话层】项目编辑记忆增强(`project.md` 类)**
   - 在 `edits/<项目>/` 旁加一份编辑决策/店主偏好记忆,和工作区会话历史挂钩,支撑"多轮改文案越聊越懂调性"。现在 `recaption`/`editFeedback`(L637/L652)是占位,真智能重写也依赖(1)+ 编排 LLM。

5. **【前端】独立视频工作台 + 策略确认交互** — 归 ts-desktop 前端窗口
   - 现状:ts-desktop 前端未建(见根 `CLAUDE.md`);`localFileResponse`(L923)已备好 Range 播放供客户端预览。
   - 做法:客户端秒级预览(播源片选中段 + DOM 字幕浮层)+ 镜头/时间线条 + "方案预览→确认→出片"显式一步 + 内置对话框改文案。把 video-use 的 strategy confirmation 落成 UX 确认。

6. **【owner 决策】两个开放项**
   - 视频编辑是否升级为审批闸(倾向:非对外/可逆,做 UX 确认即可,不设硬闸)。
   - render 后自检是否加"自动重渲最多 N 次"(倾向:先人工确认,自动重渲后置)。
