分层依赖方向:对的,大骨架没塌。内核(loop/model/tools/context/permissions/agents)都不反向依赖 server,server 是唯一组装根、方向朝下,产品 B 线(media/packs 生图剪辑+台球领域包)只在 server 装配处接入、没漏进内核。只有一处孤例倒挂:spreadsheetTool 伸手 import 了 server/services 的 officeDocuments,单点易改。另外 cc 有一整层顶层 services/ 我们没有、压进了 server/services + 散落内核,方向没违反但要立规矩(内核需要的横切能力必须留内核层,别塞 server/services)。

核心契约:大部分对齐(权限词汇 allow-deny-ask-passthrough、hook 事件/决策 JSON 抄 cc、命令技能统一成单一 PromptCommand 没犯"技能拆五件套"、Model DI seam、Anthropic content-block+proxy 双向翻译都同构),但有两处契约"形状"真分叉:①最核心的工具返回契约,cc 用 ToolResult<Output> 声明式封装工具全部产出,我们退成 execute()→string + 挂 ctx 上的可变 image/documentSink side-channel,抽象没封住(注释自认要靠串行/排除读图工具才不串图);②工具级权限从 cc 的 checkPermissions() 方法搬成了声明字段+中央瀑布。这两条能等价映射、功能已补偿,但接口形状不是 cc 的,得在矩阵里登记成已知分叉、别当已对齐。

存储架构:这是真问题,major。cc 的会话真相是一条 append-only 事件日志、每条带 uuid/parentUuid 组成会话 DAG;我们是每回合把整条 Message[] tmp+rename 整体重写快照、消息无 uuid/parentUuid。后果:分支/侧链/leaf 锚定 resume/message 级 rewind 全做不了(fork 只能整条拷贝),还有 O(n²) 写放大。这条跟内核审计 W2 波次是同一件事,不是新发现。连带 stateRoot 布局(transcript 没跟 AutoMem 一样按 projects/<slug> 分区)、中央 sessions.json 当真相源(应降级为可重建缓存)、file-history 绑 conversationId 而非 messageId,都是这个根因的分支。

一句话总结:模块地图和分层方向真同构了,契约大体对齐但工具返回/工具权限两处形状分叉,而存储模型是从地基上分叉的——差 migrations 这一整块基础设施 + 存储改成 append-only 事件日志(带 uuid/parentUuid)+ 收掉工具 side-channel sink 这三处根性改动,才算"后端架构真正对齐 cc"。别粉饰:现在是"骨架同构、剩几条架构 gap",不是"完全对齐"。

**架构级分叉清单(12 条,按根性排)**:

- **[storage-model·P1]** 会话真相存储模型:每回合整体重写快照(transcript.savePreservingExternalTail)vs cc 的 append-only 事件日志(appendEntryToFile)
  - 掰回:地基级分叉,须整块换而非打补丁。把 transcript 从'内存 Message[] tmp+rename 整体覆写'改成每回合只 appendFile 新增行、load 顺序回放重建。当前模型带来 O(n²) 写放大+整文件读内存,且直接堵死 resume/compact/branch 的对齐路径。这是 owner 要揪的核心分叉,与 W2 存储审计波次同源,别当新发现另报。
- **[storage-model·P1]** 消息身份:cc 每条 entry 带 uuid/parentUuid 组成会话 DAG,我们的 Message 是无身份扁平数组(types/message.ts)
  - 掰回:无 uuid/parentUuid 导致链式能力全塌:fork 只能整条拷贝(sessionService.fork 已自认非真分支)、无 sidechain、无 leafUuid 锚定 resume、无 message 级 checkpoint/rewind。随事件日志改造给每条 entry 补 uuid(+至少单亲 parentUuid),字段形状现在就对齐 cc 免二次迁移;真 DAG 可后置。
- **[contract·P1]** Tool 执行返回契约:cc 是 call()→ToolResult<Output>{data,newMessages,contextModifier,mcpMeta} 声明式封装,我们是 execute()→string + 挂在 ToolContext 上的可变 imageResultSink/documentResultSink side-channel
  - 掰回:最核心工具抽象的形状真分叉。cc 用返回值封闭表达工具全部产出,我们把'额外输出通道'外泄成 loop 与 tool 共享的时序脆弱可变状态(注释自陈需'串行一一对应/并行排除读图工具'才不串图=抽象没封住)。对齐做法:execute 返回改 ToolResult<Output>{data,images?,documents?,newMessages?,contextModifier?} 由 loop 统一消费,删掉 sink。若暂不改,至少在矩阵登记为已知内核契约分叉,别当已对齐。
- **[missing-module·P2]** 数据/设置迁移子系统:cc 有独立 migrations/(11 个版本化迁移器,启动按序跑),我们无对应模块(数据生命周期在 #36 待办)
  - 掰回:唯一整块缺失的内核基础设施。cc 具体迁移器多为其上游模型改名对我们不适用,但'版本化+启动按序执行'的迁移地基缺位;桌面版长期跑必然遇到 settings/数据 schema 演进。建议建轻量 migrations/ 域并在 sidecar 启动接线,落实 #36。
- **[contract·P2]** 工具级权限落点:cc 每个 Tool 实现 checkPermissions()→PermissionResult,我们 Tool 上无该方法,改成 ~12 个声明式谓词字段(fatalReasonFor/requiresApprovalFor/approvalClassFor…)+ 中央 permissions/resolve.ts 瀑布读取
  - 掰回:决策结果类型(PermissionResult/Decision/behavior allow-deny-ask-passthrough)已对齐,但工具契约成员从'方法返回'搬成'声明字段+中央瀑布',接口形状不同。属可辩护的产品简化,但行为对齐测试须拿 cc checkPermissions 的刁钻用例(passthrough、updatedInput 改写、ask+decisionReason)逐条断言瀑布判得一致,别只测自己想到的字段组合。
- **[layering·P2]** 工具层反向 import server 层(真漏点):tools/spreadsheetTool.ts import ../server/services/officeDocuments,内核工具伸手进 server/services(孤例)
  - 掰回:依赖方向大骨架是干净的(内核不反依赖 server),这是唯一一处倒挂。把 officeDocuments(csv/xlsx 单元格编辑)纯逻辑下沉到内核可共享低层(tools/ 内部或新建 utils),工具层就不再依赖 server。单点、易改,改完方向彻底干净。
- **[storage-model·P2]** stateRoot 布局 + 会话元数据真相:transcript 扁平落 transcripts/<id> 不按项目分区 + 中央 sessions.json 索引作真相,cc 按 projects/<slug> 分区且元数据内嵌事件日志、无中央索引
  - 掰回:两点:①transcript 挪到 projects/<workspaceRoot slug>/ 与已对齐的 AutoMem 一致(白标只换根目录名 .billiardbuddy 不算分叉);②把 sessions.json 降级为'可从事件日志扫描重建的缓存',元数据主真相跟 cc 一样内嵌日志,避免中央索引与日志两份真相漂移。桌面 GUI 列会话选择器用中央缓存合理,但它不该是真相源。
- **[storage-model·P2]** file-history 锚定:我们以 conversationId 为键、落用户工作区 .agent-file-history/(只能线性 undo),cc 以 messageId 为键支持 message 级 rewind
  - 掰回:等消息补上 uuid 后,把快照键从 conversationId 换成 messageId 并随事件日志统一管理,才能对齐 cc 的 message 级 rewind。另评估把 .agent-file-history 从用户工作区挪进 stateRoot,避免污染/混进用户 git 仓库。
- **[self-invented·P3]** 自造 UDS 跨会话 IPC 层:tasks/udsInbox+udsClient+udsPeerRegistry(Unix domain socket inbox),cc 无此层(teammate 走进程内 InProcessTeammateTask+AppState,跨机走 bridge/remote WS)
  - 掰回:多造了一层 cc 没有的本地 IPC,是 cc 进程内+bridge 两级模型外的第三条自造路径。确认它是否真被产品用到:在用就写清补的是 cc 哪个能力缺口(多个独立 sidecar 会话互发);若只是早期实验,收敛回 in-process teammate + bridge 两级。
- **[self-invented·P2]** 后台任务类型学被压扁:cc 是多态 TaskType 联合(local_agent/remote_agent/local_workflow/monitor_mcp/dream…)+per-type Task 类+coordinator/,我们基本只有 background_agent + spawnShell 的扁平 TaskService,子代理执行拆到 agents/
  - 掰回:缺 cc 那层统一 Task 抽象/coordinator,agents/ 与 tasks/ 两套并行会随功能增多发散。功能碎片都在(子代理/远程/team),后台 agent 也和 cc 一样进程内 runAgentLoop(对)。若 workflow/monitor_mcp/dream 是有意不做标产品裁剪即可;若要接多种后台执行,引入统一 TaskType 联合+per-type 状态守卫收敛。
- **[layering·P2]** 服务器 HTTP 层内部分层:4744 行单体 server/index.ts 手搓路由(pathname.split/startsWith 长链),无 cc 的 router+api/+middleware/ 三层切分
  - 掰回:对外端点契约(HTTP/SSE/WS 形状)一致、不影响功能,但内部分层与 cc 分叉。要'同骨架'的话按 cc 拆:cors/auth/errorHandler 提成 middleware、canvas/studio/video-edit 等拆成 api 模块、装配收进 server.ts。可增量重构、不阻断,但不拆会持续偏离。
