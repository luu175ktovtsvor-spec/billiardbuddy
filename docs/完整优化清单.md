# 完整优化清单 · 球房运营 AI 助手桌面版「产品化」

> **本文件是什么**：把一次三层链路体检（行业真实运营资料抽取 → 知识库转录对齐 → Agent调用）查出的**全部可优化项**汇成一份可执行清单。来源 = 6 路并行调研（行业真实运营资料框架/知识库结构/运行时管线/行业真实运营资料对齐/外部方法论/用户痛点）+ 2 路综合（架构师/产品负责人），证据均带 `文件:行` 或 行业资料页码。
>
> **核心目标 = 产品化**。一个有价值的产品要同时满足三件事，本清单按这三根支柱分组：
> - **支柱 A · 核心功能完备性**：承诺的能力要真能用（诊断真读报表、知识真调得到）。
> - **支柱 B · 用户使用感受**：非技术老板能上手、看得懂、信得过、不被偷偷花钱。
> - **支柱 C · Agent 机制运行规则无逻辑问题**：审批闸/知识注入/变量契约/口径一致，没有自相矛盾或静默失效。
>
> 另设 **支柱 X · 跨层架构决策**（贯穿三层的元数据/可观测/防过度设计）和**第 2 层知识内容对齐**专项。

## 0. 怎么用这份文档（给执行的 AI 读）

1. **逐项推进，一次一个**：每个优化项是一个独立 task。改前先看「牵连/风险」，必读 `docs/耦合地图与改动检查清单.md`。
2. **改代码走 TDD + 回归**：先写测试钉住「这块要什么行为」，改完跑**全量** `cd server && uv run pytest tests/ -q` + `cd web && pnpm exec tsc --noEmit`，确认没连累别处。
   - **前端真实页面验证**：主会话可用 Playwright MCP；但**派子代理去测试时，子代理一律用项目 `web/` 里的 headless（无头）Playwright 脚本（`node` 跑），不用 MCP**——子代理/无头环境里 MCP 不可靠（全局 CLAUDE.md 已规定）。要可复用回归脚本也走这条。
3. **改 prompt/YAML 不改业务码**：知识内容类（支柱 A 的硬数字、口径、来源层级）只动 `server/prompts/` 下 YAML，注意护栏测试 `server/tests/test_knowledge_guardrails.py`。
4. **每完成一项**：把该项 `- [ ]` 勾成 `- [x]`，并在条目末尾追加「✅ 完成于 / 改了哪些文件 / 跑了哪些检查」。
5. **铁律不可破**（贯穿全程）：纯 BYOK 绝不内置平台 key；POS 只读；不自动触达；行业真实但守红线（不营销实际性交易/不帮刑事级犯罪）；SQLite 兼容按方言兜底；不过度设计（见支柱 X-1，明确不上 GraphRAG/语义分块/SKILL.md 迁移）。
6. **完成全部清单 → 进第 2 步：真机端到端实测**（见 §8）。

## 2. 支柱 A · 核心功能完备性

> 衡量标准：产品**承诺的每个能力都真能用**。当前最大问题是「照报表诊断」「调行业知识」这两个核心卖点，部分是空头支票或半通。

### A-1 · 诊断↔报表真打通：让 diagnose 自动读 Excel 数字 — [x]  ✅ 完成:report_reader抽取器读Excel算决策树指标+diagnose接report_path喂diagnostic_logic;真表跑出团购占比28.9%/营收结构/客单价144/翻台率7.89h、触发规则4、缺项如实标注;313绿
- **现状/问题**：`diagnose_operation`(`server/services/agent/tools.py`) 只接 `situation`(文字)+`problem_area`；`analyze_diagnosis`(`server/services/diagnosis_service.py`) 把这段文字塞模板就生成。但 `knowledge/diagnostic_logic.yaml` 的决策树（"团购占比>70%→…""某区开台率<30%→…"）**需要真实指标才触发**。读 Excel 能力在**另一条路径**（`server/api/v1/canvas.py` 的 read-sheet / `edit_excel`），和诊断没打通——Agent 不会自动"先读报表数字→再喂诊断"。结果：起手卡"照报表诊断"承诺落空，老板不逐项打字进对话，决策树全程命中不了。
- **为什么（产品化价值）**：这是 POS 真诊断的核心卖点，现在名不副实；打通后"照报表诊断"才真能跑决策树，是支柱 A 最高价值项。
- **怎么做**：① 给 `diagnose_operation` 加 `report_path` 入参，或在编排层固化一条 SOP——老板说"照报表诊断"时，Agent 先 `read_file`/read-sheet 把营收结构/各区开台率/团购占比/充值扣卡抽成结构化 JSON → 作为 `current_situation` 的结构化部分喂 `analyze_diagnosis`；② 报表列名做一层**模糊映射**（不同收银导出列名不一）；③ 复用 `canvas.py` 已有读表能力，不新造轮子。
- **验收**：拿一份真实导出 Excel，端到端验证 `diagnostic_logic.yaml` 决策树规则能真命中（如团购占比>70% 触发对应建议），而非泛泛输出。
- **牵连/风险**：不破"POS 只读"铁律（只读不写收银）；列名映射要兜不同收银软件；先在编排层写 SOP 用真 Excel 验证可行，再决定是否改 `tools.py` 签名（见 §7 批次2 的小验证）。

### SH-1 · 缺失 tool_result 自愈（消息配对修复）— [x]  ✅ message_repair.ensure_tool_pairing 两入口请求前补缺失/删孤儿/去重,防400崩
- **现状/问题（缺什么·带文件）**：`server/services/agent/loop.py` 假设每个 assistant 的 `tool_calls` 都能配上一条 role:tool 回灌。正常路径没问题，但工具执行走异常分支没回灌、或后续 SH-7/SH-8 改历史造出孤儿时，下一轮 OpenAI 兼容端点会因「tool_calls 缺配对 tool_result」或「孤儿 tool_result」直接 400，整轮请求崩。现壳无任何发请求前的配对自检。
- **为什么（壳强在哪）**：OpenAI/Anthropic 协议硬约束——每个工具调用必须有配对结果（TU「When Claude uses tools」描述工具调用→结果回灌的闭环契约）。补上配对自愈=堵住「偶发但致命、让整个会话卡死」的边界，是 SH-7/SH-8（改历史）的前置安全网，真机长跑更耐操。
- **怎么做（Python 草图+改哪些文件+数据结构）**：新增 `server/services/agent/message_repair.py`，纯函数 `ensure_tool_pairing(messages) -> messages`：① 收集所有 assistant `tool_calls` 的 id 集合 `expected` 与所有 role:tool 的 `tool_call_id` 集合 `present`；② `expected-present` 的每个 id 在该 assistant 消息后插一条 `{"role":"tool","tool_call_id":id,"content":"[工具结果因内部错误缺失，可重试]"}`；③ 删除 `present-expected` 的孤儿 result；④ 同 id 多次出现只保第一条（防 API 拒重复 id）。接入点：`loop.py` 每次 `provider.generate(...)` **之前**（同步+流式两入口都改）调一遍，尤其放在 SH-7 压缩之后。
- **验收**：完整配对不变；缺 result 补合成；孤儿 result 删除；重复 id 去重；模拟压缩后造孤儿能被修复。pytest 全绿。
- **牵连风险**：纯函数无新状态，行为风险低；唯一要点=同步与流式两入口都接（loop.py 已知「改一处漏一处」风险点，测试需双覆盖）。
- **优先级·批次**：P1 · 批次 5（壳强化批·最先，作安全网）。

### SH-2 · 编排循环接 usage_sink + token 预算递减早停 — [x]  ✅ token预算三态(到90%停/低增量停/过半推),token_budget=None交互式零影响,真实usage落库
- **现状/问题（缺什么·带文件）**：provider 层已现成暴露 `usage_sink`（`server/services/ai/base.py`、`providers/deepseek.py` 真回填 prompt/completion/total tokens），但 `loop.py` 两入口调 `provider.generate/generate_stream` 时**从不传 usage_sink、从不累加每轮 token**；`server/api/v1/agent.py` 落库 `tokens_used=0`。结果：① anti-spin 只挡「同参重复」，挡不住「换参数空转烧钱」的发散循环；② 一次 Agent 任务真实编排消耗壳层无感。
- **为什么（壳强在哪）**：BEA 明确推荐用 stopping conditions（如最大迭代数）「to maintain control」；token 预算是其自然延伸。BYOK 是老板自掏钱，「发散打转烧光钱」是真实风险。接上现成 usage_sink，一举同时改善**省钱（预算早停）+ 防空转 + 可观测（成本看板显真实编排消耗）**三件事，改动小价值大。
- **怎么做（Python 草图+改哪些文件+数据结构）**：`context.py` 的 `AgentContext` 加 `token_budget: int|None=None`（None=交互式不限）/`tokens_used`/`budget_continuations`/`last_delta`/`last_total`。`loop.py` 每轮拿到 resp 后把 usage 累加进 `ctx.tokens_used`（端点没返回则 `len//4` 粗估）。新增 `_check_budget(ctx)`：`diminishing = continuations>=3 and delta<阈值(如500) and last_delta<阈值`；未到 90% 且不 diminishing → 回一句「已到预算 N%，继续干别总结」推动语并计数；否则停。接入点=现有「无 tool_calls → 收尾」分支，且**放在 Stop hook 之前**（预算到了优先级最高，不让 Stop hook 拉回空转）；`budget is None` 整段跳过=对现有交互式行为零影响。provider 层 usage 透出口已现成。
- **验收**：预算 None → 一轮即停（现行为不变）；设小预算+高用量 → 90% 停；连续 3 轮增量极小 → diminishing 停；推动语仅在「还有预算且有产出」时出现。
- **牵连风险**：要同改 `api/v1/agent.py` 让落库 `tokens_used` 拿真实值（顺带喂 BYOK 成本看板）；anti-spin（微观防重复）与本项（宏观防烧钱）互补、都保留。
- **优先级·批次**：P1 · 批次 5（壳强化批·改动最小、ROI 最高，建议第二个做）。

### SH-3 · 工具结果落盘（persisted-output，给路径而非硬截断）— [x]  ✅ 超阈值非deliverable非自读类落盘UPLOAD_DIR+回灌路径预览,沙箱白名单加tool-results/
- **现状/问题（缺什么·带文件）**：`loop.py._cap_tool_result` 超 12000 字直接截断+提示「分批读取」，被砍的后半段模型永远看不到，只能再调一轮缩小范围（多烧一轮）。读大报表/长文案历史时信息丢失。
- **为什么（壳强在哪）**：CE「just-in-time」原则——维护轻量标识符、用工具按需把数据动态拉回上下文，而非一次塞全。大结果落盘+回灌「路径+预览」让诊断大报表/读长历史**不丢信息又不撑爆上下文**，比「截断+让它重读」更省 token 也更稳。
- **怎么做（Python 草图+改哪些文件+数据结构）**：新增 `server/services/agent/tool_result_store.py`，`persist(tool_name, text, ctx)->(path, preview)`，落点用 `UPLOAD_DIR`（铁律：app 包内只读，可写目录是 userData）下 `tool-results/<session>/<tool>-<uuid>.txt`。改 `_cap_tool_result`：阈值以下原样；超阈值且**非 deliverable 且非「自读类」**→ 落盘，回灌 `[结果较长已存盘] <persisted-output>{path}</persisted-output>（共 N 字）+ 开头预览 + "需要更多用 read 读该路径"`。关键：`local_tools.py` 的 `_resolve` 沙箱白名单要把 `tool-results/` 加进去（否则模型读不回自己落盘的结果）。`registry.py` 的 `Tool` 加 `max_result_chars: int|None`（None=全局默认，给 read 类工具设永不落盘）。
- **验收**：小结果不落盘；大查询结果落盘+回灌含路径+预览；deliverable 大结果不落盘不截断；`read` 能读回落盘文件（沙箱放行）。
- **牵连风险**：落盘路径必须走 `UPLOAD_DIR`（不能写 app 包内只读区）；沙箱白名单改动要回归 `test_local_tools_sandbox.py`；前端可据 `<persisted-output>` 标签渲染「查看完整结果」链接（顺带改善 UI）。
- **优先级·批次**：P1 · 批次 5。

### SH-4 · max_output_tokens 截断恢复（续写拼接）— [x]  ✅ finish_reason=length续写(上限3防死循环),片段拼完整final,同步+流式
- **现状/问题（缺什么·带文件）**：模型一轮输出被 `max_tokens` 截断时 `finish_reason="length"`（非正常 `stop`/`tool_calls`），现壳把截断的半句话当最终答复直接收尾，用户看到被砍断的半句。`loop.py` 收尾分支无 length 判断，provider 响应也未必透出 `finish_reason`。
- **为什么（壳强在哪）**：TU 描述 `stop_reason` 是工具/对话流转的正式信号；`length` 是明确的「没说完」信号。识别它并续写，让长文案/长诊断不被半路砍断，直接改善「半句话」体感。
- **怎么做（Python 草图+改哪些文件+数据结构）**：`server/services/ai/base.py` 的响应对象加 `finish_reason: str|None`，provider 透出端点返回的该字段。`loop.py` 收尾分支：`if resp.finish_reason=="length" and continuation_count<上限(如3): 把已输出 append 为 assistant 消息 + append 一句"接着上次断的地方继续写完，不要重复" + continuation_count+=1 + continue`。流式版同理：length 时不发 final、回灌已收片段+续写提示，最后把多轮片段拼接成完整 final。加 `continuation_count` 上限防「一直被截一直续」死循环（呼应 max_turns 兜底哲学）。
- **验收**：`finish_reason="stop"` 正常收尾；`="length"` 触发续写+拼接完整；连续截断到上限强制收尾不死循环；流式拼接正确。
- **牵连风险**：只在收尾分支加判断，工具调用轮不受影响；同步+流式两处都要改。
- **优先级·批次**：P2 · 批次 5（改动小、立竿见影）。

### SH-5 · 工具渐进式披露 + tool_search 元工具（工具层省 token）— [ ]  ⏭️ 暂不做(鸡肋):工具不多、无膨胀压力;等工具数量真上来再做
- **现状/问题（缺什么·带文件）**：`registry.to_openai_tools()` 把**全部**工具 schema 一次性喂模型（`loop.py` 每轮都带）。现十几个工具尚可，但发布/对账/周报/各平台工具增多后，每轮请求都背着全量工具描述烧 system token。`scenario_catalog.py` 的 find_scenario 只是「场景模板」层雏形，工具层无渐进披露。
- **为什么（壳强在哪）**：CE「just-in-time」+「smallest possible set of high-signal tokens」。长尾工具初始只露「名字+一句话」，模型按需 fetch 全 schema 才可调用——代价多一轮交互，收益省掉一大票用不上工具的常驻 token。WT 强调工具描述质量与命名清晰度对效果影响显著，渐进披露不牺牲这点（解锁后仍是完整 schema）。
- **怎么做（Python 草图+改哪些文件+数据结构）**：`registry.py` 的 `Tool` 加 `defer: bool=False`+`summary: str=""`；`to_openai_tools(unlocked)` 常驻工具原样、`defer=True` 的不进数组改由 `deferred_catalog_lines()` 产「名字 — summary」清单文本。新增元工具 `tool_search`（`read_only=True`，入参 `{query, max_results}`，handler 纯本地匹配：`select:A,B` 精确取名 + 关键词对 name/summary/description 打分），命中后返回完整 schema 文本并把名字写进 `AgentContext.unlocked_tools: set[str]`。每轮 `tools = 常驻 + 已解锁`，解锁工具**追加在末尾不插中间**（保 prompt-cache 前缀，见 SH-9）。**自适应开关** `should_defer()`：延迟工具 schema 占上下文窗低于阈值就全当常驻发（工具不多时不折腾）。先给「平台内容/团购/批量/RPA发布」长尾工具打 `defer=True`，高频「写文案/海报/诊断/约客/提问」常驻。同一「先摘要后正文」也复用到 `scenario_catalog.py`（场景清单只露标题）。
- **验收**：默认不启用时全工具可见；`defer` 工具初始不在 tools 数组在 catalog 文本里；调 `tool_search("发布")` 后该工具进数组；`select:write_copy` 精确命中。
- **牵连风险**：当前工具数下收益有限（故 P2）；解锁追加必须不破前缀缓存（与 SH-9 协同）。
- **优先级·批次**：P2 · 批次 6（工具变多后再上）。

### SH-6 · 三级上下文压缩（snip→microcompact→autocompact 有序）— [x]  ✅ 完成:autocompact三级压缩(默认关·DESKTOP_MODEL_CTX_WINDOW配启用·中文估算已修),420绿
- **现状/问题（缺什么·带文件）**：`loop.py._microcompact` 只清「只读工具结果」；真正的对话历史压缩在 `api/v1/agent.py` 的 `_cap_history`——**简单粗暴丢最旧 12 条 + 每条砍到 2000 字**。多步任务里 user/assistant 的关键交代落在第 13 条前就被静默丢，模型「忘了前面让它干啥」。无语义级 autocompact。
- **为什么（壳强在哪）**：CE 把「tool result clearing」称为「最安全、最轻」的压缩，但也指出长任务需更重的语义压缩。复杂多步任务（先诊断报表→据结论写一周文案→再改 Excel）不会因对话变长而「中途失忆」——这是壳能否扛真·长任务的分水岭，比当前两机制都更治本。
- **怎么做（Python 草图+改哪些文件+数据结构）**：把现 `_microcompact` 升级为有序流水线 `_compact_pipeline(messages, registry, ctx, model_ctx_window)`：① `snip_freed=_snip(...)` 新增，把「读/搜类(read_only 且非最近)」结果折叠成一行投影（零 LLM）；② `_microcompact(...)` 已有保留；③ `est = _estimate_tokens(messages) - snip_freed`，仅当 `est >= 窗口*~0.8` 才 `await _autocompact(...)`（**前两层省下的 token 喂给 autocompact 阈值判断**，省下就不触发那次昂贵 LLM 总结）。`_autocompact` 取较旧段→调一次模型用固定「总结保留待办/已得结论/关键数据」prompt→用一条摘要消息替换那段，**保留最近若干轮原文 + 所有未配对 tool_use/tool_result**（配对完整性交 SH-1）。autocompact 默认仅自动/长任务开，交互式靠前两层。接入点：每轮开头把 `_microcompact(...)` 换成 `await _compact_pipeline(...)`，同步+流式两处都改。
- **验收**：短对话三层都不动；中等长度 snip+micro 折叠、autocompact 因阈值下降不触发；超长触发 autocompact、摘要替换且最近轮+未配对工具块保留；同步与流式两入口一致。
- **牵连风险**：autocompact 花 LLM（默认仅长任务开）；改历史结构最易造孤儿→**强依赖 SH-1 先就位**；autocompact 重建前缀破 cache，与 SH-9 协同（这是唯一允许重建前缀的点）。
- **优先级·批次**：P1 · 批次 6（依赖 SH-1/SH-9 就位后做）。

### SH-7 · 子 Agent = 工具，递归复用主循环（独立工具池/maxTurns/abort）— [ ]  ⏭️ 暂不做(鸡肋):当前短循环无多步子任务委派需求;等真有复杂编排再做
- **现状/问题（缺什么·带文件）**：`tools.py` 全是扁平单层工具，无「把子任务派给独立工具池+独立 maxTurns 的子循环」。重任务（读全部报表做季度对账、生成整月内容计划）的中间噪音全污染主对话上下文。
- **为什么（壳强在哪）**：CE「sub-agent architectures」+ SDK-Sub 明确列出收益——**context isolation**（子 Agent 跑在自己干净的对话里，中间工具调用与结果留在子内，只有最终消息回父）、tool restrictions（收窄 read-only 工具集）、specialized instructions。重任务可拆给子 Agent，子任务噪音不污染主线（既扛复杂又省主线 token）。
- **怎么做（Python 草图+改哪些文件+数据结构）**：新增 `server/services/agent/subagent.py`，`AGENT_DEFS: dict[str, AgentDef(system_prompt, allowed_tools, max_turns)]` 先硬编码 2-3 个（reconcile 对账周报、research 查历史汇总），后续升级成读 `prompts/agents/*.yaml`（复用 PromptEngine 宽松加载）。工具 `run_subagent({agent, task})`（**不标 deliverable**）handler 内：① `sub_registry = build_subregistry(default_registry, allowed_tools)` 且**显式排除 run_subagent 自身**（防无限递归）；② `sub_ctx = replace(ctx, call_counts={}, token_budget=None)`（独立防打转计数、不吃主预算）；③ 递归 `await run_agent_loop(task, sub_registry, sub_ctx, def.system_prompt, def.max_turns)`；④ 只回 `result.final_text` 不回 steps。`AgentContext` 加 `abort: asyncio.Event|None`，子循环每轮检查（主被中断连带停子）。**审批继承（比参考实现更收紧）**：子 Agent 工具池白名单**只放只读+本地文件类，不给花钱/对外工具**——花钱动作留主 Agent 走审批闸（纯 BYOK + 不自动触达铁律）。
- **验收**：子工具池不含 run_subagent（防递归）；子只回 final_text；子 call_counts 独立；子池不含花钱/对外工具；abort set 后子循环提前收。
- **牵连风险**：架构改动较大（故排后）；依赖 SH-6（子上下文压缩）；审批冒泡必须回主会话的人。
- **优先级·批次**：P2 · 批次 7（功能最强但最晚）。

### SH-8 · 审批 reason 结构化 + 连续拒绝自动回退 — [x]  ✅ 完成:审批卡结构化理由{what/why/impact}+连续拒绝自动回退(前端取消接/reject·确认后total复位),420绿
- **现状/问题（缺什么·带文件）**：`loop.py._auto_approve` 返回裸 `bool`，无「为什么要确认」的结构化 reason（前端只能干巴巴弹卡）；无「连续误触自动收紧权限」的安全网。
- **为什么（壳强在哪）**：SDK-Hooks 官方权限输出就是结构化的 `permissionDecision`（allow/ask/deny/defer）+`permissionDecisionReason`，且明确优先级 deny>ask>allow——审批卡能说清「为什么拦」更可用；连续误触自动收紧更稳。本项是把现有 force_confirm>permission_mode 瀑布**结构化**，不改判定结果，回归风险低。
- **怎么做（Python 草图+改哪些文件+数据结构）**：定义 `Decision(behavior: str, reason: str, source: str)` dataclass。`_auto_approve` 从返 bool 升级为返 `Decision`（source∈ force_confirm/mode_ask/mode_auto_files/mode_full，reason 是人话「这是花钱操作，跳过确认也强制问」），PreToolUse hook 的 deny 也包成 Decision。回灌文本与前端 `approval_request` 事件都带 reason/source（审批卡显示「为什么要你确认」）。`context.py` 加 `denials_consecutive`/`denials_total`：`api/v1/agent.py` 的 execute/reject 端点维护——拒绝则 +1，成功确认则 consecutive 归零；`_auto_approve` 开头短路 `if denials_consecutive>=3 or denials_total>=20: return Decision("ask", "你最近多次拒绝自动操作，已自动切回逐项确认")`（即便老板设了 auto_files/full 也临时强制 ask）。
- **验收**：force_confirm 工具任何模式都 deny（behavior+reason+source 正确）；连拒 3 次后 full 模式也变 ask；成功确认一次复位 consecutive；累计 20 次也触发回退。
- **牵连风险**：要 api 层配合维护拒绝计数并随会话持久化；硬红线 force_confirm 不受旋钮影响。
- **优先级·批次**：P2 · 批次 6（体验+信任）。

### SH-9 · prompt-cache 稳定性纪律（不就地改历史 / 稳定排序）— [x]  ✅ microcompact缓存纪律注释+排序稳定性审计+test_prompt_cache_discipline守门+耦合地图第9节
- **现状/问题（缺什么·带文件）**：`loop.py._microcompact` **就地改靠前的 tool 消息 content**（`messages[i]={**messages[i],"content":占位符}`）——这会破最长公共前缀、那一刻起后面全部 cache miss。无 lint/测试守门，后续改历史的代码易随手破前缀。
- **为什么（壳强在哪）**：PC 明确——缓存按 tools→system→messages 的前缀层级命中，「改前缀块在下次请求产生不同 hash」、改工具定义「invalidate 整个缓存」。BYOK 端点支持 prompt caching 时，前缀稳定=省钱省延迟。纪律=别零敲碎打反复改前缀，真要压缩就一次性重建并接受那次 miss。
- **怎么做（Python 草图+改哪些文件+数据结构）**：审计现有就地改历史点：① 给 `_microcompact` 加注释说明它**故意牺牲前缀换 token**，并把触发**对齐到压缩边界**（不是每轮都改）减少 miss 频率；② 确认 `approval.py._canonical` 与 anti-spin sig 已 `sort_keys=True`（现状已符合，加测试钉死）；③ `registry.to_openai_tools()` 工具顺序稳定（dict 插入序），SH-5 解锁工具追加末尾不插中间。新增 `server/tests/test_prompt_cache_discipline.py`：断言 `to_openai_tools()` 多次调用字节一致、`_canonical`/args 序列化键序稳定、「追加类操作不改 index<N 的消息」。写进 `CLAUDE.md`/`docs/耦合地图与改动检查清单.md`：「任何改 messages 靠前部分的代码，PR 必须回答：会不会破 cache 前缀？收益是否值这次 miss？」
- **验收**：工具数组序列化稳定；canonical 键序稳定；追加操作不动前缀（SH-6 的 autocompact 是**唯一**允许重建前缀的点）。
- **牵连风险**：无新模块，是约束已有代码+测试守门；主要风险是别在审计时反而改坏现有正确的 sort_keys 逻辑。
- **优先级·批次**：P1 · 批次 5（立约束，顺手审计 _microcompact，开发量主要是测试）。

### SH-10 · 配置驱动 hook 事件点扩展（SessionStart/UserPromptSubmit/PreCompact/SubagentStop）— [ ]  ⏭️ 暂不做(鸡肋):无外部配置化Hook需求,现有Hook三件够用
- **现状/问题（缺什么·带文件）**：`hooks.py` 只有 PreToolUse/PostToolUse/Stop 三件，且全是进程内 Python 回调；无 SessionStart（注入今日提醒）、UserPromptSubmit（输入合规预检/补门店上下文）、PreCompact（压缩前保关键信息）、SubagentStop（校验子任务产出）等事件点。
- **为什么（壳强在哪）**：SDK-Hooks 官方事件清单远不止三件——SessionStart/UserPromptSubmit/PreCompact/SubagentStop 等都是正式扩展点，且官方强调 hook 要 fail-safe（「catch errors inside your hook，未捕获异常会打断 agent」）。补事件点让壳能在「会话起手/收到输入/压缩前/子 Agent 收尾」做联动（如 SessionStart 接 `proactive.py` 今日运营提醒）。
- **怎么做（Python 草图+改哪些文件+数据结构）**：**克制版，不照搬 shell-out/command 协议（对桌面过重、安全面，⛔不收）**。保留现进程内回调，`hooks.py` 加 `run_session_start_hooks`/`run_user_prompt_submit_hooks`/`run_pre_compact_hooks`/`run_subagent_stop_hooks`，签名与现三件一致（故障安全、默认空零影响）。接入：SessionStart 接 `api/v1/agent.py` 起会话处（联动 proactive）、UserPromptSubmit 接进 `run_agent_loop` 前、PreCompact 接 SH-6 autocompact 前、SubagentStop 接 SH-7 子 Agent 收尾。可选新增 `hook_config.py` 从本地 JSON 读 `{事件:[{match:工具名glob, type:deny/builtin}]}` 转成进程内回调注册；`prompt` 型 hook 会花 BYOK 钱**默认禁用**，要老板显式开。
- **验收**：空配置零行为变化；match 不命中的工具不触发；deny 型能拦工具（reason 正确）；SessionStart hook 能注入消息；prompt 型默认不跑。
- **牵连风险**：现进程内回调已够用，属锦上添花（故 P3）；command/shell-out 型本期明确不做（桌面安全）。
- **优先级·批次**：P3 · 批次 7（有外部配置需求再上）。
