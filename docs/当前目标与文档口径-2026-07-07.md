# 当前目标与文档口径

> 状态:现行 · 最后核对 2026-07-09 · 适用范围:本仓库 `main`

## 1. 一句话目标

这个项目的第一性目标是做成一个 **coding 能力很强的桌面 AI Agent 外壳**。如果 coding agent 的底盘不强,上层的店铺问答、生图、真实素材剪辑、知识库和自动化都会变成不可靠的包装。

因此当前阶段所有实现和文档都围绕四条主线收敛:

1. **Coding agent 性能和可靠性优先**:工具检索、读写文件、patch、回滚、项目指令、压缩恢复、子代理、后台任务、provider failover、trace 可观测性都必须扎实。
2. **CC-Haha 可直接复制/抄/移植/改写,验收看能力完整度**:`~/Desktop/cc-haha-ref` 的 LICENSE 已允许 use/copy/modify/distribute/publish copies;本项目可以直接参考、移植、改写其内核代码和测试边界,复杂能力仍要用行为测试锁住同输入同决策,防止迁移遗漏或迁移失真。
3. **UI 走 Work Buddy/Codex 式低噪工具流**:主对话首屏克制,不要卡片墙、台球挂件、营销页;配色执行“走法 B”:砍蓝,绿只点缀,主按钮/用户气泡中性。
4. **生图/真实素材剪辑是插件式延伸能力**:它们挂在同一个 Agent 工作台和审批/任务框架上,跟随主 UI 配色与交互,不能另起一套产品皮肤;CD/Seedance 2.0 这类模型直接生成视频能力不再作为产品线保留;Python 能保留则保留,能 TS 化则以编译速度、运行速度、打包稳定性为准。

## 3. CC-Haha 抄用边界

- 允许且推荐:CC-Haha 内核、工具、测试边界、状态机、UI 参考实现都可以直接抄、移植、改写进本仓库;优先保证功能齐全、边界一致、测试通过。
- 应该:为复杂边界写测试,例如路径越界、工具调用配对、provider 降级、压缩恢复、文件改动实时预览;抄代码不是免测试,而是减少重复造轮子的失误。
- 区分:Work Buddy/Trae/Qoder 等闭源竞品只保留我们自己的分析、UI/交互/架构结论,不把它们的私有代码放进仓库。
- 发布口径:文档里统一明确“CC-Haha 可直接复制/抄/移植/改写”;旧阶段的防搬限制不再作为当前施工依据。

## 4. UI 与知识库口径

- 主窗口是工具流,不是营销首页。欢迎区只保留轻量起手动作;常态工作围绕输入框、状态线、工具步骤、右侧预览/画布。
- 专有知识库问答按来源分层:行业知识/领域包、店铺文件、门店记忆。默认是通用 coding Agent;用户在输入框挂载“台球运营专家”后,才把台球领域包上下文、推荐命令和专属工具带入本轮。店铺文件必须带来源和检索解释;资料库没有看到的事实要明确说没有看到。
- 文件修改要有流式可见性:工具开始、pending、完成 diff、失败态都要能在中间步骤和右侧预览里体现,不能等最终答复才暴露。
- 媒体工作台跟随主 UI token:中性主操作、绿色小点缀、紧凑面板,不加装饰性台球元素。

## 5. Main 分支口径

当前用户要求直接在 `main` 上改,不新建分支。历史文档里出现的 `ts-harness-rewrite`、`cc-haha-direct-port` 等分支名只代表当时施工记录,不再作为当前工作指令。

阶段性完成的标准不是“写了几个点”,而是:需求矩阵能解释没有遗漏,关键能力有测试或真机/浏览器验证,文档口径不会误导下一轮实现。

## 6. Python 退役口径

> **2026-07-09 owner 校准(材料性放宽)**:老 web/+Python app **还在开发阶段、没有真实用户依赖**,owner 明确"老 app 基本可以不用管、直接在改造范围内处理"。因此**"必须先保活老 app 再删"的约束解除**:退役不再以"旧栈持续可跑"为前提,而以"能力已在 TS 侧接住、或被明确判为弃用"为准。终态 = `ts/` 内核 + ts-desktop 前端做成真 app,`server/`(365 py)+ 老 `web/` 前端整体退役。**唯一不能"删了拉倒"的是仍要保留的产品能力**(§4 定的真实素材剪辑、生图、台球领域包)——这些要迁到 TS/native 或保留可迁移参考,不是直接抹掉功能;`ts/src/media/*` 目前是代理到 Python 媒体后端的,删 Python 前要么 TS/native 接住、要么显式记为"功能暂缺待重建"。

分批退役,按下面顺序;每批删除后立即提交 `main`、提交信息写清退役模块:

1. **立刻可删(无迁移前置)**:老 app 专属且不影响 TS 栈的东西——SaaS 登录鉴权残留、离线样例生成器、旧付费 eval、`server/tests/` 里只测将被删 Python 的用例、已被 TS 覆盖的桥接脚本、纯老 app 文档。
2. **接住后删**:TS 侧当前**代理/依赖**到 Python 的能力(媒体剪辑 `/video-edit/*`、生图 `/studio/*`、OCR、语音转写、RAG/店脑),要么在 TS/native 补真实现 + smoke 后删,要么 owner 拍板"暂缺待重建"再删。
3. **成栈切换**:把 desktop 主进程/打包入口从 `desktop/src/backend.js` 拉起 Python,切成拉起 `ts/` Bun 后端 + ts-desktop 前端;切完老 `server/` + 老 `web/` 整体退役。这是"删 Python"的真正主体工程,单独成阶段做。

原"四条件 + 三批风险"口径(以"旧栈持续可跑"为前提)因老 app 可弃而作废,以上为现行。
