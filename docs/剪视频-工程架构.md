> 📌 状态:✅现行 · 最后核对 2026-07-12
>
> **这是剪视频板块唯一的架构文档**,取代以下 4 份已删除的旧文档(内容已消化进本文,git 历史可回查):`生图与剪视频工作台-设计方案.md`(剪视频部分,生图部分已拆分保留)、`剪视频Agent逻辑-设计-2026-07-11.md`、`视频剪辑-落地状态核查与做齐方案-2026-07-11.md`、`video-use-剪辑编排适配研判-2026-07-09.md`。
>
> **一句话结论**:剪视频不是"Agent 自己剪"或"工作台手动剪"二选一,是接力棒——但接力棒在哪交,按口播/环境两种内容类型反着来。渲染引擎用 ffmpeg 原生管线,不用 Remotion。音乐靠 AI 现场生成保证每条视频不一样,不靠固定曲库。

## 一、三种架构方案(选一个,推荐 B)

三种方案的区别就是一件事:**Agent 该管多少、工作台该管多少**。

### 方案 A · 重工作台,轻 Agent

Agent 只把素材粗粗归拢(哪些是口播、哪些是环境镜头,大致排个顺序),**几乎所有创意判断——留哪段、配什么音乐、加什么转场——都交给用户在工作台里手动决定**。

- 优点:质量最稳、最可控,不存在"AI 瞎剪"的风险。
- 缺点:门店老板不太可能有耐心从头手动剪一条视频,效率最低,"AI 帮我干活"这个卖点基本体现不出来。
- 适合:如果判断门店客户是"完全不会剪辑、宁愿自己一点点调也不太敢信 AI"的保守型用户,选这个。

### 方案 B · 按内容类型分层(推荐,本轮反复验证过)

- **口播视频**:Agent 主导——听转写内容、判断留哪句剪哪句、写字幕、按视频风格生成配乐,出一版完整草稿;工作台只做局部微调(挪个别时间点、改几个字幕用词)。
- **环境 / 氛围视频**:反过来,Agent 只出一版"毛坯"(切好镜头、粗排个顺序),真正决定好不好看、卡点带不带感的,交给用户在工作台里精修。

**为什么这么分**:口播剪得好不好 = 听没听懂意思,这是语言理解活,AI 强项;环境剪得好不好 = 画面好不好看、卡点带不带感,这是没有标准答案的纯审美活,AI 现在还不靠谱——2026 年视频剪辑行业共识和学术评测(AgenticVBench)都认为这类判断该由人工把关,不该让 AI 独立拍板。

- 优点:两种内容各自发挥所长,质量和效率都不用牺牲。
- 缺点:需要先把"口播 vs 环境"分类判断准——项目里已经有一个基于 VAD(判断有没有人声)的自动分流器,这块地基已经打好,风险不大。

### 方案 C · 重 Agent,轻工作台

连环境视频也主要让 Agent 自动判断、自动配乐、自动加转场,工作台只在出片前扫一眼、微调收尾。

- 优点:门店老板最省心,几乎不用动手。
- 缺点:环境视频这块质量没保障——AgenticVBench 明确说"审美判断类任务不该完全交给 AI 独立做主",真放开可能剪得不好看、卡点不准,门店发出去的宣传视频砸自己招牌。
- 适合:只有判断"门店客户完全没精力做任何微调,宁可牺牲一点质量换全自动"时才选,不然不推荐。

**推荐方案 B。** 这个结论经过三轮独立验证——项目早期设计文档的方向、2026 年视频剪辑行业共识、AgenticVBench 学术评测——都指向同一个答案,不是一次性拍脑袋。

## 二、已经确定的技术选型(不用再讨论)

### 2.1 渲染引擎:ffmpeg 原生管线,不用 Remotion

- Remotion 自己的渲染方式实测"比实时还慢"——2 分钟 1080p 视频在消费级 CPU 上渲染要 15 分钟以上,因为它靠无头浏览器逐帧"录屏"生成,不是直接编码。
- Remotion 定位的主场景是"用同一个模板批量生成成百上千个数据驱动的变体视频",不是"剪用户实拍的真实素材"——门店要剪的是自己拍的口播/环境视频,跟 Remotion 的主场景不是一回事。
- Remotion 应对"渲染慢"的官方方案(Remotion Lambda)是把渲染丢到 AWS 云端并行跑,这是给"云端 SaaS 批量出片"设计的伸缩方案,跟这个项目"全本地、每家店在自己电脑上跑"的架构原则完全对不上。

**结论:ffmpeg 原生管线继续用,这本来就是对的选型,不是"没来得及升级"。**

Remotion 剩下站得住脚的两个小角色(跟"当渲染引擎"这件事分开算,规模都很小):
1. 生成几秒钟的动画叠加素材(片头 LOGO 动效这种)——video-use 自己也只是把它当可选引擎之一用,不是主渲染管线。
2. 工作台预览播放器(纯浏览器实时播放,不涉及导出编码)——查过许可证,团队规模 ≤3 人完全免费,可以留着以后评估,不急。

### 2.2 音乐怎么做到每条视频不一样

**现状核实**:项目现在**完全没有曲库或音乐选择机制**——`set_music` 原子操作只是"挂一个用户指定的文件",`beatSync.ts` 只负责分析一段已给定音乐的卡点在哪,没有任何"自动挑音乐"的逻辑。

**推荐方案:AI 现场生成音乐为主 + 免费曲库兜底**

- **主力**:用 AI 音乐生成(候选 MiniMax Music,约 $0.03~0.035/次生成,已确认支持商用)——拿视频自己的风格标签拼成一句生成提示词,现场生成一段独一无二的配乐:
  - 环境视频:用已有的 VLM 镜头打标结果("燃"/"氛围"这类)拼提示词,比如"轻快、台球厅热闹夜场氛围、90bpm 电子鼓点"。
  - 口播视频:拼"轻音乐、不抢镜"的描述,比如"舒缓轻音乐、钢琴+弦乐、60bpm、背景衬底",配合已有的闪避混音(人声出现自动压低配乐音量)。
  - 因为是现场生成,结构上就保证了每条视频音乐都不一样,不存在"曲库用完了""好几家店撞同一首歌"的风险。
- **为什么不直接接现成曲库**(Epidemic Sound / Artlist / Soundstripe 这类):这些曲库的授权模式是"每个创作者/公司自己订阅",不是设计给"一个软件产品分发给几千家门店各自商用"这种场景的,授权说不清楚。
- **兜底**:内置一小撮 Pixabay Music 这类真正零成本、免署名的公共免费曲目,作为"生成服务万一断网/超预算"时的降级方案,呼应项目自己"资产未就绪时优雅降级、绝不点了没反应"的原则。
- ⚠️ **诚实待办**:MiniMax/FAL 的完整服务条款(尤其"生成结果版权归属"这条)现在只核实了"支持商用"这个大方向,逐字条款还没读过,正式接入前必须确认清楚。

### 2.3 转场/特效怎么做到每条不一样

这跟音乐是两个不同性质的问题:**音乐"多样化"要解决"内容本身要变",得靠外部生成服务;转场/特效"多样化"要解决的是"选哪种效果",不用花钱接新服务**——ffmpeg 自带几十种转场类型(交叉溶解/擦除/滑动/圆形扩散/像素化等等),完全免费。真正缺的是"决策逻辑":根据这条视频的节奏/氛围标签,从这几十种里自动挑一种合适的——快节奏氛围片配硬切或快速擦除,慢节奏氛围片配交叉溶解,口播视频基本不用花哨转场(怕分散注意力)。

## 四、需要 owner 拍板的开放问题

1. **出片后自检闭环**要不要做、什么时候做?(video-use 有这个能力,项目现在没有)
2. **工作台预览要不要真的换成 Remotion Player**(团队 ≤3 人免费,但要接入新依赖、重写前端预览层)——现有自建方案(Range 播放 + DOM 字幕层)后端已就绪,换不换?
3. **转写要不要从本地 whisper 换成 ElevenLabs Scribe**(带说话人识别+音频事件标注,但要花钱联网)?
4. **音乐生成具体用哪家**(MiniMax Music vs ElevenLabs Music vs 别的)——需要先把 FAL 完整服务条款读一遍再定,尤其版权归属那条。
5. **优先级排序**:工作台 `/ops` 前端接入(当前最高杠杆) vs B-roll VLM 真机验证(判断"够不够燃"准不准还没测过) vs 音乐生成接入 vs 自检闭环 vs 转场——这几件事谁先谁后?

## 五、参考:与 browser-use/video-use 的方法论对照

video-use(MIT 协议,`github.com/browser-use/video-use`)的管线是 **转写 → 打包摘要 → LLM 剪辑判断 → EDL → 渲染 → 自检**,核心信条"音频优先、画面跟随"。逐条对照本项目现状:

| video-use 方法 | 本项目现状 | 结论 |
|---|---|---|
| 时间线文档为真相源 + 原子操作(EDL 骨架) | ✅已有,`TimelineDoc` + `applyOperations` + 回滚,同构实现 | 已吸收,继续用 |
| transcript-first(词级转写驱动剪辑) | ✅已有,`transcribe.ts` 词级转写已接线(早期一度是占位,现已补齐) | 已吸收 |
| 30ms 音频淡入淡出防爆音 | ✅已有 | 已吸收 |
| 出片前结构校验(`validateDoc`) | ✅已有 | 已吸收(这是 self-eval 的"前置一半") |
| **出片后自检**(抽帧查跳变/爆音/字幕遮挡,自动重剪) | 🔴没有 | **未吸收,本轮发现的新缺口,见第四节问题1** |
| 不切断单词(词边界剪口播) | 部分——依赖词级转写,转写已就绪,吸附逻辑待做 | 待补 |
| 30-200ms 切段 padding | 未明确核实 | 待补 |
| 项目记忆(`project.md` 类,跨会话记住剪辑偏好) | 部分——时间线本身持久化了,但不存"编辑决策/偏好"这层 | 待补,优先级不高 |
| 动画叠加(HyperFrames/Remotion/Manim/PIL 任选) | 未采用 | 不紧急,门店视频暂无这类需求 |

**与红线的边界**:video-use 全程是"真实素材剪辑",不涉及文生视频/图生视频,吸收它的任何方法都不会带回生成视频能力,不触碰项目"删除 AI 生成视频"的方向。
