## 一、总体判断

这个项目不是“空壳 Demo”。从当前代码看，用户注册登录、门店资料、AI 内容生成、岗位工作台、海报合成、生成历史、今日工作台这些 MVP 主链路已经搭起来了，前端生产构建也能通过。

但如果按最终产品形态来看，也就是“给真实台球房老板/店长/员工试用的 AI 运营工作台”，现在还不能直接放心上线。主要问题不是页面打不开，而是：

1. 生产部署有几个容易直接踩坑的配置问题。
2. 门店运营画像完整度计算和前端表单字段不一致，会导致用户明明填完了，系统仍提示资料不完整。
3. 今日工作台的“推荐动作”没有真正带参跳转，推荐和生成动作之间断了一截。
4. 时间统计使用 UTC，不符合中国门店“今天/周几”的业务语义。
5. 上传、AI 调用、错误处理、测试覆盖还不足，真实试用时会暴露稳定性问题。

我的结论：**代码基础可继续推进，适合内测前修一轮关键问题；不建议作为生产 SaaS 直接开放给外部客户。**

## 三、高优先级问题

### 1. 生产同域部署时，前端 API 地址会错误回退到 localhost

位置：`web/src/lib/api.ts:13`

```ts
const BASE_URL = process.env.NEXT_PUBLIC_API_URL || "http://localhost:8000";
```

部署文档写的是：生产同域反向代理时 `NEXT_PUBLIC_API_URL=` 可以留空，让前端访问 `/api`。但当前代码用 `||`，空字符串会被当成 false，然后回退成 `http://localhost:8000`。  

结果是：如果用户浏览器访问你的正式域名，前端会尝试请求用户自己电脑上的 `localhost:8000`，真实生产环境直接不可用。

建议：

- 区分“未设置”和“显式设置为空”。
- 或生产环境明确设置 `NEXT_PUBLIC_API_URL` 为后端完整域名。
- 如果要支持同域代理，应该允许 `BASE_URL=""`，让请求走相对路径。

---

### 2. AI 运营画像完整度字段与前端表单不匹配，用户填满也可能达不到 70%

位置：

- `web/src/app/dashboard/store-settings/page.tsx:153-188`
- `server/services/store_profile_service.py:326-428`

前端保存的画像字段包括：

- `positioning`
- `business_district`
- `current_goals`
- `main_customer_types`
- 私域群勾选
- 助教类型
- 是否有周赛
- 是否做团购
- 朋友圈语气
- 禁用表达
- 桌型

但后端完整度计算还要求很多前端根本没有输入入口的字段，例如：

- `basic.main_selling_points`
- `business_goals.monthly_focus`
- `assistant_system.assistant_booking_rule`
- `events.has_light_competition`
- `events.has_partner_group`
- `commerce_rules.has_membership`
- `content_style.private_chat_tone`
- `content_style.group_notice_tone`

这会导致一个很糟糕的产品体验：老板认真把页面上能填的都填了，系统仍然可能显示画像不够完整、持续提示“建议补充”，但页面上没有地方补。

按当前字段粗算，即使前端能填项全部填满，画像总体分数也很容易卡在 70% 以下。这个问题会直接影响岗位工作台的信任感。

建议：

- 要么后端完整度只计算前端真的能填写的字段。
- 要么前端补齐这些字段。
- 内测前至少先把不可填写字段从评分和 `suggested_modules` 中剔除。

### 3. 今日工作台推荐没有真正带参数进入生成页

位置：

- 后端生成推荐参数：`server/services/dashboard_service.py:215-257`
- 前端只使用链接：`web/src/app/dashboard/page.tsx:237-239`

后端推荐里已经给了 `suggested_payload`，例如“发一条朋友圈文案”会带：

```python
{
  "sub_type": "moments",
  "tone": "friendly",
  "scenario": "daily",
  "extra_note": "工作日，下班后适合约朋友来打球",
}
```

但前端渲染按钮时只跳到：

```tsx
<Link href={rec.action_url}>
```

生成页也没有解析这些 `suggested_payload`。所以用户点击“去生成朋友圈”，只会进入默认生成页，不会自动选中朋友圈、场景、语气或补充说明。

这会让“今日推荐”从一个可执行工作台退化成普通导航入口，和产品最终形态不匹配。

建议：

- 把 `suggested_payload` 编码到 URL query。
- 或在前端点击时写入状态，再跳转生成页。
- 生成页补齐对 dashboard 推荐参数的解析。

### 4. 今日统计和周几推荐使用 UTC，不符合中国门店营业语义

位置：`server/services/dashboard_service.py:41-52`

代码使用：

```python
now = datetime.now(timezone.utc)
today_start = now.replace(hour=0, minute=0, second=0, microsecond=0)
weekday = WEEKDAY_NAMES[now.weekday()]
```

项目面向国内台球房，用户当前也在中国时区。用 UTC 会导致每天 00:00-07:59 之间，中国本地已经是新的一天，但系统仍按 UTC 前一天统计和推荐。

实际影响：

- “今日生成”统计错位。
- “今天还没生成内容”的提醒可能错误。
- 周五/周末推荐在早上时段可能显示前一天逻辑。

建议：

- 业务日使用 `Asia/Shanghai`。
- 查询数据库时，把上海时区的当天起止时间转换为 UTC 再过滤。

### 5. 门店资料无法可靠清空或关闭旧信息

位置：

- 前端过滤空值：`web/src/app/dashboard/store-settings/page.tsx:191-208`
- 后端跳过 `None`：`server/services/store_service.py:105-110`

前端 `formDataToUpdate` 会跳过空字符串和 `false`：

```ts
if (value !== "" && value !== false) {
  ...
}
```

后端也只在 `value is not None` 时更新。结果是：

- 用户不能把旧电话、旧地址、旧价格、旧会员卡内容清空。
- 用户把“有陪练/有比赛/有停车”等开关从 true 改成 false 时，前端不会提交 false，后端保持旧值。
- AI Prompt 会继续注入过时信息，生成内容可能写出已经不应该出现的价格、服务或联系方式。

这对“不要编造门店信息”的产品原则影响很大，因为系统自己会保留过期信息。

建议：

- 前端更新时提交完整表单，而不是只提交非空字段。
- 后端允许显式传 `null` 或空字符串来清空字段。
- 布尔字段必须允许 true/false 双向更新。

## 四、中优先级问题

### 6. DeepSeek 调用错误没有业务化处理

位置：`server/services/ai/providers/deepseek.py:25-43`

模型调用失败、Key 缺失、限流、超时等异常会一路抛到全局异常处理，最终返回“服务器内部错误”。前端会统一显示“AI 生成失败”，但后端没有区分：

- 未配置 API Key
- 模型服务超时
- DeepSeek 限流
- 余额不足
- 请求参数过长

建议：为 AI Provider 增加明确的 `AIProviderException`，记录原始错误，返回可操作的用户提示。

---

### 7. 上传文件只校验扩展名，不校验真实图片内容

位置：`server/services/storage_service.py:32-53`

当前逻辑只做：

- 文件大小 <= 2MB
- 后缀是 `.jpg/.jpeg/.png/.gif`

但没有校验 MIME、没有用 Pillow 打开验证、没有去除 EXIF，也允许 GIF。  

真实 SaaS 中，Logo 和二维码会被公开静态服务访问，建议至少用 Pillow 验证文件确实是图片，并统一转成 PNG/JPEG。

---

### 8. 上传目录整体公开静态挂载，缺少访问边界

位置：`server/main.py:49-56`

当前 `/uploads` 直接作为静态目录公开，包括：

- Logo
- 二维码
- 生成海报

海报分享链接公开可以接受，但 Logo 和二维码是否也完全公开，需要产品层确认。更关键的是：未来一旦上传目录里出现非公开文件，这个挂载方式会天然绕过 `store_id` 鉴权。

建议：

- 至少分清公开资源和私有资源。
- 海报可公开，门店资料类图片按需公开。
- 后续切 OSS 时用不同 bucket/path 或签名 URL 策略。

---

### 9. 海报中文字体依赖系统环境，Linux 部署有风险

位置：`server/services/poster/composer.py:12-49`

代码优先找 macOS 字体，也列了一些 Linux Noto 字体路径。但项目没有随包提供字体，也没有 Dockerfile/部署脚本保证服务器安装中文字体。  

如果服务器没有 Noto CJK，Pillow 会回退默认字体，中文可能显示为方块。

建议：

- 项目内置一套可商用中文字体。
- `_find_font_path()` 优先找 `server/assets/fonts/`。
- 部署脚本安装 `fonts-noto-cjk`。

---

### 10. 海报模板布局比较静态，长门店名/地址/电话可能溢出或挤压二维码区

位置：`server/services/poster/templates.py:44-120`

模板固定坐标，文字只按宽度截断，不按整体版面重新排布。地址、电话、长店名、较长活动正文同时存在时，底部信息和二维码区域可能观感不稳定。

建议：

- 增加海报视觉回归测试，生成长文本样例后检查。
- 对店名、地址、电话分别设置更严格的行数和缩略策略。
- 必要时根据二维码是否存在切换底部布局。

---

### 11. 生产安全配置没有启动时强校验

位置：`server/config.py:6-37`

默认值包括：

- `postgres_password = "postgres"`
- `secret_key = "change-me-to-a-random-string"`
- `cors_origins = "http://localhost:3000,http://localhost:3001"`

`.env.example` 有提醒，但代码不会阻止生产环境使用默认值。

建议：增加 `APP_ENV=production` 时的启动校验，默认密钥、默认数据库密码、localhost CORS 直接拒绝启动。

## 五、低优先级问题和工程整理建议

1. `web/src/app/dashboard/generate/page.tsx` 过大，生成页把多个 Tab 的表单、状态和结果展示都堆在一起，后续维护成本会升高。
2. `web/src/lib/role-workbench-config.ts` 任务卡片配置很长，可以按岗位拆分。
3. `server/services/store_profile_service.py` 同时负责画像渲染、完整度、缺失建议，建议拆成 `renderer/completeness/suggestions`。
4. 前端文档说使用 `react-hook-form + zod`，但 `web/package.json` 里没有这两个依赖，实际表单是手写 state 校验。当前能跑，但和规范不一致。
5. `content_service.py` 中去除“好的，店长”等前缀是硬编码补丁，不是大问题，但最好通过 Prompt 约束和输出后处理统一解决。

## 六、和既有两份报告的对比

我阅读了桌面上的：

- `球房AI运营助手_代码问题与Bug分析报告.md`
- `球房AI运营助手_代码与文档匹配度分析报告.md`

### 我同意它们的部分

1. 海报中文字体是部署风险。
2. DeepSeek 错误处理不够。
3. JWT 默认密钥需要生产强校验。
4. 当前缺少标准测试覆盖。
5. 生成页、岗位配置、画像服务文件偏大。
6. SSE、OSS、AI 图片、配额属于 P2 功能，当前没有实现。

### 我认为它们说得不够准确的部分

1. **CORS 不是“允许所有来源”**。当前代码没有 `*`，而是默认允许 localhost。问题在于生产忘改会有风险，不是已经全开放。
2. **usage_quotas、ImageProvider、SSE 不应当算当前 bug**。你的 P0 限制里明确写了 P0 不做这些，所以它们是后续规划项，不是本轮上线阻断。
3. **Prompt scripts/community 目录缺失不一定是问题**。产品已经演进到岗位工作台和统一生成入口，员工话术、社群内容通过 workbench 承载是合理的。
4. **prefixes_to_strip 硬编码不该列为高优先级**。它影响输出观感，但不是部署前必须修的核心 bug。

### 我的新增发现

相比既有报告，我新增并认为更关键的问题是：

1. `NEXT_PUBLIC_API_URL=` 生产同域代理会被 `||` 回退到 localhost，可能导致正式站点前端完全连不上后端。
2. AI 运营画像完整度计算要求了前端没有入口填写的字段，用户填完也可能达不到 70%。
3. 今日工作台推荐的 `suggested_payload` 没有被前端使用，推荐无法一键带入生成页。
4. 今日统计和周几推荐使用 UTC，不符合中国台球房的“今天”。
5. 门店资料更新无法清空旧字段，也无法可靠把布尔项从 true 改回 false，会污染后续 AI 生成。
6. 上传文件只按扩展名校验，真实 SaaS 安全性不足。

整体上，既有两份报告更偏“架构是否匹配文档”和“通用代码风险”；我这份更偏“真实台球房老板/店长试用时，哪些地方会让产品体验变坏或数据变脏”。

## 八、最终评价

这个项目已经具备一个“台球房 AI 运营助手”的产品雏形，而且岗位工作台、门店画像、Prompt 规则库这些方向是对的。它的问题不在于方向错，而在于几处产品闭环还没接紧：资料完整度、今日推荐、时间语义、生产 API 地址、旧资料清理。

把这些修掉后，它会从“能演示”明显迈向“能给真实门店内测”。
