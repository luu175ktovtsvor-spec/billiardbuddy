> 适用项目：球房 AI 运营助手  
> 当前项目阶段：10I-1 已完成，准备真实球房录音 / 观察 / 内测  
> 目标：把“产品经理4.0”的方法论，转成适合本项目的 AI 编程协作流程

---

## 1. 这份文档解决什么问题？

这份文档不是让我们照搬别人的“产品经理4.0”配置，而是把里面有价值的流程，翻译成适合“球房 AI 运营助手”的项目协作规则。

你现在这个项目已经不是一个普通代码项目，而是：

```text
行业知识 + 产品设计 + Prompt 规则 + 前端页面 + 后端接口 + AI 生成质量测试 + 真实球房观察反馈
```

混在一起的复杂项目。

所以后面不能继续靠“想到什么就让执行模型改什么”，必须有更稳定的流程。

这份文档的目标是：

1. 明确 ChatGPT / Codex / VSCode-DeepSeek / 产品内 DeepSeek 的分工。
2. 把每类任务拆成固定流程。
3. 避免执行模型失忆、乱改、跳过测试。
4. 把真实球房反馈沉淀成可复用的项目规则。
5. 后续逐步形成属于本项目自己的“AI 编程协作系统”。

## 2. 从产品经理4.0资料里提炼出的核心方法

### 2.1 三层架构

产品经理4.0的核心结构是：

```text
顶层规则
↓
技能体系
↓
进化系统
```

迁移到本项目，可以理解为：

```text
项目总规则
↓
任务流程模板
↓
反馈沉淀与规则升级机制
```

### 2.2 八个 Skill

资料里提到的八个 skill 是：

1. Product Spec Builder：需求收集
2. Design Brief Builder：设计规范
3. Design Maker：设计图
4. Dev Planner：开发计划
5. Dev Builder：写代码
6. Bug Fixer：修 bug
7. Code Reviewer：代码审查
8. Release Builder：构建发布

迁移到本项目，不一定要真的搭一套 `.cloud/skills`，但我们要把这八类能力变成任务流程。

### 2.3 四个 Sub-agent

资料里提到四类执行角色：

1. Implementer：实现
2. Code Reviewer：审查
3. Feedback Observer：记录反馈
4. Evolution Runner：扫描反馈，生成进化建议

迁移到本项目，可以变成：

```text
ChatGPT：产品大脑 / 审查人 / 任务设计者
Codex：主要执行智能体 / 浏览器验证者
VSCode-ClaudeCode-DeepSeek：备用或当前稳定执行模型
产品内 DeepSeek API：内容生成与真实调用测试模型
```

### 2.4 Hook 机制

资料里提到的 Hook 机制很有价值，例如：

- commit 前自动编译检查
- agent 停止前检查是否做过 code review
- 自动检测用户反馈信号
- 反馈达到阈值后升级成正式规则

迁移到本项目，不一定马上做技术 Hook，但可以先做“流程 Hook”。

比如：

```text
任何代码修改任务完成前，必须跑检查。
任何前端 UI 修改任务完成前，必须浏览器验证。
任何 Prompt / 样例 / 反例修改任务完成前，必须跑小样本真实调用。
任何真实球房反馈，不允许直接改项目，必须先进 10I-2 分析。
```

### 2.5 不猜测原则

资料里对 Bug Fixer 的描述非常适合本项目：

```text
先收集证据
再分析模式
再提出假设并验证
最后实施修复
一次只改一个地方
改完要回归验证
```

这条要成为本项目固定规则。

尤其是前端问题、模型输出问题、真实球房反馈问题，不能看到一个现象就直接下结论。

## 4. 建议建立本项目自己的“五类任务流程”

后续不要所有任务都用一个模板。应该按任务类型分流程。

---

### 4.1 需求 / 行业资料分析流程

适用场景：

- 真实球房录音转写回来
- 店长 / 助教管理 / 前厅 / 教练反馈回来
- 用户提出新的行业规则
- 用户发现某个真实场景没覆盖

流程：

```text
用户上传资料
↓
ChatGPT 阅读完整资料
↓
按角色拆分
↓
按场景拆分
↓
按事实 / 观点 / 推断 / 单店习惯分类
↓
判断产品价值
↓
判断影响层级
↓
输出 10I-2 分析报告
↓
用户筛 P0
↓
ChatGPT 写执行任务 MD
```

注意：

```text
这类任务不要直接交给 Codex 或 VSCode-DeepSeek 改项目。
```

原因：这里需要行业理解和产品判断，不能让执行模型拿着原始录音乱改。

---

### 4.2 产品 / UI 设计流程

适用场景：

- 新增页面
- 大改页面结构
- 新增岗位工作台模块
- 修改门店资料填写流程
- 调整 AI 工作台交互
- 用户反馈“看不懂 / 不好点 / 太复杂”

流程：

```text
先写产品需求说明
↓
再写页面结构 / 交互说明
↓
必要时补设计稿或页面草图
↓
再交给 Codex / VSCode-DeepSeek 编码
↓
编码后必须浏览器验证
```

当前项目过去很多 UI 是直接编码出来的，后面如果真实球房反馈证明页面需要大改，不能再直接改代码，必须先有页面说明。

---

### 4.3 编码实现流程

适用场景：

- 前端新增组件
- 后端新增接口
- 数据库 migration
- 类型字段调整
- 页面跳转链路修复

流程：

```text
ChatGPT 写任务 MD
↓
执行模型阅读任务 MD 和相关报告
↓
执行修改
↓
跑检查
↓
生成报告 MD
↓
用户回传 ChatGPT 审查
```

必须包含：

```text
修改了哪些文件
是否改后端
是否改数据库
是否改 YAML
是否调用产品内 DeepSeek API
tsc / lint / build / pytest 结果
是否影响旧功能
是否建议进入下一步
```

---

### 4.4 Bug 修复流程

适用场景：

- 前端白屏
- 跳转参数没生效
- 端口混乱
- 后端 500
- migration 报错
- 模型输出异常

固定流程：

```text
收集证据
↓
复现问题
↓
定位原因
↓
只改最小范围
↓
验证修复
↓
回归旧功能
↓
生成报告
```

禁止：

```text
看到报错就盲改
一次改很多地方
没有复现就说修好了
没有浏览器验证就说 UI 问题通过
```

如果用 Codex，Bug 修复任务必须要求它：

```text
启动前后端
打开浏览器
实际点击
保存截图或记录页面状态
```

---

### 4.5 测试 / 回归流程

适用场景：

- Prompt 修改
- 样例库 / 反例库修改
- 新岗位卡片上线
- 门店画像字段修改
- AI 生成质量验证

流程：

```text
小样本测试
↓
发现问题
↓
小修复
↓
小回归
↓
中样本测试
↓
必要时大样本测试
```

项目里已经形成过这个节奏：

```text
30 条小样本
72 条六岗位回归
必要时 120 条大样本
```

后续继续保持。

## 6. ChatGPT / Codex / VSCode-DeepSeek / 产品内 DeepSeek 的分工

### 6.1 ChatGPT

定位：

```text
项目大脑 / 产品判断 / 行业理解 / 任务设计 / 报告审查
```

负责：

- 真实资料理解
- 角色 / 岗位 / 场景拆解
- 产品价值判断
- 全链路影响面评估
- 任务 MD 编写
- 报告审查
- 下一步决策

不负责：

- 直接操作用户电脑
- 直接长期跑本地前后端
- 直接替代执行模型做全部代码修改

---

### 6.2 Codex

定位：

```text
强执行智能体 / 代码工程师 / 浏览器验证员
```

适合：

- 读项目
- 改代码
- 写文档
- 跑命令
- 启动前后端
- 打开浏览器
- 点击页面
- 截图验证
- 生成报告

要求：

```text
Codex 不需要也不应该套娃调用 VSCode 里的 DeepSeek 执行模型。
```

Codex 如果执行任务，应直接在项目中完成。

---

### 6.3 VSCode / Claude Code 接 DeepSeek 执行模型

定位：

```text
当前熟悉的执行链路 / Codex 额度不足时的备用执行模型
```

适合：

- 执行 ChatGPT 写好的任务 MD
- 改代码
- 跑检查
- 写报告
- 处理较长文档任务

当前录音回来后的第一轮处理，用户计划优先使用这个链路，因为 Codex / CodeLX 额度暂时可能不足。

---

### 6.4 产品内 DeepSeek API

定位：

```text
项目后端调用的 AI 生成模型
```

负责：

- 朋友圈
- 群公告
- 私聊话术
- 简报
- Workbench 生成
- 真实调用测试

注意：

```text
产品内 DeepSeek API ≠ VSCode / Claude Code 接的 DeepSeek 执行模型
```

这两个必须区分。

## 7. 后续建议加入的“流程 Hook”

现在可以先用文档规则，不一定马上做技术 Hook。

### 7.1 任务开始 Hook

每个任务开始前必须确认：

```text
是否读了任务 MD？
是否读了相关报告？
是否知道当前阶段？
是否知道允许改什么、不允许改什么？
```

### 7.2 代码修改完成 Hook

只要改代码，必须检查：

```text
修改文件列表
tsc / lint / build
后端测试
是否影响旧功能
是否生成报告
```

### 7.3 前端 UI Hook

只要改前端页面，必须检查：

```text
页面能打开
按钮能点击
表单能填
跳转参数正确
旧页面不受影响
必要时截图
```

### 7.4 Prompt / 样例 / 反例 Hook

只要改 Prompt、样例库、反例库，必须检查：

```text
YAML 语法
PromptEngine 加载
小样本真实调用
风险表达
few-shot 是否带偏
```

### 7.5 真实球房反馈 Hook

只要出现真实球房新信息，必须检查：

```text
这是事实、观点、推断，还是单店习惯？
是否影响产品大脑？
是否影响门店画像字段？
是否影响岗位卡片？
是否影响 Prompt？
是否影响样例 / 反例 / 测试？
```

## 8. 反馈沉淀与进化机制

产品经理4.0里有一个很重要的点：同类反馈多次出现后，应该升级成正式规则。

迁移到本项目，可以这样做：

### 8.1 反馈记录

每次出现以下情况，都要记录：

- 用户提醒过 ChatGPT 的流程问题
- 执行模型漏读报告
- 没有任务 MD 就执行
- 没有测试就说完成
- 前端没有浏览器验证
- Prompt 改了但没有真实调用测试
- 真实球房反馈中反复出现的新场景

### 8.2 反馈升级

如果同类问题出现 3 次，就升级成正式项目规则。

比如：

```text
如果“没有 MD 就执行”出现 3 次，
则升级为：
任何正式任务必须先生成任务 MD。
```

再比如：

```text
如果“前端任务没浏览器验证”出现 3 次，
则升级为：
所有前端 UI 任务必须浏览器验证并截图。
```

## 9. 对当前项目的具体建议

### 9.1 现在不要急着搭完整 skill/agent 系统

当前阶段不建议马上花时间建立复杂 `.cloud/skills/agents` 系统。

原因：

```text
你马上要去真实球房录音，当前最大缺口是真实资料，不是流程工具。
```

现在最重要的是：

```text
先去球房
拿资料
回来做 10I-2 分析
```

### 9.2 但可以先吸收它的流程思想

也就是：

```text
先文档
再执行
先分析
再修改
先小样本
再大回归
先证据
再修复
反馈多了再升级规则
```

这些马上就能用。

### 9.3 真实球房回来后再决定是否建设流程系统

等你回来后，如果资料量大、迭代变复杂，再考虑做：

```text
docs/process/
反馈索引
项目规则库
Codex 任务模板
真实资料分析模板
```

## 10. 真实球房资料回来后的升级版流程


## 13. 总结

产品经理4.0这套东西，对本项目最有价值的不是“照抄配置”，而是提醒我们：

```text
AI 编程不能只靠一句自然语言指令。
复杂项目必须有规则、有流程、有反馈沉淀、有验证闭环。
```

球房 AI 运营助手已经进入真实行业校准阶段，后面最重要的是：

```text
真实资料先分析
影响面先评估
任务再拆分
执行再交给模型
结果再测试
报告再审查
反馈再沉淀
```

这样项目才不会因为真实球房资料回来后信息量太大而乱掉。
