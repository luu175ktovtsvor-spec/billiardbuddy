## 3. 当前门店资料现状判断

### 优势

- Store 模型已有 JSONB 使用先例（`pricing`, `member_cards`），团队对 JSONB 操作熟悉
- `update_store()` 使用通用 `setattr` 模式，兼容 JSONB 字段
- PromptEngine 的 extra_vars 机制可以灵活传递新字段
- 前端 store-settings 页面框架已就绪

### 劣势

- 当前 20 个字段中仅 ~10 个实际用于 Prompt，大量字段未使用（district, has_private_room, has_parking, common_activities）
- `has_coaching` 只能表达"有没有"，无法表达"什么类型""怎么推""什么风格"
- 前端单页表单无分组，20+ 字段平铺体验差
- 提示"有助教"时，AI 不知道是服务体验型还是技术陪练型，只能泛化输出
- `style` 字段是自由文本，无法结构化引导 AI
- 缺失经营目标、客户结构、禁用规则开关等关键维度

### 核心判断

> 当前门店资料足够支撑 Workbench 基础生成，但不足以支撑"生成像本店的内容"。10F-3 测试中 avg 8.5 的稳定表现更多依赖强规则约束，而非门店个性化定制。升级为"运营画像"后，预期在保持合规的前提下进一步提升内容贴合度。

## 4. 推荐的数据结构方案

**推荐方案 B：新增 `operation_profile` JSONB 字段。**

| 维度 | 评估 |
|------|------|
| 开发速度 | 快 — 1 个 migration，无需多次 migrate |
| 字段灵活性 | 好 — JSONB 随意增减，88 个字段无需建列 |
| 可扩展性 | 好 — 后续新增字段无需 migration |
| 查询复杂度 | 中 — JSONB 查询可用，Prompt 注入无需查询 |
| 迁移风险 | 低 — 单次 migration，可回滚 |
| 与现有模式一致 | ✅ — pricing / member_cards 已用 JSONB |
| 前端对接 | 好 — 前端传 JSON 对象，后端直接 setattr |
| Prompt 注入 | 好 — Python dict 操作灵活提取片段 |

不推荐方案 A（扩列）因为 88 字段会导致 stores 表过宽。不推荐方案 C（新表）因为当前规模不需要，JOIN 增加复杂度。

### 数据结构

```python
# models/store.py — 新增 1 行
operation_profile: Mapped[dict | None] = mapped_column(JSONB)
```
