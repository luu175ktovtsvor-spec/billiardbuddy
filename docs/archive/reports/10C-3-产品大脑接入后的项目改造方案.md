# 10C-3 产品大脑接入后的项目改造方案

---

## 1. 当前项目和产品大脑的差距

当前 MVP（含 10B 成果）与产品大脑相比，存在以下差距：

### 1.1 仍偏“内容类型入口”

`/dashboard/generate` 页面的 4 个 Tab 是：朋友圈文案、群公告、活动方案、经营场景。其中前 3 个仍然按“内容产出物类型”分类，不是按“用户想做什么经营动作”分类。这导致产品仍然容易被感知为“AI 文案生成器”，而不是“运营工作台”。

### 1.2 缺少岗位工作台

产品大脑定义了 6 个岗位（老板、店长、助教管理、教练/赛事负责人、前厅主管、运营负责人），每个岗位有差异化的工作场景和输出格式。当前项目只有一个统一的 Dashboard，没有岗位视角。用户登录后看不到“我是店长，今天该做什么”，也看不到“我是助教管理，助教今天该做什么”。

### 1.3 缺少“我想做什么”自然语言入口

产品大脑要求用户“像跟 AI 说话一样输入需求”。当前 10B 的经营场景仍需要用户在 5 个预置场景卡片中选一个，然后填表单。用户不能说“今天下午空台很多，帮我搞个促活”，而只能说“选场景→选语气→输入补充说明→点生成”。这是“场景按钮+表单”模式，不是“自然语言对话式”模式。

### 1.4 缺少客户分类体系

产品大脑定义了 8 类客户（散客/团购、新客、老客、竞技客户、助教客户、轻竞技/台费局、充值客户、大客户），每类有不同的运营策略、话术焦点和表达边界。当前 generate 页面只有一个“目标客户”文本框，没有客户类型选项，Prompt 中也没有分客户类型生成逻辑。当前 10B 的 target 参数只是自然文本，未用枚举约束。

### 1.5 缺少岗位分类

当前 users 有 `role`（owner/manager/staff），stores 有 `StoreMember.role`，但角色仅用于权限控制，不用于内容生成差异化。用户是店长还是助教管理，不影响 Prompt 策略和输出格式。产品大脑要求输出格式按岗位区分：店长=数据+总结+待办，助教管理=任务分配+激励，前厅=话术+清单+SOP。

### 1.6 Prompt 规则库未真正接入

产品大脑 Prompt 规则库有 56 条规则，当前 YAML 模板只零散实现了部分（如不乱编价格、不低俗、口吻自然），但未系统性地注入以下关键规则：
- 规则 1：不要像咨询报告
- 规则 2：不要开头写“好的，店长”
- 规则 3：不要太 AI
- 规则 4：不要太官方
- 规则 10：未提供信息用占位
- 规则 20-27：分客户类型生成
- 规则 28-33：分岗位生成

当前 Prompt YAML 在尾部有“写法要求”和“绝对禁止”，但规则是手工逐条写的，没有统一的规则注入机制。

### 1.7 缺少助教 / 前厅 / 赛事的专业化场景

当前 5 个 operation 场景（团购转私域、助教推广、搭子局/竞技局、周赛/月赛、老客维护）都是“一个 Prompt→一段输出”的模式。产品大脑要求的助教场景多达 11 个、前厅场景 11 个、赛事场景 11 个。当前一个 `assistant_promo` Prompt 无法覆盖“助教日报”“助教招聘”“助教 PK”“助教培训”“助教任务分配”等差异化场景。前厅 SOP、开店闭店、投诉安抚、卫生检查等完全没有对应 Prompt。

## 2. 当前已有能力哪些可以保留

以下能力是地基，不要推翻：

| 能力 | 说明 | 保留理由 |
|------|------|---------|
| 注册/登录 | 手机号+密码+JWT | 认证链路已跑通 |
| 门店资料管理 | stores 表 + 字段较全 | 价格、Logo、二维码、设施标识均已覆盖 |
| Logo / 二维码上传 | 本地存储 + StorageProvider 抽象 | 已支持海报合成 |
| DeepSeek 文本生成链路 | TextProvider → ProviderFactory → PromptEngine | 核心链路稳定，只需扩展 Prompt |
| 朋友圈/群公告/活动方案 | copywriting + activity 两个接口 | 保留作为店长基础场景 |
| 海报生成 | Pillow + 5 个模板 + 合成逻辑 | 后续只需优化视觉，不改架构 |
| 生成历史 | generations 表 + 分页/筛选/详情 | 已兼容 operation 类型 |
| Dashboard | 今日工作台框架 + 规则引擎 | 升级为岗位工作台的基础 |
| 经营场景 operation | 5 个场景 + POST /api/v1/generate/operation | 场景编排的起点 |
| Prompt Engine | YAML 加载 + 变量替换 | 核心机制，只扩展不改架构 |
| AI Provider 抽象 | TextProvider / ProviderFactory | 切换模型不改业务代码 |
| store_id 隔离 | 所有查询带 store_id | 数据安全基础 |

**结论：不需要重写任何核心模块。当前代码是地基，产品大脑是图纸。**

## 3. 下一阶段应该优先改哪里

候选方案分析：

| 方案 | 内容 | 判断 |
|------|------|------|
| A：继续 10B-2 海报视觉优化 | 优化海报配色/字体/排版 | ❌ 不做。这是锦上添花，产品大脑接入后用户交互模式可能影响海报使用方式。先定入口再定海报。 |
| B：做 10D 对话式“我想做什么”入口 | 自然语言输入→AI 理解意图→路由到场景 Prompt | ✅ **强烈推荐。这是产品大脑定义的交互模式的核心。不做这一步，产品永远是“AI 文案生成器”。** |
| C：重构 generate 页面为岗位/场景工作台 | 按 6 个岗位拆分工作台 | 🟡 有价值但 B 应该先做。岗位工作台依赖 B 的意图路由能力。可以先在 Dashboard 加岗位视角，不全量重构。 |
| D：先优化 Prompt 规则和经营场景 | 系统化接入 56 条规则，丰富 Prompt | 🟡 必要但要和 B 并行做。规则优化是后端 Prompt 层面，B 是前端交互层面，不冲突。 |
| E：先做助教运营模块 | 助教资料表+11 个助教场景 | ❌ 现在不做独立模块。助教场景应该通过 B 的“我想做什么”入口承载，不单独建页面。 |
| F：先做前厅 SOP/话术模块 | 前厅 11 个场景 SOP 和话术 | ❌ 同上，先通过入口承载，不单独建模块。 |

### 明确建议：**方案 B 优先，方案 D 并行**

理由：
1. **方案 B 是产品定义的质变点**：从“选场景按钮填表单”变成“说话就能生成”，这是台球房 AI 运营工作台 vs 普通 AI 工具的核心差异
2. **方案 B 改动集中在前端交互和后端一个接口**：新增一个通用的 workbench 接口，不推翻现有 4 个接口
3. **方案 B 是其他方案的基础**：岗位工作台、助教模块、前厅模块都可以通过“我想做什么”入口承载，不需要每个都建独立页面
4. **方案 D 可以和 B 并行**：Prompt 规则优化是后端独立任务，不占用前端资源

## 4. 推荐的下一阶段开发任务

### 阶段名称：**10D：对话式管理层运营工作台入口**

### 目标

将产品从“场景按钮+表单→生成”升级为“用户自然语言描述需求→系统理解意图+结合门店资料+岗位+客户类型→输出成品内容包”。

用户打开系统后，在一个输入框里说“今天下午空台，帮我推一下”“周末想搞个周赛，帮我写全套”“最近团购来的新客多，帮我写转化话术”，系统自动识别场景、匹配 Prompt、注入规则、输出可复制可执行的成品。

### 为什么现在做它

1. **这是产品大脑定义的核心交互模式**，产品大脑第 8.2 节明确要求“输入自然语言化”
2. **这是和通用 AI 工具最大的差异点**，通用 AI 让用户自己写 Prompt，本系统让用户说话
3. **改动范围可控**：后端新增一个通用接口，前端新增一个输入框+结果展示区，不改动现有代码
4. **不影响现有功能**：现有的 4 个 Tab 和场景卡片全部保留，新入口作为第 5 个 Tab 或独立页面

### 不做什么

- 不做真正的多轮对话
- 不做聊天机器人界面（不是 ChatGPT 风格的消息气泡）
- 不做意图识别的复杂 NLU 模型（用 LLM 做意图分类即可）
- 不做语音输入
- 不新增数据库表
- 不删除现有功能

### 会改哪些文件

**后端：**
- `server/schemas/generate.py`：新增 `WorkbenchRequest`（user_intent + role + target_customer_type + extra_note）
- `server/services/content_service.py`：新增 `generate_workbench()` 函数
- `server/api/v1/generate.py`：新增 `POST /api/v1/generate/workbench` 路由
- `server/prompts/workbench/`：新增 `intent_router.yaml`（意图识别 Prompt）、`system_rules.yaml`（注入 56 条规则的系统 Prompt 片段）
- 可能需新增 `server/services/ai/prompt_assembler.py`：负责拼装“系统规则+门店资料+岗位+客户类型+用户意图”的完整 Prompt

**前端：**
- `web/src/app/dashboard/generate/page.tsx`：新增第 5 个 Tab“自由输入”或新的输入区
- `web/src/types/generate.ts`：新增 `GenerateWorkbenchRequest` 类型
- `web/src/lib/api.ts`：新增 `generateWorkbench()` 方法

### 风险点

| 风险 | 严重性 | 规避方案 |
|------|--------|---------|
| 意图识别不准 | 🟡 中 | 首版用 LLM 做意图分类（给 LLM 一段 Prompt 让它输出场景 key），准确率够高；不做单独 NLU 模型 |
| 输出质量不可控 | 🔴 高 | Prompt 中必须强制注入 56 条规则的关键子集；接口返回前做简单的规则校验（如检测“好的，店长”关键词并自动去除） |
| 用户不知道能说什么 | 🟡 中 | 输入框下方提供“试试这样说”的示例文案（点击可自动填入） |
| 和现有功能重复 | 🟢 低 | 新入口和现有 Tab 共存，用户自由选择；新入口自动识别意图后可以跳到对应的现有 Tab |
| LLM 额外调用成本 | 🟡 中 | 意图识别用一次轻量 LLM 调用（max_tokens=200），正文生成用另一次调用；首版可用同一个模型 |

### 验收标准

1. 用户在输入框输入“今天下午空台，帮我推一下”，系统生成包含朋友圈+群公告+执行建议的内容包
2. 用户输入“周末想搞个周赛”，系统生成赛事报名文案+赛制说明+群公告
3. 用户输入“最近团购来的新客多”，系统生成团购转私域内容包
4. 输出成品可直接复制使用，不含“好的，店长”等 AI 回应语
5. 输出不乱编价格、奖金、助教信息
6. 现有 4 个 Tab 功能不受影响
7. 生成结果写入 generations 表（type="workbench"）
8. 历史记录可查看 workbench 类型生成

## 5. 页面层改造建议

### 当前页面分析

`/dashboard/generate` 4 个 Tab：朋友圈文案、群公告、活动方案、经营场景。

问题：前 3 个是“按产出物类型”，第 4 个是“按经营场景”，两种分类逻辑混在一个页面。

### 最小改造方案

**增加第 5 个 Tab：“自由输入”**

```
Tab 栏：
[朋友圈文案] [群公告] [活动方案] [经营场景] [自由输入]  ← 新增
```

“自由输入”Tab 的内容：

```
┌─────────────────────────────────────────────┐
│                                             │
│   💬 告诉 AI 你想做什么                       │
│                                             │
│  ┌─────────────────────────────────────────┐│
│  │ 例如：今天下午空台，帮我写一条促活朋友圈    ││
│  │                                       ││
│  │                                       ││
│  │                              [✨ 生成]  ││
│  └─────────────────────────────────────────┘│
│                                             │
│  试试这样说：                                │
│  · 下午空台比较多，帮我推一下                 │
│  · 周末想搞个周赛，帮我写全套                 │
│  · 好久没联系老客户了，帮我写个回访            │
│  · 助教今天到店，帮我推一下助教服务            │
│  · 团购新客怎么转化，帮我写话术               │
│  · 帮我写一个搭子局                           │
│                                             │
│  我是 [店长 ▼]  目标客户 [全部客户 ▼]         │
│                                             │
└─────────────────────────────────────────────┘
```

**为什么这样改：**
- 不删除现有任何 Tab，兼容已有用户习惯
- 新 Tab 是产品大脑交互模式的落地
- 输入框+示例文案的模式比纯空白输入框更友好
- 岗位和目标客户的下拉框为后续分岗位生成预留入口

**不做什么：**
- 不把整个页面改成对话式聊天界面
- 不删除现有的场景卡片
- 不做多个入口互相跳转的复杂路由

## 6. 后端接口改造建议

### 当前接口分析

| 接口 | 作用 | 是否够用 |
|------|------|---------|
| `POST /api/v1/generate/copywriting` | 朋友圈/群公告生成 | ✅ 保留，作为店长的快捷入口 |
| `POST /api/v1/generate/activity` | 活动方案生成 | ✅ 保留，作为店长的快捷入口 |
| `POST /api/v1/generate/operation` | 5 个经营场景生成 | ✅ 保留，作为场景卡片的底层 |
| （无） | 自然语言意图→场景路由→内容生成 | ❌ 缺失 |

**结论：现有 3 个接口全部保留。需要新增 1 个通用接口，不是替换。**

### 建议新增接口

**`POST /api/v1/generate/workbench`**

请求体：

```json
{
  "user_intent": "今天下午空台，帮我写一条促活朋友圈",
  "role": "manager",
  "target_customer_type": "all",
  "extra_note": "价格不要写数字，就说下午有优惠"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `user_intent` | string | 是 | 用户自然语言需求，最多 500 字 |
| `role` | enum | 否 | store_manager / assistant_manager / coach / front_desk / owner / operations。默认从当前用户 StoreMember.role 推导 |
| `target_customer_type` | enum | 否 | new / old / competition / assistant / light_competition / vip / all。默认 all |
| `extra_note` | string | 否 | 补充说明，最多 200 字 |

后端处理流程：

```
1. 接收 user_intent + role + target_customer_type + extra_note
2. 调用 intent_router Prompt（轻量，max_tokens=200）：
   - 输入：user_intent
   - 输出：{ scenario_key, confidence, suggested_output_types }
3. 根据 scenario_key 加载对应的 operation Prompt 模板
4. 注入系统规则片段（来自 Prompt 规则库的关键规则集）
5. 注入门店资料、岗位、客户类型
6. 调用 TextProvider.generate()
7. 后处理：检测并去除“好的，店长”等 AI 回应语
8. 写入 generations 表（type="workbench"）
9. 返回 content
```

### 意图路由 Prompt（`server/prompts/workbench/intent_router.yaml`）的关键逻辑

```yaml
# 伪代码，只表达设计意图
task: |
  你是一个台球房运营专家。用户在描述一个运营需求，请判断：

  1. 用户想做什么经营动作？
  2. 应该用哪个场景模板？

  可用场景：
  - groupbuy_to_private：团购/抖音/美团新客转化
  - assistant_promo：助教/陪练推广
  - partner_match：搭子局/约球撮合
  - tournament：周赛/月赛/比赛
  - old_customer_recall：老客回访/维护
  - store_moments：发朋友圈
  - store_group_notice：发群公告
  - activity_planning：策划活动
  - assistant_daily_report：助教管理日报
  - front_desk_script：前厅接待话术
  - front_desk_complaint：客户投诉处理
  - tournament_full_kit：赛事全套内容
  - coach_daily_report：教练日报
  - store_daily_report：店长日报

  输出 JSON：
  {"scenario_key": "...", "confidence": 0.9}
```

### 为什么不做一个大统一接口替代现有 3 个

1. 现有接口有精确定义的参数（tone、scenario、activity_goal 等枚举），适合快捷操作
2. 新接口是“兜底入口”，当用户不想选场景卡片时使用
3. 两个入口共存，用户可以自由选择
4. 如果后续自然语言入口使用率远超场景卡片，再考虑逐步简并

## 7. Prompt 接入方案

### 如何把 Prompt 规则库 56 条规则接入后续 Prompt

#### 7.1 分层注入策略

不要把 56 条规则全部塞进每个 Prompt。按规则类型分层注入：

**第 1 层：通用强制规则（所有 Prompt 必须包含）**

放在一个独立的 YAML 文件中：`server/prompts/system/baseline_rules.yaml`

包含规则 1-10（通用生成规则）+ 规则 11-19（禁止乱编规则）的精简版：

```yaml
key: "system.baseline_rules"
template: |
  ## 绝对遵守的规则（违反任何一条都不行）

  ### 输出形式
  1. 直接输出成品内容，不要写“你可以尝试以下方法”“建议从以下几个方面入手”等咨询报告格式
  2. 不要开头写“好的，店长！”“没问题，我来帮你...”等 AI 回应语
  3. 不要使用“在这个充满活力的球房里”“您的满意是我们最大的追求”等 AI 味表达
  4. 不要使用“尊敬的客户”“本店郑重承诺”等官方套话
  5. 朋友圈 80-150 字，群公告 200 字以内，私聊话术简短自然

  ### 信息约束
  6. 不得编造任何价格、台费、助教费、活动报名费等数字。没有数据用[请填写：XXX]占位
  7. 不得编造奖金金额、奖品内容、优惠力度
  8. 不得编造助教姓名、年龄、数量、照片描述、服务内容
  9. 不得编造门店政策（会员折扣、特定活动等）
  10. 未提供的信息用[请填写：XXX]占位，不要自己编

  ### 表达边界
  11. 不要使用：家人们、亲、宝、闭眼入、全城爆火、错过等一年、老板疯了、全网最低价
  12. 每段文案最多 2 个 emoji
  13. 台球房的沟通是轻松的、有人情味的，不是公文也不是广告
```

这个 baseline_rules 片段在 PromptEngine 渲染时**自动追加到每个 Prompt 的末尾**，业务 YAML 不需要重复写。

**第 2 层：客户分类规则（按需注入）**

当用户指定了 `target_customer_type` 时注入。放在 `server/prompts/system/customer_rules/{type}.yaml`。

例：`new_customer_rules.yaml`（规则 22 新客户规则）：
```yaml
key: "system.customer_rules.new"
template: |
  ## 本次目标客户：新客户（第 1-2 次到店）
  - 内容策略：建立关系、了解需求、引导复购
  - 话术焦点：打球体验问询、下次到店邀约、轻度推荐助教体验
  - 禁用：过于热情的连续跟进
  - 不要给客户压迫感
```

**第 3 层：岗位规则（按需注入）**

当用户指定了 `role` 时注入。放在 `server/prompts/system/role_rules/{role}.yaml`。

例：`assistant_manager_rules.yaml`（规则 30 助教管理内容规则）：
```yaml
key: "system.role_rules.assistant_manager"
template: |
  ## 你现在的身份：助教管理
  - 输出特点：任务分配 + 人员管理 + 业绩导向
  - 内容覆盖：助教团队内部管理
  - 格式：任务类偏清单，培训类偏流程，激励类偏数字和排名
  - 你对助教的称呼应该体现管理身份，不是客服口吻
```

**第 4 层：领域规则（按场景注入）**

放在具体场景的 Prompt YAML 中。例如 `operation/assistant_promo.yaml` 已包含助教规则 34-38 的核心要点。产品大脑接入后需检查是否覆盖了全部规则。

#### 7.2 PromptEngine 改造点

当前 `PromptEngine.render()` 只返回单个模板渲染结果。建议在 `content_service` 层增加一个 `assemble_prompt()` 函数，按以下顺序拼接：

```
baseline_rules（第 1 层，必加）
→ role_rules（第 3 层，如有）
→ customer_rules（第 2 层，如有）
→ 门店资料变量
→ 场景模板（第 4 层）
→ 用户 extra_note
```

不需要改 PromptEngine 本身，在 Service 层做拼接即可。

#### 7.3 重点接入的规则

以下规则最容易在开发中被忽略，必须重点确保接入：

| 规则编号 | 规则内容 | 接入方式 |
|---------|---------|---------|
| 规则 1 | 不要像咨询报告 | baseline_rules 第 1 条 |
| 规则 2 | 不要开头写“好的，店长” | baseline_rules 第 2 条 + 后处理检测 |
| 规则 3 | 不要太 AI | baseline_rules 第 3 条 |
| 规则 4 | 不要太官方 | baseline_rules 第 4 条 |
| 规则 10 | 未提供信息用占位 | baseline_rules 第 10 条 |
| 规则 11-19 | 不乱编信息 | baseline_rules 第 6-9 条 |
| 规则 20-27 | 分客户类型 | 第 2 层按需注入 |
| 规则 28-33 | 分岗位 | 第 3 层按需注入 |
| 规则 34-38 | 助教规则 | 第 4 层场景 YAML |
| 规则 39-43 | 赛事规则 | 第 4 层场景 YAML |
| 规则 44-48 | 前厅话术规则 | 第 4 层场景 YAML |
| 规则 49-56 | 合规边界 | baseline_rules 精简版 + 第 4 层场景 YAML |

## 8. 助教模块是否现在单独做

### 明确建议：❌ 现在不做独立助教运营模块

### 理由

1. **助教需要数据基础**：助教日报、助教任务分配、助教 PK/激励、助教业绩分析都需要助教名单、到岗数据、上钟数据、预约数据。当前 stores 表没有助教资料字段，没有助教数据表。先建数据基础（助教资料字段/表）再建功能模块。

2. **助教场景可以通过“我想做什么”入口承载**：助教推广、助教朋友圈、助教招聘文案、助教客户邀约话术这些纯文本生成的场景，完全可以在“自由输入”Tab 中说“帮我写助教招聘文案”“助教今天到店，帮我推一下”来触发，不需要单独的助教模块页面。

3. **助教模块是产品大脑中最复杂、最容易膨胀的模块**：11 个场景 + 招聘/培训/PK/排班/业绩分析，如果现在就做独立模块，容易做成“助教管理系统”，偏离产品主线。

### 建议路径

- **10D 阶段**：在“自由输入”入口中支持助教相关场景（助教推广、助教朋友圈、助教招聘、助教客户私聊），纯 Prompt 层面覆盖
- **10E 阶段**：新增助教资料字段（stores 表加 `assistant_info` JSONB 字段），让助教场景 Prompt 能引用真实助教数据
- **10F 阶段**：视用户反馈决定是否做独立助教管理模块

## 9. 前厅 / 赛事模块是否现在单独做

### 明确建议：❌ 都不现在单独做

### 前厅模块

**理由：**
- 前厅 SOP 的核心是话术清单、检查清单、投诉模板，这些用当前 TextProvider 完全可以生成
- 用户通过“自由输入”说“帮我写团购核销话术”“帮我写客户投诉安抚话术”“帮我写开店检查清单”就能覆盖 P0/P1 场景
- 前厅模块的 P2/P3 场景（卫生检查、开店闭店 SOP、排队管理）依赖门店设施数据，当前 stores 表字段够用但未被 Prompt 充分消费
- **先让 Prompt 消费现有 stores 数据，再决定是否需要独立模块**

### 赛事模块

**理由：**
- 当前 `operation.tournament` Prompt 已覆盖周赛/月赛的基本内容
- 赛事模块的 11 个场景中有 6 个是高频的（赛前报名、赛制说明、赛后战报、私聊邀约、群公告、朋友圈），这些都可以通过“自由输入”承载
- 赛事模块的低频场景（月赛、会员赛）依赖赛事数据积累
- **先优化 tournament Prompt 质量，再决定是否需要独立模块**

### 同样建议

10D 阶段的“自由输入”入口作为前厅和赛事场景的承载：

```
用户输入：“帮我写团购核销话术” → 路由到 front_desk_script，输出话术清单
用户输入：“周末周赛帮我写全套” → 路由到 tournament_full_kit，输出报名+赛制+提醒+战报
用户输入：“客户说台费太贵怎么回” → 路由到 front_desk_complaint，输出安抚话术
```

    │

    │  配额系统

### 为什么这么排

1. **10D 是质变**：从“工具”变成“工作台”。不做这一步，后面做的都是“更好的工具”。
2. **10E 是质量保证**：规则系统化接入确保输出不翻车。用户试用 10D 后如果发现输出质量差，信任就没了。
3. **10F 是留存**：让不同岗位的人都有理由每天打开。店长看店长工作台，助教管理看助教工作台。
4. **10G/10H 是深度**：在入口和质量都稳定后，做深特定岗位的垂直场景。
5. **10I 是体验**：视觉是最容易感知的改进，但依赖前面功能稳定。
6. **10J 是运营**：用户积累足够内容后，素材库才有价值。

## 11. 风险提醒

### 11.1 容易做成普通 AI 工具的地方

| 陷阱 | 表现 | 如何避免 |
|------|------|---------|
| 把“自由输入”做成 ChatGPT 聊天 | 消息气泡、多轮对话、AI 说“你好我是 AI 助手” | 输入框+生成按钮+结果展示，不是聊天界面；系统不自我介绍 |
| 输出通用建议而不是成品 | “你可以尝试发布一条朋友圈……建议配图……” | Prompt 强制要求直接输出可复制文案，不是建议 |
| 用户不知道怎么用 | 空白输入框让人困惑 | 提供 5-6 条“试试这样说”的示例，点击可自动填入 |
| 生成内容没有门店感 | 输出“欢迎来我们球房打球” | 强制注入门店名称、城市、价格，不明显的地方用占位 |

### 11.2 容易过度复杂的地方

| 陷阱 | 表现 | 如何避免 |
|------|------|---------|
| 意图路由做 NLU 模型 | 训练一个分类模型、做向量检索 | 首版用 LLM 做意图分类（一段 Prompt + max_tokens=200），够用了 |
| 客户分类做成 CRM | 建客户表、标签系统、自动打标 | 首版只用枚举（8 类），前端下拉框选择，不建客户数据表 |
| 岗位工作台做成独立页面 | 6 个岗位各建一个页面 | 首版用同一个“自由输入”Tab，岗位只影响 Prompt 策略 |
| PromptBuilder 做成复杂编排引擎 | 场景→多模板→并行调用→结果聚合 | 首版一个 Prompt 输出全部内容，不做多模板编排 |

### 11.3 容易触碰合规风险的地方

| 风险 | 场景 | 如何避免 |
|------|------|---------|
| 助教内容低俗化 | 用户输入“帮我写吸引男客户的助教文案” | baseline_rules 必须包含助教合规规则（不低俗不擦边）；Prompt 中明确禁止；如用户意图被识别为高风险，返回合规替代方案并提示 |
| 赌博/追分内容 | 用户输入“帮我写追分局规则” | 赛事规则中强制转译为轻竞技安全表达（台费局/饮料局/小奖品挑战）；禁止输出“追分”“下注”“输赢 XX 元” |
| 虚假优惠/夸大宣传 | 用户输入“帮我写个全场 1 折活动” | baseline_rules 不乱编优惠规则；如用户强行要求不合理优惠，输出时标注“此优惠方案建议确认后再发布” |
| 平台违规操作 | 用户输入“帮我写刷好评教程” | 合规边界规则禁止生成此类内容；如检测到，返回“该请求涉及平台违规操作，系统无法生成。建议使用以下合规替代方案：好评引导话术、差评安抚模板。” |
| AI 编造门店数据 | 门店没有价格数据时 AI 自行编造 | 生成前检查门店资料完整度；关键字段缺失时在 Prompt 中明确标注“暂无，请勿提及” |

### 11.4 不能现在做的事

| 事项 | 原因 |
|------|------|
| 真实 AI 图片生成模型接入 | P0 阶段限制；海报用本地静态背景图已够用；ImageProvider 是 10I 的事 |
| SSE 流式输出 | P0 阶段限制；普通 HTTP 请求返回完整结果已够验证产品逻辑；等 10D/10E 稳定后再做 |
| OSS 对象存储 | P0 阶段限制；本地 uploads 目录够用 |
| 助教数据表 | 需要先确认真实用户场景和字段需求；先用 stores 的 JSONB 字段存基本信息 |
| 客户数据库/CRM | 产品不做客户数据管理；客户分类只用枚举 |
| 多模型 fallback | P0 只用 DeepSeek；后续有需求再加 |
| 配额拦截 | P2 的事；现在只记录不拦截 |
| 复杂权限系统 | owner/manager/staff 三角色够用 |
| 小程序 | H5 先够用 |

## 12. 最终建议

当前项目接入产品大脑后，下一步最应该做的是：**在现有 generate 页面增加一个“自由输入”Tab，让用户能用自然语言描述运营需求，系统自动识别意图、匹配场景、注入门店资料和 Prompt 规则，输出可复制可执行的成品内容。同时将 Prompt 规则库的 56 条规则系统化地分层注入到 Prompt 拼接流程中，确保输出质量稳定、不乱编信息、不像普通 AI 工具。这一步是产品从“AI 文案生成器”升级为“台球房 AI 运营工作台”的质变点——改动范围可控（新增 1 个后端接口 + 1 个前端 Tab + Prompt 规则层，不推翻现有任何代码），但用户感知变化巨大（从“选场景填表单”变成“说话就能生成”）。这一步做完之后，再按 10E→10F→10G→10H→10I→10J 的顺序逐步深化，每一步都建立在稳定的入口和质量基础之上。
