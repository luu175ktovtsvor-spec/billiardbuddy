```
┌────────────────────────────────────────────┐

│  └────┬─────┬────────────────────┘          │
│       │     │                                │
│  ┌────┴┐ ┌──┴──────┐                        │

```

### 2.2 硬件建议

| 项目 | 建议 | 说明 |
|------|------|------|
| CPU | 2 核+ | AI 调用是请求外部 API，本机 CPU 压力不大 |
| 内存 | 4 GB+ | PostgreSQL + Next.js + FastAPI 三个进程 |
| 磁盘 | 40 GB+ | 系统 10G + 应用 5G + uploads（海报每张约 500KB-2MB）+ 数据库 |
| 带宽 | 3 Mbps+ | 试用期流量低 |
| 系统 | Ubuntu 22.04 / 24.04 LTS | 长期支持版 |

### 2.3 优点

- **成本低**：一台云服务器月费约 50-100 元（国内云厂商轻量应用服务器）
- **部署简单**：Nginx + 两个 Node/Python 进程 + 一个 Docker 容器，半天可完成
- **快速验证**：1-2 天可上线试用，快速收集真实反馈
- **适合早期**：1-2 家熟悉门店试用，用户量极小
- **无额外服务依赖**：不需要 OSS、不需要云数据库、不需要第三方前端托管

### 2.4 缺点

- **扩展性有限**：单机承载能力受限于硬件
- **图片存本地**：服务器磁盘故障可能丢失文件
- **需要自己做备份**：数据库 + uploads 都需要手动备份
- **单点故障**：服务器宕机全部服务不可用（试用期可接受）
- **部署运维需要一定 Linux 基础**：Nginx 配置、SSL 证书续期、进程守护

## 三、方案 B：云服务生产版

### 3.1 架构简图

```
┌──────────────┐     ┌──────────────────┐
│   Vercel /   │     │  云服务器 /       │
│   Cloudflare │     │  Render / Railway │
│   Pages      │     │                  │
│   (前端托管)  │     │  FastAPI :8000   │
│              │     └────────┬─────────┘
└──────┬───────┘              │
       │                      │
       │   HTTPS              │
       │                      │
       ▼                      ▼
┌─────────────────┐   ┌──────────────────┐
│  app.example.com│   │ api.example.com  │
│  (前端域名)      │   │ (API 子域名)      │
└─────────────────┘   └────────┬─────────┘
                               │
                    ┌──────────┴──────────┐
                    │                     │
               ┌────┴─────┐      ┌───────┴────────┐
               │ 云 PostgreSQL│      │ 阿里云 OSS /   │
               │ (托管数据库) │      │ AWS S3 / R2    │
               └─────────────┘      │ (文件存储)      │
                                    └────────────────┘
```

### 3.2 各组件选型

| 组件 | 国内推荐 | 海外/通用推荐 | 说明 |
|------|---------|-------------|------|
| 前端托管 | 阿里云 OSS + CDN / 腾讯云 COS | Vercel / Cloudflare Pages | Next.js 静态导出或 SSR |
| 后端托管 | 阿里云 ECS / 腾讯云 CVM | Render / Railway / Fly.io | FastAPI 需要 Python 运行环境 |
| 数据库 | 阿里云 RDS PostgreSQL / 腾讯云 PostgreSQL | Supabase / Neon / Railway | 托管数据库自带备份 |
| 文件存储 | 阿里云 OSS | Cloudflare R2 / AWS S3 | 海报 + Logo + 二维码永久存储 |

### 3.3 优点

- **更稳定**：托管数据库自带主备切换和自动备份
- **文件更安全**：OSS 提供 99.9999999% 数据持久性
- **前后端分离**：各自独立部署、独立扩容
- **CDN 加速**：前端静态资源和图片可走 CDN
- **扩展性好**：后端可水平扩容，数据库可升级配置

### 3.4 缺点

- **配置复杂**：需要配置多个云服务，网络打通，安全组策略
- **成本更高**：云数据库（最低配约 200-500 元/月）+ OSS（按量）+ 服务器 + 前端托管
- **需要处理跨域**：前后端分域名部署需要正确配置 CORS
- **学习成本**：需要熟悉多个云产品的使用
- **当前阶段过度设计**：试用期只有 1-2 家门店，不需要这么复杂的架构

## 四、当前阶段推荐方案

### 推荐：方案 A — 低成本单服务器试用版

**理由：**

1. **试用期只有 1-2 家熟悉门店**，用户量极小，QPS 几乎为零
2. **还没有支付和配额系统**，不需要高可用和高安全级别的架构
3. **uploads 本地存储可以接受**：每家店的 Logo 1 张 + 二维码 1 张 + 海报每天几张，磁盘占用很低
4. **先验证产品价值**：关键问题是"台球房老板是否愿意用"，不是"系统能否抗 1000 QPS"
5. **不必一开始上 OSS / 云数据库 / 前端托管平台**：这些是商业化阶段的事
6. **单机部署半天可完成**，快速上线收集反馈，小步快跑
7. **AI 调用走外部 API**：DeepSeek API 的延迟和费用不依赖服务器配置

**上线后重点观察：**
- 门店老板是否真的打开系统使用
- AI 生成的内容是否符合实际运营需要
- 海报下载和分享是否方便（尤其是微信环境）
- 上传 Logo 和二维码是否顺畅
- 哪些功能最常用、哪些没人用

**何时考虑升级到方案 B：**
- 试用门店超过 5 家
- 日均生成量超过 50 次
- 需要正式商业化收费
- 用户反馈 uploads 文件丢失或访问慢
- 需要更高的可用性保证

## 六、域名和 API 地址规划

### 6.1 推荐：方案 1 — 前后端同域名

```
https://app.example.com/              → Next.js 前端
https://app.example.com/api/v1/...    → FastAPI 后端
https://app.example.com/uploads/...   → 静态文件（海报/Logo/二维码）
```

**Nginx 负责：**
- `/` → 转发到 `http://127.0.0.1:3000`（Next.js）
- `/api/` → 转发到 `http://127.0.0.1:8000/api/`（FastAPI）
- `/uploads/` → 转发到 `http://127.0.0.1:8000/uploads/`（FastAPI 静态文件）

**优点：**
- 不需要配置 CORS（同域请求）
- 不需要配置 SSL 多证书（一个域名一张证书）
- 前端 `NEXT_PUBLIC_API_URL` 可留空，直接用相对路径
- 微信浏览器中更稳定（部分微信版本跨域请求受限）
- 部署最简单

**缺点：**
- 前后端无法独立扩容
- API 无法独立对外开放（这对本项目不是问题）

### 6.2 备选：方案 2 — 前后端分域名

```
https://app.example.com/              → Next.js 前端
https://api.example.com/api/v1/...    → FastAPI 后端
https://api.example.com/uploads/...   → 静态文件
```

**优点：**
- 前后端独立部署、独立扩容
- API 可对外开放（如未来做小程序）

**缺点：**
- 需要配置 CORS（当前 `main.py` 硬编码了 `localhost:3000`，需要改为生产域名）
- 需要两张 SSL 证书（或通配符证书）
- 微信浏览器跨域可能有限制
- 前端需要配置完整 API 地址

### 6.3 当前阶段推荐

**方案 1 — 同域名反向代理**。当前只有 1-2 家门店试用，一个域名足够，能省掉 CORS 配置和维护两张证书的麻烦。

### 6.4 域名选购建议

| 用途 | 建议 | 说明 |
|------|------|------|
| 主域名 | `example.com` | 建议用 `.com` 或 `.cn` |
| 应用域名 | `app.example.com` 或 `ai.example.com` | 二级域名指向应用 |

## 七、uploads 文件存储方案

### 7.1 当前状态

```
server/uploads/
├── logos/       # 门店 Logo 图片
├── qrcodes/     # 微信二维码图片
└── posters/     # 合成海报 PNG
```

- FastAPI 通过 `StaticFiles` 挂载 `/uploads` 路由
- 文件以 UUID 命名，防止猜测
- `.gitignore` 已忽略整个目录

### 7.2 试用期持久化方案

```
服务器上：/var/www/billiards/uploads/
```

- 通过 `UPLOAD_DIR` 环境变量指定绝对路径
- 不放在代码目录内（避免部署更新时覆盖）
- 确保目录权限正确：运行 FastAPI 的用户有读写权限

### 7.3 Nginx 是否可以直接服务 `/uploads`

**可以直接服务**。建议配置：

```nginx
# 静态文件直接由 Nginx 服务（性能更好）
location /uploads/ {
    alias /var/www/billiards/uploads/;
    expires 30d;
    add_header Cache-Control "public, immutable";
}
```

这样可以绕过 FastAPI，Nginx 直接返回文件，减少后端压力。但需要确保 Nginx 对 uploads 目录有读权限。

### 7.4 如何备份 uploads

```bash
# 每日定时备份（加入 crontab）
0 3 * * * rsync -avz /var/www/billiards/uploads/ /backup/uploads/$(date +\%Y\%m\%d)/
```

或使用 `tar` + 上传到远程备份存储：
```bash
0 3 * * * tar -czf /backup/uploads_$(date +\%Y\%m\%d).tar.gz /var/www/billiards/uploads/
```

### 7.5 未来迁移到 OSS

当需要升级时（P2 阶段），项目架构已有 `StorageProvider` 抽象设计：
1. 实现 `OSSStorageProvider`（或其他 S3 兼容 Provider）
2. 修改 `services/storage_service.py`，替换本地存储实现
3. 迁移已有文件到 OSS（批量上传脚本）
4. 修改 `generate_presigned_url()` 返回 OSS 签名 URL

### 7.6 当前是否必须接入 OSS

**不必须。** 试用期不需要接入 OSS。原因：
- 文件量极少（每个门店不到 10 张图）
- 无高可用需求
- 本地存储 + 定时备份已足够
- OSS 配置涉及费用、权限、跨域策略，增加部署复杂度
- 接入 OSS 不解决当前任何用户问题

## 八、PostgreSQL 数据库方案

### 8.1 试用期方案

| 项目 | 选择 | 说明 |
|------|------|------|
| 部署方式 | Docker 容器（`docker compose`） | 与开发环境一致 |
| 数据持久化 | Docker volume 或宿主机目录挂载 | 保证容器重启数据不丢 |
| 连接方式 | 本地 Unix socket 或 localhost:5432 | 与后端同机 |

### 8.2 单服务器 Docker PostgreSQL 是否可接受

**试用期完全可接受。** 理由：
- 数据量极小（几张表，试用期不超过几百条记录）
- 没有高并发需求
- Docker 部署 PostgreSQL 非常成熟
- 容器重启/崩溃后数据在 volume 中不会丢失（只要 volume 持久化）

### 8.3 Docker Compose 生产配置建议

```yaml
# docker-compose.yml 生产版关键修改
services:
  postgres:
    image: postgres:16-alpine
    container_name: billiards_postgres
    restart: always
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "127.0.0.1:5432:5432"     # 只监听本地回环
    volumes:
      - /var/lib/billiards/pgdata:/var/lib/postgresql/data   # 宿主机绝对路径持久化
```

**注意：**
- `ports` 绑定 `127.0.0.1:5432:5432` 而非 `5432:5432`，避免数据库端口暴露到公网
- volume 使用宿主机绝对路径，方便备份
- `restart: always` 确保服务器重启后自动启动

### 8.4 数据库备份

**极度重要。** 数据库是全部业务数据的唯一存放点。

#### 备份脚本（每日自动）

```bash
#!/bin/bash
# /opt/scripts/backup_db.sh

BACKUP_DIR="/backup/database"
DB_NAME="billiards_ai"
DB_USER="billiards_app"
RETENTION_DAYS=30

mkdir -p $BACKUP_DIR
```

## 九、Nginx / 反向代理建议

### 9.1 伪配置结构（单服务器同域方案）

```nginx
# /etc/nginx/sites-available/billiards

# HTTP → HTTPS 重定向
server {
    listen 80;
    server_name app.example.com;
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    ssl_certificate     /etc/nginx/ssl/app.example.com.pem;
    ssl_certificate_key /etc/nginx/ssl/app.example.com.key;

    # 安全头
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-XSS-Protection "1; mode=block" always;

    # 上传文件大小限制
    client_max_body_size 10m;

    # 静态文件：uploads 直接由 Nginx 服务
    location /uploads/ {
        alias /var/www/billiards/uploads/;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # API 反向代理到 FastAPI
    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE 流式输出需要关闭缓冲
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
    }

    # 前端页面反向代理到 Next.js
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 9.2 关键配置说明

| 配置项 | 说明 |
|--------|------|
| `proxy_buffering off` | SSE 流式输出（P2 阶段）需要关闭缓冲，当前 P0 阶段加不加不影响 |
| `client_max_body_size 10m` | 允许上传 Logo/二维码（最大 2MB）+ 缓冲 |
| `proxy_read_timeout 300s` | AI 生成可能耗时 10-30s，超时设置长一些 |
| `/uploads/` 用 alias | Nginx 直接返回静态文件，不走 FastAPI |

### 9.3 SSL 证书

推荐 Let's Encrypt + Certbot 免费自动续期：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d app.example.com
```

## 十、生产启动方式建议

### 10.1 前端

```bash
cd /opt/billiards/web
pnpm install --frozen-lockfile
NEXT_PUBLIC_API_URL= pnpm build   # API 地址留空（同域代理）
```

### 10.2 后端

```bash
cd /opt/billiards/server
uv sync --frozen
uv run uvicorn main:app --host 127.0.0.1 --port 8000 --workers 2
```

**注意：**
- 使用 `uvicorn` 而非 `fastapi dev`：`fastapi dev` 是为开发环境设计的热重载模式，生产不适用
- `--host 127.0.0.1`：只监听本地回环，由 Nginx 反向代理对外暴露，比 `0.0.0.0` 更安全
- `--workers 2`：2 个 worker 进程，匹配 2 核 CPU，不需要太多（AI 调用耗时在外部 API，不在本机 CPU）

### 10.3 进程管理

当前试用期推荐 **systemd**。不依赖额外工具，系统自带，稳定可靠。

#### systemd service 示例

**后端服务** (`/etc/systemd/system/billiards-api.service`)：

```ini
[Unit]
Description=球房 AI 运营助手 - FastAPI 后端
After=network.target docker.service

[Service]
Type=simple
User=billiards
WorkingDirectory=/opt/billiards/server
EnvironmentFile=/opt/billiards/server/.env
ExecStart=/opt/billiards/server/.venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000 --workers 2
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

**前端服务** (`/etc/systemd/system/billiards-web.service`)：

```ini
[Unit]
Description=球房 AI 运营助手 - Next.js 前端
After=network.target

[Service]
Type=simple
User=billiards
WorkingDirectory=/opt/billiards/web
Environment=NODE_ENV=production
Environment=NEXT_PUBLIC_API_URL=
ExecStart=/usr/bin/node /opt/billiards/web/node_modules/.bin/next start
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable billiards-api billiards-web
sudo systemctl start billiards-api billiards-web
```

### 10.4 其他进程管理工具对比

| 工具 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **systemd** | ✅ 当前推荐 | 系统自带，零依赖，稳定 | 需要 root 配置 |
| **pm2** | Node 有优势 | 自带日志轮转、进程监控 | 需要额外安装 Node 和 pm2 |
| **Docker Compose** | 项目已用 Docker 管理数据库 | 统一容器管理，环境隔离 | 增加一层容器复杂度，Python 容器体积大 |
| **supervisor** | Python 生态常用 | 配置简单 | 需要额外安装，不如 systemd 彻底 |
