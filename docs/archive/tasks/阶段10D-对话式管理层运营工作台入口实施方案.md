### 2.2 Schema 设计

在 `server/schemas/generate.py` 中新增：

**WorkbenchRole 枚举：**

```python
class WorkbenchRole(str, Enum):
    boss = "boss"                         # 老板
    manager = "manager"                   # 店长
    assistant_manager = "assistant_manager"  # 助教管理
    coach = "coach"                       # 教练 / 赛事负责人
    frontdesk = "frontdesk"              # 前厅主管
    operator = "operator"                 # 运营负责人
```

注意：`WorkbenchRole` 是用户在当前对话中选择的“身份角色”，不等于系统的 `StoreMember.role`（权限角色）。一个系统 role=manager 的用户可以用 workbench role=assistant_manager 来生成助教管理内容。但前端默认值可以从 `StoreMember.role` 推导：manager→manager，owner→boss，staff→frontdesk。

**WorkbenchRequest：**

```python
class WorkbenchRequest(BaseModel):
    user_intent: str = Field(
        ..., description="用户自然语言需求描述",
        min_length=1, max_length=500
    )
    role: WorkbenchRole = Field(
        ..., description="用户当前使用的岗位身份"
    )
    target_customer_type: TargetCustomerType | None = Field(
        TargetCustomerType.all, description="目标客户类型"
    )
    output_package: list[OutputPackageItem] | None = Field(
        None, description="期望输出的成品类型，为空则由 AI 自行判断"
    )
    extra_note: str = Field(
        "", description="补充说明", max_length=200
    )
```

**GenerationResponse 不需要改。** 现有 `GenerationResponse` 的 `type` 字段是 `str`，`sub_type` 也是 `str`，可以直接承载 "workbench" 和 role 值。

### 2.3 设计说明

- `user_intent` 必填，min_length=1，确保用户至少输入了内容
- `role` 必填，强制用户确认当前以什么岗位身份使用
- `target_customer_type` 可选，默认 all
- `output_package` 可选，为空时 AI 根据 user_intent 自行判断输出什么
- `extra_note` 可选，用于补充“价格用占位”“不要太长”等微调指令
- `input_params` 保存全部 5 个字段，不做省略

## 3. 后端 Service 设计

### 3.1 新增函数

`server/services/content_service.py` 新增：

```python
async def generate_workbench(
    db: AsyncSession,
    store: Store,
    user: User,
    user_intent: str,
    role: str,
    target_customer_type: str | None = None,
    output_package: list[str] | None = None,
    extra_note: str = "",
) -> Generation:
```

### 3.2 处理流程

```
1. 加载 baseline_rules Prompt（server/prompts/rules/baseline_rules.yaml）
   ↓
2. 加载 role_rules Prompt（如存在 server/prompts/rules/role/{role}.yaml）
   ↓
3. 加载 customer_rules Prompt（如存在 server/prompts/rules/customer/{type}.yaml）
   ↓
4. 加载主模板 server/prompts/workbench/free_intent.yaml
   ↓
5. 构建 extra_vars：
   {
     "user_intent": user_intent,
     "role": 中文标签,
     "target_customer_type": 中文标签,
     "output_package": 中文列表或"请根据用户需求自行判断",
     "extra_note": extra_note or "无",
   }
   ↓
6. 调用 prompt_engine.render("workbench.free_intent", store, extra_vars)
   （baseline_rules + role_rules + customer_rules 在主模板中通过变量引用注入）
   ↓
7. ProviderFactory.get_text_provider().generate(TextRequest(prompt=..., max_tokens=3000))
   ↓
8. 后处理：检测并去除"好的，店长"等 AI 回应前缀
   ↓
9. 写入 Generation(type="workbench", sub_type=role)
   input_params = {user_intent, role, target_customer_type, output_package, extra_note}
   ↓
10. 返回 Generation
```

### 3.3 与现有函数的关系

- 不复用 `generate_operation()` 的逻辑——workbench 的 Prompt 策略完全不同
- 复用 `prompt_engine`、`ProviderFactory`、`TextRequest`、`Generation` 模型
- 不修改现有的 `generate_copywriting`、`generate_activity`、`generate_operation`

### 3.4 API 响应

```python
return GenerationResponse(
    generation_id=str(generation.id),
    type=generation.type,        # "workbench"
    sub_type=generation.sub_type or "",  # 如 "manager"
    content=generation.result or "",
    created_at=generation.created_at,
)
```

**不暴露 `prompt_used`**：GenerationResponse 不包含 prompt_used 字段，当前设计已满足。

## 4. Prompt 设计

### 4.1 设计原则

**不做两步 LLM 调用（意图路由 + 场景生成）。** 首版用一个统一 Prompt 直接生成，理由：
- 减少一次 LLM 调用延迟（用户等待时间减半）
- 模型足够聪明，能从自然语言中理解用户意图
- 避免意图路由失败导致的错误场景匹配
- 后续如果需要更强的场景路由能力，可以在 Prompt 层面优化，不改变架构

**不做多模板编排（场景→多个并行 LLM 调用→结果聚合）。** 首版一个 Prompt 输出全部内容。

### 4.3 baseline_rules.yaml 设计

```yaml
key: "rules.baseline"
name: "通用强制规则"
category: "rules"
template: |
  ## 绝对遵守的铁规

  ### 输出形式
  1. 直接输出成品内容。禁止写"你可以尝试以下方法""建议从以下几个方面入手"等咨询报告格式
  2. 禁止在输出开头写"好的，店长！""没问题，我来帮你""以下是为你生成的"等 AI 回应语
  3. 禁止使用"在这个充满活力的球房里""您的满意是我们最大的追求"等 AI 味表达
  4. 禁止使用"尊敬的客户""本店郑重承诺""我们将竭诚为您服务"等官方套话
  5. 朋友圈 80-150 字，群公告 200 字以内，私聊话术简短自然
  6. 少解释多内容。补充说明（如"建议下午 3 点发"）放内容后面单独标注，不混在正文

  ### 信息约束
  7. 不得编造价格、台费、助教费、报名费等任何数字。没有数据用 [请填写：XXX] 占位
  8. 不得编造奖金金额、奖品内容、优惠力度
  9. 不得编造助教姓名、年龄、数量、照片描述、服务内容
  10. 不得编造门店政策（会员折扣、会员日、特定活动等）
  11. 没有用户输入的信息，用 [请填写：XXX] 占位

  ### 表达边界
  12. 禁止使用：家人们、亲、宝、闭眼入、全城爆火、错过等一年、老板疯了、全网最低价、最后3天
  13. 每段文案最多 2 个 emoji
  14. 台球房沟通是轻松的、有人情味的，不是公文也不是广告

  ### 合规红线
  15. 助教内容必须专业、体面。禁止低俗、擦边、性暗示。表达为"专业台球陪练服务"
  16. 赛事内容禁止涉及赌博、追分、下注、大额输赢。轻竞技用：台费局、饮料局、小奖品挑战、熟人切磋、搭子局
  17. 禁止生成刷好评、规避平台审核、虚假宣传、夸大优惠等违规内容
  18. 助教服务是付费增值服务，不是免费陪练
  19. 行业现实可以内部理解，产品输出必须专业、合规、可公开使用
```

```yaml
  期望输出：{output_package_label}
  用户说：{user_intent}
  补充说明：{extra_note}

  ## 输出要求

  1. 首先用 1-2 句话确认你理解了用户需求（作为"需求理解"段，放在最前面）
  2. 然后输出"本次生成内容"清单（1 行，列出你将输出的内容类型）
  3. 最后输出成品内容。成品格式按用户期望输出类型决定：

  - 朋友圈文案：每条 80-150 字，2-3 条，每条附建议发布时间
  - 群公告：200 字以内，包含"什么事+什么时间+谁参加+怎么做"
  - 私聊话术：简短自然，分场景，可附"客户可能怎么回→你怎么接"
  - 海报文案：标题+副标题+正文，不编造价格
  - 短视频配文：标题+配文+话题标签
  - 日报/汇报：数据摘要+文字总结+明日计划，数据用 [请填写：XXX] 占位
  - 活动方案：包含目标/对象/时间/报名方式/规则/分工/物料/预热文案/时间线/注意事项
  - SOP/检查表：逐条列出，每条可勾选执行
  - PK方案/目标表：指标+分组+奖励阶梯+公示模板+执行时间线

  4. 如果用户期望输出为空，根据用户需求自行判断最合适的输出类型
  5. 如果用户明显只要一种内容（如只要朋友圈），就不要强制输出日报、SOP 等
  6. 如果用户要的是完整方案（如周赛全套），输出完整内容包
  7. 所有价格、奖金、助教信息用占位或明确提醒用户补充
  8. 最后列出"需要您补充的信息"清单（如有）
```

### 4.7 Prompt 拼接逻辑

在 `content_service.py` 的 `generate_workbench()` 中实现，不改 `PromptEngine`：

```python
# 伪代码，表达逻辑
def _assemble_workbench_prompt(store, user_intent, role, target_customer_type, output_package, extra_note):
    # 1. 加载 baseline_rules
    baseline_rules = prompt_engine.render("rules.baseline", store, {})

    # 2. 加载 role_rules（如存在）
    role_rules = _load_rule_safe(f"rules.role.{role}", store)

    # 3. 加载 customer_rules（如存在）
    customer_rules = _load_rule_safe(f"rules.customer.{target_customer_type}", store)

    # 4. 加载主模板
    extra_vars = {
        "baseline_rules": baseline_rules,
        "role_rules": role_rules,
        "customer_rules": customer_rules,
        "user_intent": user_intent,
        "role_label": ROLE_LABELS.get(role, role),
        "target_customer_label": CUSTOMER_LABELS.get(target_customer_type, "全部客户"),
        "output_package_label": _format_output_package(output_package),
        "extra_note": extra_note or "无",
    }
    return prompt_engine.render("workbench.free_intent", store, extra_vars)
```

`_load_rule_safe()` 方法：尝试加载规则模板，如果模板不存在则返回空字符串。这样后续新增岗位/客户类型规则时只需加 YAML 文件，不改代码。

## 10. 风险点

### 10.1 会不会变成普通 ChatGPT 输入框

**风险：** 用户输入"帮我写一条朋友圈"，系统输出一条通用朋友圈，和直接问 ChatGPT 没区别。

**规避：**
- Prompt 强制注入门店资料（店名、城市、价格），输出必然带门店信息
- baseline_rules 强制台球房语境（不能是通用文案）
- 前端 placeholder 和示例文案引导用户用台球房场景的语言描述需求
- 结果展示区不是聊天界面，是"输入→输出成品"的单次操作

### 10.2 Prompt 会不会太泛

**风险：** 一个 Prompt 覆盖 6 个岗位 × 8 类客户 × 10 种输出成品 × 无限场景 = 输出质量不稳定。

**规避：**
- 岗位规则（role_rules）和客户规则（customer_rules）按需注入，缩小范围
- 输出成品类型（output_package）引导 AI 只输出指定类型
- 首版不追求完美覆盖所有组合，先在 8 个典型场景上验证
- 如果某个场景输出质量差，后续可单独为该场景增加专用 Prompt（不改变架构）

### 10.3 输出会不会太长

**风险：** AI 同时输出朋友圈+群公告+私聊话术+海报文案+执行建议+日报，内容太长用户看不完。

**规避：**
- output_package 默认空（AI 自行判断），AI 按需输出 2-4 种产物
- 如果用户选择 output_package 很多（如全选 10 种），Prompt 中提示"用户期望输出较多，但请保持每种内容精简"
- 朋友圈 80-150 字、群公告 200 字以内的规则已经控制了单条长度

### 10.4 是否会乱编数据

**风险：** 用户没有提供价格/奖金/助教信息，AI 自行编造。

**规避：**
- baseline_rules 第 7-11 条明确禁止
- Prompt 中门店资料明确标注"暂无"的字段
- 生成后的 C1-C8 测试专门检查这一点

### 10.5 type="workbench" 是否影响历史

**风险：** 历史筛选、标签显示可能出现 workbench 相关的显示异常。

**规避：**
- `filterKey` 和 `FILTERS` 显式添加 workbench
- `TYPE_LABELS` 覆盖所有 workbench sub_type（6 个 role 值）
- 不影响旧的 type 筛选逻辑

### 10.6 baseline_rules 是否影响旧 Prompt

**风险：** baseline_rules 注入到 workbench 的 free_intent 模板中，但如果代码实现不慎，可能影响 copywriting/activity/operation 的 Prompt。

**规避：**
- baseline_rules 只在 `generate_workbench()` 中加载和注入
- 不修改 `PromptEngine` 的逻辑
- 现有的 `generate_copywriting`、`generate_activity`、`generate_operation` 不走 baseline_rules

### 10.7 前端 Tab 是否过多

**风险：** 5 个 Tab 在移动端可能挤压、换行或显示不全。

**规避：**
- 首版在移动端使用短标签 + `overflow-x: auto`
- 后续可考虑将低频 Tab 收入"更多"菜单
- 如果"自由输入"使用率显著高于其他 Tab，后续可把自由输入作为主页

### 10.8 代码是否写死，影响后续扩展

**风险：** workbench 的 Prompt 结构、role/customer 枚举写死后，后续新增垂直模块需要改多处代码。

**规避：**
- role_rules / customer_rules 使用文件发现机制（`_load_rule_safe`），新增规则只需加 YAML 文件
- 前端 role/customer/output 选项以常量数组定义，后续扩展只加数组元素
- type="workbench" 不排斥未来新增 type="assistant_module" 等独立模块 type
- input_params 用 JSONB 保存，新增字段不改表结构

### 10.9 output_package 是否过度复杂

**风险：** 10 个 checkbox 选项让用户选择困难，不如直接让 AI 判断。

**规避：**
- 默认全部不选（= AI 自行判断），用户不需要勾选即可生成
- 只在用户明确想要控制输出时才勾选
- checkbox 组放在下拉折叠中，不占用主要视觉空间

### 10.10 role 是否和未来用户权限系统冲突

**风险：** workbench role 是"用户当前用的岗位身份"，系统 StoreMember.role 是"用户权限角色"。两个 role 概念可能混淆。

**规避：**
- 后端 schema 使用 `WorkbenchRole` 枚举，不与 `StoreMember.role` 字符串混用
- 前端下拉框标签明确为"我的岗位"（不是"我的权限"）
- 文档中区分"岗位身份"和"系统角色"
- 后续如果做岗位工作台（10F），workbench role 是用户主动选择的身份切换

### 11.1 10D 当前版本

```
/dashboard/generate 第 5 个 Tab：“我想做什么”
  ├── 1 个自由输入框
  ├── 岗位 / 客户类型 / 输出成品 选择器
  ├── 1 个 Prompt（free_intent.yaml）
  ├── 1 组 baseline_rules
  ├── 6 个 role_rules + 7 个 customer_rules（按需注入）
  └── 1 个后端接口 POST /api/v1/generate/workbench
```

### 11.2 未来升级方向

**方向 1：岗位工作台（10F）**

当前 10D 的 role 选择器是岗位工作台的种子。未来：
- 新增 `/dashboard/workbench` 页面（独立于 generate）
- 左侧展示该岗位的常用场景快捷入口
- 中间是"今天该做什么"的任务列表
- 右侧是"自由输入"区
- 不同 role 对应不同的 preset 场景和任务

**扩展点：** 当前 `WorkbenchRole` 枚举、`role_rules` 文件、前端 role 选项都支持直接扩展，不需要改架构。

---

**方向 2：高频场景快捷入口（10E-10H）**

基于 `user_intent` 数据分析（从 `input_params` JSONB 提取），统计用户最高频的需求。例如：
- "帮我推助教"出现最多 → 在岗位工作台加"助教推广"快捷按钮
- "周赛报名通知"出现最多 → 加"周赛报名"快捷按钮

这些快捷按钮点击后自动填入 input 框或直接跳转到对应场景的专用表单。

**扩展点：** 当前 `input_params` 保存了完整的 user_intent，可离线分析。

---

**方向 3：独立专项模块（10F-10H）**

当某个岗位的 workbench 使用频率足够高时，升级为独立页面：

- **助教运营模块**：`/dashboard/assistant` — 助教日报、助教任务、助教 PK、助教招聘
- **前厅 SOP 模块**：`/dashboard/frontdesk` — 接待话术卡、投诉模板、开店闭店清单
- **赛事活动模块**：`/dashboard/tournament` — 赛事方案、报名管理、赛后战报

这些模块内部仍可包含"自由输入"区，但增加了结构化表单和专用数据视图。

**扩展点：** 当前 `type="workbench"` 不影响未来新增 `type="assistant_module"` 等。两者在 generations 表中并存，历史筛选时各自独立。

---

**方向 4：模板库 / 素材库（10J）**

基于高频 user_intent 和 output_package 组合，沉淀为可复用的模板：
- "店长→老客户→朋友圈+私聊话术"组合使用最多 → 沉淀为"老客维护模板"
- "助教管理→全部客户→助教推广+朋友圈"组合最多 → 沉淀为"助教推广模板"

用户下次可以直接选模板，不需要重新描述需求。

**扩展点：** 当前 `input_params` 保存了完整的 role、target_customer_type、output_package 组合，可做模板匹配分析。

---

**方向 5：数据分析**

基于 `generations` 表中的 `input_params` JSONB：
- 按 `user_intent` 关键词分析高频需求（如"助教"出现频率）
- 按 `role` 分析各岗位使用频率
- 按 `output_package` 分析最常生成的成品类型
- 按时间分析周度/月度使用趋势

**扩展点：** 当前所有关键字段都在 `input_params` JSONB 中，PostgreSQL 的 JSONB 查询可以支持这些分析。

## 13. 最终建议

### 13.1 是否建议开始 10D 编码

**建议：✅ 开始。**

10D 是产品从"AI 文案生成器"升级为"台球房 AI 运营工作台"的质变点。改动范围可控——后端新增 1 个接口 + 1 个 Service 函数 + 约 15 个 YAML 文件，前端新增 1 个 Tab + 几十行表单代码 + 类型定义。现有功能全部保留。风险可控——最坏情况是新 Tab 使用率低，但不影响已有功能。

### 13.2 是否需要先做数据库迁移

**不需要。**

`generations.type` 是 `String(50)`，无枚举约束。"workbench" 可直接写入。`input_params` 是 JSONB，可以完整保存 workbench 的所有请求字段。

### 13.3 是否需要先重构现有 4 个 Tab

**不需要。**

5 个 Tab 共存，各自独立。workbench Tab 不依赖其他 Tab 的任何逻辑。不需要重构现有代码。

### 13.4 是否建议暂缓 10B-2 海报视觉优化

**建议：✅ 暂缓。**

海报视觉优化是锦上添花。10D 做完后，海报可以通过 workbench 入口触发（用户说"帮我做一张周赛海报"），海报的使用方式和频率可能发生变化。先用当前 5 个模板验证 workbench→海报的工作流，再优化视觉。

### 13.5 是否建议暂缓独立助教模块 / 前厅模块 / 赛事模块

**建议：✅ 全部暂缓。**

10D 通过一个 workbench 入口覆盖所有岗位和场景。独立模块是 10F-10H 的事。在 workbench 入口验证了用户真实使用频率和场景需求后，再决定哪些岗位值得做独立模块。如果 workbench 本身已经够用，独立模块可能不需要做。
