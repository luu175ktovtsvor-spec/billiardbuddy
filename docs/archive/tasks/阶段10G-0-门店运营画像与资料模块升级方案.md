# 阶段 10G-0：门店运营画像 / 门店资料模块升级方案

> 生成时间：2026-05-12
> 版本：v1.0 — 方案设计
> 前置依赖：10F few-shot 体系验证通过

---

## 1. 阶段定位

10G-0 是进入 10G（岗位工作台）前的底层规划任务。目标是把现有的"门店基础资料"升级为"门店运营画像"（Store Operation Profile），让 AI 更懂每一家球房的真实情况，生成更像本店、更加可用的内容。

本任务只做方案设计，不改代码。

### 2.2 当前前端表单

`web/src/app/dashboard/store-settings/page.tsx` — 单页表单，所有字段平铺排列，无分组、无引导、无完整度提示。

### 2.3 当前 Prompt 注入方式

`free_intent.yaml` 中的"门店背景"段落直接展示上述字段。方式是全量注入，无场景筛选、无摘要压缩、无敏感信息过滤。

### 2.4 核心问题

1. **AI 不够懂店**：只知道"有没有助教"，不知道"是什么类型的助教""怎么推"
2. **生成内容泛化**：无法根据门店真实经营目标调整内容方向
3. **禁用规则在 Prompt 层硬编码**：无法按门店定制
4. **前端填写体验差**：一张长表单，无引导，吓跑用户
5. **缺少经营维度**：客户结构、助教体系、内容风格全部缺失

---

## 3. 升级目标

将"门店资料"升级为"门店运营画像"，实现：

1. **AI 更懂店**：生成内容贴合门店真实经营状态
2. **风格可控**：老板可以告诉 AI"用什么样的语气说话"
3. **规则可配**：禁用规则不只在 Prompt YAML 层，门店层也可配置
4. **填写友好**：3 分钟完成最小配置，高级配置按需展开
5. **可扩展**：支持后续真实球房观察资料反哺

## 7. 前端体验设计

### 7.1 快速配置（MVP）

## 8. 后端 / 数据库方案比较

### 方案 A：扩展现有 stores 表字段

| 维度 | 评价 |
|------|------|
| 开发速度 | ⚠️ 慢 — 每个新字段需要 migration |
| 字段灵活性 | ❌ 差 — 加字段必须 migration |
| 可扩展性 | ❌ 差 — 后续每加 1 个字段都要 migrate |
| 查询复杂度 | ✅ 简单 — 直接 SELECT |
| 迁移风险 | ⚠️ 中 — 多次 migration 累积风险 |
| 多门店支持 | ✅ 原生支持 |

### 方案 B：新增 operation_profile JSONB 字段（推荐）

| 维度 | 评价 |
|------|------|
| 开发速度 | ✅ 快 — 一个 migration 完成 |
| 字段灵活性 | ✅ 好 — JSONB 随意增减字段 |
| 可扩展性 | ✅ 好 — 新增字段无需 migration |
| 查询复杂度 | ⚠️ 中 — JSONB 查询稍复杂但完全可用 |
| 迁移风险 | ✅ 低 — 一次 migration |
| 多门店支持 | ✅ 原生支持 |

### 方案 C：新增 store_operation_profiles 表

| 维度 | 评价 |
|------|------|
| 开发速度 | ⚠️ 中 — 需要新表 + API + 关联查询 |
| 字段灵活性 | ✅ 好 |
| 可扩展性 | ✅ 好 |
| 查询复杂度 | ⚠️ 中 — 需要 JOIN |
| 迁移风险 | ✅ 低 |
| 多门店支持 | ✅ 原生支持 |

### 推荐：方案 B

理由：
1. 当前 Store 模型已有 JSONB 使用先例（`pricing`, `member_cards`），团队熟悉 JSONB 操作
2. 一个 migration 完成，无需后续反复 migrate
3. 88 个字段用结构化列会导致表过宽，JSONB 更干净
4. Prompt 注入时直接从 JSONB 提取片段，比 JOIN 快
5. 与现有 `update_store()` 通用 setattr 逻辑兼容 — JSONB 字段可直接 setattr 更新

## 10. Prompt 注入方案

### 10.1 四层注入模型

```
Layer 1: 基础画像摘要（总是注入）
  → 门店定位 + 主要客户 + 经营目标 + 内容风格 + 禁用规则摘要
  → ~200 字

Layer 2: 场景画像片段（按需注入）
  → 助教场景 → 助教体系片段
  → 赛事场景 → 赛事活动片段
  → 前厅场景 → 前厅SOP片段
  → ~150 字/片段

Layer 3: 风格/语气提示（总是注入）
  → 朋友圈语气 + 私聊语气 + emoji偏好
  → ~80 字

Layer 4: 禁用规则（总是注入，最高优先级）
  → 安全合规开关映射为硬规则
  → ~100 字
```

### 10.2 注入位置

在 `free_intent.yaml` 中，替换当前的静态"门店背景"段落为动态渲染的画像摘要。位置保持不变（在 baseline_rules 和 role_rules 之后）。

### 10.3 严禁注入

- operation_profile 原文（不把 JSON 直接注入）
- 经营卡点原文（可能包含敏感内部信息）
- 员工/助教个人隐私
- 客户个人数据
- 未确认的价格数字

### 10.4 缺失处理

- 画像字段为空时，用 baseline_rules 中的通用规则兜底
- 不编造画像数据
- 首次使用且无画像时，直接用当前 free_intent 的静态门店背景

---

## 11. 安全 / 隐私 / 禁用规则

1. **operation_profile 不对外暴露**：API 返回时脱敏，不返回完整 JSONB 给前端（前端通过分组字段获取）
2. **禁用规则 > 风格偏好**：当两者冲突时，安全规则优先
3. **门店可开关**：每个禁用规则都是可配置开关，默认开启安全选项
4. **不在 Prompt 中暴露卡点**：经营卡点、内部问题只用于内部策略判断，不注入 Prompt

## 14. 风险点

| 风险 | 等级 | 说明 |
|------|------|------|
| JSONB 字段膨胀 | 低 | 88 个字段的 JSON 约 3-5KB，PostgreSQL JSONB 支持到 1GB |
| 画像摘要质量 | 中 | 摘要函数需要精心设计，避免信息丢失或误导 |
| 前端表单复杂度 | 中 | 88 个字段需要合理分组和渐进式展开 |
| 画像与 baseline_rules 冲突 | 低 | 设计为"画像更严格"原则：门店开关只能比基线规则更严格，不能更宽松 |
| MVP 字段不够用 | 低 | 12 字段覆盖核心场景，高级需求可通过完整配置满足 |
