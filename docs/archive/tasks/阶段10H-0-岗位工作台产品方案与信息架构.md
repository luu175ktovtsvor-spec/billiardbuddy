## 1. 阶段定位

10H-0 是"岗位工作台"阶段的第一步，只做方案设计和现状阅读，不做编码、不改数据库、不改 Prompt YAML、不调用 DeepSeek。

目标是把产品从：

> **AI 工作台**：用户自己说想做什么

升级规划为：

> **岗位工作台**：老板/店长/助教管理/前厅/运营/教练每天该做什么，系统直接给入口和推荐任务。

## 2. 与 AI 工作台的关系

### 2.1 当前 AI 工作台（已实现）

当前 `/dashboard/generate?tab=workbench` 是一个**对话式生成入口**：

- 用户选择岗位（role）、目标客户类型、输出类型
- 用大白话输入"我想做什么"
- 系统调用 DeepSeek 生成成品内容
- 提供快捷场景卡片和示例辅助用户输入

**优点**：灵活，用户可以说任何需求。
**局限**：用户需要自己想"今天该做什么"，对新用户和忙碌的店长不友好。

### 2.2 岗位工作台定位

岗位工作台是 AI 工作台的**上一层**：

```
岗位工作台（新增）          AI 工作台（已有）
┌─────────────────┐        ┌─────────────────┐
│ 选择岗位身份      │        │ role 自动填入     │
│ 看到今日任务卡片   │  →点击  │ user_intent 自动填入│
│ 看到门店画像提示   │  卡片   │ target_customer 自动填入│
│                 │        │ output_package 自动填入│
│                 │        │                   │
│                 │        │ 用户可微调后生成    │
└─────────────────┘        └─────────────────┘
```

**关系总结**：
- 岗位工作台是"任务发现层"，AI 工作台是"内容生成引擎"
- 岗位工作台不替代 AI 工作台，而是在其之上增加角色化的任务入口
- 用户仍可随时切回 AI 工作台自由输入
- 岗位工作台的任务卡片本质是 Workbench 参数的预设组合

### 2.3 要不要进入 `/dashboard/generate`？

**推荐方案：新建独立轻量页面 `/dashboard/workbench`。**

理由：
- 当前 `/dashboard/generate` 已有 5 个 Tab，再加岗位层会让页面过重
- 岗位工作台的信息架构与对话生成不同——它是"任务入口"，不是"生成表单"
- 独立页面后续可扩展为真正的岗位系统（10H-3+）
- 所有任务卡片点击后复用 Workbench 填参生成——不重复造轮子

10H-1 只做：
- `/dashboard/workbench` 轻量页面（岗位选择器 + 任务卡片网格 + 门店画像轻提示）
- 点击卡片→跳转 `/dashboard/generate?tab=workbench&role=...&intent=...&target=...&output=...`
- 不改后端或少改后端（仅需支持 URL 参数预填）

## 3. 岗位范围设计

| # | 岗位 | role 枚举 | 核心职责 | MVP 优先级 |
|---|------|----------|---------|-----------|
| 1 | 店长 | `manager` | 全店日常运营管理，最高频使用者 | **P0（10H-1）** |
| 2 | 助教管理 | `assistant_manager` | 助教团队管理和推广，次高频 | **P0（10H-1）** |

### 3.2 MVP 优先岗位（10H-1）

**店长、助教管理、前厅** 三个岗位优先：

- **店长**：最高频用户，覆盖场景最多（朋友圈、群公告、老客回访、活动通知、日报），是产品的核心付费推动者
- **助教管理**：助教业务是球房差异化竞争力，助教推广/招聘/管理的 AI 辅助需求强
- **前厅**：标准化话术需求最明确（团购核销、加微信、推卡、投诉），新员工上手快是老板的刚需

## 5. 岗位任务卡片结构

```ts
interface RoleTaskCard {
  id: string;                          // 唯一标识，如 "mgr-daily-moments"
  role: WorkbenchRole;                 // 所属岗位
  title: string;                       // 卡片标题（简短，6-8 字）
  description: string;                 // 卡片描述（15-25 字）
  userIntentTemplate: string;          // 点击后自动填入 Workbench 的 user_intent
  targetCustomerType: TargetCustomerType; // 目标客户类型
  outputPackage: OutputPackageItem[];  // 期望输出成品
  sceneTags: string[];                 // 场景标签（会员群、竞技群、助教、桌型等）
  requiredProfileModules: string[];    // 依赖的门店画像模块
  priority: "P0" | "P1" | "P2";       // 任务优先级
}
```

### 5.1 卡片点击行为

1. 跳转到 `/dashboard/generate?tab=workbench`
2. 自动填入 `role`
3. 自动填入 `target_customer_type`
4. 自动填入 `output_package`
5. 自动填入 `user_intent`
6. 如门店画像缺少 `requiredProfileModules`，在结果区显示补充提示（不阻塞生成）

### 5.2 与现有 Workbench 的复用

- 复用 `GenerateWorkbenchRequest` 接口（不改）
- 复用 `generate_workbench()` 后端函数（不改）
- 复用 `profile_suggestions` 提示机制（10G-3 已实现）
- 复用 `profile_context` 注入（10G-1 已实现）
- 不新增后端 API 端点（10H-1）

## 6. 门店画像联动

岗位工作台深度使用 10G 已完成的画像能力：

### 6.1 profile_context（10G-1）

生成时继续由 Workbench 注入，无需改动。

### 6.2 profile_suggestions（10G-3）

任务卡片点击后，如依赖的画像模块缺失，前端结果区展示轻提示：

```text
建议补充：助教体系 — 补充助教类型和预约规则后，助教相关内容更准。
→ 去补充门店资料
```

### 6.3 门店资料完整度（10G-3）

岗位工作台首页显示轻提示卡片：

```text
AI 运营画像完整度 83%，已适合生成大部分内容。
建议补充：赛事活动、助教预约规则。
```

### 6.4 私域群矩阵（10G-1/10G-4）

会员群/竞技群/搭子群/助教客户群作为任务卡片的重要场景标签。如果门店未配置对应群类型，相关任务卡片仍可显示但标注"建议先配置"。

### 6.5 桌型设备（10G-1.2/10G-5.5）

乔氏/独牙/斯诺克/普通台球桌进入教练/赛事、竞技客户、门店特色任务。未配置桌型时，桌型相关任务卡片使用通用表达，不编造设备信息。

### 6.6 助教体系（10G）

- has_assistant = false 时，助教相关任务卡片降级为"建议先配置助教信息"
- assistant_types 决定推广内容是偏"技术陪练"还是"服务体验"
- allow_new_assistant_notice/allow_today_assistant_available 控制对应卡片是否展示

## 7. 页面信息架构方案比较

### 方案 A：新建独立岗位工作台页面

**路径**：`/dashboard/workbench`

**页面结构**：
```
┌──────────────────────────────────────┐
│ 岗位工作台                            │
│ [店长] [助教管理] [前厅] [教练] [运营] [老板] │ ← 岗位选择器
├──────────────────────────────────────┤
│ AI 运营画像完整度 83%                  │ ← 画像轻提示
│ 建议补充：赛事活动                     │
├──────────────────────────────────────┤
│ 📋 今日推荐任务                        │
│ ┌────────┐ ┌────────┐ ┌────────┐    │
│ │ 今日    │ │ 老客户  │ │ 会员群  │    │
│ │ 朋友圈  │ │ 回访    │ │ 空台提醒│    │ ← 任务卡片网格
│ └────────┘ └────────┘ └────────┘    │
│ ┌────────┐ ┌────────┐ ┌────────┐    │
│ │ 竞技群  │ │ 周赛    │ │ 店长    │    │
│ │ 约局通知│ │ 通知    │ │ 日报    │    │
│ └────────┘ └────────┘ └────────┘    │
├──────────────────────────────────────┤
│ 💬 自由输入 → 跳到 AI 工作台           │ ← 底部入口
└──────────────────────────────────────┘
```

**优点**：
- 信息架构清晰，岗位工作台和 AI 工作台职责分明
- 不挤压现有 generate 页面（已有 5 个 Tab）
- 后续可扩展为真正的岗位系统（10H-3+）

**缺点**：
- 需要新增页面和导航入口
- 初期工作量比方案 B 稍大（新增 1 个页面 + 配置文件）

### 方案 B：在现有 generate 页面内增加岗位工作台区域

**路径**：在 `/dashboard/generate?tab=workbench` 的 Workbench Tab 顶部增加岗位任务卡片区。

**优点**：
- 工作量小，复用现有页面
- 快速上线

**缺点**：
- Workbench Tab 已经较复杂（表单、快捷场景、示例、结果区）
- 再加任务卡片区会显著增加页面复杂度
- AI 工作台和岗位工作台的层级关系在 UI 上不够清晰
- 影响现有 Workbench 用户的体验

### 方案 C（折中）：新页面 + URL 参数跳转

**路径**：新建 `/dashboard/workbench`，点击卡片后通过 URL 参数跳转到 `/dashboard/generate?tab=workbench&...`，在 generate 页面通过 URL 参数自动填入表单。

**优点**：
- 信息架构清晰（方案 A 的优点）
- 所有生成仍然走 Workbench 引擎（完全复用）
- generate 页面无需大改，只需支持 URL 参数预填
- 后续扩展性好

**缺点**：
- 需处理 URL 参数解析和预填逻辑
- 两个页面之间需要跳转

## 8. 推荐方案

**推荐方案 C：新建 `/dashboard/workbench` + URL 参数跳转到 Workbench。**
