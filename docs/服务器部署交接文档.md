### worker 数与扩容备忘（旧"协作页 50% 失败"问题已修复）

后端跑 **2 个 uvicorn worker**（systemd `--workers 2`）。

- **协作页"50% 任务不存在"已修**：`orchestrator` 的任务状态已落库 `collab_tasks` 表（`services/orchestrator.py` 顶部注释为证），多 worker 下任何进程都能查/取消。**无需再降到 `--workers 1`。**
- **worker 数怎么定**：uvicorn 是异步 worker，`worker ≈ CPU 核数` 即可（上服务器 `nproc` 看核数）。当前 2 个对应约 2 vCPU。
- **1000 用户规模够不够 → 够，不用加**：负载以 I/O 为主（DB + LLM 调用都 await），单 worker 就能扛大量并发；2 个还能让"发海报时 Pillow 合图短暂占 CPU"不卡别的请求。CPU 升级后再把 worker 提到核数。
- **多 worker 唯一残留注意点**：登录限流器 `LoginRateLimiter`（`api/v1/auth.py`）是**进程内存版**，每 worker 各算 → worker 越多，登录限流越松（安全小事、非 bug）。若以后 worker 开很多，把它挪到 DB/Redis 做全局限流。
- 店脑并发用 Postgres 咨询锁 `pg_advisory_xact_lock`，多 worker 安全；工作台主链路用 DB 存生成记录，与 worker 数无关。

### AI 图片生成架构

| Provider | API | 状态 | 原因 |
|----------|-----|------|------|
| `OpenAIImageProvider` | `images.generate` + `images.edit` | ✅ 在用 | 标准 Image API，无需组织验证 |
| `OpenAIResponseImageProvider` | Responses API（gpt-4o） | ❌ 未注册（死代码） | 需要 Organization Verification，无法通过 |

**为什么用标准 Image API：** Responses API 需完成 Organization Verification，账号无法通过，故用标准 Image API。

**"多轮对话"如何实现：** 标准 Image API 不支持 `previous_response_id`，通过 `images.edit` 把上一张图作为底图（`refine_from`）传入实现"基于此调整"；参考图（用户上传）与底图可同时传入，prompt 内声明各自角色。

**OpenAI 接口地址：** 生产直连 `https://api.openai.com/v1`（美国节点实测 ~80ms 正常）。Cloudflare Worker 代理仅为国内本地开发的备选（直连不通时用）。出口 IP 为阿里云美国（AS45102），如遇 OpenAI 对机房 IP 风控再考虑切代理。

### 前端白屏 / 静态资源 400（根因：standalone 缺 static，2026-06-15 实际发生）
现象：`/login` 等 HTML 返回 200，但 `/_next/static/*.js`、`*.css` 全 **400**（响应头带 `X-Powered-By: Next.js`）→ 白屏/无样式。根因：`.next/standalone/.next/static` 缺失（手动 build 漏了 cp）。`deploy_us.sh` 末尾冒烟检查现会拦住；若仍发生，手动修：
```bash
# 诊断：这个应是 200，若 400 即 standalone 缺 static
CHUNK=$(curl -s https://zzyppz.cn/login | grep -oE '/_next/static/chunks/[^"]+\.js' | head -1)
curl -s -o /dev/null -w "%{http_code}\n" "https://zzyppz.cn$CHUNK"
# 修复（即补 deploy_us.sh 第 5 步）
cd /var/www/billiards-ai/web
rm -rf .next/standalone/.next/static .next/standalone/public
cp -r .next/static .next/standalone/.next/static
cp -r public .next/standalone/public
systemctl restart billiards-frontend
```

### 微信提示"已停止访问该网页"（2026-06-12 实际发生过）
微信对新域名/低信誉域名的自动风控。处置流程：
1. 在微信拦截页点「申请恢复网页」→ 选「部署验证文件」，微信会给一个 `<hash>.txt` 文件名和一串内容
2. 本站是反代结构（无静态根目录），验证文件直接挂在 Nginx：`/etc/nginx/sites-available/billiards` 里 443 块加 `location = /<hash>.txt { default_type text/plain; return 200 "<内容>"; }`，80 块在 host 重定向 if **之前**加 `if ($request_uri = /<hash>.txt) { return 200 "<内容>"; }`（避免 301 干扰校验）
3. `nginx -t && systemctl reload nginx`，外部 curl 核对 http/https 均 200 且内容逐字节一致
4. 回微信申诉页提交验证 + 证明材料；**验证文件保持在线，不要删**
- 2026-06-12 已部署：`/ca919248adc0c709b1a509a246669ab4.txt`；改前配置备份在 `/etc/nginx/sites-available/billiards.bak-wechat`
- 背景：域名新 + 海外服务器（无法做 ICP 备案，备案要求大陆主机）是微信低信誉组合，存在复发可能；若微信成为核心获客渠道，中长期可评估迁大陆主机+备案（代价：OpenAI 需走代理）
- 另：www.zzyppz.cn 未配 DNS 解析、证书亦未含 www——非故障，历史上就只用主域
