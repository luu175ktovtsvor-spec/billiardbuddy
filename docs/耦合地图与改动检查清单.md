## 3. 🔴 高危联动点（"改这里 → 坏那里"）

### 租户 / 数据安全
- **自动租户过滤实际只保护 `generations` + `usage_quotas`**（`core/tenant.py:21`）。`stores`/`conversations` 在集合里是死配置。**`store_subscriptions`/`store_memories`/`collab_tasks`/`store_members`/`store_invitations` 有 store_id 却无自动保护**，靠各处手写 `.where(store_id==)`，无 fail-safe 兜底。新增对它们的查询漏带 store_id = 静默跨店泄露。
  - 护栏：`tests/test_coupling_guards.py::test_every_store_id_table_is_consciously_classified`（新增带 store_id 的表必须分类）。
- **`db/session.py` 顶部 `import core.tenant` 是隔离总开关**——被"清理无用 import"误删 = 全店数据互穿。已有 `# noqa` 守护。
- **fail-safe 无上下文返回空集（不报错）**（`tenant.py:82`）。不经 `get_current_store` 的路由查租户表 = "数据凭空消失"，难排查。`models.py`/`knowledge.py`/`templates.py`/`logs` 等只依赖 `get_current_user` 的路由**切勿查租户表**。
- **只过滤 SELECT，UPDATE/DELETE 不过滤**——generation 改写/软删隔离全靠"先 `get_generation_detail` 查归属"的人工前置。新增写路径漏掉前置校验 = 跨店越权改数据。

### 生成管道
- **店脑记忆必须注入在 prompt 末尾**（`stream.py:148` + `memory_service.format_memories_for_prompt`）——靠近因效应压过旧画像实现"改价/纠错优先"。前移它、或在它之后再 append 段落 = 该优先级静默失效。
- **`run_generation` 已注入店脑、但仍不注入 brand_voice**（`content_service.py`，2026-06-16 改）。店脑经 `with_store_brain()` 追加在 prompt **末尾**（与 stream.py 同语义/同位置约束：其后不可再 append，否则近因优先失效），覆盖诊断/绩效/SOP/玩法/约客/变体/批量全部走管道的功能。`test_run_generation_injects_store_brain` + `test_with_store_brain_*` 已锁该不变量。**brand_voice 仍缺**——batch.py 手动补、其它专项服务尚无，把手写函数收编到管道时仍需各自补 brand_voice（或后续把 brand_voice 也并入 run_generation，注意 batch 已手动补会双注入）。
- **`run_generation` 里有使用事件打点（`_safe_log_generation`，成功+失败）**——契约：**故障安全，绝不能拖垮/阻断生成、绝不能在重抛前自己抛异常盖住原 AI 错误**（独立 session + 双层吞异常）。改那段异常处理时务必保持映射等价 + 保留打点；详见 `docs/product-brain/使用事件采集-产品分析.md`，`test_security_guards.py` 已加 guard。
- **新增带 `store_id` 的表必须在 `test_coupling_guards` 分类**（自动过滤 or 手动 where），否则护栏红——`usage_events` 已归手动/分析类（admin 只聚合，不入租户自动过滤）。
- **`prompt_key` 改一个 → 四处同坏**：后端 `render` 找不到模板、`SCENARIO_ROLE_MAP` 角色推断错位、前端"常用"排序失效、仪表盘推荐回链断。`card.id` 改一个 → 推荐/收藏/历史"继续对话"/下一步深链全 404。
- **StreamGuard 泄露词含 `DeepSeek/GPT/Claude`**（`security_guard.py`）：内容正常提到这些词 → 截断后续输出，前端正常收 done 不报错 → 用户看半截内容。
- **同步 `generate_workbench`（content_service）已无前端调用方**，与线上 SSE 路径手抄两份、已少了店脑+对话历史。在它上面改/测不代表线上。

### 配额 / 前端
- **两个配额池共享一个时钟 `current_period_start`**（`quota_service.py`），跨月重置在同一处重置三字段（generations/tokens/posters）。漏改 `monthly_posters_used=0` = 海报池不跨月清零。
- **token 安全网"推导 vs 存储"双轨**：`check_quota` 用 generation_limit 现算 ceiling（不读 stored），stored `monthly_tokens_limit` 纯展示且已封顶 2e9 防 int4 溢出。别把 check_quota 改回读/写 stored。
- **429 单通道**：文案池和海报池都抛同一个 `QuotaExceededError`(`exceptions.py`, 429)，前端 `api.ts` 统一透传文案。改异常/状态码 = 两池提额引导一起断。
- **`QuotaBadge` useEffect 故意排除 onQuota 依赖**（`quota-badge.tsx:63`）。"修 lint"把它加回 = chat/workbench/posters **三页无限请求**。
- **api.ts 的 SSE 与普通请求是两套独立 401/刷新逻辑**——改 token 处理必须两处同步。
- **新建深层页：顶栏(PageHeader) 与底栏(MobileNav 按 `DEEP_PREFIXES` 自动隐) 不联动**——漏加 PageHeader = "无出口死页"。`store-settings` 靠尾斜杠区分列表/子页，易误伤。
- **X-Store-Id 头 3 处手写**（`api.ts`），登录/注册不设 storeId、靠后端"无头取第一店"兜底。绕过 request() 的新裸 fetch 漏带头 = 多门店用户操作错门店。

## 5. 🟡 值得知道的暗雷 / 隐性约定
- **FK 普遍无 ondelete 级联**（仅 `conversation_messages` 有 CASCADE）。现在无"删店/删用户"功能所以不爆；一旦新增，子表外键会 RESTRICT 报错或留孤儿。
- **JWT `exp` 缺失会让刷新窗口检查被跳过**（`auth.py`，无限可刷新）。改 `create_access_token` 的 claim 别去掉 exp/sub/jti。
- **人工在 `/dashboard/store-brain` 改的记忆，可能被下次 AI 后台 consolidate 整合掉**——人工纠错与自学之间无锁。store_memories 无唯一约束、去重靠应用层 + 每店 `pg_advisory_xact_lock`。绕过 `remember` 的新写路径会和后台学习 delete+insert 撞车丢记忆。
- **`_format_price_field`（prompt_engine）是价格出真值/打码的全局单点**，改它影响全部生成入口。
- **`sub_type` 在不同 gen_type 里语义完全不同**（workbench=prompt_key/角色、repurpose=平台名、outreach=固定"generate"……）。任何按 sub_type 筛选/统计的代码都要按 type 区分。
- **后台学习每次生成额外触发 1 次（标好评再+1）未计费 DeepSeek 调用**——配额数字不反映真实 LLM 成本，算成本模型时记得这笔。
- **时区双基准**：今日统计用北京时间日界（`dashboard_service`），30天滚动窗口/活动天数用 UTC（`behavior_service`）。别"统一"成一套，会让今日推荐/节日跨日偏移 8 小时。
- **borax 是 dashboard_service 的硬依赖**，删/降级 = 节日推荐与今日工作台一起 ImportError。

## 8. 架构决策 · 知识库形态 = 策展 YAML + 清单法（挡过度设计反复，2026-06-19）

> 来源：`docs/完整优化清单.md` X-1。这条沉淀为**正式架构决策**，给后续会话一个权威落点——**别再反复提议给知识库上 GraphRAG / 语义分块 / 向量化整库 / 迁 SKILL.md / 自动蒸馏**。

**决策（按此为准，不重开讨论）：**

1. **「策展 YAML + 清单法」就是我们的渐进式披露 / Agent Skills 等价物**——知识本就是人工切好的 132 份结构化 YAML（一份=一块，一块=一个可独立注入的知识单元），配 `scenario_catalog`（`services/agent/scenario_catalog.py` 的 `find_scenario` 清单）+ `@tool` 能力位（`registry.py` 的 `deliverable / read_only / force_confirm / is_question`）。这套**本质就是 Anthropic Agent Skills「按需披露、用到才加载」的本项目 Python 实现**，已经是渐进式披露，**不需要也不应该**再迁到官方 `SKILL.md` 格式。
2. **不迁 SKILL.md**——BYOK 走的是普通 OpenAI 兼容端点（DeepSeek / 硅基流动 / 火山…），**没有** SKILL.md 依赖的自动发现 + 运行时读文件机制，迁过去根本跑不起来；且违背"绝不抄码、用自己 Python 写"铁律。
3. **不上 GraphRAG / 不做语义分块 / 不向量化整个策展知识库 / 不自动蒸馏**——① 这是过度设计（知识已是人工切好的结构化块，无需再切再嵌）；② 违背**纯本地 + 不过度设计**铁律；③ **2025-2026 实证（NAACL / Vectara 等）显示语义分块收益不稳，固定/结构化分块反而更稳**——我们的"一份 YAML = 一块"正是稳的结构化分块。给已策展好的知识再套一层不稳的自动分块/蒸馏，是用不确定换确定，净负收益。
4. **向量 RAG 的边界**：bge-zh 本地语义召回**只用在老板本机攒的数据侧**（历史产出 / 店脑记忆 / 老板自己导入的资料，见 X-1 关联的 A-7），**不动加密策展知识库（`prompts.enc`）**。策展知识库走"清单法选 key + 关键词映射 + required_knowledge"硬注入，不走向量召回。

**触发提醒**：若新会话/审查再提"要不要把知识库向量化 / 上 GraphRAG / 迁 Skills 官方格式 / 自动蒸馏知识" —— 先读本条；除非有新的、针对本项目的实证理由推翻上述 3 点，否则**按此决策回绝，不重做**。
