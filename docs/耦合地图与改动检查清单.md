## 1. 系统总评
桌面产品 = **单窗口 Agent**（Electron 壳 + 本地 FastAPI + 本地 SQLite + 纯 BYOK + 加密知识库）。
后端只保留 9 个路由（auth/stores/dashboard/quota/members/logs/store-memory/agent/canvas），**内容生成/海报/历史/报表/工作台/协作等旧 HTTP 路由已随单窗口化删除——Agent 直接调底层 service，不经这些路由**。
风险集中在三处：① ReAct 主循环同步/流式**双写**逻辑易"改一处漏一处"；② 纯 BYOK 守卫与审批签名是花钱/对外动作的命门；③ 租户自动过滤保护面极窄，大量带 `store_id` 的表靠手写 where。

## 3. 高危联动点（"改这里 → 坏那里"）

### Agent 大脑
- **主循环同步/流式双写** `[判断]`：`loop.py` 的收尾(`:651/:1085`)、截断、预算(`_check_budget`)、工具回灌、`last_knowledge_used` 复位(`:644/:1079`)、`ensure_tool_pairing`(`:548/:966`)全是**两处各写一份**，注释反复标"别只改一处"。改任一行为务必两路同步。
- **审批闸拦截靠 `requires_approval`** `[判断]`：`loop.py:460` 见 `requires_approval and not _auto_approve` 才拦。给对外/花钱工具**漏标 `requires_approval=True` → 循环静默直接执行**，无报错。
- **HMAC 绑定 args 的序列化是硬契约** `[判断]`：`approval._canonical`(`sort_keys=True, separators=(",",":")`)，发卡(`loop.py:1050`)与 `/execute` 校验(`agent.py:887`)必须同一函数。改键排序/分隔符/转义 → 两端 token 不一致 → **所有审批确认报"确认信息已变化"**。注意 `_action_key`(`loop.py:263`)用的是无 `separators` 的 `json.dumps`，只做拒绝计数 key，**不可与签名 canonical 混用**。
- **权限放行瀑布顺序铁律** `[判断]`：`_auto_approve`(`loop.py:217`) `force_confirm`>`ask`>`auto_files`(仅 file)>`full`（file 直放/spend 撞 `auto_spend_limit`）。`plan` 模式是独立分支(`loop.py:455`，非 read_only 一律跳过)，**不走 `_auto_approve`**——改一个不影响另一个，易顾此失彼。`_auto_approve` 内**就地 `auto_spend_count += 1`**(`:243`)，别把它改成纯查询否则上限闸失效。
- **桌面沙箱默认敞开** `[判断]`：`_resolve` 在 `ctx.full_disk_access=True` 时直接放行任意路径(`local_tools.py:54`)，而桌面 `_resolve_permission` **默认 `fd=True`**(`agent.py:193`)。桌面下护栏靠权限模式+改前备份+命令黑名单，**不靠路径锁**。`run_command` 额外硬门控 `full_disk_access`(`local_tools.py:316`)。云端则强制 `("ask", False)` 且 local_tools 不注册(`local_tools.py:872`)——文件自主权绝不泄漏给租户。
- **改前备份次序** `[判断]`：`edit_excel` 故意"改值成功后、save 前"备份(`local_tools.py:557`)，write/edit/delete 在写删前备份。改调用次序→备份失效或留孤儿，回滚承诺破。
- **命令安全门** `[判断]`：`_check_command_safety` 先禁 shell 操作符再过危险黑名单，**黑名单匹配在 `cmd.lower()` 上，正则写大写永不命中**(`local_tools.py:106,304`)。`run_command` 用 `shell=False`+`shlex.split`，删任一项=命令注入。
- **hooks 异常即放行** `[判断]`：PreToolUse/PostToolUse/Stop 全 try/except 吞异常(`hooks.py`)，hook 内部 bug 不报错只"静默不拦"。写拦截类 hook 要知道异常=放行。
- **SSE 事件 key ↔ 前端硬编码 switch** `[判断]`：后端 loop 吐的 `token/tool_call/tool_result/tool_progress/approval_request/ask_question/final/done/error` 与字段名(`knowledge_used/preview/reason/question/options/multi`)，前端 `api.ts:616` switch + `AgentStreamHandlers`(`api.ts:27`)逐字对应。后端改 key→前端静默丢字段、不报错。

### 生成管道 / 租户
- **租户自动过滤实际只保护 2 张表** `[判断]`：`_TENANT_TABLES`(`tenant.py:27`)含 4 个，但 `stores` 无 `store_id` 列、`conversations` 表根本不存在(无 ORM 模型)→ 都是死配置。真正生效的只有 `generations` + `usage_quotas`。
- **带 `store_id` 却无自动保护的表**：`store_members`/`store_invitations`/`store_subscriptions`/`store_memories`/`usage_events`。新增 SELECT 漏写 `.where(store_id==)` = **静默跨店泄露**，无 fail-safe。`memory_service` 全程显式过滤、刻意绕开 fail-safe。
- **fail-safe 只覆盖 SELECT** `[判断]`：`tenant.py:70` 开头 `if not is_select: return`；INSERT 仅自动填 store_id，**UPDATE/DELETE 不受租户保护**，靠"先查归属"的人工前置。
- **店脑必须注入在 prompt 末尾（近因优先）** `[判断]`：`with_store_brain` 强制 append 末尾(`memory_service.py:232`)，`run_generation` 与 4 个 generate_* 都放在 brand_voice/护栏**之后**。⚠️ `_append_guardrails`(`content_service.py:617`)也往末尾塞行业知识——调换"先护栏后店脑"的顺序，"改价/纠错优先"会静默失效。注意：**Agent/流式路径**店脑经 `compose_agent_system_prompt`(`agent.py:714`)注入 system prompt，位置由 compose 决定、**不保证末尾**，与非流式管道不是同一套契约。
- **`run_generation` 不注入 brand_voice** `[判断]`：店脑注入了(`content_service.py:89`)但没有 brand_voice；brand_voice 只在 4 个 generate_* 各自手工注入。故经管道的 canvas_edit/diagnosis/outreach/games **缺 brand_voice**。把手写函数收编进管道时要各自补（或把 brand_voice 也并入 run_generation，注意别和已手补的双注入）。
- **纯 BYOK 守卫：文本 vs 生图行为不同** `[判断]`：没配可用 key 时，文本路径抛 503(`factory.py:54`)、生图路径返回空 key 由下游失败(`factory.py:155`)；**两者都绝不回退平台 key**（云端 web 才回退）。这是纯 BYOK 核心不变量。
- **failover 仅桌面+多档生效** `[判断]`：`build_resilient_text_provider` 只在 `DESKTOP_LOCAL=1` 且 ≥2 套有 key 档时包容灾层，写独立 `profiles.db` 不碰主库。**`run_generation` 用裸 provider、未经 failover** ——容灾只在 agent loop 路径生效。
- **canvas 沙箱** `[判断]`：所有端点先 `_require_desktop()`(非桌面 403)再 `_safe_xlsx/_safe_doc`→沙箱。`full_disk_access=True` 即越界逃生门(`local_tools.py:54`)。excel-edit 自带独立备份不走 `_backup`(`canvas.py:188`)。

## 5. 暗雷 / 隐性约定
- **`DELIVERABLE_TOOLS` 是 import 时快照** `[判断]`：`tools.py:680` 模块末尾 `frozenset(...)`，之后注册的工具（MCP）不进集合。给工具加 `deliverable=True` 但注册晚于这行 → 不落库、下一轮看不到改不了。
- **`to_openai_tools` 排序=dict 插入序** `[判断]`：`registry.py:91`，靠注册顺序稳定。改注册顺序→改模型看到的工具列表序→影响选择 + prompt cache。
- **`sub_type` 跨 `gen_type` 语义不同** `[判断]`：canvas=span/whole、copywriting=模板子类、activity 恒 planning、operation=scenario、workbench=prompt_key/role。按 sub_type 跨类聚合会错配。
- **`prompt_key` 改一个→四处坏** `[判断]`：模板查找键 + `SCENARIO_ROLE_MAP` 反推岗位 + 知识召回 intent + 打点/前端键(`content_service.py:918,928,1012`)。
- **`_format_price_field` 价格打码全局单点** `[判断]`：`prompt_engine.py:143`，由 `commerce_rules.allow_price_copy` 控明文。改它影响全部模板价格策略。
- **泄露词截断吞后续正文** `[判断]`：`StreamGuard` 命中 `DeepSeek|GPT|Claude|OpenAI` 裸词即 `_blocked` 停发所有后续 token(`security_guard.py:176`)，正文正常提及品牌名会误杀整段后文。非流式按行移除、行为不一致。
- **`_safe_refresh` 故意空转** `[判断]`：`content_service.py:37` 刻意不调 `db.refresh`（GUID 主键回查 expired 会 MissingGreenlet 崩）。依赖 `Generation.created_at` 有 Python 侧 default——去掉 default 或恢复 refresh=核心生成全崩，单测 `_FakeDB` 盖不到。
- **店脑 `manual` 记忆永不被 AI 覆盖** `[判断]`：`_replace_store_memory` 只删 `source!='manual'`(`memory_service.py:273`)。source 字段语义是硬契约，改取值=破坏"店规矩"保护。人工改的记忆与后台 consolidate 之间无锁（SQLite 无 advisory lock，靠单写假设）。
- **知识召回静默截断** `[判断]`：`_scene_cap`(默认 8)+`_SEM_THRESHOLD=0.45`(`content_service.py:317`)，命中超 cap 的知识静默丢、仅留痕。调小 cap/调高阈值=相关知识静默不进 prompt。
- **时区双基准**：今日统计用北京时间日界(`dashboard_service`)，30 天滚动窗用 UTC(`behavior_service`)。别"统一"成一套，会让今日推荐跨日偏移 8 小时。

## 8. 架构决策 · 知识库形态 = 策展 YAML + 清单法（挡过度设计反复，2026-06-19）

> 来源：`docs/完整优化清单.md` X-1。这条沉淀为**正式架构决策**，给后续会话一个权威落点——**别再反复提议给知识库上 GraphRAG / 语义分块 / 向量化整库 / 迁 SKILL.md / 自动蒸馏**。

**决策（按此为准，不重开讨论）：**

1. **「策展 YAML + 清单法」就是我们的渐进式披露 / Agent Skills 等价物**——知识本就是人工切好的 132 份结构化 YAML（一份=一块，一块=一个可独立注入的知识单元），配 `scenario_catalog`（`services/agent/scenario_catalog.py` 的 `find_scenario` 清单）+ `@tool` 能力位（`registry.py` 的 `deliverable / read_only / force_confirm / is_question`）。这套**本质就是 Anthropic Agent Skills「按需披露、用到才加载」的本项目 Python 实现**，已经是渐进式披露，**不需要也不应该**再迁到官方 `SKILL.md` 格式。
2. **不迁 SKILL.md**——BYOK 走的是普通 OpenAI 兼容端点（DeepSeek / 硅基流动 / 火山…），**没有** SKILL.md 依赖的自动发现 + 运行时读文件机制，迁过去根本跑不起来。
3. **不上 GraphRAG / 不做语义分块 / 不向量化整个策展知识库 / 不自动蒸馏**——① 这是过度设计（知识已是人工切好的结构化块，无需再切再嵌）；② 违背**纯本地 + 不过度设计**铁律；③ **2025-2026 实证（NAACL / Vectara 等）显示语义分块收益不稳，固定/结构化分块反而更稳**——我们的"一份 YAML = 一块"正是稳的结构化分块。给已策展好的知识再套一层不稳的自动分块/蒸馏，是用不确定换确定，净负收益。
4. **向量 RAG 的边界**：bge-zh 本地语义召回**只用在老板本机攒的数据侧**（历史产出 / 店脑记忆 / 老板自己导入的资料，见 X-1 关联的 A-7），**不动加密策展知识库（`prompts.enc`）**。策展知识库走"清单法选 key + 关键词映射 + required_knowledge"硬注入，不走向量召回。

**触发提醒**：若新会话/审查再提"要不要把知识库向量化 / 上 GraphRAG / 迁 Skills 官方格式 / 自动蒸馏知识" —— 先读本条；除非有新的、针对本项目的实证理由推翻上述 3 点，否则**按此决策回绝，不重做**。

## 9. prompt-cache 前缀稳定纪律（SH-9，2026-06-19）

> 来源：`docs/完整优化清单.md` 支柱C增补 SH-9。守门测试 `server/tests/test_prompt_cache_discipline.py`。

PC（prompt caching）按 **tools → system → messages** 的前缀层级命中缓存：**改前缀块，那一刻起后面全部 cache miss**。BYOK 端点支持 caching 时，前缀稳定 = 省钱省延迟。改召回链 / 工具系统 / 消息历史的代码必须守：

1. **不零敲碎打反复改前缀**——`loop.py._microcompact` 是**唯一**就地改靠前 tool 消息的点，且**故意**（拿一次 miss 换掉一大段旧只读结果的 token），触发已**对齐到压缩边界**（超过 `_MICROCOMPACT_KEEP` 才动、清成占位后不再重复清同一条）。SH-6 的 autocompact 是另一个**唯一**允许整段重建前缀的点。除这两处，**任何代码都不应就地改 messages 靠前部分**。
2. **追加只追加末尾**——SH-4 续写、SH-5 解锁工具都只 `append`，绝不插中间 / 改 index<N 的消息。
3. **排序必须稳定**——`approval.py._canonical`（`sort_keys=True`）、anti-spin 的 call sig（`json.dumps(..., sort_keys=True)`）、`registry.to_openai_tools()`（dict 插入序，非字母重排）三处的序列化都已字节稳定，别改坏。
4. **SH-1 配对修复**（`message_repair.ensure_tool_pairing`）在每次 `provider.generate` 前跑：补缺失 / 删孤儿只发生在**对应 assistant 之后**或**末尾**，不动更早的前缀。

**PR 自检**：任何改 messages 靠前部分 / 工具数组 / system 的代码，PR 必须回答——**会不会破 cache 前缀？收益是否值这次 miss？** 默认答案是"不破"；要破必须是上面两个被特许的压缩点之一。
