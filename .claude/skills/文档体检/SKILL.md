# 文档体检:扫过时文档 + 出删除候选

把"开发过程中堆下来的 spec 稿/实现计划/报告/被取代的旧文档"扫一遍,出"该删 / 该标 / 拿不准"清单。
比 SessionStart 钩子(`scripts/doc_freshness.py` 只看状态 banner)更深——**交叉验代码,确认工作真落地了再判已完成**。

## 何时用
- 用户说"文档太乱了 / 清一下文档 / 哪些过时了"。
- 一轮 spec→实现 任务合并后,想确认对应 spec 稿/计划该不该清。
- 开发周期长了、文档堆多了,定期扫一遍。

## 怎么做(按序)

1. **定基准(必读)**:① 根 `CLAUDE.md`——开头"权威入口"清单 + 「文档维护规约」(状态 banner 约定);② `docs/README.md`——文档索引。**CLAUDE.md/README 点名的权威入口一律 KEEP。**

2. **逐份判时效**(扫 `docs/**/*.md` + `交接-给新会话/`),每份给一行结论 + 证据:
   - **KEEP·现行**:权威入口 / 仍在维护 / 唯一真相源。banner 应是 `✅现行`。
   - **DELETE·已被取代**:有更新文档覆盖(指出被谁取代)。
   - **DELETE·已完成成历史**:描述的工作已落地——**必须在代码里 grep 到对应实现(文件/函数/测试)才判此类**,别凭"应该做完了"猜。
   - **DELETE·已否决/死稿**:git 提交信息或 banner 标了已否决/仅参考。
   - **UNCERTAIN**:拿不准的老实标,说明为什么(尤其大 backlog 里还有没归宿的活项时)。
   - 用只读子代理并行分簇审,效率高。

3. **出汇总表**:`文件 | 类别 | 一句理由(带代码/提交证据)`,末尾大白话说"有把握直接删的是哪几份、为什么"。

4. **删除走规约**:`git rm`(历史可恢复);删前列清单给 owner 过目确认"删哪些"(owner 已授权删,但列清单防误删);删/取代后**同步 `docs/README.md` 索引**;改了规约同步 CLAUDE.md。**验收报告写仓库外 `~/Desktop/球房-验收报告/`,不进仓库。**

## 铁律
- 判 DELETE 必须给"被谁取代 / 工作已落地"的硬证据(grep 到代码),不确定就 UNCERTAIN——**宁可少删别误删**。
- 大 backlog(如 待改清单 / 完整优化清单)要翻进去看还有没有"未做且没被别处覆盖"的活项,有就 UNCERTAIN。
- 删完别忘**同步索引 + 给对应活文档更新「最后核对」日期**。
