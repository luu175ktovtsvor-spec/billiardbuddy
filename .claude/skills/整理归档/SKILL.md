# 整理归档:把完成态文档收进 docs/归档/

把 `docs/` 现行区里"已经声明完工/被否决"的文档,搬进历史存档区 `docs/归档/`,让现行区只剩真正维护中的活文档。

跟 `/文档体检` 的分工:
- `/文档体检` = 深扫,交叉验代码确认工作真落地了才判 DELETE,拿不准的会老实标 UNCERTAIN——更彻底、更慢。
- 本 skill = 快扫,只信文档自己顶部 banner 的自我声明(📦/历史/已落地/已否决/废弃/可删),不用管代码——更快、给"文档自己都说完工了"的场景收尾用。
- `scripts/doc_freshness.py`(SessionStart 钩子)每次开窗口会自动扫出"标了完工却还留在现行区"的文档并提示跑本 skill,是本 skill 最常见的触发入口。

## 何时用
- 用户说"整理文档 / 归档完成的文档 / 文档太乱了 / 把历史文档收起来"。
- SessionStart 钩子提醒"这几份标了可删/历史/已否决却还留着,建议挪进 docs/归档/"时,顺手跑一下。
- 一轮任务合并、文档 banner 刚被标成 📦 之后,想马上把它归档掉。

## 怎么做(按序)

1. **扫描候选**:遍历 `docs/**/*.md`(**排除 `docs/归档/` 自身**——已经在里面的不用再搬),读每份文档顶部 8 行,挑出 banner 含以下关键词之一的:`可删` `历史` `已落地` `已否决` `废弃` `弃用` `📦` `❌`。
   - 可以直接跑 `python3 scripts/doc_freshness.py` 拿现成结果(它已经做了这一步的扫描,归档区也已排除)。
   - `交接-给新会话/` 下同规则一并扫。

2. **列清单给 owner 过目确认**——**不要扫完直接搬**。格式:
   ```
   以下 N 份文档 banner 显示已完工/已否决,建议挪进 docs/归档/:
   - docs/xxx.md —— (banner 里的一句话理由)
   - docs/plans/yyy.md —— ...
   确认要搬吗?(只搬不删,历史可随时回查)
   ```
   等 owner 明确同意再进入下一步;owner 若对某一份有异议(比如还有活项没迁完),从清单里剔除、不搬。

3. **确认后搬家**:
   - 已入 git 的文档:`git mv docs/xxx.md docs/归档/xxx.md`(保留历史,`git log --follow` 能追溯)。
   - 未跟踪(游离于 git 外)的文档:普通 `mv` 即可。
   - 目标路径若有子目录习惯(如同主题的一批 demo 文件),可以在 `docs/归档/` 下新建子目录归类,比如 `docs/归档/design-demos/`——不强制拍平。

4. **同步 `docs/README.md` 的两栏索引**(这一步不能漏,否则索引和实际目录对不上):
   - 从「📂 现行活文档」对应分类表格里**删掉**这一行。
   - 在文末「🗄️ 归档(历史·仅回查)」表格里**新增**一行,写清楚"是什么历史记录"(一句话:哪轮工作/为什么完工/被谁取代)。
   - 若搬的文档之前被其它现行文档引用/链接,顺手检查那些引用是否需要更新(不强制改措辞,但别留死链接指向已不存在的旧路径)。

5. **只搬不删,搬完不用额外收尾**:这套操作全程不产生真删除,git 历史 + `docs/归档/` 都能回查,不必再单独留验收报告。

## 铁律
- **只搬不删**:任何时候都是 `git mv` / `mv`,不用 `git rm` 真删除文档(那是 `/文档体检` 深扫、且已交叉验证代码落地后才可能走的更重操作,不属于本 skill 范围)。
- **动手前必须列清单给 owner 过目确认**——banner 自称"可删/已否决"不代表 owner 现在就想搬走,尤其正被别的会话引用/正在改的文档,先问不假设。
- **搬完必须同步 `docs/README.md`**:少一步都会让索引跟实际目录漂移,下次体检又要重新对账。
- 权威入口类文档(CLAUDE.md 开头点名的、`docs/README.md` 自己)**永远不进候选清单**,不管 banner 写了什么。
